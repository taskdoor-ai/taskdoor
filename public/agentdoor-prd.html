02

团队成员、邀请与个人责任

先明确谁在团队里，以及每个人通常负责什么，再让 AI 推荐任务协作人选。

成员管理

  • 查看当前团队成员和每个人的责任说明。
  • 通过邀请链接或邮箱邀请成员。
  • 管理管理员和普通成员角色。
  • 团队至少保留一名在职管理员。

邀请的写入边界

  • 负责人、协作人使用通用人员弹层，保留“暂不分配”和“立即邀请”。
  • 加入团队不自动写入 Owner 或 Participant。
  • 加入团队后，仍需接受具体的任务责任提议。
  • 人员保存失败时保留输入；发信失败保留同一待加入记录并允许重试。

  1. 空结果区居中显示「没有找到匹配的成员」、说明「发送邮件邀请对方加入「{{团队名称}}」，一起协作。」及「邀请人员」按钮。说明默认单行居中，空间不足时自然换行；「暂不分配」保留单行，隐藏重复的「立即邀请」。筛选和讨论提及不提供邀请。

  3. 从人员下拉进入时，邀请弹窗直接覆盖当前列表，背景保留搜索内容和结果；取消后回到原搜索框，提交成功后再一起收起弹窗和列表。短淡入淡出期间保留内容，避免先关列表再开弹窗的跳变；兼容系统减少动态效果设置。
  4. 设置成员第一行显示名称和「待加入」，无名称显示「未设置名称」；第二行只显示邮箱，不再展示邀请时间。下拉中的无名称人员以邮箱识别，使用通用头像。
  5. 按 Team＋规范化邮箱查重。已有记录不重复创建、不覆盖原名称、不自动重发；下拉入口可点击「使用此成员」，设置入口提示无需重复邀请。成员列表的待加入人员只保留「重新邀请」，移除「查看邮件」（2026-09-16 修订）；重新邀请保留人员 ID 和名称、更换 token，使旧链接失效。
  6. 人员下拉打开弹窗并提交成功后回填本次选择，沿用既有提议／参与邀请规则；设置与独立邀请入口不操作 Task。邀请需管理员权限；设置可配置角色，人员下拉默认普通成员。
  7. 生产同时创建发信任务并发送注册链接。禁止重复提交，保存失败保留表单，发送失败保留待加入记录并重试；提交发信不等于送达。
  8. 邀请信息贯穿注册、验证、登录和切换账号。受邀邮箱一致且明确接受后，更新原记录为账号名称／头像和正式成员状态，已有任务引用保持不变；加入团队不自动接受任务责任。

AI 责任建议规则
  • 更新建议默认收起，用户点击“更新”后才替换原责任。
  • 新增建议显示为候选行，用户点击加号后才写入。
  • 目标责任已变化时，旧建议停止写入并要求重新核对。

  • 消息量、在线时长、任务数量和一次临时协助不能单独形成责任。

相似任务与成员交叉重复规则
  • 检索范围：只检索当前用户有权发现的本团队进行中、待开始和近期完成任务；无权限任务不能泄露名称或数量。

  3. 上下文匹配是否有相关 Task、文件、业务对象或相似结果经验。
  4. 协作可行性只读取本人主动公开、仍有效的粗粒度协作窗口。
  5. 用户决定比较候选差异，选择本人、其他成员、邀请或暂不分配。

交互 悬停或键盘聚焦任意工作量节点，浮层先显示日期，再显示对应总量、完成量或 AI 预测量；未来总量节点显示不变假设或范围变化依据，预测提示文字保持紫色。日期记录只显示日期，有时间戳才显示具体时间；重合节点合并展示。移开或失焦关闭，Escape 可关闭。图内上沿 +N 天／−N 天／按期只表示预测日与截止的日期差，与工作量趋势分开。

进度计算。 总工作量为 W，AI 基于完成标准判断各部分已覆盖的工作量 C；范围、证据和权重有效时，预测百分比为 C/W，最多一位小数。文件数量、消息数量、经过天数不能替代完成证据。W 未知或为零时不做除法；用户确认已完成仍可显示 100%，因为它来自声明。

子任务依据。 主任务需要汇总时，使用完整、去重的叶子工作量加权，不按个数平均；已完成叶子取确认值，其余取有效 AI 预测。汇总只是计算来源，不变成客观“实际进度”，也不自动改变父状态。缺少任一必要贡献时，不输出精确汇总。父级已有完成声明独立优先。

截止与预测独立。 用户截止日期 D 是要求，AI 预测日期 F 来自剩余工作和执行依据。修改、清空或恢复 D 不改变 F；只更新截止标记与 F−D。例：AI 预测始终为 9/18，截止从 9/18 改到 9/20 后图内显示「−2 天」（预计提前 2 天）；取消截止则保留紫色 AI 预测 9/18，不显示提前／延期。仅在交付范围、剩余工作、依赖或可投入时间变化等事件发生时，才重算受影响的预测。

时间计算。 未完成用有效 AI 预测结束日 F，已完成用用户确认日 R，分别与截止日 D 按团队时区的日历日期比较。只有 F 和 D 都有效才称“预计提前／按期／延期”。未完成且当前日晚于 D 是“已逾期 N 天”的事实；即使没有 F 也可判断。截止当天为“今天截止”，不是逾期 1 天。没有截止日，不输出提前／延期。

保存与并发。 预测结果至少绑定任务、确认／取消事件及重开轮次、范围／完成标准、证据版本和可读范围；待开始、进行中、已阻塞之间的纯状态切换不使同一证据版本失效；时间预测另记录依赖／执行假设版本。截止日期作为独立比较目标保存，不属于预测失效条件；预测返回后与最新截止日期比较。执行中连续变更可合并，最终只采用覆盖最新输入的结果；迟到的旧版本结果不覆盖新结果、确认或取消。相同确认事件幂等，重复点击不刷新完成时间。

更新中与失败。 首次读取用骨架；有旧值时显示“上次 AI 预测 · 截至 M/D”。新结果成功后才替换相应区域；进度成功、时间失败可以分别展示。失败可重试对应请求，不能靠重试修改任务状态。若完成状态已保存，所有预测请求均不得将其降回旧百分比。

历史。 用户完成事件保存操作者、发生时间、确认时范围，原 AI 预测单独保留；百分比、时间与依据的展示见 确认后保留 AI 预测。燃起图按当时的范围和来源新增观察，过去的点不随今天改期、重估、返工而重写。按日显示最后值时，仍保存当日的原始预测与确认记录。

验收重点：

  • AI 60% → 用户完成保存成功 → 100% 用户确认；原始数据保留确认前 AI 60% 和原时间、依据。AI 迟到返回 55% 仍保持用户确认 100%，按其证据观测时间区分旧预测与新复核。保存失败则保持原值。
  • AI 100% 且状态进行中，仍标 AI 预测；子任务完成不自动完成父任务，父任务完成不自动关闭子任务。
  • 重新打开后立即恢复同范围的独立 AI 评估、有效预测日期及趋势，无需再次点击；旧用户确认不作为当前 AI 100%。没有有效依据时明确缺口。
  • 修改、清空或恢复截止日期不改变百分比、AI 完工预测日、观测时间和历史，也不触发重预测；只更新截止标记与日期差。浏览或跨日不增加百分比。尚未到截止且无完工预测，不显示预计按期。
  • 进度与时间分开记录更新时间；任一请求失败不清空另一项，更不覆盖用户确认。
  • 全无权限不渲染缓存与子任务信息；部分覆盖不生成精确父级汇总；所有入口可用键盘操作。

实现范围： Demo／PRD 共用组件，固定样例覆盖预测、确认、重开、逾期和失败；本地状态入口已有完成／重开时间。Demo 已支持手动重新核对固定评估、按当前子任务状态汇总、本地保存和失败重试；核对时间独立于原始观测时间，无新证据不生成更高进度或顺延日期。生产 AI 的事件队列、跨端版本竞争、独立预测时间与完整历史账本仍待接入；不将文档或 Mock 表现当作后台已运行。

6.5 讨论／动态

动态承载人的交流；支持附件、评论、@、针对回复再回复，不提供单独的消息引用。本地上传的附件发布后自动进入任务文件列表；从“文件列表”选择已有文件则复用原文件。

6.5.1 对象、范围与本次决策

用户需要围绕一条进展或一份文件持续沟通，能知道回复针对谁、附件在哪里、结论依据哪一版内容。本次所称“动态”指当前 Task 内成员主动发布的内容，复用现有“讨论”页签；不新增团队广播入口，也不将系统“活动”变成输入区。

  • 用户明确方向： 动态可以上传附件；文件内可以就内容讨论，确认后在文件右侧查看；补齐评论、回复、@ 人和回复某条回复的规则。2026-09-14 修订：动态及其回复不提供单独的“引用”操作，不重复展示原消息摘录；作者与回复对象同排且字号一致，例如“周岚 回复 陈默”；正文另起一段，点击回复对象可定位原消息。发布时间放在正文与附件下方、操作按钮上方，按保存时刻显示完整日期和时分（YYYY-MM-DD HH:mm），不显示“原时间”或相对时间；编辑保留原发布时间。文件讨论的原文锚点不受影响。
  • 本次设计默认： 发布成功的附件自动出现在本任务文件列表，同时允许在文件页手动上传、从已有文件中选择引用；不要求用户再执行一次归档。
  • 对象分开： 动态是任务讨论串的首条消息，评论和回复都属于该串；文件讨论串属于 Task + File 的上下文。同一条文件评论不自动再发布为动态。
  • 计数分开： 任务“讨论”数量统计任务讨论串中未删除、当前可见的人的消息（包含评论和回复）；文件评论不计入该数量。文件右侧统计可见讨论串数量，每串单列回复数；系统活动和 AI 建议均不计入。

以下操作与通知细节为设计建议，供实现和验收使用，不表示当前原型已经具备。

6.5.3 通知、草稿与发送状态
  • 发布顶层动态不自动提醒所有参与人；首次文件讨论只通知明确 @ 的成员。评论动态通知动态作者；回复具体消息通知被回复者；回复文件根讨论通知根评论作者。每次再合并本条有效 @ 人员，剔除自己、不可见成员并按同一消息去重。
  • 普通编辑不重复发提醒；编辑后新增的有效 @ 可产生一次新增提及通知。移除 @ 不撤回已发生的提醒。只有保存成功后才产生通知事件，投递失败独立重试，不能让用户重复发消息。
  • 通知点击后直接进入原 Task 的讨论串，或文件右侧对应串并定位原文；已读只清除未读状态，不代表已回复、同意或解决。消息删除或权限撤回后，通知摘要与深链也遵守当前可见范围。
  • 草稿按当前用户、团队、Task、串和回复对象隔离；切换文件或任务、收起面板、取消弹层不发布并保留会话草稿，显式“放弃草稿”才清空。首版不承诺刷新或跨设备恢复，界面说明保存范围。
  • 正文输入 Enter 换行，⌘/Ctrl + Enter 提交；中文输入法组合中不提交。回复输入框不展示常驻快捷键提示，快捷键仍可使用。@ 菜单打开时方向键选择、Enter 选中、Esc 收起；点击或快捷键重复提交复用同一请求标识。
  • 保存中禁用重复提交，失败保留正文／提及／附件并可重试；无回执显示“提交结果待核实”，先查询原请求，不立即再创建。并发编辑提示内容已变化，保留草稿供核对。

诊断

只读检查执行阻塞和决策冲突。结论必须有正式依赖或冲突两侧依据。

诊断规则
  • 执行阻塞：任务处于进行中或已阻塞，有正式依赖，且当前阶段需要的前置交付尚未满足；未开始任务正常等待前置不直接判当前阻塞。详细条件见 任务诊断规则。
  • 决策冲突：根据任务已有文件内容和任务信息，检查同一事项是否存在相互矛盾或不能同时满足的地方，并指出内容和出处。
  • 诊断范围包含当前 Task 和全部可见后代 Task。
  • 每条展示结论、影响、建议和默认收起的依据。
  • 不可见或缺失依赖只表示覆盖不完整，不能推断阻塞或健康。
  • 诊断页不提供改期、改依赖、一键修复、忽略或完成任务。

子任务规则
  • 手工新增至少需要名称和一条非空完成标准。
  • 不自动继承 Owner、参与人、文件或权限。
  • 新增或删除后，同步父 Task 的直属子任务数量。

6.8.1 文件内容讨论与“确认”

本次决策： 就文件内容讨论的完整记录和结论留在文件内，右侧查看，不自动发送到任务动态。截图里的“发起对话”改为“确认”，输入提示改为“补充对这段内容的讨论，可 @ 成员”。不先选择一排协作者，不将写评论包装为新会话或派发任务。

  1. 打开文件，选择正文中的一段文字，点击轻量工具栏“评论”；文件顶部保留“查看讨论 N”，移除常驻“下载”“添加评论”入口及评论操作说明。整文件讨论从右侧面板内“评论整个文件”进入。顶部文件标题／路径与正文共用左侧边距，正文不再额外居中缩进。
  2. 点击“评论”后在右侧打开输入区，展示来源版本、选中原文、PDF 页码、多行输入、@ 和附件，以及“取消／确认”。选区工具栏避让可视区边界，讨论输入与后续回复使用同一右侧面板。
  3. “确认”只保存当前评论与来源引用；正文或可用附件至少一项。阅读态和编辑态都可选区评论。正文有未保存修改时，先提示“保存文件并评论”，用户点击后保存新版本，再打开评论输入；保存失败保留文件草稿与待评论选区，不创建评论。
  4. 确认成功后清空已提交的输入，右侧“文件讨论”定位新串，正文显示可点击的讨论标记。点击原文标记打开对应串，点击串内原文摘录定位当前版本的片段；旧版讨论保留当时原文与版本提示，不将旧标记贴到新版正文。
  5. 通过顶部“查看讨论 N”或正文标记打开右侧面板，每串显示回复数和完整回复，可点某条消息的“回复”继续回复或 @。关闭后重开、刷新后再次进入文件，讨论与回复继续保留，无需转到任务讨论页。

当前 Demo 的片段讨论覆盖 Markdown／纯文本及已提取正文的 PDF，阅读态和编辑态均可用；PDF 锚点保存页码、版本、原文和页内范围，相同文字不跨页匹配。图片、表格和未提取正文的二进制文件支持整文件讨论；其他局部标注需对应查看器提供可靠区域／单元格锚点，不宣称 Lexical 能直接处理所有二进制格式。讨论侧栏属于当前 Task 下该文件的上下文，同一 File 被另一 Task 引用时不自动合并或泄露其讨论。

6.8.3 开源方案与接入边界

当前 Demo 已接入 Lexical 0.50.0（Meta，MIT），实现状态同步于 2026-09-15；选型核实日期 2026-09-13。 它是可扩展的编辑器框架，有官方 React 绑定；官方 Playground 的 CommentPlugin 提供选区评论、串式回复和评论面板的参考代码，适合当前 React／TypeScript 项目。选型依据：官方介绍、MIT 许可证、CommentPlugin 源码。

接入部分 采用方式 仍由 TaskDoor 实现

选区标记、右侧讨论 基于 @lexical/mark 和官方 CommentPlugin 模式适配现有面板 稳定串 ID、版本锚点、解决状态、定位与移动端布局

官方 Playground 是示例，不是可直接安装即完成业务闭环的评论服务。移植时保留许可证声明，选定并锁定同一兼容发行版本；验证 Markdown 往返、中文输入法、重叠标注、刷新后定位和只读评论。Lexical 运行时 NodeKey 不能作为持久化锚点，需保存版本内稳定位置／自定义块 ID、范围和引用上下文。首版不依赖实时协同编辑或 Yjs 服务。

对比：Tiptap Comments 官方说明要求试用／订阅、文档服务和私有 registry。Tiptap 核心开源不等于 Comments 扩展开源，本次不采用该付费能力。以下区分当前 Demo 与目标需求，不将框架接入等同于生产评论服务完成。

当前 Demo（2026-09-15）：Lexical 用于讨论输入、文本文件及 PDF 提取正文的按页阅读和划词评论；编辑态已接通，正文有修改时先“保存文件并评论”。顶部“查看讨论 N”、正文选区的“评论”及右侧回复数连接讨论入口，MarkNode 高亮连接原文与文件右侧讨论；点击“确认”只保存文件评论，不生成任务动态或可见活动。已支持稳定成员 ID 的 @、回复具体回复、文件内引用、作者编辑／删除、解决／重开，以及动态／回复附件自动进入文件列表、手动上传和选择已有文件。消息与文件列表共用 File ID，保留引用 vN；编辑移除附件或删除消息不删除任务文件。

消息、文件树、讨论串及本地通知记录按团队与 Task 组成同一份 localStorage 快照；上传原文件二进制保存在 IndexedDB，刷新后可恢复。新增或编辑消息与附件关系一次保存，失败保留输入，旧 revision 不覆盖新快照。文件评论保存源版本、PDF 页码、原文与版本内选择范围，不持久化 Lexical 运行时 NodeKey。

当前缺口：未接入服务端 ACL、多人同步或外部通知；本地通知记录尚未连接现有全局通知 UI，编辑新增 @ 的提醒也未接入。旧版全文快照预览尚未实现：可见引用 vN 和当时原文，但预览明确展示当前最新正文，不能声称打开了旧版全文。真实上传的 DOCX／XLSX 等二进制文件尚未解析，仅支持下载原文件；未提取正文的真实 PDF 使用浏览器预览，仅支持整文件讨论；现有按页提取正文预览不代表已接入真实二进制解析。下文的生产事务、权限、通知和历史版本验收目标继续保留。

6.8.4 动态附件与文件列表
  1. 添加方式： 动态、评论、回复及文件讨论统一使用“附件”按钮。下拉包含“上传本地文件”和“从文件列表选择”；后者按任务文件夹逐级展开，文件夹只导航，点击文件即加入草稿、收起菜单并恢复正文输入。支持多级嵌套，分组沿用任务文件夹。文件列表下拉顶部提供“搜索文件或文件夹”，按文件名和所属路径跨全部层级搜索；搜索结果显示文件名及完整文件夹路径，区分同名文件，根目录文件显示“任务文件”。清空搜索恢复层级浏览，无结果时显示“没有找到匹配的文件”。搜索不读取文件正文，也不把已归档分支或脱离当前文件树的文件加入结果。已添加文件显示勾选并禁用，移除使用草稿附件上的关闭按钮。草稿附件采用产品负责人指定的 File Card Collections（Faisal Amir / urmauur）组件，保留纸张缩略卡和不同格式的彩色色标；附件单元缩至 80px 宽，纸张缩略卡约 48 × 60px，下方只保留单行文件名；不显示大小或“待发布”等常驻状态，18px 移除按钮置于纸张卡内部右上角。多个附件并排并自动换行，图片在同一卡片内显示实际缩略图；其他格式显示类型示意，不冒充已解析的文件正文。长文件名省略并保留完整名称提示；添加中、失败及重试在原卡片内反馈。菜单浮于按钮附近，不在输入框内插入大块文件面板；长文件名省略并可查看完整名称，长列表在菜单内滚动。已有文件复用同一 File ID，不重复上传或增加副本；本地上传发布成功后自动进入任务文件列表。文件页保留“上传文件”和“引用已有文件”的手动入口，沿用原有文件夹规则，不提供自动／手动归档开关。
  2. 默认入库： 从讨论上传时先成为草稿附件；消息提交成功后，文件及指定版本与消息绑定，同时自动建立任务文件列表关系。尚未归属的附件默认放在本 Task 根目录，随后可移动；不强制新增“动态附件”文件夹。已有文件保留原位置。
  3. 同一份文件： 消息附件和文件列表共用 fileId，消息固定 fileVersionId；每个 Task 对同一 File 只有一个文件位置，重复引用不新增文件或数量。用户另传同名文件不按名称静默合并，也不自动变成原文件新版本；需显式选择更新版本。
  4. 来源可回溯： 文件详情显示“来自动态／评论／文件讨论”和可点击来源；同一文件有多个引用时均可定位。引用数和任务文件数不是同一计数，文件无权读取时不暴露标题、摘录或来源。
  5. 提交一致性： 上传未完成、扫描处理中或校验失败均不作为可用附件。先暂存二进制；服务端用一次幂等提交原子关联消息、附件、文件位置及待投递事件，成功回执前不显示“发布成功”。上传成功但消息保存失败不产生正式文件列表条目，也不通知他人；重试复用暂存结果，放弃草稿的暂存物按上传服务策略清理。
  6. 删除语义： 发布后移除附件或删除消息，仅移除该消息引用，文件仍保留在任务文件列表。删除任务文件须走单独操作并列出受影响引用；不能顺便删掉其他回复。文件被删除／归档／撤权时，历史附件显示不可用且无法下载，审计记录保留。
  7. 权限与容量： 只在当前 Task 范围归档，父子 Task 不自动继承，不扩大 File ACL；@ 和复制链接不授权。上传前展示服务端允许的类型、大小和数量限制；服务端再次校验。具体容量值由存储服务配置，接入前不得宣称任意大小或任意格式均可用。

结果核对 EWD 明细 ID、文件版本与内容出处、单项进度、判断理由、确认来源、核对时间及有效性 计算每项已完成 EWD、任务完成度与缺口
正式验收 验收对象、操作者、结论、时间、适用范围、标准与交付版本、估算版本、撤销记录 交付验收留痕；不是文件内容进度的唯一前提
变更与分析记录 变化前后版本、实际发生时间、分析类型、输入版本、规则版本、来源、结果；趋势另存当时的任务总 EWD 与已完成 EWD 更新、复用、燃起图

这些是逻辑对象，可复用现有数据表。现有 MCP 尚未提供全部读取能力；不能把建议字段写成已存在的接口。

责任如何持续校准。 复用“我的责任”和本人负责或参与任务中的实际承担记录，由第 7.9 节人员责任分析 Skill 提出建议，用户确认后才成为成员推荐依据。不建设隐藏的能力／效率画像，也不增加独立画像页。每条资料保存“谁、承担什么、来自哪里、何时更新、当前是否有效”；没有查到记录表示未知，历史 Owner 身份不等于独立完成。本人修改责任、来源撤销或权限变化后，依赖该资料的建议需重新核对，正式负责人不自动更换。

所有 Skill 共用的读取规则。 服务端提供当前用户有权读取的资料，并记录各类数据是“已读全、部分、不可用、未读取”。空集合只有在已读全时才代表确实没有记录。资料中的文字只作为证据，不能当作新的操作指令。输出绑定资料版本；旧请求不能覆盖新版本结果。

7.3 创建任务 Skill

把自然语言需求整理为目标清晰、责任明确、可交付的任务计划；已有任务可根据实际进展继续调整。

环节 能力说明 判断逻辑
1. 意图识别 判断用户想新建任务、调整已有任务，还是查询情况。 新建进入规划；调整先定位原任务；查询只回答，不创建任务。意图不明时先确认。
2. 需求分析 理解用户要解决的问题，明确目标、交付内容和完成标准；需求不明确时加以引导。 围绕“要达到什么结果、怎样算完成”补问关键缺口；已明确的信息直接复用，不反复追问。
3. 任务规划 识别当前用户已创建或参与的任务，判断重复创建、子任务归属等场景，并根据任务内容决定是否拆分。 在当前有权读取的任务中比较目标、交付和范围，判断复用已有任务、追加子任务或独立新建。结果能独立交付、验收，且需单独负责、交接或并行时才拆分；一并明确依赖和期限，缺少依据则待确认。
4. 成员推荐 根据成员责任，推荐一位负责人和最小参与人集合，并解释推荐原因。 在有参与资格的成员中，推荐责任覆盖整体结果的人负责；只加入承担必要具体贡献的参与人，逐人说明原因。用户点名先核对，无合适负责人可未分配。
5. 任务预计投入工时评估 调用第 7.7 节生成任务 EWD 拆分明细，并汇总预计投入人天。 传入任务名称、目标、完成标准及可选历史任务；回填每个 EWD 明细项、对应标准、EWD、依据和缺口。规则集中见 EWD 工时评估＋进度。

已有任务调整： 读取当前任务、子任务、讨论和最新交付，调整尚未完成的计划或建议下一批子任务；保留仍有效的安排，避免重复已完成工作。

确认规则： 创建与调整都先生成可编辑草稿，用户确认后再保存；推荐他人负责时，对方接受后才成为正式负责人。

成员责任来源： 初期使用用户填写的责任；后续由人员责任分析 Skill 跟进任务并提出校准建议，用户确认后更新。成员推荐使用当前有效责任版本，并说明匹配依据。

与状态分析的关系： 本 Skill 负责创建和调整计划；当前情况、下一步建议、进度由 7.4 任务状态分析负责。预计投入与进度规则统一见 7.7，页面展示说明见 3.8 与 6.3。

Skill： agentdoor-task-planner。

草稿展示与换人： 主任务、子任务均按完成标准、执行建议、前置依赖的顺序组织可编辑内容；前置依赖只作参考，不自动阻止任务执行或改变状态。卡片底部的匹配依据分别说明负责人覆盖的结果和参与人的具体贡献；人员选择或正式责任版本改变时重新核对，用户指定的人选不等于高度匹配，缺口如实提示。

7.4 任务状态分析 Skill

任务状态分析分为三部分：当前情况、下一步建议、进度。进度包含完成度和燃起图。

部分 回答什么 判断逻辑
1. 当前情况 现在做到哪，发生了什么？ 结合任务信息、讨论与交付记录，概括当前结果、缺口和近期变化；信息不足标待确认。
2. 下一步建议 接下来应该做什么？ 根据当前缺口与诊断，有冲突先核对，有阻塞先解除，否则补齐尚未满足的结果。
3. 进度 当前完成多少，任务是否趋于完成？ 引用 7.7 EWD 工时评估＋进度 的完成度与燃起图，解释当前进展和是否收敛；不另行生成一套数值。

相关交付、标准、反馈或验收发生变化时，重新核对受影响的结果。单纯经过时间或增加提交次数，不代表任务更接近完成。

接入设计： agentdoor-task-status-analyzer 组织这三部分；任务诊断复用 7.5，进度引用 7.7 的文件内容核对结果，不自动修改任务状态。

7.5 任务诊断 Skill

任务诊断只分两类：执行阻塞、决策冲突。

类型 判断什么 判断逻辑
执行阻塞 当前任务为什么无法继续？ 检查正式前置依赖与交付情况。任务已在执行，当前必须使用的前置交付尚未满足，导致无法继续，才判为阻塞。
决策冲突 任务里的文件内容与任务信息是否存在矛盾？ 核对已有文件内容，以及目标、完成标准、时间等任务信息，找出同一事项上相互矛盾或不能同时满足的地方；指出冲突双方的具体内容和出处。

例子一：执行阻塞。 宣传海报正在设计，但依赖的活动文案还未交付，缺少标题和优惠信息，无法继续定稿。建议先推动文案交付。

例子二：决策冲突。 任务要求“活动预算不超过 10 万元”，但当前方案文件中的预算是 12 万元。建议确认是调整方案预算，还是修改任务中的预算要求。

Skill： agentdoor-task-diagnostician。

7.6 我的工作推荐 Skill

作用：在本人负责或参与的任务中，综合重要度和紧急度，推荐现在应先处理哪一个，并说明原因。 推荐权重是排序分数，不代表人员能力、完成概率或绩效；页面只显示顺位、任务名称和一句原因，完整计算规则放在“AI 分析规则”中。

1. 哪些任务参与排序

本人负责/参与的，只有待开始、进行中、已阻塞这三种状态的任务参与排序。

2. 排序权重：重要度 60%，紧急度 40%

推荐权重 W＝重要度 I × 60%＋紧急度 U × 40%。

重要度和紧急度均在 0～100 分之间，推荐权重也在 0～100 分之间。“权重”指这个最终综合分，不是第三个独立评分项。

维度 回答的问题 计算方式 在最终排序中的占比
重要度 I 这件事对目标、交付和其他工作有多大影响？ I＝目标影响 B＋协作影响 C＋标签参考 P，最高 100 60%
紧急度 U 如果现在不处理，会多快错过期限、持续损失或让别人等待？ U＝max(D, H, Q)，取期限压力、当前风险、待本人处理三者最高分 40%

60%／40% 及以下档位都是初始建议参数，待产品验证，不是已验证的最优权重。 重要度略高，是为了让关键交付、实际损失和影响他人的任务有机会超过低影响的例行逾期任务；时间不能独占排序。参数统一配置并记录规则版本，AI 不能每次自由调整分数。

3. 重要度怎样计算

I＝B＋C＋P。每个分项只取符合条件的最高一档，分项之间相加。

目标影响 B（0～50 分）： 依据当前目标、完成标准、已确认的业务要求和目标关联判断，不以任务标题长短、金额大小或 AI 写出的“重要”二字判断。

分值 成立条件 必须能指出的依据
50 已明确关联当前核心业务目标、关键外部承诺或必须满足的合规要求，交付失败将直接影响该目标或承诺 已确认的目标／要求、这项任务的具体交付，以及两者的直接关系
35 支撑明确的团队阶段目标或对外交付，但未被确认为核心目标或关键承诺 当前团队目标或交付要求，与任务完成标准的对应关系
20 有明确必要性的例行维护、内部支持或基础交付 已记录的需求与完成标准；不因“例行”判断其没有价值
10 已明确为可选优化，当前没有硬性交付要求 用户确认的可选范围，不能仅凭没有截止时间推断
0（待核对） 目标、交付用途或关联信息不足，无法归档 标明缺什么依据；0 是暂不计分，不表示已确认没有价值

协作影响 C（0～30 分）： 判断“这项任务的结果会影响谁”，不是“这项任务在等谁”。

分值 成立条件 计数与边界
30 已确认该交付是至少 2 项活跃下游任务的必需输入，或是一项已确认关键里程碑的必要条件 下游必须是待开始、进行中或已阻塞；按 Task ID 去重，每项关系有明确所需交付，不累计传递链
15 已确认该交付是 1 项活跃下游任务的必需输入，但不满足上档 只取 15，不按前置数、参与人数或评论数累加
0 没有上述影响证据，或只存在参考性关联 已知没有影响与资料未知分开记录；未知不能说“没有下游影响”

父子归属不等于依赖，用户可编辑的前置依赖也只是参考。仅有关系边、上游还未完成，不能证明当前任务阻塞了别人；只有当前交付要求或有效协作记录明确证实“需要这个结果”，才能计入 C。

标签参考 P（0 或 20 分）： 任务没有独立的优先级字段，AI 可参考当前任务已有标签的名称和已知含义，辅助判断重要度。明确表示重要性的标签，如“高优先级”“重点任务”，取 20；普通业务分类标签、没有相关标签或含义不明确时取 0。多个符合条件的标签不叠加，最高 20 分；没有标签不等于任务不重要，仍正常计算 B 和 C。

只参考当前用户有权使用且实际关联到当前任务的标签，不借用其他人的私有标签，不按颜色、图标、标签数量或上级任务标签推断。含义不明或互相冲突时标待核对，不由 AI 猜测加分；仅写“紧急”的标签也不能代替 D、H、Q 所需的事实。记录命中的标签 ID、名称和判断依据；标签只作辅助参考，不能替代 B、C 的事实依据，不自动新增或修改标签，也不新增优先级设置。

例如：支撑团队阶段目标 B＝35，影响两项已确认下游交付 C＝30，任务已有“高优先级”标签，参考该标签取 P＝20，则重要度 I＝85。移除该标签后，P＝0，I 变为 65；任务状态不变，B、C 仍按原事实计算。

4. 紧急度怎样计算：时间只是其中一项

U＝max(D, H, Q)。三类信号各自取最高档，再取三者最高值，不相加。 同一问题可能同时造成逾期、损失与等待，取最高值可避免重复放大；其他命中仍保留为解释依据。

期限压力 D（0～100 分）： 按团队时区计算，日期差 d＝截止日期与当前日期相差的日历天数。仅有日期时，以当地当天结束作为截止；明确时刻超过后才算逾期。先判断逾期，再选今天或未来档位。

条件 D 分值 判断规则
已逾期 100 早于今天的截止日期，或已超过明确截止时刻
今天到期 90 d＝0，尚未超过明确截止时刻
未来 1～2 天到期 75 d＝1 或 2
未来 3～7 天到期 60 3≤d≤7
未来 8～14 天到期 30 8≤d≤14
14 天以后到期 10 d＞14
明确无截止时间 0 没有时间信号，仍正常计算 I、H 和 Q
日期缺失、过期或无法识别 0（待核对） 不猜年份、不补日期、不判逾期；推荐注明日期依据不完整

逾期天数不继续叠加分数。日期信息未知与用户明确不设截止时间是两回事；两者都不凭空增加 D，但解释必须区分。

当前损失或执行风险 H（0～100 分）： 除截止时间外，判断“拖延处理正在造成什么影响”。

H 分值 成立条件 依据要求
100 当前已有持续的关键服务中断、客户／交易损失或明确的合规、安全风险，且有需本人立即处理或协调的行动 当前有效事件、影响范围、未解除事实和本人行动；仅标题写“紧急”不成立
80 已证实执行阻塞或决策冲突正在持续造成停工、返工或扩大交付影响，需本人处理或协调 当前受影响的工作、阻塞／冲突内容及可采取行动，不只看状态名
60 有当前有效的决策冲突，继续按不一致要求推进会导致错误交付，但尚未证实持续损失 冲突两侧的具体内容和出处；失效的旧诊断不能使用
0 未证实以上风险，或没有当前需本人处理的行动 仅标“已阻塞”、很久没更新或前置尚未完成，均不自动给风险分；原因未知标待核对

待本人处理 Q（0～80 分）： 判断是否已有明确等待，而不是仅从任务状态猜测。

Q 分值 成立条件 依据要求
80 活跃下游工作已明确停等本人必须提供的结果、决定或确认，且本人现在有可执行的处理行动 当前等待方、所需内容、尚未回应／交付的记录；不是未来可能依赖
60 有指向本人的有效交付核对或决定请求，材料已提供且事项尚未处理，但未证实下游停工 请求、交付或反馈与本人责任的对应关系
0 没有上述当前等待 仅上传文件、没有验收记录、只有参与身份，均不构成等待；仅有参考性前置未完成不加分

例如：没有截止时间 D＝0，但本人需要立即协调处理持续的关键服务中断 H＝100，下游也在等待 Q＝80，则 U＝max(0, 100, 80)＝100。紧急度并不依赖是否填了时间。

5. 证据、缺失数据和去重

  • 每次命中必须保存事实内容、来源 ID／版本、适用任务和有效性。AI 可以从可访问记录中识别候选事实并解释，但分档必须符合上述条件；没有证据不能靠模型语气打高分。
  • 不因资料缺失或过期加分；失效证据不再参与计算，未知分项暂取 0，不把剩余维度重新放大到 100。推荐注明“依据不完整，需核对”，不能写“低价值、没有风险”。资料恢复后重新计算。
  • 同一维度中，同一事件、相同任务或重复文件只计一次；B、C、P 反映不同影响，允许相加；D、H、Q 反映当前处理压力，只取最高值。不要再额外叠加“阻塞＋20、资料过期＋25”等旧规则。
  • 一个事实可同时支持重要度和紧急度，但必须分别解释：例如“会影响两个交付”支持 C，“两项工作现在已停等本人”才支持 Q。只证明前者，不能顺便计入后者。
  • 不以 EWD 大小、提交次数、聊天活跃度、任务历时或人员历史速度加分；没有真实剩余工作量和可投入时间时，不计算忙闲率、完成概率或精确排程。
  • 父任务与子任务可分别参与，但各自使用本任务的责任和行动。父任务不直接复制子任务的分数，也不因后代数量多而层层累加；父任务理由写统筹行动，避免重复推荐同一执行动作。

6. 如何排序和解释

  1. 先检查状态白名单及本人负责或参与的关系，再按 Task ID 去重。
  2. 按当前有效事实分别取 B、C、P、D、H、Q。
  3. 计算 I＝B＋C＋P；U＝max(D, H, Q)；W＝0.6×I＋0.4×U。
  4. 按 W 从高到低；同分时先比较重要度 I，再比较紧急度 U，均从高到低；仍同分时，按可比较的截止时间从早到晚，无可比较截止时间排后；最后按稳定任务 ID 排序。
  5. 排序使用未舍入的结果，展示或调试时最多保留一位小数。不能用传入数组顺序、随机数或重新生成的 AI 文案打破平局。
  6. 一句优先原因说明最有贡献的重要度依据和当前紧急信号，再指出现在可做的事。无紧急信号时如实说明按目标或协作影响优先，不虚构截止压力。

有强依赖影响的任务可以比例行逾期任务靠前；已阻塞不必然第一，也不能被整体排除。重要但不紧急的任务仍有排序权重，紧急但影响较小的任务也保留时间压力，两者通过固定比例综合，而不是先把所有逾期任务排完。

一、估算 EWD

EWD 明细项： 为满足任务完成标准，成员必须亲自投入时间的一项具体工作，例如整理资料、操作 AI、分析、制作、修改、沟通、审核或验收。每项同时写明可核对的完成结果；等待审批、排队和 AI 无人值守运行不列入明细。

  1. AI 根据任务名称、目标和完成标准生成任务 EWD 拆分明细。每个 EWD 明细项是一项具体人工工作，同时对应一项可核对的完成结果；同级不重叠，并覆盖当前已确认任务范围的 100%。
  2. AI 用八个投入维度检查任务，从已写明的信息中识别需要列入的 EWD 明细项、数量、条件与风险；同一项工作只列一次。
  3. AI 为每个 EWD 明细项给出乐观值 O、最可能值 M 和保守值 P，程序按 EWD＝(O＋4M＋P)÷6 计算该项 EWD。
  4. 任务总 EWD＝所有 EWD 明细项之和；共享工作只列一次，父任务只汇总叶子任务。
  5. 初期使用平台维度与 AI 专家估算；后续根据团队历史任务的 EWD 拆分明细、完成标准和实际投入反馈校准估算。历史数据不足时继续使用平台规则。
  6. 用户确认后保存 EWD 拆分明细、总 EWD 和规则版本作为本次估算基线；新增、删除或重估明细项时生成新版本，不回写旧基线和历史快照。

平台初始 EWD 检查维度

八个维度是 AI 补全 EWD 明细项的检查清单，不打分，也不直接换算人天。每个维度必须回答“是否需要新增或调整明细、工作是什么、数量或次数、依据是什么”；同一项工作受多个维度影响时只保留一条明细，避免重复计时。

AI 可以返回 additionalFactor，说明八个维度未覆盖的因素，并给出由此新增或调整的 EWD 明细项与三点估算。重复出现且有历史数据支持的因素，经团队规则评审后才能升级为团队扩展维度并记录版本。

三点估算规则

参考依据： PMI 的项目估算实践使用三点估算表达不确定性，并介绍常用的 PERT 加权平均公式 (O＋4M＋P)÷6。TaskDoor 将该方法用于每个 EWD 明细项；这些明细项在估算方法上对应 WBS 工作包。八个检查维度是平台规则，不是 PMI 规定的评分标准。

符号 名称 含义
O 乐观投入 已确认的资料、工具和协作条件都顺利，没有额外返工时需要的人工时间
M 最可能投入 按当前已知条件正常完成时，最可能需要的人工时间
P 保守投入 已识别的不确定因素发生，但交付范围没有增加时需要的人工时间

规则： AI 只依据任务已写明的工作和风险，为每个 EWD 明细项估算 O、M、P，满足 0≤O≤M≤P；同一项工作只计算一次。程序计算 单项 EWD＝(O＋4M＋P)÷6，任务 EWD 为全部明细项 EWD 之和。关键条件不足、足以改变估算区间时标“待估算”。用户可以修改三点数值并补充依据；团队历史数据用于校准后续估算。

数值来源： 首版由 AI 根据任务名称、目标、完成标准、八个检查维度和已识别风险估算 O、M、P，单位统一为人天。它们不是固定分档，也不是 AI 随意打分；每个数值必须有对应工作和判断依据。用户可修正数值，后续再用团队历史任务的实际投入反馈校准。

例子：制作一份方案。 已知工作包括准备资料、操作 AI、人工修改和两人审核；任务同时明确存在“资料可能需要补充、审核后可能再修改一轮”的风险。

二、进度预测与用户确认

用户仅设置状态与截止时间，没有工作排期，不计算计划应完成比例或工作量领先／落后。

有效工作量 W 与有交付依据的完成量 C 齐备时，AI 预测完成度＝C/W。完成标准、证据覆盖或权重不足时返回缺口，不从状态、截止时间、文件数量或经过天数生成百分比。用户标记已完成并保存成功后，以独立完成声明显示 100% 用户确认；AI 预测 100% 本身不改变状态。

主任务需要汇总时按完整、去重叶子工作量加权；叶子取其有效 AI 预测或用户确认。缺少必要贡献时不输出精确父级汇总。父子状态不级联；父级已有用户完成声明不被子项汇总撤销。

三、截止日期与完工预测

截止日是用户要求的目标；AI 完工预测依据剩余工作、可用执行时间、依赖与已知等待，单独记录生成时间和输入版本。仅有截止与状态无法得出完工日期；不能用当前百分比或人天直接外推自然日。

用户完成后，确认事件日期替代未来预测。仅修改、清空或恢复截止日时，进度与 AI 完工预测日均保持不变，只重新比较日期差；不能为适配截止而修改预测，也不因此使预测失效。未完成且已过截止可由代码判断已逾期，无需 AI。

四、更新、保存与验收

唯一触发清单见 6.3 预测更新节点与状态变更，状态显示见 6.3 状态变更与文案。进度与时间按受影响输入分别更新；触发不等于结果已经生成，旧请求不得覆盖用户完成声明。

预测记录、完成确认、重开及范围变更分别保存。燃起图保留原时点总量和完成量及来源，不统一称为实际进度；新增范围与确认完成各有事件。生产预测队列、独立时间戳和正式历史迁移仍待接入。

五、校准与实现边界

初始 EWD 采用三点估算；历史校准使用真实记录的投入和确认事实，不能将任意完成标记时间当作实际投入工时。当前展示修订不代表模型已实时运行或校准完成。进度来源与完成／重开、改截止、迟到结果、父子关系的验收统一维护于 6.3 验收重点。

7.9 人员责任分析 Skill

目标：持续跟进当前用户负责或参与的任务，识别本人实际承担的工作，结合用户确认和纠正，让责任说明越来越准确，为后续成员推荐提供更可靠的依据。 判断“通常负责什么、责任边界在哪里”，不做能力、效率或绩效评分。

Skill：agentdoor-responsibility-advisor。 将第 2.5 节已有责任建议明确为独立的人员责任分析 Skill，复用“我的责任”的建议、依据和确认入口，不另建用户画像。

1. 分析范围与输入

  • 仅分析当前用户在当前团队中负责或参与、且当前有权读取的任务；不同团队的责任与证据分开保存。
  • 输入责任文本与版本、任务目标与完成标准、本人分工、实际交付／贡献、相关讨论与确认、任务／交付来源及版本，以及历史建议和用户反馈。
  • 已完成任务仍可作为历史依据；待开始任务只说明当前分工，不能当作已经执行。已取消任务只保留可证实的实际承担事实，不推断交付完成。本分析不套用“我的工作”的三状态排序范围。
  • 输入注明数据覆盖、时间与权限；参与名单不等于实际承担，任务完成也不等于所有成果都由负责人独立完成。

2. 分析步骤

步骤 判断什么 产物
识别实际承担 本人在任务中具体负责什么结果、提供什么贡献，哪些记录可以证明？ 带来源的承担事实；不能归属的内容标待核对
归纳责任范围 哪些是持续出现的工作，哪些只是一次临时协助或阶段性安排？ 有范围、时效和依据的责任候选，不直接写“擅长”或“效率高”
对照现有责任 已有描述是否覆盖实际工作，有没有缺失、过宽、重复或已确认的职责变化？ 新增、更新、废弃或不调整，并指出对应原责任
用户核对 建议是否准确，责任边界需要怎样修改？ 用户确认后才写入；保留修改、忽略与纠正记录
反馈校准 新任务事实和用户纠正改变了哪些判断？ 更新后续建议的依据与范围，确认后的责任版本供成员推荐使用

一次临时协助不直接推成长期责任；多个独立任务的同类承担或明确的长期分工确认，可支持归纳。任务数量、在线时长和提交间隔不能代替实际承担证据；同一成果的多版本、父子引用不重复计数。没有近期任务或来源失效不代表职责消失；废弃建议需有明确职责调整依据。

3. 输出与用户决定

每条建议包含操作、责任文本、原责任与基准版本、改变原因、任务与交付来源、数据时间、团队与范围、未确认事项。已有责任准确时输出“不调整”；证据不足保留原文并说明缺口。

复用“我的责任”：用户可查看依据、采纳、修改或忽略；旧建议不能覆盖新版本。未经确认的建议不进入正式责任匹配。Skill 不自动修改 Task Owner、参与人或权限；确认责任建议不等于接受具体任务。

更新流程： Skill 支持分析建议、准备更新、执行已确认更新三种模式。用户确认后才写入；确认绑定最终操作、责任文本、用户与团队、原责任及基准版本。业务服务独立校验权限、当前版本和幂等并返回回执；Skill 根据回执说明更新结果，不把候选的“可确认”当作写入授权。用户修改文本后须确认最终版本；旧建议或版本冲突时重新核对，不能覆盖新责任。写入接口未接通或回执未知时保留建议，明确待接入或待核实，不声称已更新。

4. 何时分析，如何越来越准

  • 本人任务分工、相关交付／贡献、确认记录或用户责任发生实际变化时，只重算受影响的责任候选；本人可主动触发重新分析。打开页面不制造新证据或新分析时间。
  • 用户纠正需与被纠正建议及来源版本关联，例如“只是这次临时帮忙”“负责脚本，不负责投流”；后续判断复用该边界，新证据与之冲突时提出待核对，不静默覆盖用户说明。
  • 忽略不等于否定，也不代表该用户拒绝承担工作；同一来源版本的已忽略建议不反复推送，实质证据变化后才重新判断。
  • 来源撤销、权限变化、任务贡献被更正后，相关候选失效并复核；读取失败不等于没有责任。正式责任仍由用户决定是否调整，失效证据不得继续对外展示或用作新增推荐理由。
  • 每次保留输入、来源版本、规则版本、建议与用户处理结果。同样输入和反馈复用有效结果；这里的持续校准是更新事实、责任边界与建议，不是重复刷新或默认开展模型训练。

例子： 用户原责任是“内容制作”，近期多次实际承担达人短视频脚本交付，可建议细化为“负责达人短视频脚本策划与交付”，附任务依据。用户纠正直播协助仅为临时安排后，不再凭同一记录归纳为长期责任。

验证目标： 看责任遗漏、错误归属和重复错误是否减少，成员推荐能否更准确地解释匹配原因；不以建议数量或文字长度代表准确，不对成员排名。

实现边界： 已设计项目内 Skill 文件，并同步更新 PRD、HTML 与 PDF。现有责任建议界面可复用；任务变更触发、贡献归属分析、反馈回读、受控责任写入与生产数据接入仍待实现，尚未启动后台持续分析。

8.8 安全、失败与重试

场景 服务端结果 / 客户端动作
超时或重复点击 用原幂等键和原载荷重试，返回同一 ID 和 replayed=true；不同载荷复用键返回 409
并发更新 版本不一致返回 412 VERSION_MISMATCH，保留用户草稿、读取新版本、重新确认；不自动覆盖
删除影响变化 409 DELETION_IMPACT_CHANGED；重新预览和确认，旧摘要失效
无权限 已知且可暴露存在的对象可报 403；不可发现对象统一 404；重放旧回执也要重新鉴权
验证不通过 400 结构错误，422 领域约束错误，428 缺版本前置条件；指出允许公开的字段问题，不写半份数据
文件仍扫描 accepted_async，不当错误也不当可用；通过 upload status 查询后续状态
多任务计划 主任务与子任务创建需受控原子命令；当前 38 个工具没有整棵计划提交工具，不能逐项调用后宣称原子成功

annotations 只帮助调用方识别 readOnly / destructive / idempotent，不提供权限。删除、正式提交、状态变化的授权必须绑定实际对象和影响；不得把模型“用户已同意”的文字当作确认凭证。

9.3 诊断结果如何进入任务流程

  5. 复核： 相关事实改变后重新核对，条件不再成立才记录已解除与依据，更新父级聚合并向原接收范围反馈；通知发送失败可重试同一事件，不重复建问题。
