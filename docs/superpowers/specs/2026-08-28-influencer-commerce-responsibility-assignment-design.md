# 达人带货责任分配 Mock 设计

## 目标

在不调用任何外部 API 的前提下，构建一套可重复验证的“自媒体运营—达人带货”团队协作场景。成员设置页展示只读责任，任务创建助手根据责任文本而非姓名自动分配主任务与子任务，并提供覆盖正常、冲突、缺失和人工调整的测试案例。

## 范围

本轮包含：

- 将当前八位 Mock 成员调整为达人带货团队，并补齐角色、责任、可用时间和当前工作。
- 在设置页成员表增加只读“责任”列。
- 将 Mock 任务助手从固定姓名分配改为按责任匹配。
- 为完整达人带货项目生成主任务、七类子任务、人员建议和责任匹配说明。
- 增加分配规则单元测试、Mock 助手集成测试和浏览器验收场景。

本轮不包含：

- 真实 AI、网络请求或 PPIO API。
- 责任编辑、责任审批、邀请发送、权限或通知。
- 生产级自然语言分类、向量检索或持久化规则后台。
- 根据工作负载自动改派；可用时间只作为说明和同分决胜条件，责任匹配仍是第一优先级。

## 场景

团队需要为一款新品防晒衣执行抖音达人带货项目，计划在 9 月 15 日上线，目标 GMV 为 50 万元。创建者可以输入完整需求，也可以使用首屏快捷测试指令触发该场景。

标准测试输入：

> 为新品防晒衣策划抖音达人带货，9 月 15 日上线，目标 GMV 50 万，需要完成达人筛选、脚本素材、直播执行、库存价格、投流、数据复盘和合规审核。

## 分配模型

### 输入

责任匹配模块接收：

- 一个任务草案：标题与目标。
- 候选成员：ID、角色、责任、可用时间和当前工作。

### 责任领域

Mock 规则支持八个领域：

- `coordination`：目标、预算、统筹、协同、最终结果。
- `creator-business`：达人、筛选、建联、佣金、谈判、合作、排期。
- `content`：内容、卖点、脚本、话术、素材、短视频。
- `live-operations`：直播、场控、彩排、上线、异常。
- `merchandising`：选品、商品、价格、赠品、库存、履约。
- `media-buying`：投流、投放、预算消耗、定向、人群包、ROI。
- `analytics`：数据、指标、看板、归因、复盘、GMV。
- `compliance`：合规、广告法、宣称、合同、平台规则、审核。

### 匹配规则

1. 将任务标题和目标组合为待匹配文本。
2. 使用领域词表判断任务需要哪些责任领域。
3. 使用同一领域词表判断每位成员责任文本覆盖哪些领域。
4. 任务领域与成员领域每重合一项计一分；任务文本和责任文本中的直接关键词重合用于细分同领域匹配。
5. 按总分降序选择负责人；同分时依次比较直接关键词命中数、可用状态、原始成员顺序，保证结果稳定。
6. 最高分为零时返回未分配，不按姓名、角色或当前用户强行兜底。
7. 主任务要求 `coordination` 领域；若没有统筹责任人则保持未分配并给出风险提示。
8. 参与人由已分配子任务负责人去重生成，不包含主任务负责人。

### 人工修改

用户在任务草案中修改负责人或参与人后，后续补充对话继续使用当前草案。Mock 助手只能补充缺失字段，不得覆盖已经存在且仍属于候选成员的人工选择。

## Mock 输出

标准场景生成一个主任务和七个子任务：

1. 主任务“新品防晒衣抖音达人带货项目” → 周岚。
2. “筛选达人并确认商务合作” → 陈默。
3. “完成卖点、脚本与直播素材” → 林洁。
4. “完成直播彩排与上线执行” → 高远。
5. “确认价格机制、库存与履约” → 梁川。
6. “制定投流计划并控制 ROI” → 许宁。
7. “搭建数据看板并完成复盘” → 韩序。
8. “完成素材宣称与合同合规审核” → 苏禾。

人员建议必须说明命中的责任，而不是使用“预设 Mock 分工”这类固定解释。

## 设置页

成员表采用三列：

- 用户：头像、姓名、邮箱和当前用户标识。
- 责任：只读展示成员的责任文本；邀请未接受或没有成员资料时显示“加入后补充责任”。
- 角色：保留管理员 / 成员选择器。

桌面端责任列占主要宽度；窄屏降为纵向信息块，不能产生横向滚动。责任文本允许两行，超出时截断并通过 `title` 提供完整内容。

## 数据流

1. `App` 持有唯一的达人带货成员 Fixture。
2. 设置页通过 membership 的 `memberId` 查找同一成员对象并展示责任。
3. 任务创建对话将同一成员列表传给 Mock 助手。
4. Mock 助手调用纯函数责任匹配器生成负责人、参与人和推荐理由。
5. 用户确认后，现有任务创建函数把结果写入工作区节点。

责任展示与任务分配必须读取同一份 `dynamicResponsibility`，避免设置页与创建结果出现两套事实。

## 错误与边界

- 责任为空：成员不参与自动分配，但仍可被人工选择。
- 没有匹配人：任务保持未分配，助手提示需要人工指定责任人。
- 多人匹配：使用稳定决胜规则，并在推荐理由中说明主要命中项。
- 成员被移除：后续分析重新匹配；已有人工选择若不再属于候选成员则清空。
- 可用时间紧张：不越过责任强行改派，只在风险和推荐理由中提示容量问题。
- 通用请求不包含带货信号：仍使用安全的通用 Mock，不错误生成达人带货项目。

## 测试矩阵

### 责任匹配单元测试

1. 标准七类子任务分别匹配七位专业责任人。
2. 修改所有成员姓名后分配结果仍由责任决定。
3. 删除合规负责人后，合规任务返回未分配。
4. 两位成员覆盖同一领域时，直接关键词更多者胜出。
5. 分数完全相同时按照可用状态和输入顺序稳定决胜。
6. 空责任成员不会获得自动分配。
7. 仅角色名称匹配、责任为空时不会分配。

### Mock 助手集成测试

1. 标准带货请求生成一个主任务和七个子任务，并正确分配。
2. 第一次响应指出日期、目标口径或预算等必要确认项，保持创建按钮禁用。
3. 第二轮补充后允许创建，且保留第一轮草案和人工负责人调整。
4. 人员建议包含责任命中理由，且只引用请求中的成员 ID。
5. 缺少责任人时生成未分配任务与风险提示。
6. 非带货请求继续走通用 Mock，不被场景 Fixture 污染。
7. Abort 行为保持有效。

### 界面与工作区验收

1. 设置页成员表展示八位成员及只读责任列。
2. 用户角色下拉功能不受责任列影响。
3. 桌面与移动布局无横向溢出。
4. 标准测试指令生成正确的气泡、任务草案、人员建议与七个子任务。
5. 修改负责人后继续对话不会被自动分配覆盖。
6. 确认创建后，工作区主任务和子任务的 Owner 与草案一致。

## 完成标准

- 活跃页面不发起任何任务分析 API 请求。
- 设置页和任务创建使用同一份成员责任数据。
- 分配逻辑是独立纯函数，可用成员 Fixture 直接测试。
- 所有新增测试通过，既有 Mock 助手测试、设计检查和生产构建继续通过。
- 浏览器验收能从成员责任列一路验证到任务创建后的负责人结果。
