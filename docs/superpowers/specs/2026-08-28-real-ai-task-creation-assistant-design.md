# 真实 AI 任务创建助手设计

## 背景与目标

现有“新建对话”页面可以把一句需求转换成任务草案，但辅助能力仍停留在前端规则填充。目标是接入 PPIO 的真实模型 `pa/gpt-5.5-pro`，让 AI 在创建过程中主动补齐信息、判断任务质量、推荐协作人员，并产出可确认的主任务与子任务计划。

成功标准不是“模型返回了一段文字”，而是用户能在对话中逐步得到结构化、可编辑、可验证的创建产物，并在最终确认后一次性创建主任务和全部子任务。

## 已选方案

采用“结构化 AI 助手循环”。每轮对话由服务端把会话、当前草案和必要的团队上下文发送给 PPIO；模型同时返回自然语言回复和结构化任务状态。前端校验结构后增量更新消息流与草案。

不采用纯自由对话，因为最后提取字段容易遗漏；不采用多 Agent 编排，因为第一版会显著增加调用时间、成本和失败面。

## 用户流程

1. 用户从左侧“新建对话”进入创建助手。
2. 用户描述要推进的事情。
3. AI 分析需求，并优先追问 1–2 个最影响创建的问题。
4. 每轮回复同时更新任务清晰度、人员建议、风险、主任务和子任务草案。
5. 用户可以自然语言继续修改，也可以直接编辑草案字段。
6. 当必填信息完整且 AI 判定可创建时，界面开放“创建主任务和全部子任务”。
7. 用户明确确认后，一次性写入主任务和全部子任务，并建立 `parentTaskId`。
8. 成功回执展示创建数量与任务清单，用户可进入主任务详情。

## 过程产出物

参考用户提供的 Agent 执行结果界面，消息流中的每轮 AI 产出按以下层次展示：

- 本轮摘要：例如“已补充目标并拆分为 4 个子任务”。
- AI 回复：简短解释判断和下一步问题。
- 缺失信息卡：列出当前仍需回答的问题及其原因。
- 质量判断卡：显示范围、目标可验证性、时间合理性和主要风险。
- 人员推荐卡：显示推荐负责人、参与人、推荐理由和未分配提醒。
- 主任务卡：名称、目标、状态、负责人、参与人、起止时间、标签。
- 子任务列表卡：每项包含名称、目标、状态、负责人建议、参与人、起止时间和标签。
- 创建结果卡：显示主任务与子任务的创建结果，并提供主任务入口。

同一会话只有一份当前草案；后续轮次增量更新它，不在消息流中堆叠多份失效表单。历史 AI 回复保留，用于解释草案如何形成。

## AI 辅助职责

### 主动追问

- 优先补齐任务名称、目标、负责人和创建所需的关键边界。
- 时间、参与人和标签可以为空，但 AI 应在确有帮助时询问，而不是机械收集所有字段。
- 每轮最多提出两个问题，避免把聊天变成一次性长表单。

### 任务质量判断

- 判断范围是否过大，是否需要拆分。
- 判断目标是否可以验证，指出模糊结果词。
- 判断时间是否与子任务数量、依赖和人员可用性冲突。
- 风险必须说明依据，不使用空泛警告。

### 人员推荐

- 根据职责、动态责任范围、可用时间和当前工作摘要推荐负责人及参与人。
- 推荐结果包含理由；没有合适成员时明确保持未分配。
- AI 只提出建议，不代表被推荐人员已经接受。

## 模型输入与隐私边界

调用模型：`pa/gpt-5.5-pro`。

发送给 PPIO 的内容包括：

- 当前会话消息。
- 当前结构化草案。
- 当前日期与时区。
- 可选标签名称。
- 团队成员的内部 ID、姓名、职责、动态责任、可用时间和当前工作摘要。
- 必要时发送与当前需求最相关的现有任务标题、状态和负责人，用于重复性与负载判断。

不发送邮箱、头像、登录信息、本地存储全量内容、API Key 或与当前创建无关的文件内容。

## 服务端与凭据

- 浏览器只调用同源 `/api/task-assistant`。
- Vite 本地服务增加仅在服务端执行的代理处理器，使用 OpenAI 兼容协议访问 `https://api.ppinfra.com/openai/v1/`。
- Key 通过 `.env.local` 的 `PPIO_API_KEY` 读取；模型通过 `PPIO_MODEL=pa/gpt-5.5-pro` 配置。
- `.env.local` 必须保持 Git 忽略；Key 不得出现在 `VITE_*` 变量、前端源码、构建资源、日志或错误响应中。
- 服务端设置请求超时并限制请求体大小。

## 结构化协议

模型响应包含：

- `assistantMessage`：面向用户的简短回复。
- `resultSummary`：本轮做了什么。
- `missingInformation[]`：字段、问题和原因。
- `qualityAssessment`：范围、目标、排期和风险。
- `peopleRecommendations[]`：成员 ID、建议角色和理由。
- `draft`：主任务与 `subtasks[]` 的完整当前快照。
- `readyToCreate`：是否具备创建条件。

服务端使用 Zod 校验响应。第一次格式错误时附带校验问题重试一次；第二次仍失败则返回稳定错误，不把未校验数据交给前端。

## 创建与数据一致性

- AI 输出始终是草案，不直接写入正式任务。
- 创建按钮仅在主任务名称、目标、负责人有效，子任务名称与目标有效，日期顺序正确且 `readyToCreate=true` 时启用。
- 确认后先在内存中构建完整节点集合，再一次性更新 `workspaceNodes`，避免只创建一半。
- 主任务先生成 ID；每个子任务使用该 ID 作为 `parentTaskId`。
- 所有参与人排除各自负责人；被推荐但未接受的人员继续表现为待邀请语义。
- 提交锁防止重复点击产生重复任务。

## 错误处理

- 网络失败、超时或 5xx：保留输入、消息和当前草案，显示可重试提示。
- 401/403：提示本地 AI 配置不可用，不向前端返回密钥或上游响应体。
- 429：提示稍后重试，保留会话。
- 结构校验失败：服务端重试一次，失败后返回通用格式错误。
- 用户在请求中继续发送：当前输入保持可见，但发送按钮锁定，防止会话轮次乱序。
- 创建失败：不清空草案，允许再次确认。

## 可访问性与反馈

- 请求期间发送按钮进入处理中状态，并提供“正在分析任务”状态文本。
- 新回复通过非打断式 live region 通知。
- 结果卡使用标题和列表语义；人员建议与风险不只依赖颜色区分。
- 移动端所有产出卡为单列，输入框位于产出物之后，不遮挡创建按钮。

## 验收标准

1. 首轮输入真实调用 PPIO `pa/gpt-5.5-pro`，不再使用本地固定回复。
2. AI 能连续追问并在后续轮次增量更新同一份草案。
3. 界面展示本轮摘要、缺失信息、质量判断、人员推荐、主任务和子任务清单。
4. 人员建议有职责或负载依据，不发送成员邮箱。
5. AI 能建议拆分任务，并在一次确认后创建主任务与全部子任务。
6. 未确认前任务列表不发生写入。
7. API Key 不出现在浏览器资源、网络响应、控制台或 Git 差异中。
8. 上游超时、鉴权失败、限流和格式错误均保留当前会话并给出可重试反馈。
9. 桌面与移动端均能完成输入、追问、调整、确认和查看任务流程。

## 验证计划

- 使用真实 PPIO 测试一次首轮分析和一次追问更新。
- 对服务端解析器使用固定合法、缺字段、错误类型和非 JSON 响应验证。
- 浏览器验证发送锁、错误重试、过程卡、主子任务确认与详情跳转。
- 检查生产构建资源与 Git 差异，确认不存在 API Key。
- 运行 TypeScript 构建和现有设计检查。

## 非目标

- 不支持历史对话列表或跨设备会话恢复。
- 不让 AI 自动通知、指派或代表成员接受任务。
- 不上传或分析附件。
- 不并行调用多个模型或多个 Agent。
- 不修改独立 MCP 的任务创建协议。
