# 子任务下级数量提示设计

## 目标

在任务详情的“子任务”列表中，让用户无需逐项打开就能判断某个子任务是否还包含下一层工作，并看到直接下一级子任务数量。同步丰富 Mock 层级，确保该提示在日常预览中有足够多的真实示例可观察。

## 方案取舍

- 采用：在任务树投影为子任务列表数据时计算直接子任务数，将只读数量传给列表行。展示组件不读取完整任务树，数量也不写入持久化数据。
- 不采用：在 `TaskSubtaskList` 内传入并遍历完整任务树。这样会让纯展示组件承担关系计算，增加耦合。
- 不采用：在任务记录中保存子任务数量。该数字可以从父子关系推导，持久化会产生同步和过期问题。

## 详细设计

1. 只统计 `parentTaskId` 等于当前列表项 ID 的直接下一级任务，不统计孙级及更深层后代。
2. 数量放在子任务名称之后，显示为轻量辅助文案“`N 个子任务`”。它与任务名称属于同一个打开入口，不新增点击动作。
3. 数量为 0、缺失或未知时不显示，避免给叶子任务增加噪声；不能把未知补成 0。
4. 数量使用辅助字号和三级文字色，不改变名称、负责人、状态和展开箭头的既有层级。长标题仍按现有布局处理，数量不挤占负责人和状态区域。
5. 新建、删除或调整父子关系后，数量由当前任务树重新投影，不单独维护缓存。

## Mock 数据

1. 优先扩充现有团队场景中的任务层级，不另建只服务截图的孤立演示数据。
2. 让多个当前可进入的子任务分别拥有 1、2、3 个直接下级，覆盖单项、少量和较多三种常见密度。
3. 至少保留一条三层以上结构，用于验证列表数字只统计直接下一层，不累计更深后代。
4. 新增任务需包含负责人、状态、目标、完成标准和合理日期，继续满足当前 Mock 数据契约；不能只为凑数量添加空壳任务。
5. 新增或调整 Mock 后同步更新依赖这些固定数量的回归基线，不把新的固定总数写进产品逻辑。

## 数据流

`App` 从当前团队任务树筛选直接子任务，在构造 `TaskRelationSummary` 时附加 `childTaskCount`。`TaskDetail` 原样传给 `TaskSubtaskList`，列表只负责按规则显示。

## 验收标准

- 某子任务有 3 个直接子任务时，名称后显示“3 个子任务”。
- 存在更深层后代时不重复累计，只显示直接下一层数量。
- 叶子任务不显示“0 个子任务”。
- 数量不产生独立按钮，名称原有的打开任务行为保持不变。
- 子任务列表的负责人、状态、进度展开与空状态不受影响。
- 当前 Mock 中至少可观察到 1、2、3 个直接下级的不同示例，并有一条更深层关系证明后代不会被重复累计。

## 定向验证

先补 `TaskSubtaskList` 渲染测试，确认有数量时出现、0 或缺失时隐藏；再补任务树投影与 Mock 层级测试，确认只统计直接下级及新增数据满足场景约束。最后运行与子任务列表、Mock 场景相关的定向测试，同步更新任务详情 PRD、实现来源和变更日志，并重新构建 PRD 页面。
