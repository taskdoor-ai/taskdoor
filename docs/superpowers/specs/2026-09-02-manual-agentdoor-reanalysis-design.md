# 手动重新分析设计

## 对象与目标

- 对象：“我的工作”的跨任务优先建议，以及任务详情“诊断”Tab 的任务诊断报告。
- 用户：需要核对当前任务变化是否已经反映到分析结果中的团队成员。
- 本次决策：两处各增加一个“重新分析”按钮，直接调用 TaskDoor 自己的分析逻辑，不打开“连接 AI”弹层，也不要求用户选择外部 Agent。
- 成功证据：用户点击后能看到明确且不可重复触发的加载状态；完成后结果基于当前最新任务数据重新计算，并显示新的分析时间。

## 入口与布局

不新增卡片、弹窗或独立页面，复用现有标题与元信息区域：

1. “我的工作”：按钮放在分析更新时间旁，与“AI 分析规则”和更新时间共同构成分析元信息区。
2. 任务诊断：按钮放在“任务诊断报告”标题区右侧，不进入单条诊断卡片，也不与“查看依据”混在一起。

两处按钮统一使用“重新分析”文案和现有次要按钮样式。窄屏下允许标题区换行，按钮仍保留至少 44px 的触控高度。

## 数据与交互

两处入口通过异步回调请求 TaskDoor 基于当前可见、已保存的任务数据重新计算：

1. 点击“重新分析”。
2. 按钮立即禁用，旋转图标替代默认图标，文案变为“分析中”。
3. TaskDoor 读取当前最新任务快照并计算对应结果；未保存的输入草稿不进入分析。
4. 成功后原位替换结果，更新时间改为本次分析完成时间，按钮恢复为“重新分析”。
5. 失败后按钮恢复可用，并在对应分析区域显示简短错误。本次失败不能把旧结果的时间改成最新，也不能把旧结果宣称为本次分析结论。

同一入口在加载期间不能重复提交。两个页面的重新分析状态彼此独立，不建立全局队列或通知。

## 组件边界

- `PersonalWorkbench` 负责工作台按钮、按钮加载状态和错误反馈；`App` 提供异步重新计算入口并在成功后更新工作台分析时间。
- `TaskDiagnosisReport` 负责诊断标题区按钮的可访问呈现；`TaskDetail` 负责触发当前任务的 TaskDoor 诊断、维护加载／错误状态，并在成功后用新的检查时间重新生成报告。
- 当前原型的 TaskDoor 分析是仓库内已有的确定性分析逻辑。新增的异步边界用于真实表达一次分析请求，并为后续替换成服务端 TaskDoor 分析保留接口；不通过“连接 AI”弹层绕行，也不伪造外部 Agent 响应。

## 状态与可访问性

- 正常：按钮显示“重新分析”。
- 加载：按钮禁用，显示旋转图标与“分析中”；对应分析容器设置 `aria-busy="true"`，按钮文案通过可访问名称表达状态。
- 成功：结果和分析时间一起更新；不额外弹出成功提示。
- 失败：保留可核对的旧内容并明确说明重新分析失败、旧结果未更新；错误使用 `role="alert"`。
- 空结果：重新分析成功后继续使用现有空状态，不伪造问题数量。
- 无权限与数据过期：本次不新增权限模型；回调失败时按失败状态呈现，不能泄露不可见任务信息。
- 键盘：按钮按现有 Tab 顺序聚焦，Enter 与 Space 均可触发；加载时不可再次触发。
- 减少动态效果：旋转动画遵循项目现有 `prefers-reduced-motion` 规则。

## 最小验收项

1. “我的工作”更新时间旁存在“重新分析”按钮，点击后显示“分析中”且禁用。
2. 任务诊断标题区存在同样的按钮，加载状态只影响当前任务诊断。
3. 两处均由 TaskDoor 当前分析逻辑重新读取已保存任务数据；不打开“连接 AI”弹层。
4. 成功后更新对应结果与分析时间，失败时不更新分析时间并提供可见错误。
5. 加载期间不会重复请求，按钮和状态具备键盘与辅助技术语义。
6. 现有推荐列表、诊断卡片、空状态与“查看依据”交互保持不变。
