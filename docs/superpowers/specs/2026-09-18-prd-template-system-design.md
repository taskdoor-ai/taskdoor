# AgentDoor PRD 模板与维护机制设计

> 日期：2026-09-18  
> 状态：已确认  
> 范围：建立统一的 PRD 源码结构、模块模板、HTML 阅读形式和需求变更机制  
> 本阶段不包含：创建远程 GitHub 仓库、迁移全部现有 PRD、发布正式站点

## 1. 目标

建立一套同时利于人和 AI 阅读的 AgentDoor PRD 范式：

- 产品人员可以快速理解页面、模块、展示内容、可执行操作和操作步骤。
- AI 可以通过稳定的文件结构、模块 ID、标题层级和语义化 HTML 准确定位内容。
- 产品需求以模块化 Markdown 作为唯一事实源，自动汇总为一份完整 HTML。
- 需求含义发生变化时，有清楚、可追溯但不过度冗余的变更记录。
- 截图、说明、操作步骤和必要规则连续排列，不要求读者在同一功能内来回跳转。

PRD 只描述要实现的目标产品，不在各模块中混写当前 Demo 状态或研发完成度。实现进度由后续独立的交付跟踪文档管理。

## 2. 文档结构

建议建立以下目录：

```text
docs/prd/
├── README.md
├── index.md
├── CHANGELOG.md
├── templates/
│   └── module-template.md
├── modules/
│   ├── 01-task-list.md
│   ├── 02-task-creation.md
│   ├── 03-task-detail.md
│   └── ...
└── assets/
    ├── task-list/
    ├── task-creation/
    └── ...
```

- `README.md`：写作、审阅、构建和维护规则。
- `index.md`：产品总览、模块顺序和模块链接，也是汇总构建入口。
- `CHANGELOG.md`：只记录需求语义变化。
- `templates/module-template.md`：新模块统一起点。
- `modules/`：按产品模块拆分的唯一需求源文件。
- `assets/`：按模块保存目标界面截图和必要图示。

源文件模块化维护；对外仍生成一份连续、可搜索、可打印的完整 HTML PRD。

## 3. 模块模板

每个模块只固定四个一级部分。

### 3.1 目的

用简短文字说明该模块解决什么问题，以及希望用户得到什么结果。不重复产品愿景，不使用“提升体验”等无法验证的空泛表达。

### 3.2 范围和边界

说明本模块覆盖什么、不覆盖什么，以及与其他模块的职责边界。跨模块规则只在唯一归属模块完整定义，其他模块保留一句必要摘要并链接引用。

### 3.3 详细功能设计

按实际页面和页面内模块展开，不要求所有功能套用相同的二级章节。每个页面模块应尽量连续说明：

1. 该模块展示什么内容。
2. 用户可以执行哪些操作。
3. 每个操作的步骤是什么。
4. 操作完成后页面或数据产生什么结果。
5. 只有确实影响实现或验收时，补充呈现逻辑、分组、排序、分页或加载、权限、状态和异常规则。

复杂功能可以使用“展示内容｜可用操作｜操作步骤与结果｜必要说明”的表格；简单功能直接使用短段落或步骤列表，不为填满模板制造内容。

列表类模块需要在详细设计中写清适用的查询、筛选、分组、排序、分页或连续加载规则，以及任务是否会重复、顺序如何保持。只有该列表实际支持的能力才需要描述。

### 3.4 验收标准

使用用户可以观察或测试可以验证的结果描述验收项。验收标准引用对应页面或模块，但不重复整段功能说明。避免“体验良好”“运行正常”等主观表述。

## 4. 图文呈现原则

- 截图用于解释目标界面，不作为装饰。
- 截图紧邻对应的模块说明、操作和步骤。
- 每张图使用稳定 Figure ID、清楚的替代文本和简短图注。
- 一张图只标注当前章节需要解释的区域；编号与正文顺序一致。
- 同一模块的截图、展示内容、操作、步骤、结果和必要说明连续排列。
- 不使用“查看对应操作及步骤”跳转去承载当前模块本应说明的内容。
- 只有规则确实属于另一个产品模块时才使用跨模块链接，并在当前段落保留必要摘要。
- 页面流程或关系仅在文字难以说明时使用流程图；优先使用可文本化的 Mermaid 或 SVG。
- 截图随界面或流程含义变化一并更新；仅视觉微调且不影响说明时无需重拍。

## 5. HTML 阅读形式

生成的完整 HTML 使用连续文档布局：

- 左侧提供产品模块目录、全文搜索和变更日志入口。
- 正文使用适合长文阅读的固定最大宽度，不采用卡片墙。
- 页面顶部提供当前版本、复制深链接、打印和 GitHub 源文件入口。
- 模块正文保留“目的 → 范围和边界 → 详细功能设计 → 验收标准”的连续层级。
- 截图与对应功能说明保持相邻，不拆成独立图库。
- 桌面端使用固定目录；窄屏使用可开关目录；打印时隐藏交互控件并保留图注和链接信息。

为利于 AI 阅读：

- Markdown 使用稳定的 `module_id`、标题层级和相对链接。
- HTML 使用 `article`、`section`、`figure`、`figcaption`、`table` 等语义元素。
- 页面正文直接写入生成的 HTML，不依赖异步请求后才出现。
- 图片必须有能独立说明内容的替代文本。
- 构建时同步生成轻量模块索引 JSON，包含模块 ID、标题、摘要、章节锚点、源文件和 HTML 链接，不复制完整正文。

## 6. 变更机制

每次需求含义变化必须在同一个 GitHub PR 中完成：

1. 更新受影响的模块 Markdown。
2. 界面或流程变化时同步更新截图或流程图。
3. 在 `CHANGELOG.md` 增加变更记录。

变更记录包含：

| 字段 | 要求 |
| --- | --- |
| 变更编号 | 稳定编号，例如 `CHG-2026-0918-01` |
| 日期与版本 | 进入 PRD 的日期和版本 |
| 影响模块 | 一个或多个稳定模块 ID |
| 变更类型 | 新增、调整或删除 |
| 变更内容 | 清楚说明需求含义改了什么 |
| 原因与影响 | 为什么修改，以及影响哪些页面或流程 |
| 关联记录 | GitHub PR、已确认决定或讨论链接 |

模块元数据只保留当前版本和最近一次变更编号，不在正文复制整份日志。生成 HTML 时，全局变更日志作为独立章节展示，并链接到受影响模块。

错别字、排版和不改变需求含义的措辞调整只保留 Git 提交记录，不进入产品变更日志，也不触发产品版本更新。

## 7. 构建与校验

构建链路：

```text
模块 Markdown + 图片
→ 校验结构和引用
→ 按 index.md 顺序汇总
→ 生成完整 HTML 和模块索引 JSON
→ GitHub PR 审阅
→ 合并后发布最新版 PRD
```

自动校验至少覆盖：

- 模块 ID 唯一且不会随标题调整而变化。
- `index.md` 中的模块文件存在，顺序明确。
- 四个一级部分存在，标题层级合法。
- 本地图片、跨模块链接和章节锚点有效。
- 图片具备替代文本和图注。
- 需求语义变化时，模块记录的变更编号可在 `CHANGELOG.md` 找到。
- 删除或改名模块时，不留下失效链接。
- 生成结果在桌面、窄屏和打印模式下可读。

校验只保证模板合同和引用完整，不以字符数量、表格数量或截图数量评价文档质量。

## 8. 迁移原则

- 保留现有 `docs/product-v2/` 与 `public/agentdoor-prd.html`，新体系通过独立目录建立后再逐模块迁移。
- 先迁移当前仍有效的目标需求，历史过程、重复说明和已被替代的规则不直接复制。
- 每个模块迁移时核对决策台账，确认唯一有效规则，再写入新模板。
- 未完成迁移前，旧 PRD 明确标记为历史来源；新 PRD 不同时从旧 Markdown 和手写 HTML 读取同一需求。
- 完成全部模块核对后，再将新 `docs/prd/` 设为唯一事实源，并停止手工维护旧 HTML。

## 9. 验收标准

- 能从模板创建一个新模块，只填写四个固定一级部分。
- 任务列表示例能连续说明页面模块、展示内容、操作、步骤、结果和必要规则。
- 同一模块内容无需跳转即可完成主要阅读。
- 构建脚本可从模块 Markdown 生成一份完整 HTML 和模块索引 JSON。
- HTML 支持模块目录、全文搜索、稳定锚点、打印和窄屏阅读。
- 一次需求调整能在同一 PR 中关联模块正文、必要图片和唯一变更记录。
- AI 能通过模块索引定位源文件和章节；人能从 HTML 直接理解页面结构和操作流程。
