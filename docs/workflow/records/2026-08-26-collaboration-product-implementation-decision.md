# AgentDoor 协作内核与产品改造 Decision Brief

> 状态：proposed
> Revision：2
> 产品负责人：卜佳菲（待确认）
> 变更级别：C2 / C3
> 关联决定：D-01–D-13；Q-01–Q-19

## 一、要解决的结果

把现有“看起来有任务、文件和人员”的原型，改造成一条符合团队真实协作方式的产品闭环：

```text
表达需求
→ 默认由我完成的最小草稿
→ 识别任务缺口，而不是评价人的缺陷
→ 用户主动选择是否协作、找谁、以什么方式协作
→ 对方可以接受、改范围或拒绝
→ 工作围绕 Task / Todo / File / Decision 留下证据
→ 子任务结果回到直接父 Task Owner 验收和整合
→ 被验收事实成为可纠正的责任画像证据
```

产品既要支持“记一件小事”，也要支持多人、多层任务、文件版本和跨边界交接。二者不能使用两套产品模型，也不能让小任务被复杂流程绑架。

## 二、当前事实

### 已确认的产品事实

- Task 与 Todo 保留；Task 可以递归扩展，Todo 是不能继续拆解的原子行动。
- 每个正式 Task 恰好一位 Owner；不同层级 Task 可以有不同 Owner。
- 任务创建默认由当前用户负责，协作必须由用户主动展开和选择。
- 团队文件是独立模块，任务文件继续保留层级；文件夹支持递归。
- 人员推荐必须可解释，并受证据覆盖、权限、隐私与可纠正性约束。
- AI 不是只在任务推进时出现，而是贯穿表达需求、找人、准备信息、执行、决定、文件、交接、验收和沉淀。
- 人与人的 Handoff 必须像 Agent 协作一样有清楚的范围、上下文、第一步、返回结果和接收确认。

### 当前仓库约束

`git rev-parse --verify HEAD` 当前失败，所有项目文件均未跟踪。没有经人类批准的 Git 初始 baseline，也没有等效的不可变 before / after 与恢复机制。因此本 Brief 只能处于 `proposed`，C2 / C3 功能代码不得先行修改。

## 三、产品判断：不要只判断“任务大不大”

“轻任务 / 大项目”只能描述表面规模，无法决定应该怎样协作。AgentDoor 应分别判断三条轴：

| 判断轴 | 可能结果 | 决定什么 |
| --- | --- | --- |
| 工作结构 | 一次行动 / 持续 Task / 独立子 Task / 递归 Task | 需要 Todo、Task 还是子 Task |
| 协作需要 | 无缺口 / 找信息 / 短咨询 / 独立结果 / 已有工作接续 | 自己做、找资料、邀请还是 Handoff |
| 风险强度 | 普通内部 / 权限或版本敏感 / 高风险或不可逆 | AI 能做到哪一步、谁必须确认、协议强度 |

用户不需要看到“复杂度 7.8”一类标签，只看到当前真正有价值的下一步。这样既避免把小事做重，也避免把高风险协作假装成一条简单待办。

## 四、目标协作流程

### 1. 表达需求

AI 先判断用户是否真的需要 Task：

- 只是找一个答案：直接回答或给文件，不强迫建 Task。
- 是可执行工作：复述期望结果。
- 信息不足：只问当前信息增益最高的一个问题，允许跳过。

此时不创建正式 Task、不通知成员、不展示完整任务树。

### 2. 最小 Proposal

Proposal 首屏只包含：

- 一句话目标。
- 当前已有的信息或附件。
- 仍缺的关键信息。
- 默认 Owner 建议为“我”。
- “创建并由我负责”这个清晰动作。

Proposal 可编辑、暂存和放弃；用户确认前不进入正式任务树。

### 3. 缺口洞察

AI 判断的是任务缺口，不是“你不够好”。缺口包括：信息、知识、相似经历、权限、独立判断、执行范围、承诺容量和利益相关方。

每个缺口都必须说明：

- 缺什么。
- 为什么现在重要。
- 依据是什么。
- 系统不知道什么。
- 不补齐的影响。
- 最小充分的补齐方式。

除权限等硬约束外，用户始终可以选择“先由我推进并保留风险”。

### 4. 用户主动展开协作

缺口出现后提供四条平级路径：

1. 继续自己推进。
2. 先找相关信息或文件。
3. 看看协作者。
4. 不知道找谁时，起草团队求助。

系统不预选人员、不预发邀请，也不因用户拒绝建议而阻止创建。

### 5. 候选比较

只展示 0–4 位有真实依据的候选，不凑数、不预选，也不显示综合匹配分。只有 1 位时解释为什么没有可比候选；0 位时进入找资料、定向求助或广播。比较维度随缺口变化：

- 能补齐哪个缺口。
- 正式职责与相似工作证据。
- 是否具有当前动作所需授权。
- 对当前 Task / File / Decision 的上下文距离。
- 本人主动公开、可撤回、会过期的粗粒度协作窗口。
- 适合的协作方式与范围。
- 证据覆盖、新鲜度与不确定性。
- 替代路径和专家税风险。

“忙闲工时”不能从任务数量、在线状态、回复速度或私人日历推断给发起人。建议采用：

- 人员侧：本人发布的“可短评审 / 可接一项有界结果 / 暂不接受 / 未公开”。
- 工作侧：当前协作包的一般投入区间，与个人效率预测分开。
- 成员本人侧：系统可以私下提示已接受承诺的冲突，但不把原始依据暴露给发起人。

这既保留真实找人时对可行性的考虑，也避免把协作工具变成员工监控。

### 6. 选择协作方式

用户不是只选“这个人”，还要选“希望他怎样帮”：

| 需要 | 产品表达 | 责任效果 |
| --- | --- | --- |
| 资料、线索、答疑 | 有界求助 / 短咨询 | Owner 不变，可不形成长期责任 |
| 独立评审或批准 | Reviewer / Approver Responsibility | 不改变 Task Owner；授权另行校验 |
| 尚未开始的独立结果 | 子 Task Proposal | 对方接受后才创建由其拥有的子 Task |
| 已经做到一半的工作 | Handoff Offer | 激活时原子变化 assignee / Responsibility / Owner |

一张邀请只绑定一位 recipient、一个 scope 和一种协作方式。多人协作使用不同范围的独立分支，避免多人接受后生成重叠责任。

### 7. 接受、改范围和拒绝

接收者首屏先看到：为什么找我、我接什么、不接什么、谁仍是 Owner、需要哪些文件、预计怎样协作。

接收者可以：

- 接受。
- 缩小或重写范围。
- 重新排优先级。
- 推荐他人。
- 请求第三方协调。
- 私密拒绝。

发出不等于接受，接受不等于权限就绪，阅读文件不等于责任变化。上下级场景中的“可以拒绝”不能被当成自由同意的充分证据。

### 8. 执行与洞察

执行过程围绕业务对象留痕：Task、Todo、Responsibility、File、Decision、Activity、ChangeSet。AI 只根据可验证事件提醒：

- 目标或范围漂移。
- 文件版本冲突。
- 决定未记录或确认者无权。
- Todo 已成长为需要独立 Owner 的 Task。
- 后续工作等待一个权限、文件或决定。
- 子 Task 已具备交回条件。

不根据在线、正在输入、静默时长或消息数量判断人在不在工作。

### 9. Handoff 与 Result Return

Handoff 只用于已有上下文、工作或责任接续，不承包所有找人动作。建议使用：

```text
draft → offered → clarification-requested → accepted → activated
                └→ declined / cancelled / expired
```

`accepted` 表示必要人员接受同一 Revision；`activated` 表示权限、版本、当前对象状态检查通过，责任变化与审计在同一事务生效。

子 Task 结果按直接父级逐级交回：

```text
子 Task Owner 发出结果
→ 子 Task 进入 Review
→ 父 Task Owner 验收或要求补充
→ 激活后子 Task Completed
→ 父 Owner 再把结果整合到父 Task
```

“已交付、已验收、子 Task 完成、父 Task 已整合”必须是四个可区分的事实。

### 10. 责任画像沉淀

已激活的 Responsibility / Handoff 可以证明“当前正在承担什么”；只有被验收的实际结果才可以进一步生成“做过或具备相关经验”的候选证据。以下行为不能成为能力证据：收到邀请、浏览文件、被 @、拒绝、回复快、在线时间长、Activity 数量多。

AI 只起草 Claim；成员可确认、纠正、隐藏或争议，并同时看到 EvidenceCoverage。平台没覆盖的会议、邮件、外部 Jira 和线下工作必须明确显示为未知。

### 新增

1. **团队文件**：一级模块；文件夹树、列表、详情、版本、权限状态、维护人和被 Task 引用关系。
2. **协作区**：放在 Task 详情内，统一呈现邀请、Responsibility、Handoff、Result Return 与待验收。
3. **团队动态**：任务外的求助、经验、风险和机会发现层；是否一级导航待 Q-01 确认。
4. **成员责任画像**：正式职责、本人声明、观察责任、证据、Coverage、公开协作窗口和纠正入口。
5. **CollaborationInsight**：贯穿创建、文件、决定、执行、交接和完成的统一洞察表达。
6. **统一 DemoRepository 与命令层**：所有页面读取同一 Task / Todo / File / Member / Activity 真相。

### 从主流程删除或隔离

1. 删除创建成功的彩纸、循环 RainbowButton 和无业务含义的 ambient 动画；普通建任务不是庆功事件。
2. 删除固定五步计时假进度；只有真实发生且值得解释的处理动作才展示。
3. 删除自动预选人员、预分责任和一次生成全部 Todo。
4. 删除向发起人展示的精确负载、任务数、完成速度、在线状态和行为推断。
5. 禁用详情中直接改 Owner 的入口；替换为“移交任务负责人”。
6. 删除固定 `coupon-fix` 覆盖式创建和页面私有 Todo / File 副本。
7. 暂时隔离未接入的旧原型组件；先确认能否成为共享模式，再决定迁移或删除文件，避免仓促清理用户已有成果。

## 七、视觉与动效基调

### 视觉方向

- 延续白色工作面、清晰排版和单一蓝色主行动。
- 重要页面像一份准备好的工作 Brief，不像泛化后台 Dashboard。
- 用“问题 → 证据 → 责任 / 权限 → 用户决定”形成 AgentDoor 特有的 Routing Thread。
- 事实、推断、冲突和未知使用标签、图标与颜色共同表达。
- 不把每个信息块都做成浮动圆角卡；用留白、分组和细边界建立层级。

### 动效只解释状态变化

| 场景 | 建议动效 | 不做什么 |
| --- | --- | --- |
| Proposal 渐进展开 | 高度与淡入 160–220ms | 不固定播放五步动画 |
| 用户打开协作建议 | 缺口卡平滑展开到比较区 180–240ms | 不让人员卡漂浮、发光 |
| 确认一个路由决定 | Routing Thread 新节点一次性出现 240ms | 不做循环流光 |
| 邀请改范围 | 旧 / 新 Revision 做字段级 diff | 不用模糊的成功庆祝遮盖变化 |
| 创建 Task | Proposal 连续转成列表行或详情标题 | 不撒彩纸、不跳回固定任务 |
| Handoff 生效 | 责任关系原地切换并保留历史来源 | 不模拟“在线的人开始运行” |

全部动效支持 `prefers-reduced-motion`；触屏目标至少 44px；树、比较表和 Dialog 必须有完整键盘路径。

## 八、实施切片

### Slice 0：统一真相与可恢复基线

- 建立经产品负责人批准的 Git 初始 baseline 或等效不可变快照。
- 在开始新的 Task / 导航 UI 前完成 `DS-V2-01`：把旧 Work Request、固定阶段、看板、自定义视图和固定导航迁入历史文档，避免实现误读旧规范。
- 定义 versioned DemoRepository、领域对象与命令接口。
- 迁移现有零售数据，让 TaskFolder、Task、Todo、TeamFileFolder、TaskFileFolder、File、Member、Activity 只有一个来源；保留现有任务目录，并与父子 Task、文件目录明确分开。
- 明确前端 Demo 不代表真实 ACL、事务和不可改写审计。

### Slice 1：默认自己负责的真实创建闭环

```text
需求 → 一句复述 / 最多一个问题 → 最小 Proposal
→ 用户选择“由我负责” → 创建真实新 Task ID
→ 新 Task 出现在递归任务树和列表
→ 打开保留结构的 TaskDetail
→ 子 Task / Todo / File 引用清楚分开
→ 刷新后仍一致
```

这条切片先不发送邀请、不改变 Owner、不发布团队动态。它同时解决“小任务被做重、任务没有真创建、层级与 Todo 混淆、File 多份真相”四个根问题。

### Slice 2：主动找人与邀请成立

- 缺口卡与“继续自己推进”。
- 0–4 人多维比较；不凑数、不预选。
- 选择协作方式与有界 scope。
- 接收者接受、改范围、推荐他人或私密拒绝。
- 新独立结果在接受后幂等创建子 Task。

### Slice 3：工作出去、结果回来

- Task 详情“协作”区。
- Handoff Revision、Consent、权限 / 版本预检和原子激活。
- Result Return 交付、验收、子 Task 完成和父 Task 整合分离。
- 候选责任证据只在结果验收后起草。

### Slice 4：团队文件与任务外发现

- 团队文件一级模块，与任务引用同一 File / FileVersion。
- help-request 动态、脱敏预览、作用域、响应和收敛。
- 响应不自动加人、不自动授权、不自动产生责任。

### Slice 5：责任画像、全平台洞察和多行业数据

- EvidenceCoverage、纠正、隐藏和争议。
- 跨 Task 的文件、决定、责任和单点风险洞察。
- 逐步补齐支付、营销、影视、零售和制造五类团队；复用同一模型和组件。

## 九、首个协作闭环验收场景

采用现有 POS 数据：周岚拥有根 Task，需要陈默完成“评审修复草案并补齐异常路径测试”这一独立结果。

1. 周岚输入需求，AI 最多追问一次。
2. 先生成周岚自己拥有的根 Task Proposal。
3. AI 解释技术评审缺口，但允许周岚继续自己推进。
4. 周岚主动比较陈默、高远、梁川。
5. 周岚选择陈默，只发一张绑定明确 scope 的子 Task Proposal。
6. 陈默反提“只负责代码评审与测试，不负责生产发布”。
7. 双方接受新 Revision 后才创建子 Task，Owner=陈默。
8. 子 Task 固定引用 patch 和事故记录版本。
9. 陈默交回修复结论、测试证据和一项业务风险。
10. 直接父 Task Owner 周岚验收或要求补充。
11. 验收后子 Task 完成，父 Task 的整合仍是独立动作。
12. AI 只起草“交易重试评审”候选责任证据；陈默可纠正。

## 十、选项与取舍

| 选项 | 用户价值 | 人性影响 | 架构 / 权限 | 成本与可逆性 |
| --- | --- | --- | --- | --- |
| A. 继续在现有页面逐项补 UI | 短期能看到更多按钮 | 仍会出现假责任、假忙闲和强制规划 | 多套 Mock 继续扩散 | 初看便宜，后续返工最高 |
| B. 一次实现全部领域与后端 | 理论上最完整 | 用户长期看不到可验证结果 | 权限、Handoff、审计都可一次建立 | 风险和周期过大，不适合当前 Demo |
| C. 先统一 Demo 真相，再按纵切闭环（建议） | 每一轮都能看到完整可用路径 | 渐进披露、可拒绝、责任边界可验证 | 接口与生产语义对齐，同时明确 Demo 边界 | 可逐步替换，回退和审查成本最低 |

## 十一、建议默认及理由

建议采用选项 C，并按下列产品默认收口：

1. Proposal 可以无 Owner；正式 Task 默认当前用户且恰好一位 Owner（Q-03）。
2. 只有正式人类 Member 可以成为首版 Task Owner；Agent 记录代谁操作，外部人员先成为受限 guest Member（Q-05）。
3. 候选比较只使用本人公开、可撤回且会过期的粗粒度协作窗口（Q-06）。
4. 观察责任满足证据门槛并显示 Coverage；成员可纠正 / 隐藏，具体证据仍按原权限（Q-07）。
5. 首版 AI 停在 L3；正式创建、邀请、广播、Owner 变化、发布和批准都由有权人确认（Q-08）。
6. TaskStatus 使用 active / waiting / review / completed / cancelled / archived；draft 属于 Proposal（Q-09）。
7. Handoff 作为 Task 下支撑实体，首版只支持具名一对一 recipient；accepted 与 activated 分离（Q-11、Q-13、Q-18）。
8. Task 详情使用统一“协作”入口；Result Return 首版只从子 Task 交给直接父 Task（Q-16、Q-19）。
9. 中高风险交接要求接收者复述；低风险上下文分享允许简化确认（Q-14）。
10. 采用防重复施压、第三方协调和协作数据不下钻的保护基线（Q-17）。
11. 团队动态建议作为一级模块，默认定向团队范围而非全公司（Q-01）。
12. Todo 可以无 assignee，但只有有 assignee 的 Todo 才进入个人待办（Q-02）。
13. task-scope File 发布到团队时保持同一 File ID；显式衍生才复制（Q-04）。
14. Owner 不可用时只允许有授权的 Steward 临时接任本人；返回使用反向 Handoff，不自动切回（Q-10、Q-15）。
15. 采用 Context、Todo、Responsibility、Result Return、Owner Transfer 五种 Handoff Profile（Q-12）。

## 十二、还需补齐的三个合同

当前 Q-01–Q-19 之外还存在三个实现前必须定稿的语义：

1. **协作 Offer 合同**：短咨询 / Reviewer / Approver 如何表达 revision、scope-proposed、declined、expired 与防重复发送。
2. **Responsibility 验收**：短责任由谁确认完成、需要什么证据、何时进入 `fulfilled`。
3. **help-request Activity payload**：结构化字段、响应、matched、linked 和 closed 如何由 Activity 派生，避免另造一个“广播项目”主对象。

建议把它们作为 Q-20–Q-22 候选，在 Slice 2 / Slice 4 的 implementation-ready Assessment 中定稿，不在首个自有创建纵切中临时手搓。
