# AgentDoor 产品定义（历史版本）

> 版本：0.1  
> 日期：2026-08-24  
> 用途：用于团队快速理解 AgentDoor 要解决的问题、产品方向与当前边界。

## 一句话定义

AgentDoor 是连接个人 AI 工作与企业团队协作的工作层：让员工继续使用自己熟悉的本地 Agent，同时把需要协作的任务、上下文、成果和决策安全地带入团队。

## 为什么做

今天的 AI Agent 大多运行在个人聊天窗口、终端或本地项目中。它们能够分析、写代码和生成内容，但工作过程通常只有使用者自己可见，团队难以知道：

- Agent 正在解决什么问题；
- 使用了哪些信息，结论是否可靠；
- 哪些结果需要同事参与、审查或批准；
- 本地成果如何安全地交给团队继续推进；
- 一次 Agent 工作如何沉淀为可复用的组织能力。

AgentDoor 要解决的不是“再造一个更聪明的 Agent”，而是让个人 Agent 的工作能够进入真实的企业协作流程。

## 产品要做什么

AgentDoor 负责连接三个对象：

1. **个人与本地 Agent**：员工可以继续使用 Codex、Claude Code、Cursor 等熟悉的工具，并保留本地执行和本地文件控制权。
2. **团队协作对象**：把需要共享的工作转化为任务、待办、文档、资料、阶段成果和明确的责任关系。
3. **企业治理要求**：控制哪些信息可以带入 Agent、哪些成果可以带回团队，以及谁可以查看、修改、批准和发布。

理想流程是：

```text
个人在本地 Agent 中发现问题
        ↓
选择必要上下文进入 AgentDoor
        ↓
形成团队任务并找到负责人和参与者
        ↓
人类与 Agent 分阶段协作、审查和交接
        ↓
成果经人类确认后进入团队知识和执行流程
```

## 核心产品方向

### 1. 从聊天转向工作对象

聊天只是入口。AgentDoor 的核心对象应是可持续推进的任务、待办、文档、资料和决策，而不是一段无法管理的对话记录。

### 2. 连接个人智能与团队协作

个人 Agent 负责高效执行，AgentDoor 负责组织协作。用户不必放弃本地工具，团队也不必依赖复制粘贴来了解进展。

### 3. 最小必要上下文

默认只向 Agent 提供完成当前工作所需的信息。添加资料不等于自动分享，能够访问某项内容也不等于可以把它传播给其他成员或外部系统。

### 4. 人类保持责任和决定权

Agent 可以分析、建议、生成草案和执行授权范围内的动作，但任务归属、关键审批、敏感权限和最终发布仍由明确的人类拥有者负责。

### 5. 可解释的协作路由

系统不仅推荐“找谁”，还应说明推荐依据：组织责任、专业能力、历史参与还是审批权限，并明确哪些判断只是推断。

### 6. 可追踪、可交接、可复用

团队需要知道工作由谁发起、Agent 做了什么、依据来自哪里、谁确认了结果，以及后续如何由其他人或 Agent 接手。

## 核心能力

- 连接本地 Agent，并选择性地传递任务上下文；
- 将个人发现转化为团队任务和待办；
- 基于责任、能力和权限建议参与者；
- 管理任务阶段、负责人、参与者、交付与验收；
- 共享团队文档、资料与 Agent 工作成果；
- 支持人类与 Agent、Agent 与 Agent 之间的工作交接；
- 展示来源、推断、运行状态和活动记录；
- 在同步、写入和高风险操作前保留人类确认。

## 本次竞品分析范围：人与 Agent 协作

本轮研究不以模型能力、Agent Builder 功能数量或代码生成效果为主，而是观察产品如何把 Agent 纳入真实团队工作。竞品分析应围绕以下问题展开：

1. **人如何把工作交给 Agent**：从聊天、任务、频道、文档还是业务对象发起；目标、Owner、截止时间和验收条件如何表达。
2. **Agent 如何理解工作上下文**：能够读取哪些文件、知识、历史消息和系统数据；上下文由谁选择；本地信息与云端信息如何划界。
3. **人如何观察和控制 Agent**：是否展示运行状态、活动记录、引用来源、推断过程、权限请求、失败原因和恢复入口。
4. **人如何审查、批准和接管**：哪些动作必须由人确认；人能否修改中间成果、退回任务、停止执行或重新分配责任。
5. **Agent 如何把成果交给下一个人或 Agent**：交接是否是正式产品对象；接收者能拿到哪些结论、证据、文件、假设、风险和未决问题；交接是否会自动启动下一位。
6. **多人如何共享 Agent 工作成果**：成果沉淀在聊天、任务、文档、知识库还是业务系统；谁可以查看、编辑、复制、发布和撤回。
7. **责任与权限如何持续传递**：Agent 身份、Role、Owner、成员权限、Connector 凭据和审计记录之间是什么关系；权限是否会随任务或交接自动扩大。
8. **协作如何形成闭环**：产品是否支持“委派—执行—观察—审查—交接—决策—沉淀”的完整链路，还是只覆盖其中一个环节。

每项结论需标记为：

- **已验证事实**：来自实际操作、官方文档或可复核证据；
- **产品推断**：基于界面和行为作出的合理判断，但尚未得到官方确认；
- **待验证问题**：目前证据不足，需要后续试用、访谈或官方确认。

本轮输出的目的不是选出“功能最多”的产品，而是回答：哪些协作机制值得 AgentDoor 借鉴，哪些边界必须由人类掌控，以及 AgentDoor 应优先验证哪条最小闭环。

## 当前阶段

当前优先验证的是一条最小协作闭环：

```text
本地 Agent 产出
→ 带入必要背景
→ 创建团队任务
→ 明确 Owner 和参与者
→ 分阶段推进
→ 人类确认成果
```

这一阶段重点验证协作价值和边界，不追求通用 Agent Builder、完全自治执行或复杂自动化平台。

## 暂不做什么

- 不替代 Codex、Claude Code 等底层 Agent；
- 不要求把完整本地项目上传到云端；
- 不默认让 Agent 获得用户的全部文件和企业数据；
- 不让 Agent 在缺少授权时代表人类做关键决定；
- 不把所有对话和中间过程都当作团队知识；
- 当前不以公共 Agent 模板市场或全自动企业流程为核心。

## 成功标准

AgentDoor 成功，不是因为 Agent 生成了更多内容，而是因为团队能够：

- 更快把个人发现转化为可执行的团队工作；
- 减少重复解释、复制粘贴和上下文丢失；
- 明确每项工作的责任、权限和审批边界；
- 安全地复用 Agent 产出，而不暴露不必要的本地数据；
- 让人类能够理解、审查并接管 Agent 的工作。

## 长期愿景

AgentDoor 希望成为企业中“人和 Agent 如何一起工作”的基础协作层：不同的个人 Agent 可以在本地保持各自能力，同时通过统一的任务、知识、权限和交接机制参与同一个团队目标。
