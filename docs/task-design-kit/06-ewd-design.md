**0．以 PMI／PMBOK 为方法依据：先管理结果与承诺，再计算指标**

PMP 是认证名称；本方案采用的是 PMI 的项目管理知识与方法，而非拼一套考试公式。2026-08-31 核对的 PMI 官方说明为 PMBOK 第八版，强调价值、适应性、责任及按情境裁剪，覆盖治理、范围、进度、财务、相关方、资源和风险。**这支持把方法落实为最少必要的管理动作，不要求每个小任务都部署整套企业流程。**核对范围为公开标准说明与公开技术文章，不宣称已经审阅付费标准全文。[PMI：PMBOK Guide](https://www.pmi.org/standards/pmbok)

对 AgentDoor，核心闭环建议为：

```text
为什么做、谁认可结果 → 范围与完成标准 → 合理拆分与责任承诺
        → 工时／资源／依赖／期限／预算计划 → 人确认适用基准
        → 收集交付与投入事实 → 比较原计划、当前范围和最新预测
        → 提出取舍并由人决定 → 更新版本 → 验收与复盘
```

以下是方法向产品的转译，不是声称 PMI 指定了这些页面、字段或优先级分档：

| 管理核心 | 在本项目如何落实 | 缺少时会造成什么错误 |
| --- | --- | --- |
| 价值与相关方 | 目标说明要改变的结果、不做的影响，以及谁有权认可；重要性有业务来源 | 按任务标题、发起人职位或已花成本判断重要性 |
| 范围与 WBS | 按可交付结果分解，子级覆盖父级范围；必要准备、整合、复核不能漏，也不额外发明工作 | 工时总数看似精确，实际遗漏关键交付或父子双算 |
| 责任与协作承诺 | 唯一结果 Owner 与执行投入分开；人选推荐经接受才是已落实安排 | 把团队总工时压给 Owner，或把被推荐人当作已承诺 |
| 进度与资源 | 依赖、工作窗口、剩余投入、里程碑共同决定可行性；有限资源冲突要显式处理 | 把18人时当18小时工期，或所有任务都单独承诺“来得及” |
| 估算与基准 | 估算记录依据、不确定性和工作方式；原基准、当前确认与完工预测分开 | 每次改估都覆盖原计划，无法解释偏差 |
| 质量与风险 | 结果证据、标准和验收资格支持完成判断；已发生问题与未来不确定风险分开 | “运行成功”即完成；把无更新直接判成风险事实 |
| 综合变更 | 先看范围、日期、资源和投入的连带影响，再由有权人确认具体版本 | 缩范围让完成率变好，却静默丢掉承诺和已发生成本 |
| 监控与收尾 | 按约定复核窗口、重要变更及交付节点更新预测；验收结果并积累可比经验 | 只报状态和静态分数，没有恢复计划或经验反馈 |

**WBS 不是把每个操作步骤都变成 Task。**PMI 公开资料区分交付物分解、实现交付所需活动以及活动的先后网络，并要求范围覆盖完整、避免重复。本产品据此保留“结果型 Task＋内部执行／估算依据”，不恢复已移除的 Todo 或逐项 Responsibility；轻任务可以不拆，长任务只有存在真实独立交付才拆。前置关系也不能从父子关系或列表顺序推导。[WBS 与范围覆盖](https://www.pmi.org/learning/library/developing-elaborating-work-breakdown-structures-7241)、[从 WBS 到进度网络](https://www.pmi.org/learning/library/moving-work-breakdown-structure-critical-path-6978)

**关键路径、紧急程度、个人优先级是三件事。**关键路径依赖完整的进度网络和工期估计；资源限制可能改变安排及完工日期。本产品先做有证据的依赖／窗口冲突检查，不能把依赖最多、EWD最大或个人时间余量最小的任务直接标成“关键路径”。没有完整网络时明确“不提供关键路径结论”。[PMI：进度与资源平衡](https://www.pmi.org/learning/library/scheduling-resource-leveling-project-progression-8006)

**基准用于比较，预测用于决策。**基准不是永远不许改；需要经明确变更保留原版与新版，不能用最新预测覆盖过去承诺。范围变化应同时评估成本和日期影响。对轻任务，一次有权人的确认与变更记录即可，不为套用方法引入审批委员会或额外工作流。[PMI：范围、进度、成本基准与综合变更](https://www.pmi.org/-/media/pmi/documents/public/pdf/pmbok-standards/pmbok-guide-6th-edition-5th-printing.pdf)

**按不确定性裁剪。**已知交付可较细估算，远期或探索工作保留范围与假设，临近执行再细化；一次完整计划不是保证。按反馈调整也必须保留范围沿革与人的选择。风险可说明情景和应对动作，但不默认给所有任务加20%缓冲或虚构发生概率。延期、返工已发生时作为问题事实记录，不继续包装成尚未发生的风险。

**人的管理职责不能被 AI 指标替代。**AI 可以提出拆分、预测和应对方案；目标取舍、接受责任、改变承诺、确认结果仍由有权人决定。分析可以在被请求或数据变化后重算，通知与外部沟通遵循另行授权，不因“项目管理需要跟进”就自动催人或持续运行。

**1．真实问题与当前基础**

当前任务个数无法表达投入差异：一项 2h 与一项 18h 的任务各完成一项，不能都解释成做完一半。单个百分比还会隐藏新增范围：交付没变、分母变大，进度下降可能是合理的。另一方面，“状态已完成”“Agent 已退出”“有一个文件”都不足以证明结果按约定完成。

| 用户与场景 | 要支持的判断 | 本方案提供的证据 |
| --- | --- | --- |
| 任务 Owner 规划复杂任务 | 拆分后的工作量是否合理、有无漏估 | 逐叶子估算、依据、覆盖和父级汇总 |
| 成员执行任务 | 估算是否仍适用、交付是否已确认 | 当前有效估算、修订原因、完成依据与标准版本 |
| Owner 跟进项目 | 交付有没有跟上新增范围，百分比为何变化 | 范围／已验收两条线与变更事件 |
| 本人安排工作 | 自己还有多少投入、截止前是否来得及 | 后续分人剩余人时与工作窗口；不直接使用总 EWD |

现有 [TaskNode](/Users/yxzuji/Documents/ChatGPT/agentdoor2/src/data/workspaceNodes.ts:15) 已按 D-153 增加可选的本地估算，保存分钟值、工作方式、依据、范围绑定、确认状态和递增版本；它不等于生产估算历史账本，也不包含验收事件。[Burn up 模型](/Users/yxzuji/Documents/ChatGPT/agentdoor2/src/lib/taskBurnUp.ts:88) 仍只投影传入快照，不能从当前估算倒造历史；[现有小图](/Users/yxzuji/Documents/ChatGPT/agentdoor2/src/components/TaskBurnUpSparkline.tsx:17) 已有双线、空态、示例标识与数据表。后续主要工作是补齐生产数据、规则和接入，不是重新选择图表库。

**2．EWD 定义的取舍：先统一量什么**

| 选项 | 解释 | 优点 | 限制与结论 |
| --- | --- | --- | --- |
| A：计划人类投入 | 按本任务约定的 AI／工具使用方式，预计需要多少人类投入 | 能连接实际协作、复核与人员投入；便于形成可验证估算 | D-153 已明确采用；工作方式改变要复核估算 |
| B：无 AI 人类等价量 | 假设不使用 AI，完成同一结果通常需要多少人工 | 可作为研究 AI 提效的对照假设 | 属于反事实，难核验；不能当容量需求，也不与 A 混算 |
| C：实际耗时 | 已经实际投入了多少时间 | 可以复盘成本 | 不适合作为规划权重，不能事后用“花得越久”增加完成信用 |

产品负责人已确认 A。准备材料、人工执行、审阅修订、必要沟通与验收投入均可计入；等待别人回复、排队和无人值守的模型运行时间不算人类工时。多人参加 1h 的必要工作会议，实际投入是各自的人时之和，不是只记会议自然时长；是否纳入本 Task 的范围需明确，不能在多项任务重复分摊。

示例：一份材料预计人工准备 0.5h、AI 辅助制作时人工操作 0.5h、人工复核 1h，则建议 EWD 为 2h。AI 后台运行 3h、等待负责人两天不会使 EWD 变为 5h 或两天，但会影响工期。示例数字仅说明口径，不作为产品默认工时。

若未来研究“不用 AI 要多久”，另保存对照假设、人员熟练度、质量标准与范围，不能把 `无 AI 估计 − 当前估计` 直接宣称为真实节省。各任务工具可不同，但同一统计的 EWD 定义必须一致；定义不同的历史不能混入同一条线。

**3．五个量分开存、分开解释**

| 量 | 含义与更新规则 | 前台名称 |
| --- | --- | --- |
| 初始基线 B₀ | 第一次明确确认且完整的范围、叶子及估算快照；之后不覆盖。未完整估算时，不把已知小计称为完整基线 | 初始确认范围 |
| 当前 EWD Eᵢ(t) | 叶子 i 在当前范围与工作方式下仍有效的确认估算；作为进度权重，变更必须显式确认 | 预计总投入 |
| 剩余 Rᵢ(t) | 从现在完成剩余结果还需投入多少人时，可后续分人；需要独立估计 | 预计剩余投入 |
| 实际 Aᵢ(t) | 有来源的已发生人工投入，缺记录为未知，修订留痕；MVP 不强制采集 | 已记录实际投入 |
| 完工预测 Fᵢ(t) | 范围、人员覆盖和记录完整可比时，可计算 Aᵢ(t)+Rᵢ(t)；只作预测或改估建议 | 预计完工总投入 |

`Eᵢ(t) ≠ Aᵢ(t)+Rᵢ(t)` 可以成立：前者是当前确认的规划权重，后者是基于最新实际和剩余的预测。系统不能每次收到执行报告就用 A+R 自动覆盖 EWD，也不能用 E−A 自动填 R。只有有权人确认新的估算版本后，当前权重才改变。

“未验收 EWD”也不是剩余人时：一项 18h 工作已提交、预计仅剩 1h 修改，它在验收前仍贡献 0h 已验收量，但排期应使用剩余 1h。单叶子只在验收时从 0 到该项全部权重，不生成“完成 73%”；若确实有独立结果可分步验收，可在业务规划中分为叶子，不为曲线平滑而拆任务。

建议存储整数分钟，API/展示可换算为小时，减少浮点累计误差；人工输入转换后需明确显示保存值，不静默取整。AI 用与证据相称的粒度给建议，不输出 3.728h 等伪精确值。0 表示明确确认不需人类投入，null 表示未知，二者不互换。

**4．怎么估算：AI 给有依据的建议，人确认范围**

估算输入最少包含任务目标、交付物与完成标准、已知资料、工作方式、必要人工步骤、明确限制；复杂任务还需完整子任务范围。可使用有权且可比的历史任务作为参考，但需保留来源，不能用成员在线时间、消息量或职位推测效率。

| 判断维度 | AI 要核对的内容 | 信息不足时 |
| --- | --- | --- |
| 交付边界 | 做到什么算完成，哪些明确不做 | 先补影响数量级的缺口，不默认“完整项目” |
| 数量与重复度 | 一份还是几十份、是否可复用模板 | 保留数量假设；不能无依据套乘数 |
| 人工步骤 | 准备、操作、必要复核、协调中哪些实际需要人 | 列短依据，不强制四阶段全有值，更不生成四个子任务 |
| 不确定性 | 新领域、资料不齐、外部依赖的返工风险 | 给范围/限制，或返回未知；不隐藏在任意风险系数中 |
| 工作方式 | 哪些由人、AI、自动工具承担；结果如何复核 | 工作方式不明且影响很大时先问，不推定全自动 |
| 可比证据 | 类似任务的范围、标准、投入记录是否相当 | 无数据说明“经验建议”；不编造历史平均值 |

建议返回一个中心估计、可选上下界、简短依据、假设与待确认项。上下界是情景范围，不声称统计置信区间；父任务把上下界相加只能叫情景边界，不能当作概率预测。缺少关键资料时 `ewdHours=null`，任务仍可保留或创建，只是不能提供完整工作量百分比。

创建流程仍遵循现有最多两项关键补问，把问题优先留给目标与交付范围；不能为了填工时新增一轮长问卷。Tips 中的步骤可作为估算依据，无需变成业务子任务。

交互分为“AI 建议 → 核对/修改 → 明确保存确认”。建议由具有该任务计划编辑权限的人确认估算，负责人有权复核与修订；最终权限矩阵须产品与服务端确认。**估算确认不等于负责人接受、不等于工期承诺，也不等于业务验收。** 不增加另一个 AI 审批对象。

已有有效估算 E=10h，AI 新建议 14h 尚未确认时，统计继续用 10h，并提示有未应用建议；若任务范围已正式变成不同交付，旧 10h 不再适用，则显示“待重新估算”，不能继续冒充完整统计。无关标题或标签修改不触发改估；范围、标准、工作方式实质改变时才复核，影响不明确则请人判断。

**5．完成与验收：不让工时偷换业务状态**

建议“已验收”来自有权人对当前结果的明确确认记录，至少绑定 Task、任务范围版本、完成标准版本、交付证据及其版本、确认人和时间。文字说明、可引用的业务记录也可作证据，不要求所有任务上传文件。

| 事实 | 是否计入当前已验收 EWD |
| --- | --- |
| Agent 报告完成、工具成功、文件已生成 | 否，只是执行/交付声明 |
| 成员提交结果、等待有权人确认 | 否；可以显示待核对结果，但不加新 TaskStatus |
| 新任务有完整事实链且明确尚未验收 | 确定贡献 0，不是数据缺失 |
| 有权人确认当前范围和标准，证据有效 | 是，计入当前有效 EWD |
| 老任务状态是“已完成”，但来源、标准版本或确认记录缺失 | 验收事实未知，不补造旧记录，也不自动记为通过 |
| 任务重开或验收被明确撤销 | 撤回当前贡献；历史记录不删除 |
| 新标准或范围实质生效，旧验收只覆盖旧版本 | 旧记录保留，对新结果不生效；重新确认后才计入 |

建议复用未来有权人的“确认任务完成”业务动作，在同一事务写业务状态和结果确认记录，而不是另造 EWD 验收页面。当前任意选择“已完成”的原型交互不能直接视作这个受控命令。谁能确认、是否允许负责人自行确认、需不需要指定验收人必须单独决策；默认建议唯一 Owner 确认，不额外引入必需的审批角色。

业务状态的反向变化也必须明确：有权人选择“重开”时，预览并确认退回现有的“进行中／待开始／已阻塞”等适用状态；撤销错误验收或修改已完成任务的实质范围时，默认建议在同一命令中明确退回“待审核”，目标状态需产品确认。不能只撤回 C 却继续声称当前范围已完成，也不能由 AI 或后台投影静默改状态。如果外部同步产生了“状态已完成、当前确认却无效”的冲突，显示“历史状态已完成；当前结果待核对”，使总体 P 不可计算并请求人工处理，不擅自决定业务状态。

父任务的整体结果确认还需绑定 `acceptedScopeRef`，包含当时的子树结构/范围版本及交付清单。新增、移出或实质改变子任务后，应核对父任务原确认是否覆盖当前整体范围；不得因旧父任务已完成而自动接受新子项。未发生范围变化的叶子估算与验收不因此作废。

标准只是错别字或等价表述调整时，可由有权人明确记录“原确认继续适用”，指向新旧版本和依据；AI 不能自己宣称等价。若没有这样的记录，按待核对处理。新文件版本的产生不自动推翻旧验收，旧记录仍指向当时证据；只有新版本取代已接受的交付范围、发现反证或有权人撤销时，再处理当前有效性，避免“最新文件”偷偷替换历史证据。

同范围的纯工时更正不自动撤销验收。验收记录保存当时的估算引用供追溯，但资格绑定结果范围，不以工时金额作为通过条件。已验收项原则上冻结估算；确属错误更正时，由有权人记录原因及修正，从此刻对范围 S 与已验收 C 同幅调整，明确“工时更正，本次无新增交付”。严禁为了抬高百分比改估。

**6．叶子聚合、未知与权限的完整公式**

给定一个任务根范围和时刻 t：

```text
L(t) = 服务端完整结构中，此范围当前纳入计量的叶子 Task 集合
Eᵢ(t) = 叶子 i 的当前有效确认 EWD
Vᵢ(t) = 当前有效验收资格：1（已验收）、0（明确未验收）、未知

S(t) = Σ Eᵢ(t)                         当前范围工作量
C(t) = Σ [Eᵢ(t) × Vᵢ(t)]              当前范围内有效验收工作量
P(t) = C(t) / S(t)                      工作量进度
```

只有数据条件成立才使用公式，而不是先把 null 变成 0 再运算：

- 完整 S 要求所有叶子的 EWD 已确认、仍适用于当前范围，且结构与统计口径有效。
- 完整 C 要求验收资格均可判定，且所有已验收叶子的 EWD 已知；明确未验收叶子即使缺估也确定贡献 0。验收未知不能冒充明确未验收。
- 总体 P 还要求完整汇总权限、数据已同步到同一版本且 S>0。任何必要条件不成立，`overallRatio=null` 并说明原因；不显示 0% 或 100%。
- 可展示“已估子集 S”和其已验收量，但必须标注子集范围；估算覆盖是已估项数／可统计全部项数，不能说成工时覆盖率。首屏不突出子集百分比，以免误读为总体。
- 工时百分比只展示适当小数，不靠逐项四舍五入累计；0≤C≤S。数据异常违反该不变量应报错，不裁切为 100%。

特殊边界：

| 情况 | 必须如何呈现 |
| --- | --- |
| 空范围或所有叶子确认 0h | 不计算百分比，显示“暂无可计量工时”；结果是否完成另看验收 |
| 正工时叶子全部验收，另有 0h 叶子待验收 | 工时可能是 100%，同时提示“仍有结果未验收”，绝不自动关闭父任务 |
| 新增未估叶子 | 总 S/P 未知；若新项明确未验收，原 C 可以保持已知；不拿已估小计作完整分母 |
| 当前补齐估算，过去有缺估 | 当前 P 可计算，历史缺口保留；不能用当前确认倒填过去 |
| 当前用户只看到部分子任务 | 服务端决定真实叶子身份；不把“看不到子任务”的父任务当作叶子，不返回总体 P |
| 无权获得完整范围统计 | 只返回允许的子集；不泄露隐藏 Task 标题、工时、数量或历史差值。连完整性信息也由权限策略控制 |
| 页面列表有筛选、分页或多标签 | 不改变任务详情根范围的整体进度；跨任务汇总按 ID 去重，不能累加相互重叠的父子汇总 |
| 旧投影尚未追上已提交事件 | 展示明确的“截至版本/时间，更新中”，不把旧数标为最新；撤权时不能继续显示旧缓存里的受限数据 |

完整汇总权限不从“可读父任务”自动推导。MVP 建议只有拥有完整范围数据权限时提供总体统计；若未来要“允许汇总、禁止明细”，必须单独设计聚合授权和防差分泄露规则。本方案不默认开放。

**7．范围与结构变化：每一次数字变化都能解释**

叶子由服务端真实结构判定，不能由当前筛选后的树、是否取消或是否可见来临时判定。有子任务的父级不单独计量；取消全部子任务不会自动复活父级原估算。删除最后一个子任务或把聚合任务改回叶子，需要明确新的计量范围与确认估算，不能自动切换。

| 事件 | 当前范围 S / 已验收 C | 保留与限制 |
| --- | --- | --- |
| 新增工作 | 新叶子有确认估算则 S 增加；未验收不增加 C，未估则总体 S 未知 | 新增是范围事件，不算过去已完成 |
| 确认改估 | 未验收项只改 S；同范围已验收项经错误更正则 S/C 同幅改 | 保留基线与旧版本；不能称新增交付 |
| 取消／移出范围 | 叶子排除自身S/C；非叶子须明确本次移出的后代叶子集合，不能只处理不计量的父级自身 | 已发生实际投入和历史验收保留；比例上涨注明范围减少；不静默取消子任务责任 |
| 重开 | 保留 S，撤回对应 C | 历史验收不删除，剩余投入需重新估计 |
| 新范围／标准生效 | 旧估算、验收对新结果的适用性重新核对 | 尚未对齐时总体未知；不自动维持旧 100% |
| 未开工叶子拆分 | 在一个结构版本中用新叶子替代旧叶子；父级旧估算不再相加 | 纯结构拆分总量守恒；总量变化必须另说明范围变化/改估 |
| 已执行或已验收叶子拆分 | 不按比例复制实际工时或已验收量 | 需有权人核对结果和投入的沿革；未对齐先停止完整汇总，不阻断继续保存任务草稿 |
| 合并任务 | 不重叠的未验收结果可核对后合并计量 | 已验收/未验收混合优先用父任务归组保留叶子；不得把部分完成整体变成已验收 |
| 重挂父任务 | 有权人核对目标、范围、标准和工作方式均未变时，原根减、新根加，工作区去重总量不变 | 当前代码按父链继承目标；若继承目标或有效范围改变，走范围变更并复核估算/验收，不能无条件沿用 |
| 修改标签／负责人／依赖 | 本身不改变 S/C | 若实际范围/方法也变更，应另提交对应事件，不能隐式改工时 |

取消非叶子任务时，命令应显示受影响范围并由有权人明确选择如何处理。默认建议把该分支后代从本根任务的当前范围移出，但不更改后代 TaskStatus 或已生效的人员责任；仍在承担的子任务应继续出现在个人承诺清单，提示上级取消后需核对继续执行/重挂，不能借项目范围减少掩盖个人负荷。若要把其中部分工作继续纳入项目，需同一批变更中明确重挂或保留范围，不留下不明归属。取消整个根范围时当前S为0、P不可计算，历史仍可查。恢复时核对当前版本及范围，只恢复仍有效的事实，不复活已被撤销的旧确认。

MVP 不做自动的已验收结果拆合映射。**纯候选/草稿不影响当前正式统计**，继续显示当前生效版本；只有结构已正式应用且计量映射尚未对齐时，新版本完整统计才进入 `reconciliation_required`。它是数据质量标记，不是新的 Task 审批状态。正常受控命令应先在预览中暴露对齐问题，允许保留草稿；外部同步带来的已生效不一致也要能降级展示。后续实现正式拆合时再明确映射协议，不通过百分比分摊验收。

父级协调工作如何计入：如果有独立交付（如整体验收与交接），可按任务规划原则形成真实叶子；若只是支持已有叶子的工作，则在对应叶子的估算依据中分配且只计一次。不能每个父级自动追加固定比例“管理费”，也不能为了记工时制造无独立交付的子任务。无法合理归属时标明未覆盖，先核对，不报完整估算。

**8．Burn up 的行为与手算示例**


**创建时：**工时是候选计划中的可选数据。简单任务在当前任务信息中按需展开“工时估算”；复杂任务对叶子估算，父任务只显示“汇总”及覆盖。允许明确批量确认一组已审阅估算，但按钮与确认摘要须表明包含哪些工时；不能仅因点击“生成计划”就确认，更不能因未估阻止保存任务。沿用局部修改的差异预览，不恢复旧聊天或默认空表入口。

**执行中：**从“查看数据”或当前任务菜单编辑本任务估算；改估显示前后值、原因，以及对当前范围/进度的影响预览。同范围候选未应用前，原数字不跳动。父任务不能直接输入一个覆盖叶子汇总的总数；用户提出“总共控制在20h”应视为约束与冲突提示，不让 AI 按比例压缩子任务以凑数。

**查看子任务：**沿用既有子任务列表；每项菜单可查看/修改本项工时，批量核对时按需展开紧凑表格（名称、估算、确认状态、依据），不是第二套独立任务清单。D-148 左侧任务索引继续只显示名称，不新增工时列、彩色风险标签或进度卡。

**确认结果：**业务动作位置与权限在第5节另行确认；工时面板只定位结果及标准，不提供“把进度拖到100%”。人的讨论保持干净，估算/范围/验收的真实变化进入活动；AI 尚未采用的建议不写成已经变更。

| 状态 | 内容与恢复方式 |
| --- | --- |
| 未估 | “尚未估算”，允许打开估算或请求 AI 建议；不默认1h |
| AI 建议待确认 | 显示建议、范围、依据和未确认标识；不写正式汇总 |
| 数据完整 | 显示范围/已验收与可核对百分比，来源和更新时点可展开 |
| 部分缺估/待核对验收 | 显示已知量和具体缺口；能定位有权查看的待处理项 |
| 仅部分范围有权访问 | “无法提供完整范围统计”；只显示允许的可见内容，不显示隐藏数量 |
| 加载 | 保留合法旧值并标截至时间或显示加载；不闪成0% |
| 请求失败 | 保留输入与原有效值，提示重试；不显示已保存 |
| 同字段版本冲突 | 展示新版本及原输入，要求重新核对；不默默覆盖 |
| 数据过期 | 明示截至时间与待同步；不推断成员没工作 |
| 示例/迁移旧任务 | 明示示例或历史不足；不伪造基线与验收 |
| 窄屏/键盘 | 小图随详情容器换行；表格可横向访问；弹层内部滚动，主动作可达；Esc退出不写入、焦点回到入口 |

首屏每个新增元素的必要性：两个工时值回答规模与交付，趋势回答二者变化，缺口标识防止误读；估算依据、历史和版本都按需展开。不增加没有独立动作价值的“AI健康分”或总览区。

**10．最小数据与服务契约（建议，不是现有 API）**

不先建设通用事件溯源平台。建议采用正常的版本化 Task 存储、不可变估算/结果确认/范围变更记录，以及可重建的进度投影。领域记录才是事实源；活动流用于阅读，不能依靠中文日志反推工时。

**11．个人维度：重要性、紧急程度与优先级**

本节直接承接 M-PERSON、U-JOINT；F-SCHEDULE 是老板文件中的未来建议。以下规则是把资源约束与目标管理转译为 AgentDoor 的候选方案，**不是 PMP 规定的排序公式**。本轮完成联合设计，G10/G11 跟踪数据接入和验证，D-148 的 Dashboard 状态不变。

**11.1 三个判断分开保存**

| 判断 | 回答的问题 | 建议输出与依据 | 不可替代它的信号 |
| --- | --- | --- | --- |
| 重要性 | 不做或做错，会损失什么结果？ | 关键／常规／明确可延后／未知；附目标关系、不做的后果、承诺来源 | 工时或金额大、发起人职位高、标题写“紧急” |
| 紧急程度 | 最迟何时必须采取动作，才能守住约定？ | 已逾期／已知排期冲突／需占用下一必要窗口／尚有余量／信息不足；保留已知事实 | 距截止天数、总EWD、多久没更新 |
| 优先级 | 在这些约束下，本人现在先做哪个动作？ | 可解释的建议次序、动作与理由；允许并列、冲突待决定和人工顺序 | 重要×紧急、一个永久总分、低工时优先 |

重要性由有权业务人员确认影响依据，AI 可建议但不能仅从继承目标自动把全部子任务定为“关键”。没有明确目标影响时为未知。没有截止不自动等于“不紧急”，仍可能存在阻塞他人的必要动作；缺少该证据时就不判断。已经确定逾期但剩余工时未知时，应显示“已逾期；尚不能评估恢复时间”，不能用一个未知标签抹掉逾期事实。

**11.2 分清排序范围与容量范围**

- **排序范围：**本人正式负责且有权访问的全部有效 Task，在个人工作空间层分析；分页、标签和临时搜索不能截断完整判断。父任务的协调／决定责任可保留，不能把其他人的执行子任务工时全算给父 Owner。
- **容量范围：**除上述任务，还包括本人在他人负责任务中已接受的具体执行投入，以及非任务固定占用。只被列为参与人不代表承诺了投入；待接受提议不计给候选人，未落实的任务剩余投入也不能消失。本人自己的占用信息与任务内容按各自权限读取，不泄露无权 Task 的名称或细节。
- **分析输出：**“任务＋本次具体动作”是对现有 Task 的建议，不新增第二种 Todo 实体。一个协调动作和其目标 Task 的剩余投入须去重，不能又作为额外工作再算一遍。

12h 叶子由甲2h、乙10h完成，总量是12h；甲为Owner不意味着甲执行12h。总剩余R已知、分人不明时，任务成本预测可以有依据，但个人负荷仍未知。

**11.3 先核对工时与窗口，才能谈急不急**

个人排期使用独立确认的 `Rᵢ,u(t)`：本人从现在完成第i项承诺还需的人时。不得使用总EWD、未验收EWD或E−A自动填充。日期要带时区、硬承诺／期望日期和来源；日期型截止的具体时点须采用已确认规则，不能擅自按午夜或8小时工作日换算。

对每个有效截止d，检查累计窗口 `W=[当前t,d]`：

```text
Hᵤ(W) = 本人工作窗口 − 不属于所分析Task投入的固定占用
Dᵤ(W) = 截至d必须完成的所有有效承诺剩余人时
       ＋其他任务明确安排到W的投入（按同一投入去重）
窗口缺口 = max(0, Dᵤ(W) − Hᵤ(W))    [仅完整、可比时]
负荷比率 = Dᵤ(W) / Hᵤ(W)           [仅H>0且数据完整时]
```

不能遗漏已逾期、未排入日历但已承诺的工作。Task 预约时段视为该投入的安排约束，**不能既从H扣掉，又在D加一遍**；无法区分日历占用来源时标记待核对。H=0且D>0是容量冲突，二者均0是不适用。缺数据不报精确总量／比率；若已知需求下界已经超过可信容量上界，可以报告“至少冲突”，不冒充完整缺口。

`D≤H`只是未发现总量超载，**不是证明排期可行**。还需验证前置最早可用时间、不可拆分的连续工作块、固定时段及安排无重叠。若资料14:00才到，不能把09:00的空档算作依赖该资料的可执行窗口。依赖或日历不全时只列已知约束，不造最迟开始时间，不标“准时概率95%”。个人可用工时余量也不是 CPM 的总浮动时间。

仅在输入齐备且已构造一个满足这些限制的安排时，才称“按当前假设可行”。候选排程算法找不到安排只表示该候选不可行；除非已有需求超过容量等确定证据或穷尽适用搜索，不断言所有安排都无解。未来某一天这种不从现在起算的窗口，使用到窗口起点的剩余预测或已分段安排，不能把今天全部剩余塞进去。

**11.4 最小行动规则，不强行合成分数**

1. **先显示已知承诺问题。**已逾期、已知资源／依赖冲突，以及错过下一必要窗口就会违反硬承诺的事项，列“需要处理”；动作可能是协商范围、日期或分工，不等于盲目优先执行原任务。
2. **区分可执行与需解除阻塞。**等待前置的结果不能直接开工；可提出核对交付时间、处理自己能解除的阻塞、或先做不依赖该产出的部分。仅沉默或离线不算阻塞证据。
3. **再比较可执行事项。**先保护已确认硬约束，在剩余选择中参考有证据的重要性、最近必要窗口与本人计划；同档且依据不足时并列或保留人工次序，不默认“小任务先做”。软目标未满足称计划风险，不升级成违约事实。
4. **有冲突就暴露取舍。**两项重要承诺无法同时满足时，给出改变范围／期限／资源的候选和影响；不以模型排序代替相关方决定，也不因“已花很多”坚持继续投入。
5. **人工顺序与客观事实分开。**保留用户调整及理由，重算不静默覆盖；置顶不会消除期限冲突。期限、范围、R、依赖或日历改变时标记建议过期并重算依据，事实更新与人工选择分别保留。

“需占用下一必要窗口”要由可核查时段或明确约定的下次决策窗口支持；没有这些数据时只写截止与已知约束，不默认24小时／三天阈值。关键且无硬截止的工作可以进入本人的计划窗口，避免永远被小型急事挤走；预留多少时间由人选择，不设通用百分比。

**11.5 最小输出和验证**

建议输出：`Task → 现在的具体动作 → 为什么此时做 → 影响／截止／窗口证据 → 缺失与更新时间`。例：“核对发布审核时间；今日17:00前需完成，本人剩余2h，前置材料预计16:00才到；当前安排存在至少1h缺口，先确认能否提前交付。”这是一条有依据的管理建议，不自动发消息或改日期。

呈现优先考虑在现有工作区上下文按需查看一份分析列表；具体入口另行确认，不给名称索引加评分，不恢复首页或四象限工作台。相关方看不到完整任务或日历时只展示允许的结论与覆盖，不能通过隐藏任务数量或总量差值推断内容。

验收除了“顺序是否合理”，还要问：用户是否能据此采取动作；证据是否可追溯；已知冲突是否漏报；未知是否被错当低优先级；人工选择是否保留。具体边界案例见第16节，不使用未经确认的综合质量分。

**15．任务维度：投入成本分析，以及与 EWD／挣值管理的关系**

**15.1 “成本”和 EWD 相近在哪里，不同在哪里**

用户本轮明确要求任务下的成本分析（U-JOINT）。建议首版先回答“这项结果预计需要多少人力、已投入多少、还要多少”，与 EWD 共用人时事实；以后确有决策用途且数据具备时，扩展人工参考折算、AI／工具费用和其他直接费用。**人时投入、金额费用、自然工期各自有单位，不能放进一个总数。**

| 量 | 在成本分析中的用途 | 与 EWD 的区别 |
| --- | --- | --- |
| 当前确认预计 E | 当前工作范围的规划人时，复用当前范围叶子 EWD | 可作为人力预计投入，但不是已支付金额 |
| 已记录实际 A | 已发生且有来源的人工投入 | 即使成果未验收、被取消或需要返工，投入仍发生过 |
| 预计剩余 R | 从现在完成现有承诺及仍需承担的收尾工作的人时 | 必须独立估计，不能用E−A或未验收EWD代替 |
| 预计完工 F | A完整且R完整、归属可比时，F=A+R | 最新预测，不自动覆盖E或原基准 |
| 工作量进度 P | 当前有效验收EWD／当前范围EWD | 不使用A/E、A/F或花费／预算表示完成度 |
| 工期及等待 | 日期、依赖、工作窗口形成的完工约束 | 多人并行、等待和机器运行使它不等于人时 |

EWD 解决“用什么工作量权重表达交付”；成本分析解决“为结果消耗和还需投入多少资源”。PMI 的 EVM 标准也把范围、进度、资源、实际表现与预测联在一起，但本产品并不因此已经具备完整挣值管理能力。[PMI：The Standard for Earned Value Management](https://www.pmi.org/standards/earned-value-management)

**15.2 两种范围必须分开：当前工作与历史投入**

E／P使用当前范围的有效叶子集合；A使用**有发生时归属的投入记录集合**。当前树改变，不得删除已发生记录。单个Task全生命周期、某父项目按发生时归属累计、当前范围内叶子投入，是三个可不同的查询；每个结果必须注明范围，不能默认互换。

建议任务成本默认显示“本任务／本项目累计投入”，并保留取消、移出及返工的归属：

```text
A_life = 归属于本任务周期的实际投入记录及更正，去重求和
R_life = 当前工作与未解除收尾工作的未来剩余投入，按投入/承诺记录去重求并集
F_life = A_life + R_life               [覆盖完整才可计算]
```

第3节同范围的F=A+R仍有效。本节下标用于提醒范围差异，不是另造工时单位。R_life使用剩余投入，不使用当前EWD总量；同一交接还需1h，若同时在当前Task的R与收尾清单出现，仍只计1h。若要比较 `F_life` 与当前E，必须单列已经退出范围但仍被本周期承担的投入；两者范围不同就不直接称“当前范围超支”。保留初始B₀及当前已确认版本，各自比较时明确新增、移出、改估和工作方式变化。

| 事件 | 成本必须保留的事实 | 与EWD完成的不同 |
| --- | --- | --- |
| 取消／移出 | 已发生投入保留；剩余是否归零取决于是否明确解除执行与收尾承诺 | EWD当前S/C可减少，已发生成本不能跟着消失 |
| 返工／重开 | 新投入追加；剩余重新估；说明原因但不推断人的能力 | 验收贡献可撤回，过去投入不清零 |
| 拆分／合并 | 原记录保持唯一来源，沿革明确后重新分配；未对齐标缺口 | 不按新子任务个数复制原成本 |
| 重挂父级 | 默认保留发生时项目归属；未来投入按明确新安排归属 | 当前EWD可转移，历史成本不随父链静默搬家 |
| 更正归属／投入 | 追加带原因的更正与前后分配，保证全局不重复 | 不通过删除旧记录美化偏差 |
| 多人／协调工作 | 多人各记真实人时；同一人同段投入只分配一次 | Owner不是所有投入的执行者；不按父级额外加“管理费” |

每条投入至少有来源ID、执行人、量、发生时间、发生时归属、分配版本和更正引用。分给多个Task的份额总和不得超过100%，未分配部分独列；父级读取去重记录，不把子级汇总再加一遍。只有支持已有叶子的协调活动可分摊一次；有独立整合交付才形成真实叶子，不为计成本强拆。

**15.3 偏差要解释原因，不只给红色百分比**

在同工作范围、工作方式及记录覆盖可比时，`F−E`可称“预测与当前确认预计的差异”，`F−B₀`可称“预测与初始基准的差异”。如果只是E被改大、R改变或范围新增，分别说明，不能统称效率下降。金额“超预算”还需有被确认的金额预算，不能把人时差直接叫超支。

原因只能依据范围事件、返工记录、等待事实和估算修订。可以给多个已证实因素及未解释部分，不能让AI将同一差额重复归到两个原因，或用没有依据的百分比分摊。估算误差需在稳定范围和完整实际样本下复盘；未经验证的情景上界不能叫95%置信区间。

成本结论须导向可选择的管理动作，例如“补齐交付边界再改估”“提前取得依赖资料”“将非必要结果移出本次交付”“保留范围但协商日期或资源”。已经花了多少用于复盘，继续投入主要看未来结果与尚需资源，不能以沉没投入提高个人优先级。增加人员也不默认等比例缩短工期，要考虑可并行性、交接和复核。

**15.4 金额是可选层，不等于强制采集工资**

第一版人时分析不要求费率。若后续启用金额，分开列：

```text
人工参考折算 = Σ(有来源的人时 × 经授权的参考费率快照)
已记录直接费用 = Σ(唯一费用来源 × 经确认的Task分配份额)
预计后续费用 = 尚未计入已记录费用、但预计还会发生的同口径费用
金额完工预测 = 已发生同口径金额 + 预计后续费用  [完整、同币种时]
```

参考费率可以是组织明确采用的计划费率，不默取个人工资或市场单价。参考折算不是实际付款，直接费用的“已发生”也不必等于已经付款；来源应标记录口径。可以在明确声明组成、不重叠且获授权时形成“按该假设计算的资源投入值”，不能称现金支出或会计成本。本方案不设计报销、税务、支付或财务记账制度。

需要保留来源、币种、费用期间、分配版本、已发生／尚未发生、费率版本、是否含额度。订阅包含的用量不再按假设单价计一次；外包固定价已含的人工不再加为同一笔直接费用。退款或纠错追加可追溯调整，不删除原费用。已确认的后续费用义务不会因Task取消而自动消失。不同币种先分列，不猜汇率；缺费率／缺费用项／未确定包含范围时只报已知部分，不报“全部成本”。

可读Task不等于可读费率、费用明细或成本总额。只返回被授权数据，不通过“总额−可见费用”“个人工时＋总折算额”泄露受限费率；撤权使缓存与旧分析失效。金额权限不足不妨碍用户查看其有权的人时事实，但不能回传隐藏金额后仅靠前端遮挡。

**15.5 为什么不能把当前 EWD 直接叫 EVM 挣值**

挣值管理比较的是**同一受控基准**下计划应完成、实际完成的预算价值和实际投入。PV/EV/AC可以采用一致的成本单位；使用人时也需要完整、可比的基准与记录，而不只是有一个EWD总数。[PMI：The earned schedule](https://www.pmi.org/learning/library/evm-cpm-evaluate-project-performance-6355)

| EVM量 | 含义 | 当前方案缺什么／不能拿什么替代 |
| --- | --- | --- |
| BAC | 该绩效基准的完工总预算 | 当前EWD是可修订的工作量估算，不自动是金额预算或绩效基准 |
| PV(t) | 截至t按分时基准计划应完成工作的预算价值 | 当前S是全部范围，不是截至今天应完成量；Burn up无PV计划线 |
| EV(t) | 截至t实际完成工作按基准计得的价值 | 当前C可随确认改估变化；不能拿最新EWD重估过去挣值 |
| AC(t) | 截至t同口径工作的已发生成本 | 不等于模型估算、工具在线时间或只记录了部分的实际工时 |
| ETC / EAC | 预计剩余成本／预计完工总成本 | 需明确预测假设和范围，不能靠改变基准让预测看起来达标 |

需要时可采用 `CPI=EV/AC`、`SPI=EV/PV`，以及 `CV=EV−AC`、`SV=EV−PV`；分母为0或记录不全则不算。SPI与SV描述基准价值维度的进度表现，不能直接翻译为“还差几天”或“晚了20%的工期”，日期仍看实际进度网络与资源。[PMI：EVM计算与管理动作](https://www.pmi.org/learning/library/evm-data-analysis-executive-action-8520)

若将来实施，需另外保存绩效基准版本b、逐工作包预算权重及分时计划、客观完成计量规则、同口径实际成本。可写成 `PV=Σbᵢ×计划计得比例ᵢ(t)`、`EV=Σbᵢ×实际计得比例ᵢ(t)`；两者使用同一批准版本，不能自动用当前EWD替换b。0/100、里程碑等属于需选择的计量方法，不声称所有项目都只能按二元验收。原基准和获确认变更后的基准均保留，不能事后重写计划消除偏差。

**本产品首版不展示CPI/SPI，不开发完整EVM模块。**先把原基准、当前范围、真实投入和剩余预测做好；当前按验收计EWD的Burn up继续回答交付与范围变化，不加入实际工时／金额第三条线。只有出现明确的绩效基准管理需求、数据齐备并另行确认后，才启用相应指标。这是方法裁剪，不是忽略项目管理。

**15.6 与个人分析共享数据，但不互相替代**

任务有E/A/R不代表个人一定能排期：还要把R落实到人员、窗口和前置可用时间。个人已经安排了2h也不代表任务只需2h；未分配投入仍在任务总R内。任务成本的结论在该Task下按需查看，个人顺序在工作空间层比较本人任务，不在每个子任务放全局四象限。

建议任务内最小内容为一张紧凑表，而非四张统计卡：

```text
投入分析（人时）                 截至版本／时间、覆盖状态
当前范围预计   12h     来自已确认EWD
本周期已记录   12h     包含哪些范围、是否完整
预计剩余        1h     来源、尚未落实的投入
预计完工       13h     同口径完整时才显示
已验收工作量 10/12h    与投入量分开解释
差异：交付原估10h、实际11h；整合仍需1h → 核对安排 → 查看来源
```

复用第9节“查看数据”／任务菜单作为候选入口；金额默认不出现，当前名称索引不增列、头卡不扩成工作台。如将来独立诊断Tab获确认，成本结论作为任务诊断内容复用，不再做第二份同类面板。入口是设计建议，不随本次文档自动上线。

**16.2 一组案例同时检验三种判断**

以下全部为合成假设；除明确说明缺失、受限或待确认的情形外，假设对应范围、估算确认、记录覆盖和权限齐备。数值输入另存 [联合分析案例](/Users/yxzuji/Documents/ChatGPT/agentdoor2/docs/task-design-kit/06-joint-analysis-examples.json)。这些是未来验收预期，不是已运行的真实产品场景。
