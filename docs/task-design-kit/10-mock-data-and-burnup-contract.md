# 多团队 Mock 数据与燃起图契约

本文约束 TaskDoor 原型中的本地合成数据。数据用于验证产品交互与规则，不代表真实团队、真实成员、线上任务状态或 AI 已接入生产服务。

## 1. 数据边界

- 每条成员、任务、讨论、文件与进度事件都必须属于一个明确团队；团队切换只切换本地演示数据域，不模拟真实权限变更。
- 人名、邮箱、项目、客户、批次号和业务数字均为合成信息；不得混入生产凭据、真实客户资料或未脱敏文件。
- 固定历史必须标记为 `example`。界面可以据此演示判断，但不能把它表述为实时 AI 结论、真实验收或浏览器当前状态。
- 固定工时必须使用 `mock` 依据并在界面标记为“演示估算”。TaskStatus 不决定是否可估；只要叶子定义、工作方式和估算记录有效，“待开始”等状态也可显示工时，但不得把演示值表述为模型估算或实际工时。
- 用户在原型中新增或修改的数据与固定 fixture 分开对待。版本迁移只补入缺失的 fixture，不反复覆盖用户后续编辑或删除。

## 2. 当前规模与 v7→v15 沿革

当前 `multi-team-v15-mock-effort-coverage` 固定快照共有 **215 条任务**、**159 个叶子任务**。数量只统计 `kind: "task"` 的合成 fixture，不含工作区／项目目录，也不含用户随后在浏览器中创建的任务。v9 的 211 条任务规模作为扩容历史保留；v11 是可能已经写入版本标记、但复盘 fixture 尚未完整落盘的早期过渡快照，v12/v13 已包含复盘结构但部分早期 Mock 估算仍使用旧 `scopeKey`，v14 的 214 条任务完成复盘补齐，v15 再完成全叶子 Mock EWD 覆盖。

| 团队 | v8 既有任务 | v9 扩容新增 | v14 复盘补齐 | v15 覆盖调整 | 当前合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 达人带货运营团队（内容电商） | 14 | 41 | 3 | 1 | 59 |
| 协作平台团队（企业 SaaS） | 12 | 38 | 0 | 0 | 50 |
| 智能硬件试产团队（制造与供应链） | 13 | 38 | 0 | 0 | 51 |
| 企业客户成功团队（B2B 客户运营） | 12 | 43 | 0 | 0 | 55 |
| **合计** | **51** | **160** | **3** | **1** | **215** |

扩容校验以“**每团队至少 40 条任务**”为硬门槛，并同时要求每个团队具备多个项目树、至少三级任务层级、至少四项不属于项目树的周期／独立工作，以及至少五种任务状态。任务标题不能使用编号占位凑数，也不能跨团队借用成员、父任务或依赖。

v8 → v9 迁移按稳定 ID 合并 160 条扩容任务：只追加存储中尚不存在的扩容节点，不覆盖同 ID 的已有记录。v9 → v10 只对仍与历史 fixture 精确一致的状态标签、计划日期和旧默认依赖做语义更正，不改变任务数量，也不覆盖用户改写。

v7–v13 → v14 是历史组合迁移，不把所有旧版本直接重置为当时 fixture：v7 先补新团队，再补 v9 扩容并执行依赖／状态语义更正；v8 先补 v9 扩容并执行语义更正；v9 先执行语义更正；三条路径随后统一执行复盘补齐。v10、v11 则直接执行复盘补齐。复盘补齐只处理 `weekly-retro-notes` 这一组 fixture：为根任务补齐原本缺失的完成标准、执行建议和计划周期，并按稳定 ID 追加尚不存在的 `weekly-retro-decisions`、`weekly-retro-open-issues`、`weekly-retro-actions` 三个叶子。v12、v13 也进入该迁移，但对已有叶子估算只在除 `scopeKey` 外的 `basis`、确认状态、工时、依据、版本和工作方式仍与 fixture 完全一致时修正旧 `scopeKey`；只要用户改过工时或任一估算字段，整条估算连同原 `scopeKey` 一并保留。

v14→v15 使用 map-only 安全迁移，只遍历存储中仍存在的节点，不追加缺失 ID。对当前 fixture 已有 Mock 估算，只有当存储值的 `scopeKey` 恰好等于按叶子自身目标生成的旧范围键、其余估算字段完全未编辑，且按继承后的父级有效目标与当前叶子定义能匹配 fixture 时，才替换为当前范围键。内容电商 11 个目标叶子只在完成标准／执行建议字段缺失时补 fixture 定义；只有原始记录没有显式 `effortEstimate` 字段且补齐后的有效范围仍匹配时才加入演示估算。`completionCriteria: []`、`executionTips: []`、显式估算清空、用户改过的估算或定义、用户任务及已删除节点全部保留，迁移不重置、不追加、不复活。标签不因本次覆盖迁移重置，版本标记仍在节点和标签写入完成后提交。

## 3. 团队与任务完整性

每个团队数据集至少包含：

- 一名对目标负责的人、若干唯一负责人和最小参与人集合；成员职责、可投入时间和当前工作相互一致。
- 一个复杂主任务、两层以上子任务、一个独立任务，以及进行中、待审核、阻塞、完成等不同状态。
- 跨分支前置依赖、明确的完成标准、执行建议、计划区间与叶子任务 EWD；父任务不再重复计入 EWD。
- 至少一项证据缺失、范围变化、重开或外部等待，用于验证“未知”与“阻塞”不会被误写成零或已完成。

结构校验必须拒绝或报告：重复 ID、悬空父任务、跨团队父子关系、跨团队依赖、父子循环、依赖循环、负责人不在团队、任务标签无定义，以及叶子估算格式无效。

### 3.1 全叶子 EWD 覆盖

- 当前 159 个叶子均有有效的 `mock` 估算；“待开始”“进行中”“待审核”“已阻塞”“已完成”“已取消”等 TaskStatus 只描述任务状态，不参与可估性判断，也不由 EWD 反写。
- 子任务的有效范围继承最上层任务目标，并与该叶子的完成标准、执行建议和工作方式共同生成 `scopeKey`。叶子自身用于说明局部交付的 `goal` 不替代父级有效目标。
- 父任务和中间任务只汇总当前范围内叶子 EWD，不将自身值与子项再次相加。若父级整合确有独立人工投入，应建成有清楚交付边界的叶子再估算。
- 内容电商本轮补齐 11 个叶子的业务完成标准、执行方法与演示估算：香氛礼盒达人带货收尾的 8 个叶子合计 **43h**，新品发布会筹备的 3 个叶子合计 **26h**。这些数字只用于本地演示，界面统一标“演示估算”。
- EWD 覆盖不产生历史事件。叶子本身不画燃起图；父任务即使叶子工时完整，只要没有显式事件账本也只展示当前汇总，不补造曲线或完成百分比。

## 4. 文件与动态

- 文件只存在于任务上下文。目录、文件 ID 和父目录必须唯一且无环；文件活动引用必须能解析到同一任务的文件。
- 文件版本从正整数递增，并保留更新时间、更新人、生命周期（草稿、评审、批准、替代或签署）与访问边界。历史版本不得被当前正文静默覆盖。
- 人类讨论与系统变更分开建模。回复必须指向存在的根讨论；状态、排期、责任人和范围变化使用结构化 before/after，而不是伪装成人类发言。
- AI 洞察只能指出可见证据、缺口和下一步核对动作，不能替 Task Owner 验收，也不能把缺失文件推断为已交付。
- 时间型历史使用带时区的 ISO 时间；相对时间仅用于显示文案，不作为排序依据。

固定任务详情分为三层，避免为了数量复制同一份项目证据：

1. 内容电商原有 9 个代表任务继续使用各自的专用固定详情。
2. 平台发布、智能硬件试产和企业同步故障三棵核心协作树共有 **31 个高密度固定详情**。每个详情固定包含 5 个目录、9 个文件、11 条活动和 4 次提交；总计 155 个目录、279 个文件、341 条活动和 124 次提交。文件含正文、表格／多工作表、PDF 分页、版本谱系、访问级别、脱敏状态、复核人和关联活动；动态含五条人类讨论及五条结构化字段变化。三棵树之外的任务不能借用这些项目证据。
3. 其余 **175 个固定 fixture 任务**在界面打开时使用 `createWorkspaceTaskDetail(task)` 确定性回退：根据稳定任务 ID、标题、负责人、参与人、状态、日期和现有标准生成任务专属 ID 与内容。当前回退契约提供 4 个目录、4 个文件、5 条活动和 1 次提交，不进行随机抽样，也不从其他任务复制业务结论。覆盖测试还会直接对全部 184 个非高密度任务运行该生成器，确保这一机制不依赖 9 个内容电商专用详情。

确定性回退只是为了让固定合成数据可完整浏览，生成的文件和动态仍是演示证据，不能表述为真实历史。用户通过任务创建器或编辑器新建的任务不会获得这段合成执行历史；没有真实进展时保持空文件、空动态和“尚未收到执行进展”。

## 5. 燃起图事件账本

每条固定 Mock 进度序列必须在任务创建时保存初始总工作量，创建基线与后续进度观察分开：创建基线只说明当时确认的范围公式，不制造已完成量。叶子任务使用自身创建时估算；父任务和中间任务按创建时有效叶子去重汇总，不累计中间层。若创建日至下一次观察之间总工作量没有变化，灰色总工作量线应从创建日水平延续；后续新增、缩减或改估只从对应事件日期起改变曲线，不能把当前总量回填为历史。

燃起图只从不可变事件账本投影，不从任务当前状态、当前 EWD 或扩容任务数量倒推历史。当前为 `fragrance-creator-wrapup`、`weekly-retro-notes`、`platform-mobile-release`、`factory-pilot-ramp` 和 `service-incident-recovery` 五个父任务登记显式账本；账本事件只指向这些范围内的叶子任务，并按时间升序聚合到对应父任务曲线。叶子任务本身和没有显式账本的其他父任务不会自动生成曲线。

D-170 新增的复盘账本使用 3 个叶子：`weekly-retro-decisions` 为 2h、`weekly-retro-open-issues` 为 3h、`weekly-retro-actions` 为 2h，总范围 7h。前两项在 2026-08-29 进入基线，行动项在 2026-08-31 加入范围；同日仅 `weekly-retro-decisions` 产生 2h 的 `accepted` 事件，因此当前 `scopeHours=7`、`completedHours=2`、工作量百分比为 `2/7≈28.6%`。三项估算的 `basis` 必须为 `mock`，固定账本来源必须为 `example`；页面分别显示“演示估算”和“示例”，不能把根任务“进行中”的 TaskStatus、2h 已验收工作量或曲线互相反写。

| 事件 | 对当前范围的影响 | 对已验收量的影响 |
| --- | --- | --- |
| `scope-added` | 把叶子纳入范围；`isBaseline` 只说明它属于观察期起点 | 初始为未验收 |
| `estimate-revised` | 从事件发生时起使用新 EWD；不得回填更早快照 | 已验收叶子同步使用当时有效 EWD |
| `accepted` | 范围不变 | 累加该叶子当前有效 EWD |
| `reopened` | 范围不变 | 从事件发生时起撤销该叶子的已验收量 |
| `scope-removed` | 从事件发生时起移出范围 | 同时移除其已验收量 |

每个快照的计算规则：

1. `totalLeafCount` 是当时范围内的叶子数；`estimatedLeafCount` 是其中有有效 EWD 的叶子数。
2. `scopeHours` 汇总已知叶子 EWD。覆盖不完整时它只是已知子集，必须同时显示覆盖数；未知不能写成 `0`。
3. `completedHours` 只汇总已验收且 EWD 已知的叶子。覆盖不完整、任一当前值未知时不计算总体完成率。
4. 同一时间戳按账本顺序应用，快照中最后的有效状态胜出；原事件仍保留，便于审计。
5. 父任务自己的估算、状态和完成百分比均不进入曲线，避免和叶子重复计算。
6. 无子任务不展示燃起图；有子任务但没有显式账本时也不补造历史曲线，只展示当前可用的叶子 EWD 分布。只有一个快照时只展示点和“历史不足”；缺失值使对应线段断开；非法历史整组标为待核对，不能过滤后继续绘制。

## 6. 验证证据

提交前至少执行以下检查：

- 数据集结构校验：215 条任务总量、59／50／51／55 的团队分布、159 个叶子和每团队至少 40 条，以及成员、标签、父子关系、依赖 DAG、EWD 与详情引用。
- 浏览密度校验：每团队至少三棵项目树、四项独立工作、五种状态、七名负责人；排期和目标／完成标准／执行建议覆盖率不低于 70%，159 个 Mock 叶子 EWD 有效率为 100%，每团队至少六条真实产出依赖。按状态抽样必须包含“待开始”，避免把状态误作估算开关。
- 事件账本测试：基线、增项、改估、验收、重开、移除、缺估、同时间戳、单点和空范围；复盘账本另固定验证 3 个叶子、7h 范围、2h 已验收和 28.6%。
- 创建基线测试：所有带进度序列的 Mock 均在真实创建日提供初始总工作量；创建量与首条观察量一致时形成水平线，父任务初始量等于叶子创建基线去重汇总，且创建节点不生成完成量。
- 详情测试：31 个高密度固定详情的文件树、版本、活动线程、文件引用和结构化变更，以及全部 184 个非高密度任务的确定性详情回退；叶子详情显示自身状态和有效演示工时，不因缺历史显示燃起图。
- 迁移测试：先保留 v7→v14 的原扩容、语义和复盘迁移断言，再验证 v14→v15 只 map 已有节点；只有旧自目标 `scopeKey` 且其他估算字段未编辑时才修复，11 个目标叶子只补缺失定义和未显式填写的估算。用户估算、显式清空、用户任务和删除均保留，重复读取幂等且不复活节点。
- 团队切换测试：列表、工作台、成员选择器、任务创建上下文只读取当前团队；新任务继承当前团队。
- 全量单元测试、TypeScript/Vite 构建，以及至少一次多团队界面切换检查。
