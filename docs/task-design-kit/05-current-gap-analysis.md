**二、个人分析应该提供什么**

真实问题是：本人同时负责多件事，不清楚今天先做哪一件、哪些需要自己决策、哪些只需等待，以及承诺是否超过可用时间。建议把分析分成“任务内诊断”和“个人工作区排序”两层，共用任务与证据，不新增第二份任务对象。

| 本人要回答的问题 | 最小输出与动作 | 所需数据 |
| --- | --- | --- |
| 现在先推进什么？ | 少量有依据的建议：任务、当前下一步、为什么现在做；点击进入现有任务 | 本人有效责任、目标影响、可执行状态、期限、依赖、剩余投入 |
| 什么必须由我拍板？ | 列出待确认目标／方案／交付及具体问题，定位讨论或证据 | 明确待决策记录与责任归属；不能把消息提及自动当作正式分工 |
| 哪些做不了，怎么解除？ | 区分“等待前置产出”“需要我的决定”“资料不足”；给出可执行的解除动作 | 真实依赖及可见证据，不以无更新、离线判定停工 |
| 我的时间够不够？ | 对同一时间窗口显示本人剩余投入、可用人时、冲突及缺失信息 | 工作日历、本人确认的可用窗口、按执行人分配的剩余人时、硬截止 |
| 哪些完成情况需要核对？ | 已有交付但未确认、标准缺证据、范围增加后的进度变化 | 完成标准版本、文件版本、执行报告、业务验收记录、范围事件 |

**推荐最小承载：**在个人任务范围提供一个按需打开的分析列表，复用现有任务详情与处理入口；每条按“任务 → 具体动作 → 理由 → 证据/更新时间”呈现。先不新增首页、统计卡墙、四象限图或团队排行榜，也不把这些信息塞进 D-148 仅名称的任务索引行。具体入口需产品确认，这里只是可审阅方案。

范围应从本人**全部有权可见且已生效的负责关系**计算，不受当前列表分页或临时标签筛选截断。可以提示待接受分工，但要与已承诺工作分开。本人作为父任务 Owner，仍需关注整体结果；他人执行的子任务工时不能全部算成本人的执行负荷。本人的协调、审核投入可单独估计，不恢复逐项 Responsibility 对象。

数据不足时仍可提供“请确认截止日／剩余投入／前置交付”这样的下一步，但不能给确定的排序或容量百分比。只有更新鲜的可靠证据到达后，才能改写原判断；人工调序可保留原因，不静默回排。

**三、建议采用的工时、完成度与优先级标准**

以下是本产品的建议口径，不是行业统一标准或已批准算法。应把三类评估分开：AI 有没有判断对、任务结果有没有满足标准、工作量完成了多少。三者不能共用一个“AI 质量分”。

| 指标 | 建议定义 | 不得替代的概念 |
| --- | --- | --- |
| EWD | 完成既定范围预计需要的人类投入，人时 h；保留来源、依据、版本、确认人和时间 | 不是自然工期、机器运行时长、实际工时或员工效率；若要计算 AI 节省工时，还需另定义可比较的人工基线 |
| 剩余人时 | 从当前时刻完成剩余工作预计还需的人类投入，可按执行人分配；未知允许为空 | 不是初始 EWD 减实际工时，也不是“总 EWD 减已验收 EWD” |
| 实际人时 | 有来源的人工投入记录，缺记录则未知 | 心跳、消息数量、在线时长不能代替工时记录 |
| 自然工期 | 从开始到结束跨越的日历时间，受依赖、等待和工作窗口影响 | 不能把 16 人时直接转换为两天，也不等于所有人的工时之和 |
| 工作量完成度 | 当前范围内已业务验收叶子任务的已确认 EWD ÷ 当前范围全部叶子任务的已确认 EWD | 不是任务个数完成率、标准勾选比例、AI 自报百分比；缺估时不报完整总体值 |
| 完成标准检查 | 逐项给出“已有依据／不满足／未知”，引用精确证据版本 | AI 检查不等于有权人的业务验收，不新增 AI 审批状态机 |
| 重要性 | 依据与目标的关系、不做的后果、影响范围及明确承诺，先用有解释的分档 | 不根据字面“紧急”、任务长度、发起人职位或已有“高优先级”标签直接推断 |
| 紧急性 | 依据有效截止、剩余投入、前置完成时间和本人可用窗口判断排期余量 | 不只是离截止还有几天，也不能用 EWD 直接代表剩余工作 |

EWD 的最小可验证规则：

1. **按叶子汇总，父子不重复。** 独立单任务自身是叶子；父级整合若确有独立工作量，要明确计量位置。父任务 Owner 的结果责任仍保留。
2. **未知不是零。** 估算缺失或未确认时，总体进度不可计算；可以显示“已估范围进度”，同时显示已估项数／全部项数，不把项数覆盖率叫工时覆盖率。零工作量也不显示 100%。
3. **验收有来源。** 需定义谁能确认何种结果、对应哪个标准及文件版本。现有“已完成”状态不能未经规则映射就视为已验收；本建议不恢复勾选验收 UI。
4. **历史按当时事实记账。** 新增、移出范围、取消、重开、改估均记录生效时间；保留最初基线与修订原因，不用今天的估算重写过去。当前净范围和净已验收线允许因移出或重开而下降，标明原因。
5. **工作量完成不等于业务成功。** 即使叶子 EWD 全部验收，也不自动关闭父任务或宣布目标达成，仍需核对整体结果。

合成例子：两项工作分别 2h、18h，只验收前一项，工作量进度为 `2/20=10%`，不是 50%。再新增 10h 范围后变为 `2/30≈6.7%`，应说明范围增加。原 18h 任务已做大部分、只剩 1h，但尚未验收时，验收完成量仍是 0h，排期使用剩余 1h；不能把它再当作还需 18h。

多人例子：一项交付共需 12 人时，其中甲 2h、乙 10h，总量仍是 12h，不能给两人各计 12h。若缺少分人投入，不因甲是唯一 Owner 就断言甲要执行全部 12h。估算还需先确认工作方式：是否按预期使用 AI/工具后的人工投入计算；工作方式变化应记录修订，不能把不同口径的估算与实际值直接比较或宣传提效。

个人排期建议先采用可解释规则，暂不设计 0–100 综合分：先识别硬截止冲突和本人必须解除的阻塞，再在当前可执行事项中结合目标影响与排期余量选择；被阻塞的高重要任务保留关注，但下一步应指向解除阻塞。硬截止存在冲突时提出缩范围、协商时间或调整分工的候选，不自动改任务。

容量计算必须在同一窗口比较：`该窗口本人需承担的剩余人时 / 本人可用人时`。分子应覆盖窗口内必须完成的全部已生效承诺（含逾期未完成、尚未排入计划的投入），并加上其他任务已安排到此窗口的投入，按 Task/投入记录去重；同时披露数据与排期覆盖，不能靠漏排任务制造“容量充足”。同一小时不能同时分配给多项任务；截止日不同还要逐窗口核对。可用人时为 0 且有剩余投入时直接提示容量冲突，双方为 0 时标不适用，不做除法；缺工作日历、剩余估算或分人工时则显示未知。负荷比率超过 1 只能说明当前安排超出已知容量，不能推出个人能力不足。缓冲阈值、重要性分档和排序规则待试用后确认。

回传最小协议建议包含：事件 ID、Task ID、会话/运行 ID、事件序号、客户端协议版本、发生时间与服务端接收时间、上下文基准版本、执行声明、交付物及其版本引用；授权的人类主体由服务端会话解析，不信任客户端自报。心跳记录单独保存最后成功时间和连接状态，不能混入业务进度或人的讨论。校验要覆盖重复、乱序、时钟偏差、断线重连、过期和撤销。

当前 MCP 的创建标记在文件写入前进入内存（E09）；后续接入要验证写盘失败后的重试是否误报成功，以及进程重启和并发写入。工具上的 `idempotentHint` 声明或 UI“仅确认后调用”提示，均不能替代持久幂等及服务端授权。
