# 个人与团队生命周期结束

## 1. 目的

让用户能够安全结束当前会话、切换工作团队、终止团队成员关系或停用账号，同时确保唯一管理员和仍在生效的任务责任不会悬空。离开不会抹去已经发生的工作；撤权后也不能借旧会话、CLI 设备或缓存继续访问团队内容。

## 2. 范围和边界

本模块覆盖退出登录、切换团队、成员主动离开团队、管理员移除成员、责任处置、Owner 失联死锁恢复、CLI 设备授权撤销和账号停用。角色与邀请见模块 09，正常任务负责人变更见模块 09，删除任务见模块 13，统一权限与错误见模块 15。

当前 MVP 的已挂载行为见 3.0；3.1–3.7 均为上线目标，服务端责任检查、撤权、账号停用和审计尚未实现。当前本地删除团队入口也不等于下述生产数据处置能力。

退出登录、离开团队和停用账号是三个不同动作：退出登录只结束会话；离开团队只结束一个 Team Membership；停用账号结束全部新会话能力。切换团队不退出任何团队。TeamRole 用于团队级动作，Task ACL 决定具体任务的负责人转移与读取能力；团队管理员不能仅凭 admin 身份绕过 Task ACL 修改任务责任。

上线目标首版不提供生产“删除团队”或把历史作者改名为当前管理员。历史讨论、正式 Commit 和 Activity 保留原作者归属；账号停用后只保留审计所需的最小身份引用，不把作者显示成匿名系统用户。

## 3. 详细功能设计

### 3.0 当前 MVP：退出与团队设置入口

账户菜单“退出登录”清除浏览器工作区 sessionStorage 身份并返回登录页；团队切换更新本地活动团队。当前没有真实服务端会话、刷新凭据或 CLI 设备授权可供撤销，也没有证明所有受限缓存均已安全清理。

设置页提供“离开团队”和“删除团队”二次确认，二者当前均从本地个人中心状态移除选定团队并切换到剩余团队；只有还有其他团队时可用，删除还要求当前本地成员为有效管理员。存储失败保留团队并报错。页面虽使用永久删除提示，但没有生产数据清理服务、退出责任检查或唯一管理员转交闭环，不能把本地限制当作正式权限保障。

当前未实现管理员移除其他成员的完整责任处置、Owner 失联恢复、账号停用入口与服务端执行；不承诺离开即完成跨端撤权。下面保留这些上线目标，不把浏览器中团队消失解释为全部成员关系和设备授权已经终止。

证据：`src/components/PersonalCenterPage.tsx`、`src/lib/workspaceSession.ts`、`src/App.tsx`、`server/personalCenterProfile.test.ts`；当前实现矩阵和 intake audit 用于记录仍待落实的服务端边界。

### 3.1 上线目标：退出登录与切换团队

用户从账户菜单选择退出登录后，服务端撤销当前 Web 会话和刷新凭据，客户端清除团队投影、受限缓存和未提交的本地敏感副本，再返回登录页。退出登录不删除任务、讨论、文件或团队关系，也不默认撤销其他浏览器会话和 CLI 设备；用户可在安全设置中另行撤销全部会话或指定设备。

切换团队只改变当前活动团队。系统先检查目标团队成员关系仍有效；有未保存草稿时要求保存、放弃或取消切换。切换成功后，列表、通知、搜索、AI 上下文、回收站和成员缓存以新团队重新加载，旧团队数据先进入安全空态，不混入新团队页面。目标团队无权或已被移除时返回团队选择页，不泄露原团队最新内容。

### 3.2 上线目标：离开团队前的责任检查

成员在团队设置选择“离开团队”后，系统生成当前版本的离开检查，而不是直接撤权。检查至少覆盖：是否为唯一管理员、仍由本人负责的有效任务、待接受的负责人提议、尚未收口的任务参与邀请、本人发起且仍有效的团队邀请，以及与本人 CLI 设备关联的当前团队授权。

唯一管理员被阻止离开，必须先把另一位有效成员提升为管理员，并在角色变更成功后重新检查。正式 Task 的 Owner 为 `0..1`；仍是有效任务负责人且本人可正常操作时，必须逐项发起负责人转移，并等待目标成员接受、Owner 正式生效后再离开；仅创建待接受提议不算完成转移。不能转移的任务必须取消离开并返回对应任务处理，不能在正常流程中把已有 Owner 静默改为未分配。

待处理责任按对象收口：发给本人的负责人提议由本人接受或拒绝；本人发起但未接受的负责人提议和任务参与邀请需撤销或由仍有权限的成员重新发起；本人发起的团队邀请可保留，但系统把后续管理责任转给有权限的团队管理员并留下记录。检查结果绑定 membership 版本和摘要，责任变化后必须刷新。

所有阻断项清零后，用户再次确认。服务端重新校验成员、管理员数量、有效 Owner、待处理责任和版本，在一个事务中终止 Membership、撤销该成员对当前团队的 CLI 设备授权及会话范围、结束未处理的个人邀请响应权，并生成成员离开 Activity 与回执。其他团队成员关系和账号本身保持有效。

### 3.3 上线目标：管理员移除成员

管理员从成员页选择“移除成员”时，先看到目标成员的团队角色、有效任务负责人关系和待处理责任摘要。不能移除唯一管理员；需要先指定另一位管理员。目标成员仍是有效任务负责人时，必须先完成负责人转移；管理员若未被对应 Task ACL 授予 `task.transfer_owner`，只能打开责任处置清单并通知有权主体，不能以 Team Admin 身份自动绕过 Task ACL。

管理员可撤销目标成员发起或收到的未完成团队级邀请；任务参与邀请和负责人提议按其对象权限撤销或交由有权主体处理。所有阻断项解决后，移除命令以 membership 版本、责任摘要和幂等键执行。成功后成员立即失去该团队的列表、任务、文件、通知、回收站和 AI 上下文访问；其 Web 会话若仍可访问其他团队，则回到团队选择页。

移除操作同时撤销目标成员所有指向该团队的 CLI 设备授权和委托 scope。撤权先于任何后续读取；旧幂等回执重新鉴权，不能回显已无权内容。成员恢复加入必须走新的团队邀请，不复活旧 Membership、Task ACL 或设备授权。

### 3.4 上线目标：Owner 失联死锁恢复

`task.assignment.recover` 是独立受控能力，只处理成员移除或账号停用时，现有 Owner 已失联、拒绝继续配合，或系统中不存在可执行正常转移的 `transfer_actor` 而导致的责任死锁。它不是普通 Owner 编辑、批量管理员接管或 Team admin 的普遍 Task ACL；Owner 可联系、正常 `transfer_owner` 仍可用或只是目标成员尚未响应时，服务端必须拒绝恢复命令并继续正常流程。

恢复前服务端先在不向操作者暴露任务正文的条件下确认：目标 Membership 正在移除／账号正在停用、Owner 当前不可用、正常 `transfer_owner` 无可用路径，以及当前操作者是该团队有效 admin。管理员必须完成 step-up auth，并读取只含必要任务引用与关系状态的影响预览；确认提交明确理由、预览摘要、任务与 membership 版本、幂等键。服务端再次检查死锁与唯一管理员规则，写入不可变安全审计；任何条件变化都要求重新预览。

恢复确认只允许两种结果：把受影响 Task 分配给已经明确接受的有效成员，或在本次恢复确认中明确同意接任的有效成员；确无接任人时将 `ownerId` 设为未分配 `null`。恢复命令不允许读取或改写任务正文、完成标准、Participant、ACL、状态、文件或历史记录，也不能把管理员自己默认为 Owner。一次命令只处理影响预览绑定的任务集合，不扩大到同团队其他 Task。

成功事务保存旧 Owner、新 Owner 或 `null`、理由、批准管理员、目标成员同意、版本、ChangeSet、Activity 和 operation ID，并通知旧 Owner（仍可达时）、新 Owner、Task 有权主体及成员管理发起人。历史 Owner 和既有 Activity 保留，不回写过去责任。恢复为未分配后，本人创建任务的个人恢复分组规则不适用离职管理员；有权成员仍可从“负责人：未分配”查找，并通过正式 `0 → 1` 提议／接受建立新 Owner。

### 3.5 上线目标：CLI 设备授权撤销

个人安全设置列出设备名称、授权团队、授权范围、创建时间、最近使用时间和状态。用户可撤销单个设备、某个团队 scope 或全部设备；团队离开、成员移除和账号停用会自动撤销对应范围。撤销后新请求立即返回未授权，已签发的短期凭据按服务端撤销表失效，排队中的高影响写入在提交前重新鉴权。

设备撤销只终止访问，不删除该设备此前创建的 Task、Discussion、FileVersion、Commit 或 Activity。安全日志记录撤销主体、设备、团队、时间和原因，但普通成员不能读取密钥、令牌或完整网络标识。

### 3.6 上线目标：停用账号

用户在个人设置发起停用账号。系统跨全部团队生成责任检查：唯一管理员身份、仍负责的有效任务、待处理责任、有效 Membership、Web 会话和 CLI 设备授权必须逐项处置。每个团队中的负责人转移必须已被目标成员接受；有任一唯一管理员或未转移有效任务时阻止停用并提供定位入口。只有 Owner 已失联且正常转移确无可用路径时，当前团队管理员才可另行启动 3.4 的受控恢复；停用动作本身不能自动改 Owner。

检查完成后，用户重新验证身份并确认停用。服务端以账号版本、检查摘要和幂等键执行：把账号标记为停用，撤销全部 Web 会话、密码重置会话、CLI 设备授权和委托，终止剩余 Membership，并拒绝后续登录或新会话。停用不是即时物理删除，恢复能力若未来提供须另行定义身份核验和保留边界，首版不显示可自行恢复承诺。

账号停用后，历史 Discussion、正式 Commit 和 Activity 保留原作者归属及发生时身份引用；作者卡片显示“账号已停用”，不展示已清理的个人敏感字段。安全审计保留最小主体键。历史内容的读取继续取决于查看者当前权限，停用账号本身不能登录读取。

### 3.7 上线目标：反馈、并发与可访问性

责任检查显示数据截至时间和来源版本。检查加载失败不允许继续；版本变化保留用户已经完成的选择，刷新后标出新增和已解决项。重复幂等请求返回同一离开、移除或停用回执，不重复发送通知或生成 Activity。

窄屏按阻断原因、处理动作和最终确认单列呈现。键盘用户可以进入每个阻断任务、返回检查页并恢复原焦点；对话框关闭后焦点回到发起按钮。唯一管理员、未转移责任和失效授权由文字与图标共同表达，不能只靠颜色。

## 4. 验收标准

当前 MVP 验收：退出登录清理本地工作区身份；离开／删除团队需二次确认、保留至少一个团队，失败不能显示已移除。以上本地动作不表示服务端责任转交、跨端撤权或账号停用已经实现。

以下为上线目标验收：

- 退出登录只结束当前会话；切换团队只替换活动上下文，并在展示新团队前清除旧团队缓存。
- 离开团队与管理员移除都先检查唯一管理员、有效任务负责人和待处理责任；负责人转移必须被目标成员接受后才算完成。
- 唯一管理员在指定另一位有效管理员前不能离开、被移除或停用账号。
- TeamRole 与 Task ACL 分开校验；团队管理员未获任务 capability 时不能绕过 Task ACL 转移 Owner。
- `task.assignment.recover` 只在 Owner 失联且服务端确认正常 `transfer_owner` 无可用路径的死锁中开放；当前团队管理员需 step-up auth、影响预览、明确理由、版本、幂等与审计，不能读取或改写任务正文。
- 死锁恢复只能分配给已明确接受或在恢复确认中明确同意的有效成员，或把 Owner 设为未分配 `null`；历史 Owner 与 Activity 保留，并通知相关人。
- 离开或移除成功后立即终止 Membership，并撤销该成员指向当前团队的 Web 会话范围和 CLI 设备授权。
- 停用账号前完成全部团队责任检查；停用后撤销所有会话与设备授权，并拒绝登录和新会话。
- 历史 Discussion、正式 Commit 和 Activity 保留原作者归属，停用账号只清理不再必要的个人敏感字段。
- 冲突、失效检查和网络重试不会产生悬空 Owner、重复退出或越权回执；窄屏、键盘和焦点路径可完整完成或取消操作。
