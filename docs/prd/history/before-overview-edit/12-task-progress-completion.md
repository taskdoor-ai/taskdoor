# 任务推进与结果收口

## 1. 目的

让成员基于可定位的任务事实判断当前发生了什么、工作推进到哪里、本人下一步应关注什么，并在核对完成标准和必要证据后明确完成任务。系统帮助整理事实和候选动作，但把业务判断与状态变更留给有权限的用户。

## 2. 范围和边界

本模块覆盖任务当前情况、内容完成度、时间进度、预计投入、阻塞、我的工作、AI 建议与来源链接、状态推进、完成前核对和重新打开。任务字段与普通状态入口见模块 08，文件与 Commit 见模块 11，删除不等于完成且由模块 13 定义。

当前 MVP 的完成入口直接更新本地任务状态，尚未接入独立完成核对页。下文的完成标准阻断、证据核对、服务端鉴权及完成回执均为上线目标，不代表当前界面已执行这些校验。

未知必须保持未知：缺少历史、投入、日期或证据时不显示 0%、运行正常或虚构曲线。AI 建议不自动写入任务、不自动分配人员、不自动改变状态，也不执行业务验收。正式 Commit 只是可引用证据之一，不自动等于任务完成；子任务完成或进度达到 100% 也不自动关闭父任务。

## 3. 详细功能设计

### 3.1 当前情况

任务详情概览中的 AI 分析默认折叠，展开后展示完成进度、当前情况和下一步建议，与讨论、文件、活动分别位于独立 Tab。当前情况按可见事实说明已发生事项、仍有差距、近期变化、风险与阻塞；区头显示数据截至时间、分析版本和刷新状态。每条结论可展开来源，至少包含来源对象、来源版本、发生或读取时间和权限决定。

来源仅包括当前用户有权读取的任务字段、完成标准、讨论、文件版本、正式 Commit、活动和验收记录。来源变化后旧快照立即标为过期并请求刷新；权限收紧时先移除不可见内容和缓存，再基于剩余事实重算。刷新失败可保留仍有权查看的旧内容供核对，但持续显示“已过期”，不能冒充当前事实。

阻塞可以来自用户明确记录、受控状态或有来源的证据冲突；依赖关系本身只提供参考，不自动把任务改成已阻塞。无证据、来源过期或权限不足分别显示未知、待刷新或受限，不补造原因。

### 3.2 完成进度、内容完成度、时间进度与投入

**当前 MVP · 逐条标准。** 每条完成标准用四段 AI 梯度环表示评估，人工通过圆环独立确认，标题显示已确认条数。梯度、人工确认和任务状态是三个不同事实；全条确认不自动完成任务。交互及失败恢复见模块 08。

**上线目标 · 完成核对。** 内容完成度按完成标准逐项显示“有证据／待核对／未知”，并链接到支撑该判断的文件版本、Commit、讨论确认或验收记录。它是核对视图，不是 AI 审批结果；没有完成标准时明确显示“尚未定义”，不推算百分比。完成标准为空时阻止完成，要求用户先补充至少一条可核验的完成标准；不能因为没有待核条目而静默视为全部通过。当前本地状态切换尚未执行这套阻断规则。

时间进度只在存在有效计划周期时按当前时间与开始／结束边界计算，并明确标为计划时间位置，不代表内容完成。日期缺失、非法或过期时显示未知或待核对。预计投入 EWD 来自任务的正式估算字段，表示约定工具方式下的人类净投入，不等于已发生投入、剩余投入、自然工期或机器耗时。现有首版合同没有实际工时对象或受控写入接口，因此首版不展示实际工时，也不提供录入入口；不能从 Activity、Commit 时间或在线时长反推。后续若要增加，必须先定义独立对象、录入口径、权限和更正机制。

界面统一使用“完成进度”。执行中的百分比是 AI 评估：基于可见来源评估当前范围内已经完成的工作量，按有效范围投入表达比例，并保留依据、观察时间与范围版本。父任务和中间任务按有效叶子范围去重汇总，不与叶子重复累计；缺少、过期、非法或部分投入数据时不补 0。完成任务数、正式 Commit 数和时间进度都不能替代评估依据，AI 不自动改变任务状态，即使评估达到 100% 也等待用户确认。

用户明确将任务状态选为已完成后，主展示为 `100% · 用户确认`。当前显示依据是本地状态更新，不证明上线目标的证据核对已通过。用户确认记录与 AI 原始评估独立保留，不把确认值写回历史 AI 评估，也不将 AI 的百分比当作业务验收结论。重新打开后撤下用户确认的 100% 主展示，只有与当前范围仍匹配的独立 AI 记录可恢复为评估值；没有有效记录则显示未知，不能沿用确认值冒充新评估。

当前界面中的 mock 预测和示例历史仅用于演示，不能写成生产评估事实，也不能据此宣称生产预测服务、持续分析或真实历史已经接入。生产展示仍需可核对的数据来源；没有真实来源时明确显示未知或演示状态。

当前 Mock 燃起图从任务创建日记录初始总工作量，而不是到首条进度观察或当前日期才出现。创建节点只保存当时确认的范围公式，不生成完成量；父任务和中间任务按有效叶子的创建基线去重汇总，不重复累计中间层。若创建量与后续观察量相同，灰色总工作量线从创建日水平延续；新增、缩减或改估只从对应记录日期起改变曲线，不以当前总量覆盖历史。

### 3.3 我的工作

“我的工作”是当前团队内个人任务的连续优先清单，不是第二套任务数据。候选范围必须同时满足：当前用户是正式 Owner 或正式 Participant，且 TaskStatus 为待开始、进行中或已阻塞。待接受 Owner／Participant 提议、未分配、已完成及其他状态都不参与排序；同一 Task ID 无论以几种关系命中都只出现一次。这个范围不受任务列表当前搜索、筛选、分页或分组折叠影响。

每项只显示连续顺位、任务名称和一句可理解的优先原因；名称进入任务详情，不在任务行展示分数、状态徽章、完整依据或下一步面板。排序使用规则版本 `PERSONAL-PRIORITY-2026-09-03-v4`，推荐权重 `W = 重要度 I × 60% + 紧急度 U × 40%`。60%／40% 和以下分档都是待验证的初始建议参数，不宣称是用户已确认比例或经验证算法；本轮只规定产品合同，不表示应用排序已经接入。

重要度 `I = B + C + P`，最高 100。目标影响 B（0／10／20／35／50）只读取已确认目标、交付与合规要求；协作影响 C（0／15／30）只读取当前交付对活跃下游任务或关键里程碑的已确认影响，按 Task ID 去重，父子关系或参考依赖本身不算影响。标签参考 P 为 0／20：只在当前任务已有标签名称和已知含义明确表示重要时加 20，例如“高优先级”或“重点任务”；普通业务分类、无标签或含义不明均取 0，多个符合条件的标签或重复标签也不叠加。含义冲突时标待核对；不按颜色、数量或上级标签猜测，不新增优先级字段，也不把标签当作目标或协作影响事实。

紧急度 `U = max(D, H, Q)`，期限压力、当前损失或执行风险、待本人处理三类分别取最高档后再取最高值，不相加。期限压力 D 按团队时区计算：已逾期 100、今天 90、未来 1～2 天 75、3～7 天 60、8～14 天 30、14 天以后 10、明确无截止为 0；日期缺失、过期或无法识别时取 0 并标待核对，不猜日期或判逾期。当前损失或执行风险 H 只在可定位的持续关键中断／损失／合规安全风险、已证实且需本人处理的停工返工影响或有效决策冲突成立时取 100／80／60；只有“已阻塞”状态、参考依赖未完成或陈旧记录不加分。待本人处理 Q 只在下游明确停等本人结果／决定／确认，或材料齐备且存在指向本人的有效核对请求时取 80／60；仅 Participant 身份、上传文件或未来可能依赖取 0。

每个命中保存事实、来源 ID／版本、适用 Task 和有效性。同一事实或重复来源在同一维度只计一次；缺失、过期、受限或失效来源不加分，不把其余维度放大，优先原因需标“信息不足”或“待核对”。按 W、I、U 依次降序，同分再按可比较截止时间及稳定 Task ID；负责人、参与人、状态、目标、完成标准、已确认影响、标签、期限、有效风险、待处理事项或来源版本变化时重算，页面打开或无变化刷新不制造新时间。

### 3.4 人员责任分析

“人员责任分析”复用模块 04 的“我的责任”入口，保持 Team-bound。它只读取当前团队中本人负责或参与的任务（即正式 Owner 或正式 Participant 关系）、本人实际承担的可定位工作事实，以及当前 `responsibility_document`；对照后可形成责任新增或更新建议。任务标题、关系身份或 AI 推断不能单独冒充实际承担，缺证据时只说明资料不足。

分析结果只写入带依据、来源版本、目标责任快照和基准 `revisionId` 的只读 `responsibility_proposal`。用户明确“添加”或“更新”后，建议才进入正式责任并可作为后续成员推荐依据；用户可忽略，或通过独立人工编辑纠正责任文本，冲突处理沿用模块 04。未经确认不修改正式责任或成员推荐依据，也不自动改变 Task Owner、Participant、ACL、状态或邀请。

该分析不产生人员评分、能力／效率画像、绩效排名或完成概率，不以任务数量和活跃度评价个人。来源过期、关系失效或 Team 切换后建议标过期并重新核对；持续分析服务、事件接入和反馈闭环若未实现，页面必须明确实际能力，不能把静态建议冒充持续运行。

### 3.5 AI 建议与来源

下一步建议用“事实—判断—候选动作”表达，展示数据截至时间和来源链接。建议可以引导用户打开讨论、核对文件版本、补充完成标准、处理阻塞或发起受控状态动作；点击建议先进入对应来源或预填草稿，不直接写入任务。来源无法读取时移除敏感摘要，并将建议标为无法核对。

用户可采纳、忽略或反馈建议。采纳只执行界面明确展示且再次确认的具体动作；需要邀请、负责人、状态、文件或完成的动作继续遵循各自权限、版本和审计规则。AI 报告“已完成”仅是待核对声明。

### 3.6 状态推进、完成与重新打开

**当前 MVP。** 用户在状态选择器中选择已完成后，`App.tsx` 的 `changeTaskStatus` 直接更新任务的本地状态并追加本地状态变更活动。当前未接入独立完成核对页，也未执行下述完成标准、证据、文件和关系的完整核对；不能把本地状态变化当作服务端业务验收成功。AI 不自动改变任务状态。

**上线目标。** 状态推进使用专用命令。用户选择目标状态后，页面展示当前状态、目标状态、必要影响和可恢复错误；服务端按权限与任务版本重新校验，成功后原子写入状态、ChangeSet 和 Activity。依赖、建议或通知都不能自动推进状态。以下权限、完成核对和重新打开流程均属于上线目标合同。

TeamRole 只证明成员是否仍属于团队，Task ACL 决定具体状态动作。上线默认规则如下：

| 动作 | 可以执行的人 | 必需能力与约束 |
| --- | --- | --- |
| 完成任务 | 当前正式 Owner，或代表该 Owner 的受托 Agent Principal | `task.complete`；Owner 关系与 capability 必须同时成立，任务未分配时先建立正式 Owner |
| 重新打开任务 | 当前正式 Owner，或代表该 Owner 的受托 Agent Principal | `task.complete`；任务当前为 completed，且以最新版本执行受控状态转换 |

Participant 不能仅凭参与关系完成或重新打开任务；团队管理员不能仅凭 admin 身份绕过 Task ACL。Team Admin 若同时是当前正式 Owner，仍须由 Task ACL 授予 `task.complete`；Agent 还须满足设备授权、用户委托和 Task scope。

**上线目标 · 完成核对。** 选择“完成任务”进入独立核对页：逐项展示当前版本的完成标准、关联证据、未提交草稿、处理中的文件、未收口的负责人／参与邀请、有效阻塞以及子任务与父任务关系。完成标准为空时直接阻止完成并定位到“补充完成标准”，至少保存一条可核验的完成标准后才能继续；必需完成标准缺少证据、关键文件仍在扫描或任务版本变化时同样阻止确认并定位问题。非阻断未知项由规则明确标注，用户不能被误导为全部通过。

有权限的用户确认后提交任务版本、核对结果与幂等键；服务端再次鉴权并原子创建 completion record、变更 TaskStatus、形成 Activity 与回执。正式 Commit 可作为证据被选中，但 Commit 只是证据，不自动等于完成。完成后任务保留讨论、文件、Commit 与活动。

**上线目标 · 重新打开。** 当前 Owner 在已完成任务选择“重新打开”，填写原因并选择恢复为 open 或 in_progress。客户端提交 `expected_version`、目标状态、原因和幂等键；服务端重验成员状态、当前 Owner、`task.complete`、任务仍为 completed 且版本一致。成功时原子追加 reopening record、更新 TaskStatus，并生成包含前后状态与原因的 Activity；回执返回 operation ID、变更前后版本、目标状态和 `projectionState`。版本冲突保留原因并要求读取最新任务，重复幂等请求返回原回执。重新打开不删除或改写原 completion record。

### 3.7 回执、冲突与多端体验

**上线目标。** 刷新分析、状态推进和完成分别返回 operation ID、输入版本、结果版本与实际变化；重复幂等请求不生成第二条完成记录或 Activity。版本冲突保留用户核对进度，刷新最新完成标准和证据后显示差异并要求重新确认。无权限与不存在不回显隐藏任务、证据或进度。

加载时不显示旧百分比为当前值；局部来源失败不清空任务定义。窄屏按当前情况、进度、建议、来源和确认顺序单列；键盘用户可展开来源、处理核对项和完成确认。阻断错误把焦点移到首个问题，其他已核对结果保留。

## 4. 验收标准

### 4.1 当前 MVP 验收

- 用户选择已完成后直接更新本地状态和本地活动，显示 `100% · 用户确认`；AI 不自动改变任务状态。
- 当前没有独立完成核对页；本地状态成功不表示已核验完成标准、证据、文件、关系或服务端权限。
- mock 预测和示例历史属于演示，不代表生产评估服务已接入；用户确认值不覆盖独立 AI 评估。
- 每条带进度历史的 Mock 在任务创建日提供初始总工作量，创建节点不补造完成量；父任务按叶子创建基线去重汇总。创建日至后续观察未改量时，总工作量显示为水平线，后续范围变化只从实际记录日期生效。

### 4.2 上线目标验收

- 当前情况展示数据截至时间、分析版本和来源；来源变化后旧判断标为过期，权限变化后不可见内容立即移除。
- 内容完成度、时间进度和预计投入使用不同口径；首版不展示或录入实际工时，缺失或失效数据保持未知，不补 0 或虚构趋势。
- 完成进度在执行中表达 AI 评估；用户确认已完成时显示 `100% · 用户确认`，原始 AI 评估独立保留，AI 不自动改变任务状态。
- mock 预测与示例历史明确属于演示，不能冒充生产事实；重新打开后只恢复仍有效的独立评估，无有效记录时显示未知。
- 我的工作只对当前用户作为正式 Owner 或正式 Participant，且处于待开始、进行中、已阻塞的任务排序；待接受、未分配、已完成和其他状态均排除，每项仅有顺位、名称和优先原因。
- 推荐权重的 60% 重要度与 40% 紧急度明确标为待验证初始建议参数；标签只作 P 项参考，普通分类、无标签、含义不明或重复标签不会被补造成重要性或业务影响。
- 人员责任分析只基于本人负责／参与任务的实际承担形成 Team-bound 新增或更新提议；用户确认后才进入正式责任与后续推荐依据，不评分且不自动改变 Owner、Participant 或 ACL。
- AI 建议提供来源链接且只形成候选动作；未经用户明确操作，不写任务、不分配人员、不推进状态或完成任务。
- 完成任务前核对当前完成标准、证据、草稿、文件、阻塞和关系；服务端基于最新版本再次校验。
- 完成标准为空时阻止完成，要求先补充至少一条可核验的完成标准，不会把空集合静默视为全部通过。
- 只有同时为当前 Owner 且持有 `task.complete` 的成员或其受托 Agent 可以完成或重新打开；Participant 与 Team Admin 不能绕过 Task ACL。
