## 0. 文档效力与阅读方式

本 PRD 把 TaskDoor 已分散确认的产品逻辑整理成一条端到端业务闭环，供产品、设计、研发和测试使用。它不创建新的产品决定，也不替代产品决策台账。

发生冲突时按以下顺序处理：

1. 产品决策台账中最新且未被替代的决定。
2. 本 PRD 对这些决定的流程化投影。
3. 页面设计、组件说明和当前代码实现。
4. Mock 数据、演示文案和历史方案。

文中使用四种状态：

| 标记 | 含义 | 是否可直接作为当前研发依据 |
| --- | --- | --- |
| 已确认规则 | 产品负责人已经确认，且未被后续决定替代 | 是 |
| 当前实现 | 本地原型中存在并可从代码核对 | 是，但只能证明本地原型行为 |

## 1. 产品命题

### 1.1 一句话定义

TaskDoor 把一个工作意图转化为可定义、可负责、可协作、可核验的 Task，并让人和个人 AI 围绕同一份任务事实持续推进。

### 1.2 要解决的问题

团队在引入个人 AI 后，执行速度提高，但以下问题仍然存在：

- 需求表达了，但目标、完成边界和真实交付不清楚。
- 复杂工作被写成一个大任务，无法形成独立结果和清楚责任。
- 选择了协作者，却没有区分推荐、邀请、接受和正式责任。
- 讨论、文件、变更和 AI 产出散落，后加入的人需要重新考古。
- 任务状态、完成进度和“接下来做什么”缺少可核证据。
- AI 容易把建议包装成事实，或在没有授权时替人做决定。

### 1.3 目标用户

| 用户 | 核心任务 |
| --- | --- |
| 工作发起者 | 把模糊需求整理成可以确认的 Task 方案 |
| Task Owner | 持续对结果负责，理解当前情况并推动下一步 |
| Task 参与者 | 在清楚边界和上下文下贡献讨论、文件或子结果 |
| 使用个人 AI 的成员 | 在本人授权范围内读取任务上下文、获得建议或产出草稿 |
| 团队管理员 | 维护团队、成员和团队范围内的责任说明 |

### 1.4 成功证据

产品成功不以页面数量或 AI 文案数量衡量，而以以下行为结果衡量：

1. 用户能说明一个 Task 的目标、完成边界和当前责任状态。
2. 简单工作不会被机械拆分，复杂工作可以按独立结果形成子 Task。
3. AI 推荐不会被误解为正式责任；创建用户确认并成功写入后，所选任务成员直接建立正式关系。
4. 未参与近期讨论的有权成员能从任务详情理解当前情况和下一步。
5. 任务进度、AI 建议和个人优先顺序可以追溯到当前可见事实。
6. 信息不足、过期或无权限时，产品明确表达未知，而不是补造正常、零或完成。

## 2. 当前范围与非目标

### 2.1 当前产品范围

当前 PRD 覆盖：

- 团队上下文切换。
- “我的工作”个人任务优先顺序。
- 任务列表、关键词搜索及外部快捷筛选：全部任务／我负责的／我参与的单选范围、状态多选与独立排序；高级筛选提供状态、标签、截止日期、创建日期。同类多选取并集，不同类型组合取交集。已选条件与清除全部仅在弹层底部展示，分类行无清除叉；入口计数不含范围或关键词，不重复计入状态。搜索、清除及详情联动遵循[任务列表 PRD](../prd/modules/01-task-list.md)。
- AI 辅助的新任务创建与候选方案确认。
- Task 名称、目标、完成标准、负责人、参与人、状态、周期和标签。
- 父子 Task、前置依赖和手工子任务管理。
- Task 内讨论、文件和活动。
- 当前情况、下一步建议和基于 EWD 账本的完成进度。
- 任务上下文和讨论上下文的个人 AI 连接入口。
- 个人信息、团队信息、成员和团队范围责任说明。
- 本地原型中的状态保持、错误保护和可访问性要求。

- Todo 对象、Todo 页面或 Task/Todo 双轨流程。
- Task Folder、以文件夹组织任务或新建时选择目录。
- 独立团队文件一级模块。
- 看板作为主要推进方式。
- Task 详情“概览”页签或新增独立诊断页。
- 逐项 Task Responsibility 的创建和详情分配界面。
- AI 自动选择并指派协作者。
- 用活动量、在线时长、历史速度或伪精确空闲率评价成员。
- 自动业务验收、自动关闭 Task 或把 AI 自报完成当作结果完成。
- 当前未确认的 Handoff、Result Return、团队动态一级入口和云 Agent 长期运行。

## 3. 核心业务闭环

```text
工作意图
  → P1 意图进入
  → P2 任务成形
  → P3 责任与协作边界确认
  → P4 围绕任务执行
  → P5 基于证据判断状态
  → P6 结果收口与事实沉淀
```

这六个流程阶段描述工作如何发生。任务列表、创建页、任务详情、“我的工作”和设置只是流程的界面投影，不是彼此独立的业务系统。

| 阶段 | 输入 | 核心判断 | 输出 |
| --- | --- | --- | --- |
| P1 意图进入 | 原始需求与当前团队上下文 | 信息是否足够，是否属于新建 Task | 已澄清的工作意图或明确的不可处理结果 |
| P2 任务成形 | 已澄清意图与可见已有任务 | 简单／复杂、父子结构、关系与依赖 | 可编辑、尚未正式写入的 Task 候选 |
| P3 责任边界 | Task 候选、成员与责任证据 | 直接分配或未分配 | 正式 Task 及明确的责任状态 |
| P4 围绕任务执行 | 正式 Task 与有权可见上下文 | 交流、拆分、文件和变更应进入哪个事实对象 | 讨论、子结果、文件成果与活动事实 |
| P5 证据判断 | Task、讨论、文件、活动和有效历史 | 哪些是事实、风险、下一步和优先事项 | 不覆盖原事实的当前情况与个人排序 |
| P6 结果收口 | 完成标准、交付、状态与确认记录 | 结果是否足以由有权人确认 | 可复核、可继续使用的结果事实 |

## 4. 核心对象与全局不变量

### 4.1 Task

Task 是当前产品唯一行动对象，表示需要持续跟进的工作结果。

| 字段 | 业务含义 | 当前规则 |
| --- | --- | --- |
| `id` | 稳定身份 | 同一 Task 在所有投影中保持同一 ID |
| `name` | 快速识别的动作标题 | 不得直接复制目标全文 |
| `goal` | 希望改变的结果与范围 | 子 Task 可以继承父目标，但保留自己的独立结果 |
| `completionCriteria[]` | 可核对的完成边界 | 可以为空；为空不自动补演示标准 |
| `ownerId` | 当前正式结果负责人 | `0..1`，不得出现多 Owner |
| `participantIds[]` | 当前参与关系 | 不产生 Owner、责任或权限 |
| `parentTaskId` | 直属父 Task | `0..1`；父子使用同一种 Task 对象 |
| `dependsOnTaskIds[]` | 前置依赖 | 只能引用有效、可见且不形成循环的 Task |
| `plannedStartOn/plannedEndOn` | 可选计划周期 | 同时为空或同时存在，结束不得早于开始 |
| `status` | 当前任务状态 | 使用同一真实状态源，不由工时或 AI 建议反写 |
| `labels[]` | 扁平分类 | 无标签组；可选；不替代层级或状态 |

### 4.2 全局不变量

以下规则适用于全部流程：

1. Task 是唯一行动对象，子 Task 仍是 Task。
2. 每个 Task 的正式 Owner 数量为 `0..1`。
3. 创建者、Owner、参与者、团队受邀人和被推荐人是不同关系。
4. 推荐不等于选择；团队邀请不等于加入。创建用户确认并成功保存任务后，所选当前团队成员直接成为 Owner 或参与者，不再增加任务内二次接受。
5. 没有足够责任证据时允许未分配，不能默认回填创建者或首位成员。
6. Owner 变化必须由有编辑权限的用户明确保存并通过版本校验，不能由推荐、阅读或邀请动作暗改。
7. 文件引用不复制文件、不自动扩大权限。
8. 讨论只承载人的交流；活动只承载任务变更事实。
9. 派生判断不得覆盖原始任务、文件、讨论或活动事实。
10. AI 可以理解、建议、起草和解释；不能替人承诺、接受、验收或扩大授权。
11. 未知不是零，无证据不是正常，无权读取不是没有风险。
12. Mock、示例、当前代码存在和生产可用必须分别表达。

## 5. P1：工作意图进入

### 5.1 流程目标

把用户的自然语言需求转换为可以继续分析的工作意图，同时避免在信息不足或意图不属于创建时误建 Task。

### 5.2 触发与输入

- 触发：用户在任务工作区选择“新建”，或从允许创建子 Task 的上下文进入。
- 输入：原始需求文本、当前团队、当前成员、可见已有任务、当前日期、可用标签。
- 当前范围：只处理新建 Task；修改已有 Task 和查询任务不通过本创建流程伪装实现。

### 5.3 主流程

1. 用户输入希望完成的事情。
2. 系统保留原文，并判断是否具备形成候选方案的最小信息。
3. 信息不足且会改变目标或交付时，最多提出两个关键问题。
4. 用户回答后重新生成候选；未回答的信息保持未知。
5. 无法处理时保留原文、说明原因并允许用户返回修改，不生成假方案。

### 5.4 确定规则

| ID | 规则 |
| --- | --- |
| P1-R01 | 不为了表单完整而追问；只有会改变目标、交付或结构的信息才补问 |
| P1-R02 | 单轮最多展示两个关键问题，问题必须说明要确认的业务含义 |
| P1-R03 | “不知道”“待定”等回答继续表示未知，不得被当成有效事实 |
| P1-R04 | 原始需求在停止、失败和返回修改后仍保留 |
| P1-R05 | 未调用真实检索时不得展示“已查重”“已核对全团队任务” |
| P1-R06 | 当前团队和成员上下文变化后，旧分析结果必须失效或重新核对 |

### 5.5 状态与异常

| 状态 | 产品行为 |
| --- | --- |
| 空白 | 展示输入和明确发起动作，不生成空候选 |
| 分析中 | 只显示实际到达的步骤；未执行步骤不显示占位完成态 |
| 待补充 | 保留原始输入，展示最多两个关键问题 |
| 停止 | 只保留实际发生的步骤，不补出未来步骤或成功回复 |
| 失败 | 说明失败边界，原文和已确认回答不丢失 |
| 不可处理 | 明确未生成方案，不清空输入或假装创建成功 |

### 5.6 验收标准

- 给定信息充分的代表性输入，用户能够进入候选方案审阅。
- 给定目标或交付缺失的输入，只询问会改变方案的关键问题。
- 给定未知输入、无效日期或上下文变化，系统保留原文并明确没有生成正式 Task。
- 停止生成后，不显示未到达步骤、成功回复或已完成标记。

## 6. P2：任务成形

### 6.1 流程目标

把已理解的工作意图整理为可编辑的 Task 候选，明确目标、完成边界、必要结构和关系，但不直接正式写入。

### 6.2 核心判断

#### 简单任务

当工作可以由一个结果对象持续跟进，不需要独立责任、独立上下文或独立验收时，生成一个 Task，不为“看起来完整”机械拆分。

#### 复杂任务

当工作包含多个可独立交付、可由不同人负责或存在真实前置关系的结果时，生成一个父 Task 和一层可编辑子 Task。子 Task 后续仍可继续拆分，领域模型不限制深度。

### 6.3 主流程

1. 生成主 Task 候选：名称、目标、完成标准、负责人建议、参与人、可选周期、标签和执行建议。
2. 必要时生成一层子 Task 候选，每项具有独立名称、完成标准、负责人建议和前置关系。
3. 检查是否存在可见的相似任务或可能的父 Task。
4. 让用户选择查看已有任务、关联为子 Task 或继续独立创建。
5. 用户可以直接编辑候选字段，或通过“AI 帮你改”查看差异后应用到草稿。
6. 系统在确认前校验字段、人员、日期、依赖和范围。

### 6.4 确定规则

| ID | 规则 |
| --- | --- |
| P2-R01 | 名称用于识别，目标用于说明结果，两者不能由系统填成相同句子 |
| P2-R02 | 完成标准允许多条，也允许显式为空；不得用演示标准回填真实任务 |
| P2-R03 | 计划周期可选；设置时开始和结束必须成对，结束不得早于开始 |
| P2-R04 | 子 Task 按独立结果拆分，不使用固定“分析／执行／验收”模板 |
| P2-R05 | 父子只通过 `parentTaskId` 表达，目录和标签都不能代替父子关系 |
| P2-R06 | 依赖必须使用稳定 Task 标识；排序变化不能改变依赖对象 |
| P2-R07 | 文件始终可选；父 Task 与各子 Task 的文件候选和选择不自动继承 |
| P2-R08 | 关系候选只是建议；用户确认前不得修改已有任务 |
| P2-R09 | AI 调整先显示目标范围和字段差异，用户明确应用后才修改当前草稿 |
| P2-R10 | 创建阶段 EWD 表示约定工具方式下的预计人类投入，不是工期、剩余投入或个人效率 |

### 6.5 候选校验

确认前至少校验：

- Task 名称非空且可以识别。
- 人员 ID 属于当前成员上下文，或保持未分配。
- Owner 不重复出现在 Participant 中。
- 日期成对且顺序有效。
- 子 Task 截止不与父 Task 截止形成明显矛盾。
- 依赖不自指、不悬空、不重复、不形成已知循环。
- 关联父 Task 仍存在、可见且目标版本未发生影响继承的变化。
- EWD 存在时包含有效口径、范围键、来源和版本。

### 6.6 验收标准

- 简单输入只生成一个 Task 候选。
- 复杂输入按独立结果生成父 Task 与必要子 Task，不自动串行可并行工作。
- 用户调整顺序后，依赖仍指向原 Task。
- 关系候选失效或重名无法唯一定位时，系统阻止关联并保留原方案。
- AI 调整未明确应用前，候选字段不发生变化。

## 7. P3：责任与协作边界确认

### 7.1 流程目标

让用户在正式创建前看清谁负责、谁参与；确认写入后人员关系直接生效，在责任证据不足时允许安全地保持未分配。

### 7.2 责任语义

| 关系 | 何时成立 | 是否表示正式 Owner | 是否自动产生权限 |
| --- | --- | --- | --- |
| 推荐人选 | AI 或规则提出候选 | 否 | 否 |
| 用户选择 | 用户把候选放入草稿 | 否 | 否 |
| 团队邀请 | 向尚未加入团队的人发出邀请 | 否 | 否 |
| Owner 候选 | AI 或用户在草稿中选择负责人 | 否，写入前仍是候选 | 否 |
| 正式 Owner | 创建用户确认并成功写入，或有编辑权限的用户保存变更 | 是，最多一人 | 仍需单独权限判断 |
| Participant | 已建立参与关系 | 否 | 不得作为权限捷径 |

### 7.3 主流程

1. 用户审阅主 Task 与全部子 Task 的责任状态。
2. 当前用户选择本人或其他当前团队成员负责时，确认并成功写入后直接成为该 Task Owner。
3. 任务内不生成负责人提议、待接受状态或接收方二次确认步骤。
4. 没有足够人选或用户选择暂不分配时，以空 `ownerId` 创建。
5. 整份方案只聚合提示一次未分配 Task 数量，不逐项制造阻断告警。
6. 人员搜索输入完整有效邮箱且无匹配时，可直接邀请并回填本次人员选择。该记录显示「待加入」；尚未加入团队前只记录草稿人选，不认定为任务成员。独立团队邀请不回填 Task 关系。
7. 用户确认当前方案后，系统才正式写入 Task。

### 7.4 确定规则

| ID | 规则 |
| --- | --- |
| P3-R01 | 正式 Task 的 Owner 基数是 `0..1`，不是强制一人，也不是多人共同 Owner |
| P3-R02 | 不得默认把创建者、首位成员或被邀请者填为 Owner |
| P3-R03 | 未分配不阻断创建，但必须在可找回的任务索引中保留 |
| P3-R04 | 本人创建且未分配的 Task 进入“待确认负责人”分组，不进入正式负责任务范围 |
| P3-R05 | 经创建用户确认并成功写入后，选定 Owner 直接进入“我的工作”排序和连接 AI 的负责任务快照 |
| P3-R06 | 独立团队邀请不写入 Task；选择器中的「邀请并选中」可回填本次草稿人选，成员加入团队后仍须由创建用户确认方案并成功写入 Task |
| P3-R07 | 有编辑权限的用户保存 Owner 变化后直接生效并记录任务活动；生产端仍须执行权限与版本校验 |
| P3-R08 | 创建者事实独立保存，不因 Owner 变化而重写 |
| P3-R09 | 创建者与本项负责人人选不同时（含负责人待定），默认加入本项参与人；同人不重复加入。主任务和子任务分别判断，保留其他参与人并去重。默认值在确认前可见，用户可调整，保存时不覆盖已确认的参与人选择。 |

### 7.5 正式写入

当前本地原型在用户最终确认后把 Task 写入浏览器本机存储。研发和测试必须把以下两件事分开：

- “本地创建成功”：本机数据已写入，可在当前原型重新打开。
- “生产创建成功”：可信身份、服务端校验、持久幂等、原子父子写入和跨端重读全部成功。

当前 PRD 不允许用前者的成功提示宣称后者已经实现。

### 7.6 验收标准

- 无 Owner 的主 Task 和子 Task均可创建，且不会自动回填成员。
- 选择当前团队成员时保存为正式 Owner，不区分当前用户或其他成员，也不生成二次接受。
- 正式负责人和参与人的头像不显示绿色“已接受”角标；尚未加入团队的成员仍保留团队邀请状态提示。
- 从设置独立邀请新成员不改变 Task；从人员选择器邀请只回填当前草稿选择，对方加入团队不会自动创建或修改任务，仍以创建用户最终确认的方案为准。
- 未分配 Task 可以从“待确认负责人”范围找回，但不进入“我的工作”。
- 最终确认前，刷新或返回不会出现正式 Task 副作用。

## 8. P4：围绕任务执行

### 8.1 流程目标

让有权限的成员围绕同一个 Task 进行交流、拆分、文件协作和变更追踪，不把不同性质的信息混成一条动态流。

### 8.2 Task 工作区结构

Task 详情由头部任务定义和四个内容页签组成：

1. 讨论：默认页签，只承载人的交流。
2. 子任务：承载直属子 Task 及其生命周期入口。
3. 文件：承载当前 Task 有权可见的文件与引用。
4. 活动：只读展示任务变更事实。

不提供“概览”页签。当前情况位于页签之前，不与任何页签重复。

### 8.3 讨论

- 本次“动态”指当前 Task 的成员发言，复用讨论页签；系统活动继续只读，不新增团队广播入口。
- 展示动态、评论、回复、@ 和附件／文件引用。回复具体评论或回复时保存被回复消息 ID，始终在同一根讨论串中，仅缩进一层；动态不提供单独的“引用”操作，也不重复展示原消息摘录；回复头部以相同字号同排展示“周岚 回复 陈默”；正文及附件位于下方，再显示保存的发布时间（YYYY-MM-DD HH:mm）和回复操作；点击回复对象定位被回复消息。时间按 Asia/Shanghai 展示，编辑不替换原发布时间，不显示“原时间”或相对时间。预置演示消息使用固定示例日期，真实旧记录缺失时间时不推算。文件讨论原文锚点仍保留。
- 讨论计数为当前可见、未删除的任务讨论消息总数（包含评论和回复）；文件讨论在文件右侧单独计数，不包含系统变更或自动 AI 建议。
- 发布正文或纯附件动态；输入框统一使用“附件”下拉，其中“上传本地文件”选择电脑文件，“从文件列表选择”支持多级文件夹分组，并可按文件名／文件夹名称跨层级搜索，结果显示完整所属路径以区分同名文件，清空恢复层级浏览；点选文件即加入草稿、收起菜单并回到正文，已添加文件勾选且不可重复选择，不在输入框内展开大面板。本地文件发布后自动加入任务文件列表，已有文件复用同一 File ID、不重复上传；也支持拖入文件、粘贴图片。上传成功不等于消息发布，确认保存后才同时建立消息附件与任务文件关系；失败保留草稿，重试幂等。
- 可编辑／删除自己的消息、取消回复对象、移除提及／草稿附件、展开回复、复制定位链接。删除后从列表隐藏，不保留“已删除”占位，计数只含未删除消息；保留回复关系和未删除回复，整串无消息时隐藏讨论组及文件原文标记，不连带删他人回复或已归档文件。
- @ 只选择当前上下文可访问的已加入成员，使用稳定 ID；不自动授权。回复通知被回复者，普通评论通知根作者，合并本条 @ 并排除自己、去重；不默认通知全 Task，也不将已读当作同意。
- Enter 换行，⌘／Ctrl + Enter 提交，中文输入组合中不提交；发送中禁重复、失败可重试，并发修改保留草稿供核对。草稿按用户／团队／Task／串隔离，首版会话内保存范围明确。
- 讨论中的“连接 AI”只带入当前选定讨论及必要上文，不代表 AI 已连接或已写回。
- AI 产出若需要成为团队事实，必须通过正式任务字段、文件、讨论或活动对应的明确动作进入。

### 8.4 子任务

- 子任务页签展示直属子 Task 数量。
- 列表每项只显示图标、名称和负责人；名称是进入详情的入口。
- 子任务只显示正式负责人；未分配保持未分配，不显示任务内待接受候选人。
- 列表不重复展示状态、截止、完成标准、依赖、箭头或行内菜单。
- 页签头部保留整体 AI 调整和新增入口。
- 手工新增子 Task 至少需要名称和一条非空完成标准；不自动继承父任务负责人或参与人；本项创建者按 P3-R09 默认参与。
- 删除 Task 前展示影响范围；主任务下的全部子任务一并删除。助手预览默认展开子任务名单，数量只在标题展示，去掉「将删除 N 项任务」段落；确认按钮统一为「确认删除」。删除完成后刷新不恢复该任务树。

### 8.5 文件

- 只展示当前 Task 中按权限有权可见的文件与引用。
- 任务内文件夹只负责组织，不改变 File 身份或权限。
- 引用已有文件使用同一个 File ID，不复制内容。
- 固定版本和跟随最新必须区分；版本变化时旧引用不能无提示漂移。
- 当前 Demo 的文件树、消息及附件关系按团队／Task 保存在同一份 localStorage 快照，真实上传原文件二进制保存在 IndexedDB，刷新可恢复；这不代表生产 FileVersion 写入服务。
- **本轮用户方向：** 选择已保存版本的原文 → “评论” → 填写讨论 → “确认”。确认只保存文件评论，成功后仍留在文件并打开右侧讨论栏；不自动发到任务动态，不自动修改正文或验收任务。顶部移除“下载”“添加评论”和评论操作说明，仅保留“查看讨论 N”进入右侧串，正文选区“评论”及正文标记继续使用；整文件评论从右侧面板内进入。顶部文件标题／路径与正文左侧对齐。
- 完整讨论与结论保存在当前 `Task + File` 的串中；原文标记与右侧串双向定位，支持回复、回复某条回复、@ 和附件。文件改名／移动不改变关联；跨 Task 引用不自动共享讨论。
- **设计默认：** 右侧提供未解决／已解决／全部；根作者或有讨论管理权的人可标记已解决、重新打开，记录操作者和时间。已解决不删除历史、不代表文件获批；纳入正文仍需文件编辑权及“编辑 → 保存”新版本。
- 评论绑定源 FileVersion 与原文快照。阅读和编辑状态均支持选区；有未保存修改时先显式“保存文件并评论”，成功后绑定新版本，失败保留文件草稿和选区、不创建评论。旧片段不在新版猜测位置。Markdown／纯文本及 PDF 提取正文支持片段讨论，PDF 保存页码和页内范围，相同文字不跨页匹配；其他格式支持整文件讨论。
- **附件默认：** 发布动态／评论／文件讨论后，附件自动进入本 Task 文件列表；未归属文件放根目录，已有文件保持位置。手动上传和引用已有文件继续可用。Task + File 位置唯一，消息固定版本；重复引用不复制内容，不按同名合并新上传。
- 删除消息或移除其附件不删任务文件；删除文件是单独动作并列明影响。文件来源可返回原动态／评论，撤权后的附件、引用和通知统一显示不可用。
- **当前 Demo（2026-09-15）：** 已接入 Lexical 0.50.0（Meta，MIT）的讨论输入、文本及 PDF 提取正文阅读与 MarkNode 划词高亮；阅读／编辑选区、确认后查看回复及回复再回复、关闭重开与刷新恢复已接通；“确认”仅保存到文件右栏。稳定 ID 的 @、具体回复／文件内引用、作者编辑／删除、解决／重开、附件自动入列表、手动上传和已有文件选择均已接入本地保存，消息与文件列表共用同一 File ID，保存固定源版本。
- **实现缺口：** 尚无服务端 ACL、多人同步或外部通知；仅保存本地通知记录，现有全局通知 UI 未接入。旧版全文快照预览未实现，保存引用 vN／原文并明确显示当前最新正文；真实上传的 DOCX／XLSX 等未解析，只支持原文件下载，未提取正文的真实 PDF 由浏览器预览，仅支持整文件讨论。上述目标权限与历史版本要求继续保留。
- 最小数据：串含 scope／Task／File／源版本／锚点／解决状态；消息含回复对象、正文、提及、修订；附件含固定文件版本、唯一任务位置和来源；提交及通知均有幂等标识。不得将 Lexical 运行时 NodeKey 或屏幕坐标作为持久锚点。

### 8.6 活动

- 活动记录状态、周期、人员、完成标准、字段或文件等任务变更。
- 每条记录包含操作者、具体动作、时间和有意义的前后值。
- 无实际变化不新增活动。
- Owner 和参与人修改成功后直接记录为人员变更活动；保存失败或版本冲突不得伪报责任已经变更。
- 删除或隐藏可读展示不能删除正式审计事实。
- 文件评论、回复和解决状态仅展示于文件内，底层保留审计，不生成任务动态或可见活动条目；本次局部替代所有讨论均投影活动的旧默认。任务动态／评论仍可生成摘要，实际附件上传与文件更新仍可生成文件活动；都只在正式保存成功后发生。

### 8.7 验收标准

- 打开 Task 默认进入讨论，且活动消息不会计入讨论数量。
- 新增、编辑或删除子 Task 后，父 Task 的直属数量和列表同步更新。
- 子任务列表显示保存后的正式负责人，未分配状态可辨。
- 文件引用不改变源文件 ID，也不会因放入 Task 自动扩大可见范围。
- 字段值没有变化时，不生成伪变更活动。
- 文件选区评论点击“确认”后出现于右侧，可定位原文，任务讨论计数及动态不增加；解决串不改变任务状态。原文变版后正确提示源版本；无权来源不泄露。
- 回复某条回复仍在原串内，作者与引用目标准确；@ 与回复同一人只通知一次，编辑不重复通知，失败／结果未知不重复提交。
- 动态附件与文件列表使用相同 File／固定版本；重复引用不增加文件数，手动上传仍可用；删除评论保留文件，删除文件保留消息和回复关系。
- 空、加载、失败、无评论权、原文过期分别呈现；窄屏讨论全屏打开并可恢复文件阅读位置，键盘可选区评论、提及、回复、取消并恢复焦点。

## 9. P5：基于证据判断状态

### 9.1 流程目标

让成员回答两个问题：当前 Task 发生了什么；本人现在应该优先关注什么。

### 9.2 Task 当前情况

所有 Task 在内容页签前按以下结构呈现：

| 区域 | 回答的问题 | 内容边界 |
| --- | --- | --- |
| 当前情况 | 现在发生了什么 | 摘要、已完成事实、差距、近期变化、风险或阻塞 |
| 下一步建议 | 可以怎样继续 | 有依据的候选行动，不形成自动指派 |
| 完成进度 | 已核验范围完成多少 | 现有账本按有效历史展示；内容与时间的新设计见 9.3，不能混读 |

确定规则：

- TaskStatus 只在任务属性中维护，不在现状区重复。
- 当前情况和下一步建议必须基于有权可见事实；有分析截至时间时标明，标题旁不展示最近讨论时间。
- 证据变化后，旧判断标记过期或回退为可核事实。
- 没有证据时表达未知，不生成“运行正常”或默认摘要。
- 下一步建议是候选行动，不修改 Owner、状态、周期或子任务。

任务详情将「当前情况与下一步建议」和「AI 预测」合并为一个默认收起的「AI分析」区域；一次展开即可查看当前情况、下一步建议、完成进度和燃起图，内部不再设置独立的预测折叠入口。展开后，标题右侧提供「重新分析」，统一重读任务协作记录、刷新当前情况和下一步建议，并重新核对进度预测。已完成或已取消的任务仍可刷新文字分析，保留确认或取消时的进度。

### 9.3 完成进度

**当前口径（2026-09-14）：** 用户只有任务状态与截止时间，没有工作排期，不手填百分比。过程完成度标为紫色 AI 预测，不能称实际进度；用户标记已完成保存成功后，立即显示 100% 用户确认，确认日期替代未来 AI 日期。预测 100% 不自动完成任务。取消计划应完成刻度、工作量差额及符合预期。

用户确认不覆盖 AI 原预测：主显示 100% 用户确认，原始数据独立保存确认前 AI 百分比、时间和依据，不在组件内展开；子任务同理。只有确认后的新证据复核才可能提示核对，旧百分比差异不视为冲突；先后不明或记录缺失要明确说明。规则见 [确认后保留 AI 预测](./PRD-AgentDoor-协作任务全流程.md#progress-ai-retention)。

主子任务共用组件；子项缩小但保持自己的来源、状态与日期，父子不级联关闭。上方为单条完成度与来源，不在右侧显示截至日。预测摘要（包括子任务汇总）统一为紫色「AI 预测」，汇总口径和记录时间保留在结果数据中。主任务时间对比合入下方燃起图：灰色截止竖线、紫色 AI 预测虚竖线、蓝色确认完成竖线；同日来源用「｜」分隔、日期一次。截止／预测日期说明放在图下，图内上沿用连接线对比计划与预测日期，差值显示「+N 天／−N 天／按期」，正数延期、负数提前；间距不足时文字放在线上方，日期位置不变。数据截至日仅保留下方日期与曲线端点，不画常驻灰色竖虚线。子任务保留较小日期轴。完整组件为完成进度、子任务分布和燃起图；移除计算明细及展开内容，进度说明只保留计算公式与用户确认规则；历史完成量注明 AI 预测／用户确认来源。总工作量用中性灰细线和空心节点，完成量用蓝色粗线和实心节点，AI 预测完成日用紫色竖虚线和独立方点；图例同步标记样式。从当前完成点接紫色阶梯虚线，按独立保存的未来交付节点增长，等待阶段持平，最后在预计完成日达到当日预计总量。当前总量向未来接灰色虚线，覆盖截止日与预测完成日；无预计新增时保持水平，有依据的范围变化按节点升降，不改写历史或当前进度。只有完工日期时仅标日期，不插值生成逐日进度。一次历史评估只保留工作量点，图下不追加说明文字，仍可展示独立未来节点。上沿连接线仅表达日期差，预测方点不作为已完成记录。

**样式与示例同步（2026-09-15）：** Demo 与 PRD 的 AI 来源文字、预测日期和预测图例统一紫色；用户确认保留原来源，子任务汇总口径保留在结果数据中；提前／延期文字保留各自语义色。内置任务已补齐有核对依据的固定预测，真正缺少依据的任务保留未知；预测不由状态或截止时间生成。完整示例范围与缺失规则统一维护于 [任务进度模块](./PRD-AgentDoor-协作任务全流程.md#task-progress-design)。

**时间 Mock 覆盖（2026-09-16）：** 220 个内置任务中，190 个有完工预测，18 个已完成、1 个已取消，7 个因明确依赖缺口无完工日期，4 个无进度数据。常规任务配齐工作量、预测日期和执行时间假设，日期不得早于未完成的前置任务；不从截止倒推、不按状态补百分比。库存核对保留待开始与 40%，预测 9/17 完成。详细样例与缺失名单统一维护于任务进度模块。

**未来预测趋势（2026-09-16）：** 190 个有完工日期的内置任务同步提供未来节点，父任务按子项节点汇总。交付节点包含日期、累计完成量与依据；预计范围变化单独保存日期、总量与依据。两者关联同一观察日、起点与范围版本，完成量不得超过当日预计总量，完工时达到预计总量；失配不画对应趋势。父级分别汇总子项未来总量与完成量。库存示例为当前 40% → 9/15 等待 40% → 9/16 初核 70% → 9/17 收口 100%。这组数据是演示预测，不属于历史记录；用户确认完成后退出未来曲线。另有封面制作示例：当前总量 4 人时，9/15 预计新增横版适配 1 人时，9/16 预测完成量达到 5 人时；当前百分比与历史总量保留。

**燃起图完整性（2026-09-16）：** 常规 Mock 补齐历史观察并逐日汇总父任务；215 个任务有多次历史，1 个保留单次观察，4 个无数据。图例显示最近记录的总量与完成量数值；总量与完成量重合时用灰色外沿、蓝色内线和同心端点区分，不改坐标。现有百分比与 190 个未来预测不变；仅有一次记录的真实任务仍不自动补造历史。

燃起图节点支持悬停和键盘聚焦：浮层显示日期与该点工作量，AI 预测节点以紫色标明预测；有时间戳才显示具体时间。同位置的总量与完成量合并提示，移开、失焦或按 Escape 关闭。

**状态与评估独立：** 待开始也可已有产出。总量按范围、完成量按产出内容评估，不按状态或文件数量折算；仅在待开始、进行中、已阻塞之间切换，原百分比、历史与有效完工预测不变。Demo 行动项保留待开始与 50% AI 预测；单次评估保留工作量点，不补造历史。当前情况提示核对已有文件，不写成尚无产出。

**创建总量：** 燃起图从任务创建日期开始，延伸至截止与预测／确认日期。创建时的预估人天就是首条总工作量记录，有预测和无预测都要展示；一次进度观察也保留创建至观察日的总量线。完成量从首条有依据的记录开始，不倒填创建值。暂无进度预测时仍展示灰色总量线／点；无负责人或截止不影响总量。后续估算保留初始值，未知完成量不补成零。

**更新触发：** 状态保存成功先处理事实；产出或标准变化触发受影响内容预测，剩余工作／依赖变化触发时间预测；修改、清空或恢复截止不改变完成百分比和 AI 预测日期，不触发重预测，只更新日期差；跨日只更新到期事实。重开后旧确认退出当前值，自动恢复同范围下独立保存的 AI 评估与有效完工预测；旧 AI 返回不能覆盖用户确认。完成进度标题右侧「重新预测」在 Demo 中重新核对固定评估和当前子任务确认，保存结果；无新证据可保持相同数值，缺少依据或保存失败明确提示并支持重试。详细状态与触发唯一维护于 [文字 PRD 第 6.3 节](./PRD-AgentDoor-协作任务全流程.md#progress-component-events)。

Demo／PRD 固定样例和本地状态展示已接入，实时 AI 队列、跨端版本校验、独立时间戳与正式历史账本仍待接入。本次替代旧工作排期基线设计，不改写历史会议记录。

### 9.4 “我的工作”

"我的工作"是当前用户负责任务的个人排序投影，不是第二套任务系统。

每条只展示：

1. 连续顺位。
2. 任务名称；名称是进入该 Task 详情的唯一入口。
3. 一句优先原因；只回答为什么排在这里。

范围与排序规则：

- 数据范围是当前用户全部负责任务，不受左侧搜索、状态、标签筛选或分组折叠影响。
- 未分配 Task 不进入范围；任务人员不再存在待接受提议。
- 同一 Task ID 只出现一次。
- 排序可以使用真实状态、期限、依赖、完成标准和权限内的讨论、活动及文件。
- 资料不足、过期或受限若会影响顺位，只在优先原因中简短表达“信息不足”或“待核对”。
- 不在任务行展示状态、当前情况、下一步建议、依据明细或其他对象深链。
- 数据层继续保留经过权限过滤的来源引用、版本、输入快照时间和权限决定，用于失效判断和审计。
- 排序输入实际变化才更新时间；页面打开、重绘或无变化刷新不得制造新时间。

“AI 分析规则”默认收起，只解释“排序”和“范围”，不设置虚构的“生成”能力说明。

### 9.5 验收标准

- 无历史的 Task 不显示 0% 或空燃起图容器。
- 使用固定账本 `2h / 7h` 时显示 28.6%，而不是按完成 Task 数量计算。
- 改变页面筛选不改变“我的工作”的底层正式负责任务范围。
- 相同 Task 因多个规则命中时仍只出现一次。
- 未分配 Task 不进入“我的工作”；新分配 Owner 在保存成功后直接进入。
- 只有排序输入变化时，更新时间才变化。

## 10. P6：结果收口与事实沉淀

### 10.1 流程目标

让工作结果以可以复核、继续使用且不改写历史的形式留在 Task 中。

### 10.2 当前收口方式

当前产品通过以下事实共同表达结果：

- Task 当前状态。
- 完成标准及其当前版本。
- Task 文件和明确引用的文件版本。
- 人的讨论和确认。
- 任务字段及人员变更活动。
- 显式提供时的 EWD 范围与已验收历史。

这些事实可以支持人判断工作是否完成，但当前产品不建立新的 AI 审批状态机，也不允许 AI 自动执行业务验收。

### 10.3 确定规则

| ID | 规则 |
| --- | --- |
| P6-R01 | AI 报告“已完成”只能作为待核对声明，不能直接成为业务验收 |
| P6-R02 | 状态“已完成”不能未经规则映射自动生成已验收 EWD 历史 |
| P6-R03 | 文件成果必须引用明确 File 和版本，不能只记录一个不可定位的名称 |
| P6-R04 | 活动保留谁在何时改变了什么；撤销不能通过删除历史实现 |
| P6-R05 | 结果事实与权限分开；看到结果名称不代表可以读取正文 |
| P6-R06 | 父 Task 的结果责任不因子 Task 完成而自动消失 |

### 10.4 当前边界

人与人的 Handoff、Responsibility 转移和 Result Return 仍是后续方向，但不得恢复任务人员的二次接受流程。当前 Task Owner 由有编辑权限的用户保存后直接生效并记录活动；更广义的结果交接仍不得由发送、阅读或邀请动作暗中触发。

### 10.5 验收标准

- AI 或外部工具的完成声明不会直接修改业务验收和完成进度。
- 文件版本变化后，引用能够区分固定旧版与跟随最新版。
- 子 Task 全部完成不会自动关闭父 Task。
- 相同变更重试不会生成重复可见活动；生产实现还必须具备持久幂等。

## 11. 四类跨流程底层能力

### 11.1 B1：统一 Task 模型

- Task 是唯一业务行动对象。
- 父子 Task 使用同一 Schema，通过 `parentTaskId` 建立直属关系。
- 每层 Task 独立维护名称、完成标准、Owner、参与者、周期、状态、标签、文件和活动。
- 父子不自动继承人员、文件引用或权限。
- 父 Task 的汇总是派生投影，不覆盖子 Task 原始事实。

### 11.2 B2：身份、团队与权限

当前本地原型提供团队切换、成员和设置投影，但不代表生产身份与 ACL 已接入。生产实现必须满足：

1. 每次读写使用可信 Principal，而不是相信客户端提交的成员 ID。
2. 先做权限过滤，再进行检索、AI 分析或聚合。
3. 无权对象不能以标题、数量、状态、缓存内容或“存在一个秘密任务”等形式泄露。
4. Participant、责任说明、能力画像和被推荐状态都不能产生权限。
5. 授权撤销或过期后，后续读取与写入立即重新判定。
6. 前端隐藏按钮不是权限控制。

### 11.3 B3：证据、版本与活动

- AI 判断、当前情况和个人排序必须记录输入快照时间和可追溯来源。
- 文件内容通过 FileVersion 表达，不原地改写历史版本。
- 完成标准、EWD 和责任说明的正式更新必须保留版本与操作者。
- 活动供成员阅读；生产审计必须使用不可改写的正式变更记录，二者不能混为一体。
- 证据被删除、撤权或更新后，旧判断必须失效，不得继续以当前事实展示。

### 11.4 B4：AI 行动边界

| AI 可以 | AI 不可以 |
| --- | --- |
| 理解需求并提出关键问题 | 在信息不足时补造目标、期限或负责人 |
| 生成和调整候选草稿 | 未经确认创建正式 Task |
| 提出负责人或协作候选 | 自动指派或替目标成员接受 |
| 汇总有权可见的当前情况 | 把受限对象、旧缓存或推断写成事实 |
| 给出下一步和个人排序建议 | 自动修改状态、Owner、周期或业务验收 |
| 帮助连接个人工具并准备上下文 | 把复制内容或唤起客户端声称为真实连接成功 |

所有 AI 输出都要满足：

- 事实、推断、建议和已确认决定分开表达。
- 显示能力边界和必要的数据新鲜度。
- 正式写入前展示目标对象和变化范围。
- 停止或失败时不伪造剩余步骤、工具调用或成功结果。
- 不展示模型内部思维链、系统提示或隐藏日志；只展示用户可核查的动作摘要。

## 13. 设置与责任说明

设置是底层团队上下文的维护界面，不是第七条业务流程。

### 13.1 导航

- 个人设置：个人信息、我的责任。
- 团队设置：团队信息、成员。
- “我的责任”虽然位于个人设置，数据仍绑定当前 Team。
- 责任页的 Team Select 与应用 `activeTeamId` 使用同一真相，切换前保护未保存草稿。

### 13.2 团队和成员

- 团队信息允许修改名称，并对离开或删除执行二次确认。
- 至少保留一个 Team。
- 成员支持邀请链接、邮箱邀请和管理员／成员角色切换。
- 至少保留一名在职管理员。
- 当前写入只保存到浏览器本机，不代表真实邮件、生产 membership 或组织删除。

### 13.2.1 人员搜索邀请与邮件模板（2026-09-14 修订）

- 人员搜索下拉和「设置 → 成员」共用「邀请人员」弹窗。名称或邮箱无匹配时，下拉只提供邀请入口：点击后预填对应字段，明确提交后才创建人员。
- 弹窗提供名称（选填，最多 100 个字符）和邮箱（必填且格式有效）。只有邮箱也能邀请，未完整邮箱可在弹窗内补全；取消不写入、不改变当前选择。
- 从人员下拉进入时，邀请弹窗直接覆盖当前列表，保留搜索内容和结果；取消后返回原搜索框，提交成功后一起收起列表与弹窗并返回人员入口。使用短淡入淡出，关闭完成前保留表单，兼容系统减少动态效果设置。
- 空结果区显示「没有找到匹配的成员」、单行居中的邀请说明和「邀请人员」按钮；有「暂不分配」选项时保留单行，隐藏重复邀请入口。空间不足时说明自然换行。
- 人员列表统一使用「待加入」。设置成员第一行显示名称与状态，名称为空显示「未设置名称」；第二行只显示邮箱，不展示邀请时间。人员下拉无名称时以邮箱识别。对方验证受邀邮箱并明确接受后，原记录更新为账号名称／头像及正式成员状态。
- 提交按 Team＋邮箱查重，不覆盖原名称或重复发信；下拉入口可「使用此成员」回填已有人员，设置入口提示无需重复邀请。待加入人员的操作仅保留「重新邀请」，移除「查看邮件」（2026-09-16 修订）；重新邀请保留人员 ID 和名称、更换 token。保存失败保留表单，发送失败保留待加入记录并允许重试。
- 从人员下拉提交成功后回填本次选择；设置与独立邀请入口不修改 Task。管理员可邀请，设置可选择成员／管理员角色，人员下拉默认普通成员。筛选和提及入口不邀请；加入团队与任务人员分配是两个独立动作。
- 邮件标题为「{{邀请人姓名}} 邀请你加入「{{团队名称}}」｜TaskDoor」，正文包含加入角色、受邀邮箱、注册／登录提示、「接受邀请并加入」按钮及完整链接、到期与忽略说明。
- 模板全文、异常状态、数据依赖和验收项见 [产品 PRD §2.2](./PRD-AgentDoor-协作任务全流程.md#22-邮箱搜索与邀请)。原型采用 7 天有效期，生产有效期与重发频率属于待确认配置。
- Demo 使用「邀请已发送，等待对方加入」「重新邀请」等正式文案。当前支持本机邀请、重新邀请，以及邀请链接对应的同浏览器注册／接受及状态更新；成功提示用于展示运行效果，不是实际发信回执。生产邮件、账号与权限仍待接入，实现说明只保留在研发文档中，正常链接不打开验证码调试模式。

### 13.3 我的责任

- 每个 Team 维护一份纯文本责任说明。
- 阅读态按同权重条目呈现，不把责任说明变成绩效评分。
- AI 可以生成带证据的新增或更新提议，但提议默认不写入。
- “自动更新”勾选项按当前 Team 保存，默认关闭；开启后授权自动应用该团队现有及后续可用的责任新增、更新建议，取消勾选后停止。
- 未开启自动更新时，更新提议通过“AI 建议”展开，只读展示替换文本和依据，成员点击“更新”才写入；新增提议作为只读候选行，成员点击加号才写入。
- 自动更新保留建议依据和变更历史，明确记录自动操作；正在手动编辑时暂停当前团队的自动更新，保存或取消后恢复。无效或冲突建议保留在“AI 建议”中待处理，保存失败保留原内容并支持重试。
- 目标责任已经变化时阻止旧更新提议写入。
- 责任说明和 AI 提议都不能改变 Task Owner、Task 参与关系或授权。
- 当前原型在应用运行期间处理本机已有的责任建议并持久化；本次不新增后台持续分析服务或建议生成链路。

## 14. 统一状态与异常处理

每个可交互流程都必须覆盖以下状态，不能只实现正常态：

| 状态 | 统一要求 |
| --- | --- |
| 正常 | 当前数据、动作和成功结果语义一致 |
| 空 | 说明为什么为空以及用户可执行的最小动作；未知不显示为 0 |
| 加载 | 展示实际进行中的动作，不提前展示成功内容 |
| 失败 | 保留用户输入或草稿，说明失败范围和安全重试方式 |
| 无权限 | 不泄露对象名称、ID、数量、状态或缓存内容 |
| 数据过期 | 标明旧结论失效，不用旧判断覆盖新事实 |
| 冲突 | 保留双方版本，阻止静默覆盖并要求重新核对 |
| 本地存储不可用 | 当前内存会话可继续时明确不可持久化；不得提示已永久保存 |
| 移动端 | 单列阅读，操作允许换行，不产生横向滚动 |
| 键盘 | 可达、焦点可见、Dialog/Popover 关闭后返回触发点，Tab 不进入隐藏内容 |
| 减少动态 | 尊重系统设置，不用动画作为唯一状态表达 |

### 全局操作提示 Toast（2026-09-14）

- 邀请发送、保存、复制、删除／撤销等短时操作反馈统一使用共用 Toast，固定在视口顶部居中；桌面距顶部 24px，窄屏 12px，并避让安全区域。弹窗打开时仍显示在上方，不跟随页面或弹窗滚动。
- 成功、失败、普通说明复用同一尺寸、圆角、阴影与关闭入口，以图标和文案区分；普通提示 4 秒、错误 6 秒、带操作的提示 8 秒自动消失。悬停、键盘聚焦或窗口失焦时暂停倒计时。
- 同一提示重复触发时更新内容并重新计时，不重复堆叠；最多显示 3 条。新提示不抢焦点，F6 可聚焦提示区；关闭和操作按钮支持键盘与至少 44px 触达，窄屏长文案及操作换行，不产生横向滚动。减少动态效果时关闭过渡。
- 邀请成功提示只显示「邀请已发送，等待对方加入」和关闭按钮；重发只显示一条「邀请已重新发送，旧链接已失效」。两者均不提供「查看邮件」，按普通提示 4 秒自动消失（2026-09-15 修订）。文件删除后的「撤销」保持原恢复操作；带上下文的操作在离开对应任务或切换团队后移除，避免操作旧对象。
- 输入校验、草稿冲突、加载及需要持续处理的错误留在相关字段／区域，不用会自动消失的 Toast 替代。界面显示正式运行文案。

## 15. 非功能要求

### 15.1 可访问性

- 所有图标按钮具有完整可访问名称。
- 状态不能只依赖颜色表达。
- Tab、Dialog、Popover、Disclosure 和列表遵循对应键盘模式。
- 页面导航后焦点进入新的主标题或保留合理列表上下文。
- 隐藏页签和未到达生成步骤不进入可访问树。

### 15.2 数据一致性

- 同一 Task ID 在任务列表、我的工作、详情、父子关系和 AI 上下文中读取同一事实。
- 同一 Team 切换状态在顶栏、设置和责任页中保持一致。
- 保存失败不得留下“活动成功、对象失败”或“对象成功、活动失败”的半状态。
- 正式生产写入必须支持持久幂等、版本冲突和失败恢复。

### 15.3 性能与容量

- 任务索引的搜索和筛选不能阻塞当前详情交互。
- “我的工作”投影必须按 Task ID 去重。
- AI 请求只携带完成当前动作所需的最小上下文。
- 当前协议对成员、任务和消息数量设置明确上限；超过时必须截断并向用户说明覆盖范围，不能静默冒充全量分析。

### 15.4 安全与隐私

- 客户端提供的 currentUserId、memberId 或角色不能作为可信授权事实。
- AI 和检索只接收权限过滤后的数据。
- 责任画像、协作窗口和活动数据不得用于个人绩效排名。
- 外部客户端被唤起、内容被复制或弹窗被关闭都不能作为连接、接单或写回成功证据。

## 16. 研发验收矩阵

| 模块 | 最小可交付结果 | 关键反例 | 验收层级 |
| --- | --- | --- | --- |
| P1 意图进入 | 输入、必要补问、停止和失败均保留原文 | 未知输入被生成确定方案 | 本地交互 + 服务集成 |
| P2 任务成形 | 简单／复杂结构、日期、人员和依赖可校验 | 排序后依赖错位；相似任务被自动合并 | 本地逻辑 + 服务集成 |
| P3 责任边界 | Owner `0..1`、已分配与未分配可区分；创建确认后人员直接生效 | 团队邀请未完成就成为 Owner；保存失败仍显示已分配 | 本地逻辑 + 服务端事务 |
| P4 任务执行 | 讨论、子任务、文件、活动边界清楚 | 系统活动计入人的讨论；文件引用扩权 | 本地交互 + 服务端 ACL |
| P5 状态判断 | 当前情况可追溯，完成进度口径正确，个人排序去重 | 无历史显示 0%；未分配进入“我的工作” | 确定性回放 + 用户验证 |
| P6 结果收口 | 状态、证据、版本和活动可复核 | AI 自报直接验收或关闭父 Task | 服务端数据 + 业务验收 |
| B2 权限 | 先过滤再检索，撤权后立即失效 | 模型收到无权对象或泄露数量 | 安全测试 |
| B4 AI 边界 | 正式变化前可见范围并明确确认 | 失败仍显示成功；隐藏思维链被展示 | 协议测试 + 交互测试 |

验收报告必须区分：

- L1：本地逻辑或组件行为成立。
- L2：真实服务、身份、权限和持久化闭环成立。
- L3：目标用户能完成真实业务闭环。

任何 L1 通过都不能被写成 L2 或 L3 已完成。

## 18. 生产化的最小依赖顺序

本节只描述已确认产品表面走向生产所需的技术依赖，不引入未来产品模块。

1. 可信身份、Team、Member 和对象级 ACL。
2. 统一 Task 服务、版本、持久幂等和原子父子写入。
3. 权限过滤后的意图解析、相似任务检索和候选生成。
4. 讨论、活动和 FileVersion 的同源存储与引用。
5. EWD、范围事件和业务验收历史。
6. 基于真实证据的当前情况和个人排序。
7. 单个个人 AI 客户端的授权读取、撤权、执行报告和安全写回。

依赖顺序不表示全部能力必须一次上线。首个可验证纵切应覆盖：可信上下文 → 一个简单 Task 和一个复杂 Task 的候选 → 人确认 → 统一存储 → 另一授权客户端重读。
