# 需求驱动的任务创建与协作选择

> 核心原则：先帮助用户把事情做成，再判断协作是否真的增加成功率。默认由当前用户拥有任务，协作是用户主动选择的增强路径。
> 状态说明：“默认自己、按缺口建议、用户主动选人”以及人际 Handoff 必须清晰已确认；Proposal 无 Owner、Handoff Profile、Steward 接管和 AI 默认停在 L3 是建议默认，见决策台账。

## 一、为什么不能一次生成完整方案

一次性生成阶段、人员、责任、待办和文件，表面上显得智能，实际容易造成四种伤害：

1. **过度规划**：AI 在信息不足时制造虚假的确定性。
2. **自主权损失**：执行者收到的不是目标，而是一套别人预先规定的做法。
3. **协作负担**：简单任务也被迫进入多人流程。
4. **角色威胁**：系统直接指出“你不行，需要某专家”，会提高用户求助的面子成本。

因此创建流程应当是一段渐进决策，而不是一次表单填充。

## 二、目标流程

```text
1. 用户表达需求
   ↓
2. AI 用一句话复述目标，并判断目前能否开始
   ↓
3. 只在高价值信息缺失时追问一个问题
   ↓
4. 默认生成“由我完成”的最小任务草稿
   ↓
5. 检查完成任务所需的信息、经验、权限和执行范围
   ↓
6a. 没有关键缺口：展示“创建任务”或继续完善
6b. 存在关键缺口：解释缺口，并询问是否查看协作建议
   ↓
7. 用户主动打开候选人比较
   ↓
8a. 向一位明确对象发出一张有界邀请；多位协作者使用不同 scope 的独立邀请
8b. 不知道找谁：发布结构化团队求助
8c. 暂不协作：保留风险，仍由自己推进
   ↓
9. 根据协作者接受、拒绝或调整范围，正式创建相应子 Task / Responsibility；已有工作接续则直接进入 Handoff
```

### 草稿与正式写入边界（建议默认，待确认）

- AI 默认只创建用户可编辑的 Proposal、邀请草稿和广播草稿。
- “创建任务”必须是用户的明确动作；正式 Task 创建时才写入 Owner、通知和审计记录。
- Proposal 可以没有 Owner；正式 Task 不能没有 Owner，默认 Owner 是当前用户。
- 用户若希望同事直接拥有新任务或子任务，系统先发出 Owner 候选邀请；对方接受后再正式创建，不能静默指派。
- 首版不提供“AI 可以长期自动创建正式任务”的默认授权。未来即使开放，也只能针对可撤销、范围明确的内部写入，并可随时撤销授权。

### AI 的停止条件

满足以下任一条件时，AI 不应继续增加结构：

- 用户已经可以执行下一步。
- 新增结构不能降低明显风险。
- 任务的执行方法应由被邀请者决定。
- 当前信息不足以支持可靠拆分。
- 用户明确选择先自己处理。

## 三、协作缺口判断

AI 不是判断“任务大不大”，而是判断“由当前用户独立完成是否存在关键缺口”。

| 缺口 | 判断问题 | 典型建议 |
| --- | --- | --- |
| 信息 | 完成任务所需资料是否已知、可访问、足够新？ | 推荐文件或知道资料位置的人 |
| 知识 | 是否需要用户不具备的专业知识？ | 找领域顾问共同判断 |
| 经历 | 是否需要做过类似场景的人避免重复踩坑？ | 找相似任务经历者短时评审 |
| 权限 | 是否涉及审批、发布、数据访问或业务授权？ | 找真正有授权的人，不用能力替代授权 |
| 判断 | 是否存在不可逆或高风险选择，需要独立复核？ | 增加 Reviewer / Approver |
| 执行范围 | 是否需要线下、跨区域或外部团队执行？ | 找具有现场触达能力的协调者 |
| 承诺容量 | 当前用户是否有足够可投入时间，不会阻塞其他关键责任？ | 比较协作或调整范围，不做强制调度 |
| 利益相关 | 结果是否需要某群体接受，且当前用户缺少代表性？ | 邀请利益相关方参与定义或验收 |

缺口有三个等级：

- **提示**：独立完成可行，协作可能提高质量。
- **重要**：独立完成风险明显，建议先补齐。
- **硬约束**：没有权限或必要责任主体，不能执行特定动作。

只有硬约束可以阻断高风险动作；其他情况保留用户选择。

## 四、协作建议的交互

不要一开始展示十个人和一张评分表。建议采用两步展开。

### 第一步：解释为什么可能需要协作

示例：

> 你可以先自己整理修复方案。不过“退款与撤单是否沿用原核销键”属于业务授权判断，仅凭代码和事故记录无法确认。要不要看看谁能补上这部分？

按钮：

- 看看协作者
- 先由我推进
- 只找相关信息

### 第二步：候选人对比

只展示 2–4 个真正有差异的候选人，不展示单一总分。

| 维度 | 陈默 | 周岚 | 许宁 |
| --- | --- | --- | --- |
| 可以补齐什么 | 重试实现经验 | 交易规则授权 | 相邻会员域经验 |
| 判断依据 | 完成 3 项相关任务 | 正式负责 POS 交易规则 | 处理过跨域券权益 |
| 本人公开的协作窗口 | 仅可做短时评审 | 可处理一项规则确认 | 暂不接受新协作 |
| 协作方式 | 30 分钟技术评审 | 确认一项业务决策 | 暂不建议邀请 |
| 权限 | 可编辑代码，无业务批准权 | 可确认规则 | 无 POS 批准权 |
| 不确定性 | 活动证据较新 | 正式职责已确认 | 当前可用性未知 |

系统可以给候选人贴“本人公开可短时响应”“有最终决定权”“最适合共同探索”等解释标签，但不输出人格化排名，也不预测谁回复最快。

这里的协作窗口由成员主动设置并控制受众与失效时间；候选卡不展示活跃任务数、审核队列、个人历史交付速度或由在线活动推断的空闲度。系统可以在成员本人明确选择后，私下提示其承诺冲突；发起人只看到成员愿意公开的粗粒度方式。任务类型的一般投入区间只有在满足团队匿名聚合门槛时才可展示，不能包装成某位成员的速度预测。

## 五、人员选择的人性与心理设计

### 1. 自主感

自我决定理论指出，自主、胜任和关系是持续动机的重要心理需要。工作中的自主支持与更高质量的动机、投入和幸福感相关。产品因此只建议，不替用户发送邀请，也允许被邀请者调整工作方法。

设计规则：

- 默认“我来负责”，而不是默认 AI 分配。
- 用户主动展开人员建议。
- 被邀请者可以接受、拒绝、建议换人或缩小责任。
- 委派者表达目标与边界，不默认替执行者生成全部步骤。

依据：[APA 对自我决定理论的综述](https://www.apa.org/research-practice/conduct-research/self-determination-theory)、[Gagné 与 Deci 的工作动机研究](https://selfdeterminationtheory.org/SDT/documents/2005_GagneDeci_JOB_SDTtheory.pdf)。

### 2. 胜任感与面子风险

求助可能被体验成“承认自己不够专业”。研究显示，求助方式会影响他人对求助者能力的判断；自主型求助比完全依赖式求助更有利于维持胜任感。

设计规则：

- 把问题描述为“任务存在一个专业/权限缺口”，不是“你缺能力”。
- 默认请求具体判断、资料或复核，不直接把整个任务甩给对方。
- 允许先匿名或限范围广播问题，再决定邀请谁。
- 强调用户仍是任务 Owner，求助是增强判断而非放弃责任。

依据：[工作中的自主型与依赖型求助研究](https://doi.org/10.1111/peps.12479)、[心理安全与团队学习](https://web.mit.edu/curhan/www/docs/Articles/15341_Readings/Organizational_Learning_and_Change/Edmondson_1999_Psychological_safety.pdf)。

### 3. 程序公平

成员不仅在意是否被分配，也在意为什么是自己、有没有发言权、系统是否对所有人使用一致规则。任务分配研究表明，不同分配程序会显著影响公平感。

设计规则：

- 展示推荐理由和未被选择的主要原因。
- 展示成员主动公开的粗粒度协作窗口，不向发起人展示个人任务计数、历史速度或无法验证的精确“空闲率”。
- 允许候选人申诉不准确的职责或忙闲判断。
- 给重复承担隐性工作的成员提供轮换或替代建议。

依据：[任务分配程序与公平感研究](https://doi.org/10.1177/1059601198231005)、[OECD 2025 算法管理报告](https://www.oecd.org/content/dam/oecd/en/publications/reports/2025/02/algorithmic-management-in-the-workplace_3c84ed6d/287c13c4-en.pdf)。

### 4. 责任清晰与责任扩散

多人共同参与会降低个人主观责任感。AgentDoor 坚持每层任务一位 Owner，同时把协作者的具体责任写清楚。

设计规则：

- 广播求助必须有明确的问题和响应方式。
- 有人回应不等于任务已有人负责。
- 多人参与后仍显示唯一 Owner。
- 共同责任拆到子任务或明确责任说明中。

依据：[群体中的责任扩散研究](https://doi.org/10.1177/0146167202281005)、[团队责任关系研究](https://pmc.ncbi.nlm.nih.gov/articles/PMC8600914/)。

### 5. 专家税与熟人偏差

团队总是找最显眼的专家，会让少数人长期超载，也让新成员没有建立可信经历的机会。

设计规则：

- 区分“最终授权人”和“可以先提供帮助的人”。
- 提供主候选与成长型候选组合。
- 当成员本人公开“只接受短咨询”，或正式职责结构显示团队依赖单一角色时，提示缩小咨询范围并提供替代路径；不靠个人任务数和响应速度判断“专家负载”。
- 不因为“历史做得多”就永久提高推荐频率；引入时间衰减与轮换。

### 6. 关系安全与地位差

直接向高地位成员求助可能增加暴露风险。用户应能选择私下邀请、经共同联系人引荐或团队广播。

设计规则：

- 候选对比中可以显示协作距离，但不展示私人关系评分。
- 提供“请共同联系人引荐”的低压力路径。
- 广播允许限制团队、角色和可见字段。
- 拒绝默认私密，不向团队解释个人原因。

## 六、邀请、协作成立与 Handoff（建议默认 Q-12 / Q-13）

普通协作邀请不是系统单方面写入责任关系。建议状态机：

```text
suggested → invited → accepted
                    ↘ declined
                   ↘ scope-proposed → accepted
```

邀请内容至少包含：

- 为什么找你。
- 希望你补齐什么。
- 预计协作方式和投入区间。
- 哪些文件可以访问。
- 谁仍然是任务拥有者。
- 接受、调整范围、推荐他人、拒绝。

一张邀请必须绑定一个 `scope + collaborationMode + recipient`：

- 同一子 Task Owner 候选不能同时向多人发出可自动生效的邀请；不知道找谁时先广播，选择一人后再邀请。
- 多位协作者并行时，每人对应不同子 Task 或有界 Responsibility，不能因多人点击接受而复制出多个同义任务。
- Reviewer、Advisor 与 Owner 候选不能混在同一张邀请里，避免接收者误解责任。

接受普通邀请只形成约定的协作关系或后续对象，不改变 Owner。随后根据工作的实际语义选择：

- 求助或短评审：邀请成立后形成有界 Responsibility，Owner 不变。
- 尚未开始的新独立结果：对方接受后正式创建由其拥有的子 Task，必要背景进入 Task Brief，不再重复一次 Handoff 接受。
- 已经做了一部分的工作、责任或上下文要接续：创建 Handoff。
- 子 Task Owner 完成后把结果、证据与剩余风险交给直接父 Task Owner：创建 `result-return Handoff`。Todo 与短咨询使用自身完成 / 回复机制。
- 整个 Task 结果责任转移：使用 `owner-transfer Handoff`，不另建第二套状态机。

```text
协作建议
  ├→ 新工作：发出邀请 → 接受 → 正式创建子 Task + Task Brief
  └→ 已有工作：直接发出 Handoff Offer → 复述 / 协商 → 激活
  → 关联 Task / Todo / Responsibility 执行
  → 子 Task 发起 Result Return
  → 直接父 Task Owner 验收；后续在父 Task 中整合
```

邀请回答“是否、以什么方式参与”；Handoff Offer 本身同时承担已有工作接续的邀请，不要求先接受一张普通邀请。Handoff 回答“究竟交什么、接什么、何时生效”；发出或被阅读都不改变责任。必要人员接受同一 Revision，且权限、关键版本和当前对象状态检查通过后，才原子激活。转移生效前原 Owner 始终保留。若原 Owner 已停用，只能使用有明确授权与审计理由的 Steward 应急接管例外；正式任务任何时刻都不能出现 0 位或 2 位 Owner。完整协议与唯一规范流程见 [11-human-handoff.md](./11-human-handoff.md)。

## 七、不知道找谁：团队广播

团队广播不应只是发一句“有人懂这个吗”。AI 帮助形成结构化求助卡：

```text
需要解决：确认部分退款是否沿用原核销键
已有信息：事故复盘、规则 v3.2、候选修复
缺少：有授权的业务判断 / 相似实施经验
希望获得：一条规则结论，或推荐合适负责人
预计投入：15–30 分钟
可见范围：零售交易团队
截止意图：今天开始灰度前
```

防止“旁观者效应”的机制：

- 明确邀请范围，而不是全公司无差别广播。
- 提供“我可以帮”“我知道谁合适”“需要更多信息”三种低成本响应。
- 有人响应后显示当前状态，避免所有人以为别人会处理。
- 长时间无人响应时，AI 建议缩小问题、换范围或定向邀请，但不自动骚扰成员。

企业社交网络研究表明，可见沟通能够提高员工对“谁知道什么、谁认识谁”的元知识；但信息噪音和中断也是实际成本，因此广播必须有作用域、结构和自动收敛机制。依据：[Ambient Awareness and Knowledge Acquisition](https://aisel.aisnet.org/misq/vol39/iss4/3/)、[Enterprise Social Media 的收益与中断权衡](https://doi.org/10.25300/misq%2F2023%2F16499)。

## 八、三个创建示例

### 独立完成

输入：“整理明天复盘会的三个问题。”

AI：生成一个由我拥有的轻任务和三个可选待办，不显示人员推荐。

### 建议协作但不阻断

输入：“为新会员活动写上线文案。”

AI：用户可以自己完成；提示品牌最新禁用词文件尚未加入，建议先补文件或请品牌同事快速审阅。

### 权限硬约束

输入：“把优惠券修复直接灰度到十二家门店。”

AI：可以准备方案，但当前用户没有门店灰度授权。系统提示选择授权人，不在确认前执行发布动作。

## 九、验证指标

- 用户看到人员建议后主动展开的比例。
- 候选建议被接受、修改、拒绝的分布。
- 被邀请者接受或协商范围的比例。
- 从表达需求到获得有效协作响应的时间。
- 从发出 Handoff 到双方形成一致范围的时间，而不是单纯点击接受的速度。
- 接收者能否准确复述目标、非目标、第一步和仍缺内容。
- Result Return 首次验收通过率，以及因上下文缺失被重新打开的比例。
- 广播问题获得有效回应而非仅浏览的比例。
- 同一少数专家被重复推荐的集中度。
- 用户和成员纠正推荐依据的次数与原因。
- 任务创建后删除 AI 生成结构的比例；过高说明 AI 过度规划。

### 首轮可用性验证门槛

这些是用于验证交互假设的首轮门槛，不是长期业务 KPI：

- 轻任务场景中，至少 80% 的测试者能在不打开协作者比较的情况下完成创建。
- 存在明确缺口的场景中，至少 80% 的测试者能正确说出“为什么系统建议协作”。
- 至少 70% 的测试者能根据对比卡选择协作方式，并能解释自己取舍的两个维度。
- 100% 的普通协作邀请不得改变 Owner；100% 的 Owner 转移必须经过同 Revision 双方同意、权限 / 版本检查与原子替换。
- 100% 的 Handoff 在激活前不得形成责任空窗或重叠；协议内容变化后旧接受必须失效。
- 结构化广播在测试中不得泄露任何预置为受限的客户名、任务名或文件名。
- 若超过 20% 的轻任务在创建后立即删除 AI 生成的结构，判定为过度规划，需要收缩默认输出。

首轮建议用 8–12 名跨角色参与者完成轻、中、重三组任务；样本用于找交互问题，不用于证明统计显著性。
