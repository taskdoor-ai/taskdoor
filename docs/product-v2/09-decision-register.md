## 若采用上述设计，必须成立的架构安全约束

这些不是产品负责人已经确认的新功能，而是选择相应 Q 项后，为兑现单 Owner、权限与可审计原则必须同时成立的安全约束：

- 所有正式写入经过可信 Command Gateway，并追加不可改写的 ChangeSet。
- 撤销通过补偿 ChangeSet 表达；外部发布、批准、发送等动作不能假装可撤回。
- Responsibility、能力画像和被推荐状态都不产生权限。
- Agent 访问是成员权限、委托授权、对象/版本策略与 Task scope 的交集，撤权后立即生效。
- Handoff 不授予权限；必须由 PolicyDecision 以接收者身份检查。
- 同一 Handoff Revision 的 Consent 才有效；协议变化必须让旧 Consent 失效。
- Handoff 激活、责任效果与 ChangeSet 同事务提交，发送、阅读和接受邀请都不改变责任。
- 正式 Task 首次从已接受 Proposal 物化后，`ownerId` 只能由 owner-transfer Handoff 激活事务修改；旧接口、普通 ChangeSet、管理员或 Agent 直改均拒绝。
- Profile 必须把 kind、scope、Task、source / recipient、Effect 与必要 Consent 强绑定；激活时使用 CAS / 串行化隔离并重算授权。
- Agent 可以起草 Handoff，不能替人同意或拒绝；Agent 能否接任 Owner 服从尚待确认的 Q-05。

## 已否定或被替代

- 正式 Task 可以长期没有 Owner。
- 用文件夹替代 Task 层级。
- 每次创建一次性生成完整阶段、分工和待办。
- AI 自动选择并指派协作者。
- 把发出文件、已读或已接受邀请直接视为责任完成转移。
- 用单独 Owner 转移状态机与 Handoff 重复表达同一握手。
- 用单一综合分排列成员。
- 以看板和手动拖拽作为主要推进方式。
- 以平台活动量、在线时长或伪精确空闲率评价成员。
