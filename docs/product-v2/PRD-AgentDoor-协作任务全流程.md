# AgentDoor 产品 PRD（文字简版）

> 版本：1.1  
> 日期：2026-09-03  
> 用途：产品流程、Skill、判断规则与 MCP 参数设计；同步提供 HTML 与 PDF

> 规则修订：`EWD-BREAKDOWN-2026-09-04-v5`。任务 EWD 拆成可核对的明细项；AI 按八个投入维度识别人工投入并逐项进行三点估算，再核对文件内容、按 EWD 权重汇总完成度和燃起图，尚未接入应用。

> 推荐规则修订：`PERSONAL-PRIORITY-2026-09-03-v4`。本人负责/参与的，只有待开始、进行中、已阻塞这三种状态的任务参与排序；重要度与紧急度共同计算推荐权重，P 参考任务标签，不依赖独立优先级字段。60%／40% 为初始建议参数，本次仅更新文档，尚未接入应用。

## 1. 产品流程

```text
加入团队
  → 维护个人责任
  → 创建任务
  → AI 分析并生成任务方案
  → 用户确认任务、人员和投入
  → 任务进入左侧列表
  → “我的工作”推荐当前优先事项
  → 在任务详情中持续协作和跟进
```

AgentDoor 中只有一种工作对象：Task。

子任务也是 Task。标签、文件夹、讨论和活动都不能代替 Task，也不能代替父子关系或依赖关系。

## 2. 团队成员、邀请与个人责任

### 2.1 团队成员

用户可以在“设置 → 成员”中：

- 查看当前团队成员。
- 查看成员的责任说明。
- 通过链接或邮箱邀请新成员。
- 管理管理员和普通成员角色。

邀请只表示邀请对方加入团队，不表示对方已经参与任务或负责某项工作。

### 2.2 邀请规则

- 负责人和协作人使用同一人员弹层，保留“暂不分配”与“没找到合适的人，邀请更多同事进来协作 · 立即邀请”。
- 邀请成功后，不自动写入 Task Owner。
- 邀请成功后，不自动写入 Participant。
- 被邀请人加入团队后，仍需接受具体的任务责任提议。
- 团队至少保留一名管理员。

### 2.3 我的责任

“我的责任”记录成员在当前团队中通常负责什么。

用户可以：

- 手工新增、修改或删除责任。
- 查看 AI 对已有责任的更新建议。
- 查看 AI 建议新增的责任。
- 查看建议所依据的任务或交付记录。

### 2.4 AI 责任建议

AI 可以根据已确认的任务责任和交付记录，建议新增、更新或废弃一条责任。

AI 先生成建议，人员责任分析 Skill 组织用户核对及确认后的更新流程；未经用户确认，不直接修改责任。

- 更新建议默认收起。
- 用户点击“更新”后，才替换原责任。
- 新增建议通过候选行展示。
- 用户点击加号后，才写入责任。
- 原责任已经被修改时，旧建议不能继续覆盖。
- 权限不足或证据不足时，AI 不生成确定结论。

### 2.5 人员责任分析 Skill

建立“人员责任分析” Skill，复用现有责任建议契约名 `agentdoor-responsibility-advisor`。持续跟进当前用户负责或参与的任务，结合实际承担的工作和用户反馈，让“我的责任”越来越准确，再用于成员推荐；不做能力、效率或绩效评分。完整规则见第 7.9 节。

输入：

- 当前用户和当前团队。
- 当前责任文本及版本。
- 当前用户负责或参与且有权限查看的任务、本人实际贡献、交付和相关讨论／活动记录。
- 证据时间和来源。
- 用户对历史责任建议的确认、修改、忽略及纠正记录。

输出：

- 新增、更新、废弃或不调整。
- 建议文本。
- 对应的原责任。
- 建议依据。
- 数据时间和信息缺口。

Skill 负责责任建议与确认后的更新流程；业务服务校验用户确认、权限和当前责任版本后写入，并返回实际结果。写入能力未接通时只返回建议，不声称已更新，也不能修改 Task Owner、参与人或权限。

## 3. 创建任务

### 3.1 创建流程

1. 用户点击左侧“新建任务”。
2. 用户输入希望完成的事情。
3. AI 判断信息是否足够。
4. 必要时提出最多两个关键问题。
5. AI 检查已有任务、成员责任和可用资料。
6. AI 生成主任务和必要的子任务。
7. AI 建议负责人、参与人、标签和预计投入。
8. 用户修改或让 AI 帮助调整方案。
9. 用户最终确认后，系统正式创建任务。

最终确认之前，页面中的内容都是草稿，不能提前写入正式 Task。

### 3.2 创建任务 Skill

当前已有 `agentdoor-task-planner` Skill，用于生成和调整任务方案。

它负责：

- 判断用户是创建、调整、继续规划还是查询。
- 补问真正影响目标和交付的问题。
- 检查相似任务和已有关系。
- 生成主任务和子任务草稿。
- 建议负责人和参与人。
- 建议标签、依赖和预计投入。
- 输出调整前后的差异。

它不负责：

- 创建正式任务。
- 自动指派负责人。
- 自动邀请成员。
- 替成员接受任务。
- 自动修改已有正式责任。
- 自动验收或关闭任务。

### 3.3 任务内容

每个 Task 至少包含：

- 名称。
- 目标。
- 完成标准。
- 正式负责人或待接受负责人。
- 参与人。
- 状态。
- 时间。
- 标签。
- 父任务和前置依赖。
- 预计人类投入。

名称用于快速识别，目标用于描述希望达到的结果，两者不能写成相同内容。

### 3.4 子任务拆分

结果必须能独立交付、独立验收，并至少需要独立负责、单独交接或并行推进之一，才拆成子任务。详细判定见第 7.3 节；单纯需要复用资料，不构成拆分理由。

以下内容通常不拆成子任务：

- 普通操作步骤。
- 同一交付中的分析、执行和复核。
- 只需要一次咨询或资料补充的协作。
- 为了让方案显得完整而增加的阶段。

父子关系只表示范围包含，不自动产生前置依赖。

### 3.5 人员匹配

AI 按以下顺序推荐人员：

1. 检查成员是否可被发现，以及是否有权限参与当前工作。
2. 检查成员的正式责任是否覆盖整个任务结果。
3. 检查相关任务、文件和业务对象经验。
4. 检查成员主动公开的协作方式和可投入窗口。
5. 展示候选差异，由用户决定。

AI 不能通过任务数量、在线状态、回复速度或私人日历判断成员是否空闲。

没有合适人选时，任务可以保持未分配。不能默认把创建者、主管或首位成员填为负责人。

### 3.6 负责人规则

- 一个 Task 最多有一位正式 Owner。
- 用户选择自己负责时，可以直接成为正式 Owner。
- 用户选择其他成员时，先记录为待接受提议。
- 对方接受后，才成为正式 Owner。
- 待接受人不能进入“我的工作”。
- 已有正式 Owner 的变更不能通过普通编辑直接完成。

### 3.7 标签

AI 可以根据任务对象和交付结果建议已有标签。

- 标签可以修改或清空。
- 标签不是状态、目录或父子关系。
- 不创建主标签或标签组。
- 一个任务可以有多个标签，但在左侧列表中只出现一次。

### 3.8 工时和成本

当前只确定预计人类投入 EWD。

EWD 表示：在明示的估算条件下，完成当前范围预计需要多少人类投入；首版按常用工具及模板条件粗估，不假定用户实际采用了 AI。

**对任务的价值：** 预计投入人天表示完成任务预计需要的总人工工作量，帮助团队看清任务规模、投入主要花在哪里，并按工作量衡量完成进度。

**统一展示单位为人天，1 人天＝8 人时＝480 分钟。** 页面仍叫“预计投入”，例如“预计投入约 5 人天”；这是总人工投入的换算单位，不是日历工期，也不表示每位成员每天有 8 小时可用于此任务。40 小时的总人工投入应换算成 5 人天，不能直接改标签变成 40 人天。

首版根据任务名称、目标和完成标准生成任务 EWD 拆分明细，再按平台八个投入维度为每项进行三点估算；任务总 EWD 为各明细项之和。没有历史也能使用；规则、算例及后续学习方法见第 7.7 节「EWD 工时评估＋进度」。

计入：人工准备、操作、沟通、审阅、修改和验收。

不计入：等待时间、排队时间、无人值守的 AI 运行时间和自然工期。

- 未知不能按 0 计算。
- 子任务缺少估算时，不计算完整总投入。
- 父任务汇总叶子任务，不能重复累计。
- 目标、完成标准或工作方式变化后，需要重新估算。
- EWD 不等于工期、剩余时间、个人效率或任务优先级。

预计投入以 EWD 明细项为单位，记录对应完成标准、八维检查结果、三点估算、估算依据和 EWD；无法判断的工作保留待估。用户修改估算另存来源，不能当作实际耗时直接训练。

初期使用平台规则；后续积累团队历史任务的目标、完成标准、交付结果和投入反馈，逐步校准该团队的三点估算，供后续任务使用。数据不足时沿用平台规则；没有真实人工投入反馈时，不声称已校准真实工时，也不根据提交间隔设置个人效率系数。判断逻辑见第 7.7 节。

创建页在预计总投入下展开数字列表，按预计工时从高到低展示“任务名称 · 预计 1.25 人天 · 占总投入 25%”；不再展示条形或饼图，避免将投入占比误读为完成度。占比的分母是当前全部叶子任务的有效 EWD；缺估或需重估时只显示已估部分，不计算占比。

金额成本暂不进入首版。人员费率、外部费用、币种和查看权限确认后，再设计金额公式。

### 3.9 创建确认

用户确认前，系统检查：

- 名称和完成标准是否有效。
- 人员是否属于当前团队。
- Owner 是否重复出现在参与人中。
- 日期是否合法。
- 依赖是否自指、悬空或形成循环。
- 子任务时间是否与父任务明显冲突。
- 预计投入是否仍对应当前任务范围。

无负责人不阻止创建。系统只统一提示一次未分配任务数量。

## 4. 左侧任务列表

### 4.1 页面结构

```text
搜索 ｜ 筛选 ｜ 新建
我的工作
按标签分组的本人任务
待确认负责人
```

### 4.2 标签分组

- 默认使用任务的第一个标签作为展示分组。
- 没有标签的任务进入“未打标签”。
- 一个任务只在一个分组出现。
- 标签筛选时，按第一个命中的已选标签临时归组。
- 清除筛选后，恢复默认分组。

### 4.3 列表范围

- 本人任务通过稳定成员 ID 和正式 `ownerId` 判断。
- 创建者身份不能代替负责人身份。
- 参与人不能代替负责人身份。
- 待接受负责人不进入本人正式任务列表。
- 本人创建但尚未分配的任务进入“待确认负责人”。

搜索、状态和标签筛选只影响左侧列表，不影响“我的工作”的分析范围。

## 5. 我的工作

### 5.1 模块作用

“我的工作”回答：在我正式负责的任务中，现在应该先关注什么。

它不是第二套任务系统，也不创建新的待办。

### 5.2 展示内容

每条只显示：

1. 顺位。
2. 任务名称。
3. 一句优先原因。

点击任务名称进入原任务详情。

页面不展示 AI 内部评分、复杂权重、完整依据列表或其他任务的深层链接。

### 5.3 分析范围

本人负责/参与的，**只有待开始、进行中、已阻塞这三种状态的任务参与排序。**

### 5.4 推荐逻辑

产品规则采用“推荐权重＝重要度 × 60%＋紧急度 × 40%”，两维均为 0～100 分；比例是待验证的初始建议参数。程序按固定规则计算，AI 基于同一事实解释，具体分档、算例和同分规则见第 7.6 节。

1. **重要度：** 目标影响（0～50）＋已确认协作影响（0～30）＋标签参考（0 或 20）；任务没有独立的优先级字段。
2. **紧急度：** 期限压力、正在发生的损失或执行风险、当前待本人处理事项，三者取最高分，不重复叠加。
3. **排序：** 推荐权重降序，同分依次比较重要度、紧急度、可比较截止时间、稳定 Task ID。
4. **证据：** 每项分值必须有有效来源，资料缺失或过期不额外加分，按已知依据计算并提示待核对。仅有参考性前置未完成，不等于已阻塞，也不直接加分。

本节与第 7.6 节描述新产品规则，当前应用尚未接入，不代表只靠修改文档就已改变实际顺位。

没有截止时间是合法状态，不等于低优先级。

资料不足时，优先原因应表达“待核对”，不能推断任务正常或没有风险。

缺少真实日历、剩余工作量和个人可投入时间时，不输出忙闲率、完成概率或精确排程。

### 5.5 AI 分析规则

页面顶部保留默认收起的“AI 分析规则”，只说明：

- 哪些任务会进入分析范围。
- 重要度与紧急度的定义、权重、分档依据和同分规则，AI 如何据此解释原因；不在任务行展示内部打分。
- AI 不会自动修改任务。

只有分析输入真实变化时，更新时间才变化。打开页面或重新渲染不能制造新的分析时间。

## 6. 任务详情

### 6.1 任务头部

头部展示：

- 名称、目标和完成标准。
- 正式负责人、待接受负责人和参与人。
- 状态、时间和标签。
- 任务属性编辑入口。

字段保存成功后才形成活动记录。没有真实变化时，不生成活动。

### 6.2 当前情况

任务头部下方展示三部分：

| 区域 | 内容 |
| --- | --- |
| 当前情况 | 当前摘要、已完成事实、差距、风险和近期变化 |
| 下一步建议 | 有依据的候选行动 |
| 进度 | 以 EWD 衡量工作量和完成度；通过燃起图判断任务是否趋于完成 |

下一步建议只是一项建议，不自动修改状态、负责人、时间或子任务。

没有足够记录时显示未知或“尚无可核对记录”，不能显示“运行正常”。

### 6.3 完成进度和燃起图

“完成进度”的说明图标支持悬浮、键盘聚焦和点击，说明“任务先形成 EWD 拆分明细，AI 对照完成标准与文件内容判断每个明细项的进度，再按 EWD 加权汇总”。标明文件版本、引用位置和判断来源；上传本身不算完成。规则见第 7.7 节，当前原型尚未接入此流程。

完成百分比同一行右侧显示“预计投入 8.75 人天”，无需展开即可查看。主任务汇总当前范围的叶子工时，独立任务显示自身估算，不重复累计父级；使用当前有效估算，不沿用历史快照中的旧总量。缺估时显示“已估部分 2.5 人天”，无估算显示“预计投入 待估算”，过期／异常分别显示“需重估／待核对”。总工时代表预计投入，不代表已花费时间；下方子任务明细不变。

燃起图标题不再显示 `EWD · h`。有可绘制历史时，图例为虚线“当前总工作量”与实线“已完成工作量”；空状态不补图例。“查看数据”内说明按 EWD（预计人类投入）加权、已完成以标准项对应的文件内容核对结果为准且不代表实际耗时，统一以人天展示，1 人天＝8 人时＝480 分钟。既有 scopeHours 等字段仍按原小时含义读取并除以 8 展示，不改历史数值、不将工作量解释为工期。

任务总 EWD 为所有 EWD 明细项之和；AI 对照完成标准与文件内容判断每项进度，单项已完成 EWD＝单项 EWD×进度，再按 EWD 加权汇总任务完成度；不自动修改 TaskStatus。

- 不按已完成任务数量计算。
- 不根据 TaskStatus 推导。
- 当前 EWD 拆分明细完整、总量大于 0，且全部明细项均可判断但没有有效完成内容时可显示 0%；存在待确认项、读取失败或结果过期时显示待核对。
- 没有历史不伪造趋势；单个真实快照只显示一个点，不补画过去的线。
- 父任务只汇总叶子 Task，不重复计算。
- 进度达到 100% 不自动关闭父任务。
- 状态与进度记录冲突时，显示“待核对”。

有子任务时，在整体进度条下默认收起一行“子任务投入与进度 · 展开”，不重复百分比旁的总工时，也不显示“已验收 / 范围”图例。展开后按预计工时从高到低排列；同值保持原序，未知项置后，不改变实际任务顺序。

- 每项第一行显示黑色加粗的任务名称，可点击进入该子任务详情；暗色主题使用对应主文字色。
- 第二行左侧显示“预计 1.25 人天 · 占总投入 25%”，右侧显示“已完成 60%”。预计投入不等于实际耗时。
- 下方进度条只表示该子任务自身的完成度：按本项标准分配 EWD，并根据已确认文件内容计算，不与投入占比混用。
- 文件无法读取或核对结果缺失时显示“进度待核对”和灰色空进度条，不补 0%；有效核对结果为 0 时显示 0%。过期估算、无效 EWD 明细或零分母同样提示待核对。
- 部分任务缺估时百分比旁显示“已估部分 2.5 人天”，明细保留未知项，不把已估部分当完整分布；其中已有有效估算和内容核对结果的单项仍可展示自身完成度。
- 仅一个子任务也支持展开；没有子任务不显示此入口。多层任务只统计叶子，不重复累计父级。
- 窄屏明细允许换行，展开按钮和任务名称支持键盘操作；燃起图继续独立表达时间趋势。

### 6.4 页签顺序

```text
讨论 ｜ 诊断 ｜ 子任务 ｜ 文件 ｜ 活动
```

### 6.5 讨论

讨论只承载人的交流：

- 发布消息。
- 回复。
- @ 成员。
- 引用文件和讨论上下文。
- 从讨论连接个人 AI。

任务变更、诊断结果和自动 AI 建议不计入讨论数量。

### 6.6 诊断

诊断回答：当前任务能否继续，依据是什么。

首版只检查两类问题：

- 执行阻塞：任务处于进行中或已阻塞，有正式依赖，当前阶段需要的前置交付尚未满足；未开始任务正常等待前置不直接判当前阻塞。详细条件见第 7.5 节。
- 决策冲突：根据任务已有文件内容和任务信息，检查同一事项是否存在相互矛盾或不能同时满足的地方，并指出内容和出处。

诊断范围包含当前 Task 和全部可见后代 Task。

每条诊断展示：结论、影响、建议和默认收起的依据。

诊断页只读，不提供一键修复、改期、改依赖、忽略或完成任务。

不可见或缺失的依赖只表示检查范围不完整，不能推断为阻塞、正常或已完成。

### 6.7 子任务

子任务列表每项只显示：

- 图标。
- 名称。
- 负责人或待接受负责人。

点击名称进入子任务详情。

- 手工新增至少需要名称和一条完成标准。
- 不自动继承负责人、参与人、文件或权限。
- 新增或删除后，父任务的直属子任务数量同步更新。
- 删除有下级的子任务时，必须说明影响范围。
- 子任务全部完成不自动关闭父任务。

### 6.8 文件

文件页用于管理当前任务有权查看的文件和引用。

- 引用已有文件时复用同一 File ID，不复制内容。
- 文件夹只用于组织，不改变文件身份和权限。
- 父子任务的文件不自动继承。
- 固定版本和跟随最新版本必须区分。
- 文件无权限、已删除或缺失时，明确显示不可用。

### 6.9 活动

活动只记录已经真实发生并保存成功的变化。

活动分为三类：

- 任务信息。
- 讨论。
- 文件。

每条活动说明谁在什么时间做了什么。

- 没有真实变化时不生成活动。
- 未保存草稿不进入活动。
- AI 建议和诊断结论不进入活动。
- 活动只读，不能在活动页编辑或删除正式记录。

## 7. Skill 与判断规则

### 7.1 各自负责什么

本章按业务流程组织，不把每个判断步骤都建成一个 Skill。创建任务是完整 Skill，澄清、查重、拆分、人员匹配、依赖与时间安排是它的内部步骤。EWD 工时评估与进度作为独立规则模块：创建任务调用预计投入，任务状态分析引用完成度和燃起图。

人员责任分析是独立 Skill，负责持续校准当前用户的责任说明；创建任务中的成员推荐读取用户已确认的责任，不把责任分析重复做成创建时的必跑步骤。

| 所属流程 | 回答的问题 | 返回什么 |
| --- | --- | --- |
| 人员责任分析 | 我实际承担哪些工作，现有责任说明需要怎样校准？ | 有来源的责任新增、更新、废弃或不调整建议；组织用户确认后的更新并解释回执 |
| 创建与人员匹配 | 要拆成哪些交付，谁适合负责？ | 任务草稿、人员建议、依赖与预计投入 |
| 状态分析 | 当前情况怎样，下一步做什么，进度如何？ | 当前情况、下一步建议、进度（完成度与燃起图） |
| 任务诊断 | 哪项工作受阻，哪些要求互相矛盾？ | 问题、受影响任务、双方依据、处理建议 |
| 我的工作推荐 | 我负责或参与的任务先处理哪个？ | 固定规则计算的顺位和一句原因 |
| EWD 工时评估＋进度 | 预计投入多少，完成多少，是否在收敛？ | EWD、完成度与燃起图；供创建任务和状态分析引用 |

**模块划分：** 第 7.7 节集中维护工时评估维度、三点估算、完成度和燃起图；创建任务与状态分析保留调用说明。任务状态分析仍按当前情况、下一步建议、进度组织。

**当前实现：** 六类能力均有项目内 Skill 入口、判断规则和离线接入设计；创建规划保留 `agentdoor-task-planner` v0.2 契约，其余五类明确各自输入输出。入口与调用关系记录在 `skills/registry.json`，该清单不是运行时注册。前端已有责任建议查看与确认、本地工时、进度、诊断和排序逻辑；本轮更新 Skill 文件与 PRD，未修改应用运行代码，也未接通后台持续分析或责任写回服务。

**文件对应：** 人员责任分析 `agentdoor-responsibility-advisor`；创建任务 `agentdoor-task-planner`；状态分析 `agentdoor-task-status-analyzer`；诊断 `agentdoor-task-diagnostician`；我的工作 `agentdoor-personal-priority`；工时与进度 `agentdoor-ewd-progress`。各入口在 `skills/对应名称/SKILL.md`。产品规则从本章同步为各 Skill 的规则快照，避免两处独立修改。详细接入设计见 `docs/product-v2/14-agentdoor-skill-suite.md`。

### 7.2 判断前需要的数据

| 保存对象 | 必须保存的内容 | 用在哪里 |
| --- | --- | --- |
| 任务与完成标准 | 任务 ID、目标、交付物、数量、每条标准的 ID、状态、日期、负责人、父子关系、正式依赖、版本 | 拆分、工时、诊断、推荐 |
| 成员责任与声明 | 团队与成员 ID、正式责任、本人技能说明、明确公开的协作窗口、来源与更新时间 | 人员匹配、估算工作条件 |
| 历史贡献 | 成员、任务、具体贡献、交付版本、依据；区分本人说明与已核实贡献 | 判断相关经验 |
| 责任分析与反馈 | 当前用户及团队、责任文本与版本、任务／交付来源及版本、实际承担内容、候选操作、原责任、覆盖范围、用户确认与纠正、失效状态 | 持续校准责任；已确认责任供成员推荐使用 |
| 文件与提交 | 文件 ID、版本、可读取正文、提交人、提交时间、关联任务和标准 | 核对结果、诊断；不是初始 EWD 的必需输入 |
| 估算依据 | 名称、目标、完成标准及版本；EWD 明细 ID、明细项、对应标准、八维检查结果、三点估算、预计 EWD、依据与缺口；采用的平台或团队规则版本、团队 ID、来源历史任务及调整原因 | 计算任务总 EWD，作为单项进度和燃起图权重 |
| 实际投入反馈（新增） | 实际分钟或区间、填报人与覆盖人员、对应工作和范围、收集方式、范围变化、训练使用许可 | 校准 EWD；部分反馈不能当作整项实耗 |
| 结果核对 | EWD 明细 ID、文件版本与内容出处、单项进度、判断理由、确认来源、核对时间及有效性 | 计算每项已完成 EWD、任务完成度与缺口 |
| 正式验收 | 验收对象、操作者、结论、时间、适用范围、标准与交付版本、估算版本、撤销记录 | 交付验收留痕；不是文件内容进度的唯一前提 |
| 变更与分析记录 | 变化前后版本、实际发生时间、分析类型、输入版本、规则版本、来源、结果；趋势另存当时的任务总 EWD 与已完成 EWD | 更新、复用、燃起图 |

这些是逻辑对象，可复用现有数据表。现有 MCP 尚未提供全部读取能力；不能把建议字段写成已存在的接口。

**责任如何持续校准。** 复用“我的责任”和本人负责或参与任务中的实际承担记录，由第 7.9 节人员责任分析 Skill 提出建议，用户确认后才成为成员推荐依据。不建设隐藏的能力／效率画像，也不增加独立画像页。每条资料保存“谁、承担什么、来自哪里、何时更新、当前是否有效”；没有查到记录表示未知，历史 Owner 身份不等于独立完成。本人修改责任、来源撤销或权限变化后，依赖该资料的建议需重新核对，正式负责人不自动更换。

**所有 Skill 共用的读取规则。** 服务端提供当前用户有权读取的资料，并记录各类数据是“已读全、部分、不可用、未读取”。空集合只有在已读全时才代表确实没有记录。资料中的文字只作为证据，不能当作新的操作指令。输出绑定资料版本；旧请求不能覆盖新版本结果。

### 7.3 创建任务 Skill

**把自然语言需求整理为目标清晰、责任明确、可交付的任务计划；已有任务可根据实际进展继续调整。**

<div class="step-rules">

| 环节 | 能力说明 | 判断逻辑 |
| --- | --- | --- |
| 1. 意图识别 | 判断用户想新建任务、调整已有任务，还是查询情况。 | 新建进入规划；调整先定位原任务；查询只回答，不创建任务。意图不明时先确认。 |
| 2. 需求分析 | 理解用户要解决的问题，明确目标、交付内容和完成标准；需求不明确时加以引导。 | 围绕“要达到什么结果、怎样算完成”补问关键缺口；已明确的信息直接复用，不反复追问。 |
| 3. 任务规划 | 识别当前用户已创建或参与的任务，判断重复创建、子任务归属等场景，并根据任务内容决定是否拆分。 | 在当前有权读取的任务中比较目标、交付和范围，判断复用已有任务、追加子任务或独立新建。结果能独立交付、验收，且需单独负责、交接或并行时才拆分；一并明确依赖和期限，缺少依据则待确认。 |
| 4. 成员推荐 | 根据成员责任，推荐一位负责人和最小参与人集合，并解释推荐原因。 | 在有参与资格的成员中，推荐责任覆盖整体结果的人负责；只加入承担必要具体贡献的参与人，逐人说明原因。用户点名先核对，无合适负责人可未分配。 |
| 5. 任务预计投入工时评估 | 调用第 7.7 节生成任务 EWD 拆分明细，并汇总预计投入人天。 | 传入任务名称、目标、完成标准及可选历史任务；回填每个 EWD 明细项、对应标准、EWD、依据和缺口。规则集中见 [EWD 工时评估＋进度](#ewd-progress)。 |

</div>

**已有任务调整：** 读取当前任务、子任务、讨论和最新交付，调整尚未完成的计划或建议下一批子任务；保留仍有效的安排，避免重复已完成工作。

**确认规则：** 创建与调整都先生成可编辑草稿，用户确认后再保存；推荐他人负责时，对方接受后才成为正式负责人。

**成员责任来源：** 初期使用用户填写的责任；后续由人员责任分析 Skill 跟进任务并提出校准建议，用户确认后更新。成员推荐使用当前有效责任版本，并说明匹配依据。

**与状态分析的关系：** 本 Skill 负责创建和调整计划；当前情况、下一步建议、进度由 7.4 任务状态分析负责。预计投入与进度规则统一见 7.7，页面展示说明见 3.8 与 6.3。

**Skill：** `agentdoor-task-planner`。

**草稿展示与换人：** 主任务、子任务均按完成标准、执行建议、前置依赖的顺序组织可编辑内容；前置依赖只作参考，不自动阻止任务执行或改变状态。卡片底部的匹配依据分别说明负责人覆盖的结果和参与人的具体贡献；人员选择或正式责任版本改变时重新核对，用户指定的人选不等于高度匹配，缺口如实提示。

### 7.4 任务状态分析 Skill

**任务状态分析分为三部分：当前情况、下一步建议、进度。进度包含完成度和燃起图。**

<div class="step-rules">

| 部分 | 回答什么 | 判断逻辑 |
| --- | --- | --- |
| 1. 当前情况 | 现在做到哪，发生了什么？ | 结合任务信息、讨论与交付记录，概括当前结果、缺口和近期变化；信息不足标待确认。 |
| 2. 下一步建议 | 接下来应该做什么？ | 根据当前缺口与诊断，有冲突先核对，有阻塞先解除，否则补齐尚未满足的结果。 |
| 3. 进度 | 当前完成多少，任务是否趋于完成？ | 引用 [7.7 EWD 工时评估＋进度](#ewd-progress) 的完成度与燃起图，解释当前进展和是否收敛；不另行生成一套数值。 |

</div>

相关交付、标准、反馈或验收发生变化时，重新核对受影响的结果。单纯经过时间或增加提交次数，不代表任务更接近完成。

**接入设计：** `agentdoor-task-status-analyzer` 组织这三部分；任务诊断复用 7.5，进度引用 7.7 的文件内容核对结果，不自动修改任务状态。

### 7.5 任务诊断 Skill

**任务诊断只分两类：执行阻塞、决策冲突。**

<div class="step-rules">

| 类型 | 判断什么 | 判断逻辑 |
| --- | --- | --- |
| 执行阻塞 | 当前任务为什么无法继续？ | 检查正式前置依赖与交付情况。任务已在执行，当前必须使用的前置交付尚未满足，导致无法继续，才判为阻塞。 |
| 决策冲突 | 任务里的文件内容与任务信息是否存在矛盾？ | 核对已有文件内容，以及目标、完成标准、时间等任务信息，找出同一事项上相互矛盾或不能同时满足的地方；指出冲突双方的具体内容和出处。 |

</div>

**例子一：执行阻塞。** 宣传海报正在设计，但依赖的活动文案还未交付，缺少标题和优惠信息，无法继续定稿。建议先推动文案交付。

**例子二：决策冲突。** 任务要求“活动预算不超过 10 万元”，但当前方案文件中的预算是 12 万元。建议确认是调整方案预算，还是修改任务中的预算要求。

**Skill：** `agentdoor-task-diagnostician`。

### 7.6 我的工作推荐 Skill

**作用：在本人负责或参与的任务中，综合重要度和紧急度，推荐现在应先处理哪一个，并说明原因。** 推荐权重是排序分数，不代表人员能力、完成概率或绩效；页面只显示顺位、任务名称和一句原因，完整计算规则放在“AI 分析规则”中。

#### 1. 哪些任务参与排序

本人负责/参与的，**只有待开始、进行中、已阻塞这三种状态的任务参与排序。**

#### 2. 排序权重：重要度 60%，紧急度 40%

**推荐权重 W＝重要度 I × 60%＋紧急度 U × 40%。**

重要度和紧急度均在 0～100 分之间，推荐权重也在 0～100 分之间。“权重”指这个最终综合分，不是第三个独立评分项。

| 维度 | 回答的问题 | 计算方式 | 在最终排序中的占比 |
| --- | --- | --- | --- |
| 重要度 I | 这件事对目标、交付和其他工作有多大影响？ | I＝目标影响 B＋协作影响 C＋标签参考 P，最高 100 | 60% |
| 紧急度 U | 如果现在不处理，会多快错过期限、持续损失或让别人等待？ | U＝max(D, H, Q)，取期限压力、当前风险、待本人处理三者最高分 | 40% |

**60%／40% 及以下档位都是初始建议参数，待产品验证，不是已验证的最优权重。** 重要度略高，是为了让关键交付、实际损失和影响他人的任务有机会超过低影响的例行逾期任务；时间不能独占排序。参数统一配置并记录规则版本，AI 不能每次自由调整分数。

#### 3. 重要度怎样计算

**I＝B＋C＋P。每个分项只取符合条件的最高一档，分项之间相加。**

**目标影响 B（0～50 分）：** 依据当前目标、完成标准、已确认的业务要求和目标关联判断，不以任务标题长短、金额大小或 AI 写出的“重要”二字判断。

<div class="priority-score-table">

| 分值 | 成立条件 | 必须能指出的依据 |
| --- | --- | --- |
| 50 | 已明确关联当前核心业务目标、关键外部承诺或必须满足的合规要求，交付失败将直接影响该目标或承诺 | 已确认的目标／要求、这项任务的具体交付，以及两者的直接关系 |
| 35 | 支撑明确的团队阶段目标或对外交付，但未被确认为核心目标或关键承诺 | 当前团队目标或交付要求，与任务完成标准的对应关系 |
| 20 | 有明确必要性的例行维护、内部支持或基础交付 | 已记录的需求与完成标准；不因“例行”判断其没有价值 |
| 10 | 已明确为可选优化，当前没有硬性交付要求 | 用户确认的可选范围，不能仅凭没有截止时间推断 |
| 0（待核对） | 目标、交付用途或关联信息不足，无法归档 | 标明缺什么依据；0 是暂不计分，不表示已确认没有价值 |

</div>

**协作影响 C（0～30 分）：** 判断“这项任务的结果会影响谁”，不是“这项任务在等谁”。

| 分值 | 成立条件 | 计数与边界 |
| --- | --- | --- |
| 30 | 已确认该交付是至少 2 项活跃下游任务的必需输入，或是一项已确认关键里程碑的必要条件 | 下游必须是待开始、进行中或已阻塞；按 Task ID 去重，每项关系有明确所需交付，不累计传递链 |
| 15 | 已确认该交付是 1 项活跃下游任务的必需输入，但不满足上档 | 只取 15，不按前置数、参与人数或评论数累加 |
| 0 | 没有上述影响证据，或只存在参考性关联 | 已知没有影响与资料未知分开记录；未知不能说“没有下游影响” |

父子归属不等于依赖，用户可编辑的前置依赖也只是参考。仅有关系边、上游还未完成，不能证明当前任务阻塞了别人；只有当前交付要求或有效协作记录明确证实“需要这个结果”，才能计入 C。

**标签参考 P（0 或 20 分）：** 任务没有独立的优先级字段，AI 可参考当前任务已有标签的名称和已知含义，辅助判断重要度。明确表示重要性的标签，如“高优先级”“重点任务”，取 20；普通业务分类标签、没有相关标签或含义不明确时取 0。多个符合条件的标签不叠加，最高 20 分；没有标签不等于任务不重要，仍正常计算 B 和 C。

只参考当前用户有权使用且实际关联到当前任务的标签，不借用其他人的私有标签，不按颜色、图标、标签数量或上级任务标签推断。含义不明或互相冲突时标待核对，不由 AI 猜测加分；仅写“紧急”的标签也不能代替 D、H、Q 所需的事实。记录命中的标签 ID、名称和判断依据；标签只作辅助参考，不能替代 B、C 的事实依据，不自动新增或修改标签，也不新增优先级设置。

例如：支撑团队阶段目标 B＝35，影响两项已确认下游交付 C＝30，任务已有“高优先级”标签，参考该标签取 P＝20，则重要度 I＝85。移除该标签后，P＝0，I 变为 65；任务状态不变，B、C 仍按原事实计算。

#### 4. 紧急度怎样计算：时间只是其中一项

**U＝max(D, H, Q)。三类信号各自取最高档，再取三者最高值，不相加。** 同一问题可能同时造成逾期、损失与等待，取最高值可避免重复放大；其他命中仍保留为解释依据。

**期限压力 D（0～100 分）：** 按团队时区计算，日期差 d＝截止日期与当前日期相差的日历天数。仅有日期时，以当地当天结束作为截止；明确时刻超过后才算逾期。先判断逾期，再选今天或未来档位。

<div class="priority-score-table">

| 条件 | D 分值 | 判断规则 |
| --- | --- | --- |
| 已逾期 | 100 | 早于今天的截止日期，或已超过明确截止时刻 |
| 今天到期 | 90 | d＝0，尚未超过明确截止时刻 |
| 未来 1～2 天到期 | 75 | d＝1 或 2 |
| 未来 3～7 天到期 | 60 | 3≤d≤7 |
| 未来 8～14 天到期 | 30 | 8≤d≤14 |
| 14 天以后到期 | 10 | d＞14 |
| 明确无截止时间 | 0 | 没有时间信号，仍正常计算 I、H 和 Q |
| 日期缺失、过期或无法识别 | 0（待核对） | 不猜年份、不补日期、不判逾期；推荐注明日期依据不完整 |

</div>

逾期天数不继续叠加分数。日期信息未知与用户明确不设截止时间是两回事；两者都不凭空增加 D，但解释必须区分。

**当前损失或执行风险 H（0～100 分）：** 除截止时间外，判断“拖延处理正在造成什么影响”。

| H 分值 | 成立条件 | 依据要求 |
| --- | --- | --- |
| 100 | 当前已有持续的关键服务中断、客户／交易损失或明确的合规、安全风险，且有需本人立即处理或协调的行动 | 当前有效事件、影响范围、未解除事实和本人行动；仅标题写“紧急”不成立 |
| 80 | 已证实执行阻塞或决策冲突正在持续造成停工、返工或扩大交付影响，需本人处理或协调 | 当前受影响的工作、阻塞／冲突内容及可采取行动，不只看状态名 |
| 60 | 有当前有效的决策冲突，继续按不一致要求推进会导致错误交付，但尚未证实持续损失 | 冲突两侧的具体内容和出处；失效的旧诊断不能使用 |
| 0 | 未证实以上风险，或没有当前需本人处理的行动 | 仅标“已阻塞”、很久没更新或前置尚未完成，均不自动给风险分；原因未知标待核对 |

**待本人处理 Q（0～80 分）：** 判断是否已有明确等待，而不是仅从任务状态猜测。

| Q 分值 | 成立条件 | 依据要求 |
| --- | --- | --- |
| 80 | 活跃下游工作已明确停等本人必须提供的结果、决定或确认，且本人现在有可执行的处理行动 | 当前等待方、所需内容、尚未回应／交付的记录；不是未来可能依赖 |
| 60 | 有指向本人的有效交付核对或决定请求，材料已提供且事项尚未处理，但未证实下游停工 | 请求、交付或反馈与本人责任的对应关系 |
| 0 | 没有上述当前等待 | 仅上传文件、没有验收记录、只有参与身份，均不构成等待；仅有参考性前置未完成不加分 |

例如：没有截止时间 D＝0，但本人需要立即协调处理持续的关键服务中断 H＝100，下游也在等待 Q＝80，则 U＝max(0, 100, 80)＝100。紧急度并不依赖是否填了时间。

#### 5. 证据、缺失数据和去重

- 每次命中必须保存事实内容、来源 ID／版本、适用任务和有效性。AI 可以从可访问记录中识别候选事实并解释，但分档必须符合上述条件；没有证据不能靠模型语气打高分。
- 不因资料缺失或过期加分；失效证据不再参与计算，未知分项暂取 0，不把剩余维度重新放大到 100。推荐注明“依据不完整，需核对”，不能写“低价值、没有风险”。资料恢复后重新计算。
- 同一维度中，同一事件、相同任务或重复文件只计一次；B、C、P 反映不同影响，允许相加；D、H、Q 反映当前处理压力，只取最高值。不要再额外叠加“阻塞＋20、资料过期＋25”等旧规则。
- 一个事实可同时支持重要度和紧急度，但必须分别解释：例如“会影响两个交付”支持 C，“两项工作现在已停等本人”才支持 Q。只证明前者，不能顺便计入后者。
- 不以 EWD 大小、提交次数、聊天活跃度、任务历时或人员历史速度加分；没有真实剩余工作量和可投入时间时，不计算忙闲率、完成概率或精确排程。
- 父任务与子任务可分别参与，但各自使用本任务的责任和行动。父任务不直接复制子任务的分数，也不因后代数量多而层层累加；父任务理由写统筹行动，避免重复推荐同一执行动作。

#### 6. 如何排序和解释

1. 先检查状态白名单及本人负责或参与的关系，再按 Task ID 去重。
2. 按当前有效事实分别取 B、C、P、D、H、Q。
3. 计算 I＝B＋C＋P；U＝max(D, H, Q)；W＝0.6×I＋0.4×U。
4. 按 W 从高到低；同分时先比较重要度 I，再比较紧急度 U，均从高到低；仍同分时，按可比较的截止时间从早到晚，无可比较截止时间排后；最后按稳定任务 ID 排序。
5. 排序使用未舍入的结果，展示或调试时最多保留一位小数。不能用传入数组顺序、随机数或重新生成的 AI 文案打破平局。
6. 一句优先原因说明最有贡献的重要度依据和当前紧急信号，再指出现在可做的事。无紧急信号时如实说明按目标或协作影响优先，不虚构截止压力。

有强依赖影响的任务可以比例行逾期任务靠前；已阻塞不必然第一，也不能被整体排除。**重要但不紧急的任务仍有排序权重，紧急但影响较小的任务也保留时间压力，两者通过固定比例综合，而不是先把所有逾期任务排完。**

#### 7. 完整算例

假设当前为团队时区 2026 年 9 月 3 日 10:00，以下任务均为本人负责或参与，状态在白名单内；相关事实已确认、资料完整。B／C／P 与 D／H／Q 的顺序固定如下，可逐项复算。

<div class="priority-score-table">

| 顺位与任务情境 | 重要度 I：B＋C＋P | 紧急度 U：max(D, H, Q) | 推荐权重 W |
| --- | --- | --- | --- |
| 1. 关键服务故障：无截止；关联核心承诺、影响多项交付、有“高优先级”标签；损失持续且下游停等本人 | 50＋30＋20＝100 | max(0, 100, 80)＝100 | **100** |
| 2. 阶段交付：9 月 10 日到期；支撑团队目标、影响两项下游、有“高优先级”标签；下游当前已停等本人 | 35＋30＋20＝85 | max(60, 0, 80)＝80 | **83** |
| 3. 方案核对：无截止；支撑团队目标、影响一项下游、有“重点任务”标签；已有材料待本人核对，未停工 | 35＋15＋20＝70 | max(0, 0, 60)＝60 | **66** |
| 4. 关键里程碑准备：无截止；关联核心目标、是里程碑必要条件、有“重点任务”标签；暂无当前损失或等待 | 50＋30＋20＝100 | max(0, 0, 0)＝0 | **60** |
| 5. 团队常规交付：今天到期；支撑团队目标，仅影响本项交付，只有业务分类标签；暂无其他问题 | 35＋0＋0＝35 | max(90, 0, 0)＝90 | **57** |
| 6. 例行内部整理：昨天逾期；有明确内部支持用途，无已证实下游影响，没有相关标签；暂无其他问题 | 20＋0＋0＝20 | max(100, 0, 0)＝100 | **52** |

</div>

第二项：W＝85×60%＋80×40%＝51＋32＝83。第三项：W＝70×60%＋60×40%＝66。没有日期的关键工作能够排在例行逾期工作前面，是重要度和非时间紧急信号共同作用的结果，不是遗漏了期限。

第一项的一句原因可写：“关键服务中断正在影响多项交付，需先协调恢复并回应等待方。”不能写成“未设置期限，所以不紧急”。

同分例子：任务 X 的 I＝80、U＝30，任务 Y 的 I＝60、U＝60，W 都为 60；按重要度，X 在前。若两项 I、U、截止均相同，则只按稳定任务 ID 决定顺序。

#### 8. 何时更新、保存什么、实现边界

负责人、参与人、状态、目标／完成标准、已确认的下游影响、标签的关联、名称或含义变化，以及截止时间、当前损失、阻塞／冲突、待本人处理事项、来源版本变化时重新计算。日期跨日、明确截止时刻经过或进入新的期限档位时，也更新 D。单纯刷新或页面重绘不改变分值和分析时间。

内部保存：规则版本、当前判断时刻与团队时区、输入摘要、入选／排除原因、B／C／P／D／H／Q、I／U／W、命中事实与来源版本、未知项、最终顺位和一句优先原因。相同输入、相同有效时刻及相同规则版本，应得到相同排序；变更参数需升级版本并重算，不静默改历史结论。

**规则版本：`PERSONAL-PRIORITY-2026-09-03-v4`。Skill：`agentdoor-personal-priority`。本节为 PRD 设计，本次未修改应用排序代码。** 当前原型仍用时间分＋问题分＋补充分，仍存在旧审核状态和同分逻辑；重要度事实识别、标签参考、本人负责或参与的推荐范围、上述状态白名单及新权重公式需后续接入，不能把文档更新表述为算法已上线。

### 7.7 EWD 工时评估＋进度

**先形成任务 EWD 拆分明细，每个明细项分别估算 EWD；AI 再逐项核对文件中的完成内容，最后按 EWD 权重计算任务完成度。** EWD 明细项是计算与核对单位，不会自动创建成子任务。

**Skill：** `agentdoor-ewd-progress`，按需执行 estimate（生成 EWD 拆分明细与预计投入）、progress（单项与总体完成度）、trend（燃起图）模式；创建任务时不运行执行阶段的文件核对。

| 部分 | 输出 |
| --- | --- |
| EWD 工时评估 | 任务 EWD 拆分明细：明细项、对应完成标准、预计 EWD、估算依据 |
| 完成度 | 每个 EWD 明细项的完成比例、文件依据、已完成 EWD，以及任务总完成度 |
| 燃起图 | 每个历史时点的任务总 EWD 与已完成 EWD |

<a id="ewd-platform-rule"></a>

#### 一、估算 EWD

**EWD 明细项：** 为满足任务完成标准，成员必须亲自投入时间的一项具体工作，例如整理资料、操作 AI、分析、制作、修改、沟通、审核或验收。每项同时写明可核对的完成结果；等待审批、排队和 AI 无人值守运行不列入明细。

1. AI 根据任务名称、目标和完成标准生成任务 EWD 拆分明细。每个 EWD 明细项是一项具体人工工作，同时对应一项可核对的完成结果；同级不重叠，并覆盖当前已确认任务范围的 100%。
2. AI 用八个投入维度检查任务，从已写明的信息中识别需要列入的 EWD 明细项、数量、条件与风险；同一项工作只列一次。
3. AI 为每个 EWD 明细项给出乐观值 O、最可能值 M 和保守值 P，程序按 `EWD＝(O＋4M＋P)÷6` 计算该项 EWD。
4. 任务总 EWD＝所有 EWD 明细项之和；共享工作只列一次，父任务只汇总叶子任务。
5. 初期使用平台维度与 AI 专家估算；后续根据团队历史任务的 EWD 拆分明细、完成标准和实际投入反馈校准估算。历史数据不足时继续使用平台规则。
6. 用户确认后保存 EWD 拆分明细、总 EWD 和规则版本作为本次估算基线；新增、删除或重估明细项时生成新版本，不回写旧基线和历史快照。

#### 平台初始 EWD 检查维度

八个维度是 AI 补全 EWD 明细项的检查清单，不打分，也不直接换算人天。每个维度必须回答“是否需要新增或调整明细、工作是什么、数量或次数、依据是什么”；同一项工作受多个维度影响时只保留一条明细，避免重复计时。

| 维度 | AI 检查什么 | 如何进入估算 |
| --- | --- | --- |
| 交付规模 | 结果数量、覆盖范围和适配版本 | 确定要制作、适配和交付几份结果 |
| 实现难度 | 完成结果所需的方法与专业判断 | 识别分析、设计、制作或开发动作 |
| 信息不确定性 | 需求、方法和结果是否明确 | 已识别风险进入 O／P 差异；关键条件未知则待估算 |
| 资料准备 | 输入资料是否可以直接使用 | 识别收集、整理、清洗、授权等准备动作 |
| 协作依赖 | 人工协调和外部输入有多少 | 识别沟通、等待前的人工跟进和交接动作；纯等待不计 |
| 修改迭代 | 已明确需要多少轮调整 | 按已明确轮次和受影响内容识别修改动作 |
| 核验验收 | 检查与验收要求有多重 | 识别自检、审核、复核和验收动作及人数 |
| 工具环境 | 工具、权限和环境准备工作 | 识别配置、接入、联调等 EWD 明细项；无人值守运行不计 |

AI 可以返回 `additionalFactor`，说明八个维度未覆盖的因素，并给出由此新增或调整的 EWD 明细项与三点估算。重复出现且有历史数据支持的因素，经团队规则评审后才能升级为团队扩展维度并记录版本。

#### 三点估算规则

**参考依据：** [PMI 的项目估算实践](https://www.pmi.org/learning/library/leveraging-new-practice-standard-project-estimating-6222)使用三点估算表达不确定性，并介绍常用的 PERT 加权平均公式 `(O＋4M＋P)÷6`。AgentDoor 将该方法用于每个 EWD 明细项；这些明细项在估算方法上对应 WBS 工作包。八个检查维度是平台规则，不是 PMI 规定的评分标准。

| 符号 | 名称 | 含义 |
| --- | --- | --- |
| O | 乐观投入 | 已确认的资料、工具和协作条件都顺利，没有额外返工时需要的人工时间 |
| M | 最可能投入 | 按当前已知条件正常完成时，最可能需要的人工时间 |
| P | 保守投入 | 已识别的不确定因素发生，但交付范围没有增加时需要的人工时间 |

**规则：** AI 只依据任务已写明的工作和风险，为每个 EWD 明细项估算 O、M、P，满足 `0≤O≤M≤P`；同一项工作只计算一次。程序计算 **单项 EWD＝(O＋4M＋P)÷6**，任务 EWD 为全部明细项 EWD 之和。关键条件不足、足以改变估算区间时标“待估算”。用户可以修改三点数值并补充依据；团队历史数据用于校准后续估算。

**数值来源：** 首版由 AI 根据任务名称、目标、完成标准、八个检查维度和已识别风险估算 O、M、P，单位统一为人天。它们不是固定分档，也不是 AI 随意打分；每个数值必须有对应工作和判断依据。用户可修正数值，后续再用团队历史任务的实际投入反馈校准。

**例子：制作一份方案。** 已知工作包括准备资料、操作 AI、人工修改和两人审核；任务同时明确存在“资料可能需要补充、审核后可能再修改一轮”的风险。

| EWD 明细项 | 对应检查维度 | O | M | P | 单项 EWD（人天） | 判断依据 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 准备资料 | 资料准备、信息不确定性 | 0.05 | 0.10 | 0.15 | 0.10 | 现有资料基本可用，但已明确可能需要补充 |
| 操作 AI | 实现难度、工具环境 | 0.05 | 0.10 | 0.15 | 0.10 | 使用现有工具生成一份方案初稿；保守情况包含一次提示调整 |
| 人工修改 | 实现难度、修改迭代 | 0.10 | 0.25 | 0.60 | 0.28 | 正常修改一轮；保守情况包含已识别的第二轮修改 |
| 两人审核 | 协作依赖、核验验收 | 0.10 | 0.20 | 0.30 | 0.20 | 两人分别审核；保守情况包含问题复核 |
| 任务合计 | 交付规模为一份方案 | **0.30** | **0.65** | **1.20** | **0.68** | 同一项工作虽对应多个维度，只计算一次 |

计算结果：`(0.30＋4×0.65＋1.20)÷6≈0.68`，**该任务 EWD≈0.68 人天**。

本规则同时采用面向交付的 WBS、范围 100% 覆盖、工作包逐项估算、估算依据和版本基线。“已完成 EWD”可类比挣值 EV；当前未记录按时间分配的计划值 PV 和实际投入 AC，因此燃起图只表示范围与完成工作量趋势，不作为完整的挣值管理 EVM。

<a id="ewd-completion"></a>

#### 二、逐项判断进度

AI 根据每个 EWD 明细项及任务已提供的内容判断该项完成进度，再按各项 EWD 汇总任务完成度；无法判断的明细项标记“待确认”。

**例子：AI 根据活动方案的完成标准生成 3 个 EWD 明细项，总 EWD 为 1.50 人天。**

| EWD 明细项 | EWD | AI 判断进度 | 已完成 EWD |
| --- | ---: | --- | ---: |
| 明确目标、预算和约束 | 0.25 | 100%：目标、预算和限制条件完整 | 0.25 |
| 形成完整活动方案 | 1.00 | 80%：主体流程和分工已完成，风险预案仍缺 | 0.80 |
| 核对并交付 | 0.25 | 40%：已完成格式检查，内容核对尚未完成 | 0.10 |
| 合计 | **1.50** | | **1.15** |

**任务完成度＝1.15 ÷ 1.50≈76.7%。**

<a id="ewd-burnup"></a>

#### 三、燃起图

每次 EWD 拆分范围、估算值或单项进度变化时保存快照。燃起图显示两条线：**任务总 EWD＝当时所有 EWD 明细项之和；已完成 EWD＝当时已有数字进度的各明细项「EWD × 单项进度」之和。** 存在待确认项时标明待确认 EWD，不把它解释为 0% 完成。两条线差距持续缩小表示任务趋于收敛，扩大表示新增工作超过已完成工作。

新增、删除或重估 EWD 明细项时标明范围变化；文件内容变化只更新受影响项。没有历史快照不补画趋势，同一文件反复上传不重复累计。

<a id="ewd-learning"></a>

**保留依据：** EWD 明细 ID、明细项、对应完成标准、八维检查结果、补充因素、各明细项的 O／M／P、EWD 与团队规则版本；文件版本、内容引用、单项进度、判断来源；每次任务总 EWD 与已完成 EWD 快照。团队历史数据用于更新团队 EWD 评估规则，当前文件内容用于判断当前进度。本节为待接入设计，未修改应用运行代码。


### 7.8 谁调用规则，什么时候更新

#### 创建任务的完整流程

| 流程步骤 | 归属 | 产物 |
| --- | --- | --- |
| 识别意图、明确目标和关键补问 | 创建任务 Skill 内部 | 有范围的需求 |
| 查重、拆分结果、判断父子与依赖 | 创建任务 Skill 内部，代码校验关系 | 任务草稿 |
| 匹配责任、安排必要协作与日期、建议已有标签 | 创建任务 Skill 内部 | 人员与时间建议 |
| 估算预计投入 | 创建任务调用 7.7 EWD 工时评估模块 | EWD、依据、假设与缺口 |
| 校验草稿、展示差异、用户确认 | 业务服务 | 确认后的提交 |
| 保存任务、估算和变更记录 | 业务服务统一事务 | 正式任务；选他人时负责人仍待接受 |

拆分、人员匹配不各开一个 Skill；规则表也不各开一个 Agent。创建时只调用需要的估算部分；执行中的结果核对和验收不是创建流程的必跑步骤。

#### 保存之后的更新表

| 保存的变化 | 更新什么 | 保留什么 |
| --- | --- | --- |
| 目标、交付数量或标准改变 | 检查受影响范围；相关估算依据和核对结论需复核；检查诊断和推荐 | 未受影响的结果与原始证据 |
| 子任务新增、移除、移动 | 更新新旧父级范围与汇总，相关诊断、进度和趋势；新增叶子按规则估算 | 已有历史点 |
| 本人责任、相关经验或公开窗口改变 | 刷新依赖这些资料的人员建议；实际工作假设改变才重估 | 正式 Owner 不自动更换 |
| 本人任务分工、实际贡献或责任建议反馈改变 | 调用人员责任分析，更新受影响的责任候选；用户确认后再刷新人员匹配依据 | 正式责任与原始来源，旧建议不覆盖新版本 |
| 正式 Owner 改变 | 更新新旧负责人的“我的工作”，核对相关工作假设 | 人名变化本身不改变工时 |
| 文件新版本、相关反馈或明确贡献记录 | 核对关联标准，更新已完成 EWD、完成度、燃起图、内容诊断与摘要；内容改变估算假设时才重估总量 | 仍适用的 EWD 和历史快照 |
| TaskStatus 改变 | 更新状态说明、关系诊断、个人推荐 | EWD 与正式验收不随之修改 |
| 截止日期或正式依赖改变 | 检查日期、依赖诊断，更新推荐和摘要 | 仅日期变化不改 EWD；依赖改变实际交付工作时再重估 |
| 内容核对或确认结果改变、撤销或失效 | 更新已完成 EWD、完成度、父级汇总和燃起图；读取失败时标待核对，不补 0 | 原始估算、历史点 |
| 实际跨日 | 按团队时区重新计算到期与个人排序 | 工时、验收、交付核对结果 |
| 权限改变 | 清除当前用户不再有权读取的内容与分析缓存，重新核对覆盖 | 服务端受控历史保留，但不继续展示给无权用户 |

**运行方式：** 正式修改和变更记录一起保存；后台根据上表找受影响任务、祖先、后续依赖任务及相关负责人。代码能算的先算，需要理解文字的再调用对应 Skill。每次结果保存任务版本、证据版本、规则版本和读取范围；发布前重新核对，旧请求丢弃。

同一输入已有有效结果就复用。切页签、展开明细、尚未保存的输入不重算。失败保留有权限的旧结果并标“已过期”，用户可重试；刷新不伪造新的数据截至时间。同一页面的诊断、进度和摘要必须明确各自版本；不能将旧摘要包装成已解释新进度。

**规则维护：** 新规则发布要有编号、适用条件、参数来源、例子和版本。新版本使相关分析需复核，不自动改已采用估算或历史曲线。参数调整、模型理解错误和算术错误分别记录；当前未采集实际投入，不开展个人效率排名或声称估算已完成校准。

### 7.9 人员责任分析 Skill

**目标：持续跟进当前用户负责或参与的任务，识别本人实际承担的工作，结合用户确认和纠正，让责任说明越来越准确，为后续成员推荐提供更可靠的依据。** 判断“通常负责什么、责任边界在哪里”，不做能力、效率或绩效评分。

**Skill：`agentdoor-responsibility-advisor`。** 将第 2.5 节已有责任建议明确为独立的人员责任分析 Skill，复用“我的责任”的建议、依据和确认入口，不另建用户画像。

#### 1. 分析范围与输入

- 仅分析当前用户在当前团队中负责或参与、且当前有权读取的任务；不同团队的责任与证据分开保存。
- 输入责任文本与版本、任务目标与完成标准、本人分工、实际交付／贡献、相关讨论与确认、任务／交付来源及版本，以及历史建议和用户反馈。
- 已完成任务仍可作为历史依据；待开始任务只说明当前分工，不能当作已经执行。已取消任务只保留可证实的实际承担事实，不推断交付完成。本分析不套用“我的工作”的三状态排序范围。
- 输入注明数据覆盖、时间与权限；参与名单不等于实际承担，任务完成也不等于所有成果都由负责人独立完成。

#### 2. 分析步骤

| 步骤 | 判断什么 | 产物 |
| --- | --- | --- |
| 识别实际承担 | 本人在任务中具体负责什么结果、提供什么贡献，哪些记录可以证明？ | 带来源的承担事实；不能归属的内容标待核对 |
| 归纳责任范围 | 哪些是持续出现的工作，哪些只是一次临时协助或阶段性安排？ | 有范围、时效和依据的责任候选，不直接写“擅长”或“效率高” |
| 对照现有责任 | 已有描述是否覆盖实际工作，有没有缺失、过宽、重复或已确认的职责变化？ | 新增、更新、废弃或不调整，并指出对应原责任 |
| 用户核对 | 建议是否准确，责任边界需要怎样修改？ | 用户确认后才写入；保留修改、忽略与纠正记录 |
| 反馈校准 | 新任务事实和用户纠正改变了哪些判断？ | 更新后续建议的依据与范围，确认后的责任版本供成员推荐使用 |

一次临时协助不直接推成长期责任；多个独立任务的同类承担或明确的长期分工确认，可支持归纳。任务数量、在线时长和提交间隔不能代替实际承担证据；同一成果的多版本、父子引用不重复计数。没有近期任务或来源失效不代表职责消失；废弃建议需有明确职责调整依据。

#### 3. 输出与用户决定

每条建议包含操作、责任文本、原责任与基准版本、改变原因、任务与交付来源、数据时间、团队与范围、未确认事项。已有责任准确时输出“不调整”；证据不足保留原文并说明缺口。

复用“我的责任”：用户可查看依据、采纳、修改或忽略；旧建议不能覆盖新版本。未经确认的建议不进入正式责任匹配。Skill 不自动修改 Task Owner、参与人或权限；确认责任建议不等于接受具体任务。

**更新流程：** Skill 支持分析建议、准备更新、执行已确认更新三种模式。用户确认后才写入；确认绑定最终操作、责任文本、用户与团队、原责任及基准版本。业务服务独立校验权限、当前版本和幂等并返回回执；Skill 根据回执说明更新结果，不把候选的“可确认”当作写入授权。用户修改文本后须确认最终版本；旧建议或版本冲突时重新核对，不能覆盖新责任。写入接口未接通或回执未知时保留建议，明确待接入或待核实，不声称已更新。

#### 4. 何时分析，如何越来越准

- 本人任务分工、相关交付／贡献、确认记录或用户责任发生实际变化时，只重算受影响的责任候选；本人可主动触发重新分析。打开页面不制造新证据或新分析时间。
- 用户纠正需与被纠正建议及来源版本关联，例如“只是这次临时帮忙”“负责脚本，不负责投流”；后续判断复用该边界，新证据与之冲突时提出待核对，不静默覆盖用户说明。
- 忽略不等于否定，也不代表该用户拒绝承担工作；同一来源版本的已忽略建议不反复推送，实质证据变化后才重新判断。
- 来源撤销、权限变化、任务贡献被更正后，相关候选失效并复核；读取失败不等于没有责任。正式责任仍由用户决定是否调整，失效证据不得继续对外展示或用作新增推荐理由。
- 每次保留输入、来源版本、规则版本、建议与用户处理结果。同样输入和反馈复用有效结果；这里的持续校准是更新事实、责任边界与建议，不是重复刷新或默认开展模型训练。

**例子：** 用户原责任是“内容制作”，近期多次实际承担达人短视频脚本交付，可建议细化为“负责达人短视频脚本策划与交付”，附任务依据。用户纠正直播协助仅为临时安排后，不再凭同一记录归纳为长期责任。

**验证目标：** 看责任遗漏、错误归属和重复错误是否减少，成员推荐能否更准确地解释匹配原因；不以建议数量或文字长度代表准确，不对成员排名。

**实现边界：** 已设计项目内 Skill 文件，并同步更新 PRD、HTML 与 PDF。现有责任建议界面可复用；任务变更触发、贡献归属分析、反馈回读、受控责任写入与生产数据接入仍待实现，尚未启动后台持续分析。

## 8. MCP：工具与参数设计

### 8.1 用来解决什么

让个人 AI、MCP App 和普通页面操作同一份任务事实。REST 与 MCP 共用身份、权限、版本、幂等和事务服务，不能让 MCP 再存一套正式任务。

```text
页面 / 个人 AI → MCP 适配器或 REST → 同一领域服务 → 业务数据 / 变更回执
```

下面合并原《任务 REST API 与 MCP 工具契约》v0.1 的 **38 个候选工具**，并补齐阅读所需的参数类型和条件。它们仍是 Proposal；本次补充的必填性、枚举和字段白名单是待评审建议，不是现网 Schema。当前运行代码只有第 8.10 节的两个演示工具。

### 8.2 通用参数与回包

下表工具均使用完整 `agentdoor_` 名称。表中未标 `?` 的参数必填；`?` 表示可选。ID 均为非空 string；ID[] 为去重字符串数组；version 为正整数；null 是明确清空，不等于省略。

| 记号 / 参数 | 类型、默认值与校验 |
| --- | --- |
| `W` | 所有写工具共同带 `idempotency_key:string`；同一次业务操作及同一载荷重试用同一键 |
| `V` | 修改已有对象带 `expected_version:integer>=1`；从最近读取返回的 version 获取，不由模型猜 |
| `P` | 列表带 `cursor?:string, limit?:integer>=1`；默认 50，服务端限制最大值并回显；游标不跨查询条件复用 |
| 日期 | `YYYY-MM-DD`，日历日期校验；时间戳使用含时区的 ISO 8601，服务端记录 UTC |
| 未列字段 | 拒绝额外字段；不接受任意 JSON Pointer、SQL、任意本地路径或模型自报权限 |
| 身份 | team scope、真实 Principal、代表的成员和委托来自认证上下文；可选过滤参数不能扩权 |

**MCP → REST 映射**：`expected_version` 由适配器转换为 `If-Match`，`idempotency_key` 对应 `Idempotency-Key`；snake_case 工具参数转换为服务端 camelCase 字段。只在适配层映射，不能存两份不同字段。列表 `list_*` 对应 GET 集合，`get_*` 对应 GET 单资源，其余映射见各表。

成功返回 `content`（给人一两句话）和 `structuredContent:{data,receipt}`；错误为 `isError:true` 与 `structuredContent.problem:{code,message,retryable,recoveryAction}`。调用方解析结构化字段，不解析自然语言当作事实。

| 回执字段 | 意义 |
| --- | --- |
| `schemaVersion / operationId` | 写回执版本 `agentdoor.write-receipt.v0.1` 与操作标识；外层 meta 带 requestId、asOf |
| `outcome` | `succeeded / no_change / accepted_async / needs_confirmation` |
| `effect` | `none / proposed / applied`；只有 applied 才表示正式数据生效 |
| `replayed / atomic` | 是否幂等重放、是否整批原子成功 |
| `affectedResources[]` | 对象类型、ID、动作、beforeVersion、afterVersion；新建前版本为 null |
| `changeSetId / changeDigest / generatedActivityIds / committedAt` | 可追踪变更与实际提交时间；未应用不得伪造业务提交时间，Proposal 需细化各 outcome 的字段必填条件 |

默认 compact 返回 ID、状态、版本、关键差异和回执；长讨论、证据、文件正文分页获取。版本冲突或确认预览使用 standard。原契约的 detailRef / full 回传仍需补充具体资源读取地址，不能把一个不可读取的引用当作完整实现。

### 8.3 Task 与子任务：9 个工具

| 工具 / 操作 | 参数与返回重点 |

| `agentdoor_list_tasks` · GET /tasks | `filters?:TaskFilters, P` → 可见 Task 列表、nextCursor、asOf |
| `agentdoor_get_task` · GET /tasks/{id} | `task_id:ID` → 当前 Task、version；不可发现对象不透露其存在 |
| `agentdoor_create_task` · POST /tasks | `TaskCreateFields, W` → 正式 Task 与写回执；不是模型准备草稿步骤 |
| `agentdoor_update_task` · PATCH /tasks/{id} | `task_id:ID, V, updates:TaskUpdate[], W` → 更新后的对象或 no_change |
| `agentdoor_get_task_deletion_impact` · GET /tasks/{id}/deletion-impact | `task_id:ID` → 当前 taskVersion、可公开影响、impactDigest、requiresExplicitCascade |
| `agentdoor_delete_task` · DELETE /tasks/{id} | `task_id:ID, V, impact_digest:string, cascade?:none或descendants, W` → 逻辑删除回执；默认 none，有后代必须明确确认 |
| `agentdoor_change_task_status` · POST /tasks/{id}/status-transitions | `task_id:ID, V, to_status:TaskStatus, reason:string, evidence_refs:ID[], W` → 状态转换回执；证据必需性按转换规则校验 |
| `agentdoor_list_subtasks` · GET /tasks/{id}/subtasks | `parent_task_id:ID, P` → 仅直属、可见子 Task；继续按子 ID 获取下一层 |
| `agentdoor_create_subtask` · POST /tasks/{id}/subtasks | `parent_task_id:ID, TaskCreateFields, W` → 普通 Task，parentTaskId 由服务端绑定，不重复接收父级字段 |

`TaskFilters`：`team_id?:ID, status?:TaskStatus, owner_id?:ID, parent_task_id?:ID或null, label?:string, query?:string, updated_after?:ISO时间`。建议 parent_task_id 省略=不限制，null=根任务，ID=直属子任务；前端标签或状态查询不等于完整查重。

| TaskCreateFields 字段 | 类型与默认 / 规则 |
| --- | --- |
| `name` | 非空 string；正式接口统一用 name；planner 的 title 在适配层转换 |
| `goal` | 非空 string；子任务沿用已读取的主目标，不借子任务创建修改主目标 |
| `completion_criteria` | string[]，至少一项非空完成标准；对应 REST completionCriteria |
| `owner_id?` | ID 或 null，默认 null；选他人时产生责任提议，不伪造其接受；已有 Owner 变更不走普通更新 |
| `participant_ids?` | ID[]，默认 []；同团队有效成员、不重复 Owner；正式参与成立仍受现行接受规则控制 |
| `planned_start_on? / planned_end_on?` | 日期或 null，默认 null，不默认今天或 7 天后；校验前置和父级范围 |
| `depends_on_task_ids?` | ID[]，默认 []；禁止自指、循环和无效引用，父子关系不自动生成依赖 |
| `labels?` | string[]，默认 []；本 v0.1 原契约尚未确定标签字符串是稳定 ID 还是名称，接入标签模块前统一 |

`TaskUpdate` 为 `{field,value}`，数组至少一项；白名单及 value 类型：`name:string`、`goal:string`、`completionCriteria:string[]`、`participantIds:ID[]`、`dependsOnTaskIds:ID[]`、`plannedStartOn:date|null`、`plannedEndOn:date|null`、`labels:string[]`。这里 field 枚举沿用原文 camelCase；MCP 外层仍为 snake_case。数组整体替换，靠版本防止覆盖他人修改。

`TaskStatus` 使用 `open / in_progress / blocked / completed / cancelled`，分别对应待开始、进行中、已阻塞、已完成、已取消。不新增审核状态；交付核对是处理事项，不替代任务状态。状态转换图、正式验收、Owner Transfer 均未在本次补成可用接口。

**删除边界**：影响包括可见后代、依赖方、文件引用及草稿；确认绑定 impactDigest。影响变化报 `DELETION_IMPACT_CHANGED` 并重做预览；不可见影响由服务端判定能否操作，不透露隐藏名称、ID 或数量。逻辑删 Task 不删共享 File、正式 Commit 或审计事实。

#### 文件参数展开

| 结构 | 具体字段与条件 |
| --- | --- |
| `UploadTarget` 新文件 | `{kind:new_file,task_id:ID,folder_id?:ID|null}`；文件夹必须属于目标任务且有权限 |
| `UploadTarget` 新版本 | `{kind:new_file_version,file_id:ID,expected_file_version_ordinal:integer>=1}`；准备和完成阶段都校验当前基准，避免覆盖新版本 |

| `FileMetadataUpdate` | 本次建议先仅开放 `{field:name,value:string}`；原契约未列具体白名单，maintainer / visibility 等先不开放，不能借元数据更新改权限 |

### 8.8 安全、失败与重试

| 场景 | 服务端结果 / 客户端动作 |
| --- | --- |
| 超时或重复点击 | 用原幂等键和原载荷重试，返回同一 ID 和 replayed=true；不同载荷复用键返回 409 |
| 并发更新 | 版本不一致返回 412 VERSION_MISMATCH，保留用户草稿、读取新版本、重新确认；不自动覆盖 |
| 删除影响变化 | 409 DELETION_IMPACT_CHANGED；重新预览和确认，旧摘要失效 |
| 无权限 | 已知且可暴露存在的对象可报 403；不可发现对象统一 404；重放旧回执也要重新鉴权 |
| 验证不通过 | 400 结构错误，422 领域约束错误，428 缺版本前置条件；指出允许公开的字段问题，不写半份数据 |
| 文件仍扫描 | accepted_async，不当错误也不当可用；通过 upload status 查询后续状态 |
| 多任务计划 | 主任务与子任务创建需受控原子命令；当前 38 个工具没有整棵计划提交工具，不能逐项调用后宣称原子成功 |

annotations 只帮助调用方识别 readOnly / destructive / idempotent，不提供权限。删除、正式提交、状态变化的授权必须绑定实际对象和影响；不得把模型“用户已同意”的文字当作确认凭证。

### 8.9 Skill 与 MCP 如何对接

| 能力 | 可复用工具 | 尚缺的数据能力 |
| --- | --- | --- |
| 人员责任分析 | list_tasks、get_task、讨论／文件／Commit／Activity 查询 | 本人负责或参与的任务范围、责任文本与版本、贡献归属、用户确认与纠正记录、增量触发、建议生成、确认绑定与受控责任写回；不增加隐性能力／效率评分 |
| 创建与人员匹配 | list_tasks、get_task、list_subtasks、list_task_discussions、read_file_version_content | 授权成员与正式责任读取、语义查重服务、计划确认绑定和原子提交；现有工具不能仅靠名字搜索完成全部判断 |
| 状态分析 | get_task、list_subtasks、讨论 / 文件 / Commit / Activity 查询 | 引用工时评估与进度模块的结果；当前情况与建议需绑定同一范围和版本 |
| EWD 工时评估＋进度 | get_task、list_subtasks、文件版本与内容读取；历史任务可选 | EWD 拆分明细生成与估算、文件内容核对、单项进度及快照服务；上传或 Commit 本身不计完成 |
| 任务诊断 | Task 与后代 / 前置查询、讨论 / 文件版本 | 任务信息与文件的当前内容、来源版本、可见范围完整性声明；须递归读取可见后代而非只查一层 |
| 个人优先级 | list_tasks／Task 读取、上述状态与诊断结果 | 本人负责或参与的任务范围筛选、当前用户身份注入、同快照聚合与过期策略；左侧筛选结果不能当作个人全集 |

表中工具名为去掉 `agentdoor_` 前缀的简称。缺项属于后续接口设计，不伪装为已有 MCP。最先对接的是受控读取与统一回执，再接单任务写入、文件和正式提交；验收与责任转移规则确认后再增加相应命令。

### 8.11 调用示例：预览后更新任务

以下为候选协议示例，不是本次真实调用；身份、权限和确认由受信协调层完成。

```json
{
  "tool": "agentdoor_update_task",
  "arguments": {
    "task_id": "task-example",
    "expected_version": 7,
    "updates": [
      { "field": "goal", "value": "完成已评审的发布会媒体邀请名单" }
```
