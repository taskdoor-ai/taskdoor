## 1. 产品流程

```text
加入团队
  → 维护个人责任
  → 创建任务
  → AI 分析并生成任务方案
  → 用户确认任务、人员和投入
  → 任务进入左侧列表
  → “我的工作”推荐当前优先事项
  → 在任务详情中持续协作和跟进
```

TaskDoor 中只有一种工作对象：Task。

子任务也是 Task。标签、文件夹、讨论和活动都不能代替 Task，也不能代替父子关系或依赖关系。

---

### 1.1 全局操作提示 Toast（2026-09-14）

- 邀请发送、保存、复制、删除／撤销等短时操作反馈统一使用共用 Toast，固定在视口顶部居中；桌面距顶部 24px，窄屏 12px，并避让安全区域。弹窗打开时仍显示在上方，不跟随页面或弹窗滚动。
- 成功、失败、普通说明复用同一尺寸、圆角、阴影与关闭入口，以图标和文案区分；普通提示 4 秒、错误 6 秒、带操作的提示 8 秒自动消失。悬停、键盘聚焦或窗口失焦时暂停倒计时。
- 同一提示重复触发时更新内容并重新计时，不重复堆叠；最多显示 3 条。新提示不抢焦点，F6 可聚焦提示区；关闭和操作按钮支持键盘与至少 44px 触达，窄屏长文案及操作换行，不产生横向滚动。减少动态效果时关闭过渡。
- 邀请成功提示只显示「邀请已发送，等待对方加入」和关闭按钮；重发只显示一条「邀请已重新发送，旧链接已失效」。两者均不提供「查看邮件」，按普通提示 4 秒自动消失（2026-09-15 修订）。文件删除后的「撤销」保持原恢复操作；带上下文的操作在离开对应任务或切换团队后移除，避免操作旧对象。
- 输入校验、草稿冲突、加载及需要持续处理的错误留在相关字段／区域，不用会自动消失的 Toast 替代。界面显示正式运行文案。

## 2. 团队成员、邀请与个人责任

### 2.1 团队成员

用户可以在“设置 → 成员”中：

- 查看当前团队成员。
- 查看成员的责任说明。
- 通过链接或邮箱邀请新成员。
- 管理管理员和普通成员角色。

邀请只表示邀请对方加入团队，不表示对方已经参与任务或负责某项工作。

### 2.2 邮箱搜索与邀请

**本次决策（2026-09-14 修订）：** 人员搜索下拉和「设置 → 成员」共用「邀请人员」弹窗。下拉只提供入口，填写名称和邮箱、明确点击「发送邀请」后才创建待加入人员。名称选填，邮箱必填；账户是否注册与是否加入团队分开记录，成员状态统一为「待加入」。Demo 展示正式运行时的用户文案；生产中的「邀请已发送」反馈须依据真实发送结果。

1. 在人员下拉输入名称或邮箱无匹配时，空结果区域居中显示「没有找到匹配的成员」、说明「发送邮件邀请对方加入「{{团队名称}}」，一起协作。」及「邀请人员」按钮。说明默认单行居中展示，空间不足时自然换行。有「暂不分配」选项时保留单行，隐藏其说明与重复的「立即邀请」。人员筛选和讨论提及不提供邀请。
2. 点击「邀请人员」打开统一弹窗：名称搜索预填名称，邮箱搜索预填邮箱；包含 @ 的未完整邮箱保留在邮箱字段，供用户补全。两项均可编辑，名称选填（去除首尾空格，最多 100 个字符），有效邮箱必填。取消、关闭或 Escape 只退出弹窗，不新增人员、不发送邀请、不改变当前选择。 从人员下拉打开时，邀请弹窗直接覆盖在列表上方，保留背景中的搜索内容和结果，不先关闭或清空列表；取消后回到原搜索框，发送成功后再一起收起弹窗和列表并返回人员入口。打开和关闭采用短淡入淡出，关闭动画结束前保留表单内容；系统要求减少动态效果时取消明显动画。
3. 点击「发送邀请」后按当前 Team＋规范化邮箱查重并保存。邮箱去除首尾空格、忽略大小写，不自行删除加号别名或邮箱中的点。新人员使用稳定 ID，并保存邀请时填写的名称；无姓名时人员下拉以邮箱识别，使用通用头像。
4. 设置成员列表第一行显示名称及「待加入」，未填写名称时显示「未设置名称」；第二行只显示邮箱，不再显示邀请时间。对方完成对应邮箱的注册／登录、验证并明确接受后，更新原记录为账号名称／头像和正式成员状态，已有 Task 引用保持不变。
5. 从人员下拉打开弹窗，成功保存后回填本次人员选择；创建草稿保留选择，详情继续遵守既有提议／参与邀请流程。设置和其他独立邀请入口只维护团队成员，不操作当前 Task。
6. 生产流程同时创建发信任务并发送注册链接。保存失败时弹窗保留名称、邮箱和原有选择；发信失败保留同一待加入记录并提供重试，已提交发信不等于送达。
7. 已有成员／待加入记录不重复创建、不自动重发，也不覆盖原名称。从下拉打开弹窗后若填写了已有邮箱，可点击「使用此成员」回填原人员；设置中提示无需重复邀请。成员列表的待加入人员只提供「重新邀请」，移除「查看邮件」（2026-09-16 修订）；重新邀请仍使用原人员 ID 和名称，生成新 token 并使旧链接失效。
8. 接受链接保留受邀邮箱、团队和邀请信息，贯穿注册、验证、登录与切换账号。邀请、注册、验证和加入团队均不代表接受任务责任，不自动确认 Owner 或参与邀请，也不改变任务状态。
9. 首版沿用团队管理员邀请权限。设置弹窗可以选择成员／管理员角色；人员下拉及其他独立入口默认普通成员。普通成员可选择已有人员但不能生成新邀请；团队至少保留一名管理员。

**边界和交互状态：**

| 情况 | 行为 |
| --- | --- |
| 名称／邮箱无匹配 | 显示居中的邀请入口，打开弹窗并预填对应字段，不直接创建 |
| 邮箱未填写／格式无效 | 不能发送；允许补充或修改邮箱 |
| 只有邮箱、未填写名称 | 可以发送；后续加入时更新为账号名称 |
| 已有成员或待加入记录 | 复用原人员；下拉入口允许「使用此成员」，设置入口提示无需重复邀请 |
| 搜索仍加载／失败 | 不把未知结果当作不存在；生产目录完成查询后再显示无匹配入口 |
| 提交中 | 阻止重复提交；生产异步发信时显示「正在发送邀请…」 |
| 无权限／多选已满 | 邀请入口禁用并说明原因 |
| 取消／关闭 | 不新增人员、不发信，不改变原选择；从下拉进入时返回原搜索内容和结果，设置入口返回原按钮 |
| 保存失败 | 保留名称、邮箱和当前选择，展示错误并允许重试 |
| 发信失败／链接过期 | 人员保持待加入；重试／重新邀请复用原记录和名称 |
| 邀请已撤销／团队已删除／角色已变化 | 接受时服务端重新核验，无效链接不产生加入或权限效果 |
| 当前登录邮箱不符 | 展示受邀邮箱并提供切换账号，不能认领他人的邀请 |
| 窄屏与键盘 | 弹窗不超出视口；Tab 可访问表单和按钮、Enter 提交、Escape 关闭并恢复焦点 |

#### 2.2.1 邮箱邀请模板

主题：**{{邀请人姓名}} 邀请你加入「{{团队名称}}」｜TaskDoor**

正文：

> {{邀请人姓名}} 邀请你以{{加入角色}}身份加入「{{团队名称}}」，在 TaskDoor 一起协作。
>
> 请使用 {{受邀邮箱}} 注册并验证邮箱；已有 TaskDoor 账号可直接登录，然后确认加入团队。
>
> **接受邀请并加入** → {{邀请链接}}
>
> 链接自生成起 7 天内有效。过期后请联系邀请人重新邀请。如果你不认识邀请人，可以忽略此邮件。

模板同时提供 HTML 和纯文本版本，按钮不可用时可复制完整链接。发信人地址、回复地址及发信服务在生产接入时配置；邮件只包含本次加入团队所需信息。**7 天为本次原型采用的默认值，生产有效期与重发频率仍需在接入时确认。**

#### 2.2.2 数据、验收与实现边界

- 数据至少包括 Team ID、稳定人员／membership ID、邀请名称（可空）、规范化邮箱、成员状态、加入角色、邀请人、token、创建／到期时间、发信状态及服务商回执。账户绑定和任务责任状态独立于成员邀请状态。
- 生产要求：服务端鉴权与邮箱验证、按 Team＋邮箱唯一约束、邀请记录与发信任务可靠提交、幂等重试、token 安全存储和失效、发信限流、接受时重新核验权限，并保留真实发送／加入事实。
- 验收：名称／邮箱无匹配均可打开同一弹窗并正确预填；取消不写入；仅邮箱也能邀请，名称保存后正确展示；下拉入口提交成功后回填、设置邀请不改任务；成员第二行只显示邮箱；刷新后仍存在且不重复；成员列表和选择器均显示待加入；接受前后 ID 不变、任务引用不丢失；错误邮箱、失效链接或未验证账号不能激活成员；加入不自动接受任务责任；失败可重试。
- **Demo 文案：** 用户界面按正式流程显示「邀请已发送，等待对方加入」「重新邀请」，不出现「预览」「不会实际发送」等实现说明。邮件中的正常注册链接不附带调试参数，加入成功后显示「进入工作区」。
- **当前实现是本地交互原型：** 人员和邀请保存在浏览器本机，支持重新邀请，以及邀请链接对应的同一浏览器内注册／登录／接受和原成员状态同步；成员列表与 Toast 均不提供查看邮件入口，邮件模板保留在本节。注册为演示验证流程，账号保存在当前浏览会话中，验证码仅在显式开启调试模式时展示。真实邮件、生产账号与权限服务尚未接通，Demo 的成功提示是模拟运行效果，不是实际发信回执；其他设备不能使用本机邀请。以上实现边界只保留在研发文档中，不进入用户操作界面。

### 2.3 我的责任

“我的责任”记录成员在当前团队中通常负责什么。

用户可以：

- 手工新增、修改或删除责任。
- 查看 AI 对已有责任的更新建议。
- 查看 AI 建议新增的责任。
- 查看建议所依据的任务或交付记录。

### 2.4 AI 责任建议

AI 可以根据已确认的任务责任和交付记录，建议新增、更新或废弃一条责任。

AI 先生成建议，人员责任分析 Skill 组织用户核对及确认后的更新流程；未经用户确认，不直接修改责任。

- 更新建议默认收起。
- 用户点击“更新”后，才替换原责任。
- 新增建议通过候选行展示。
- 用户点击加号后，才写入责任。
- 原责任已经被修改时，旧建议不能继续覆盖。
- 权限不足或证据不足时，AI 不生成确定结论。

### 2.5 人员责任分析 Skill

建立“人员责任分析” Skill，复用现有责任建议契约名 `agentdoor-responsibility-advisor`。持续跟进当前用户负责或参与的任务，结合实际承担的工作和用户反馈，让“我的责任”越来越准确，再用于成员推荐；不做能力、效率或绩效评分。完整规则见第 7.9 节。

输入：

- 当前用户和当前团队。
- 当前责任文本及版本。
- 当前用户负责或参与且有权限查看的任务、本人实际贡献、交付和相关讨论／活动记录。
- 证据时间和来源。
- 用户对历史责任建议的确认、修改、忽略及纠正记录。

输出：

- 新增、更新、废弃或不调整。
- 建议文本。
- 对应的原责任。
- 建议依据。
- 数据时间和信息缺口。

Skill 负责责任建议与确认后的更新流程；业务服务校验用户确认、权限和当前责任版本后写入，并返回实际结果。写入能力未接通时只返回建议，不声称已更新，也不能修改 Task Owner、参与人或权限。

## 3. 创建任务

### 3.1 创建流程

1. 用户点击左侧“新建任务”。
2. 用户输入希望完成的事情。
3. AI 判断信息是否足够。
4. 必要时提出最多两个关键问题。
5. AI 检查已有任务、成员责任和可用资料。
6. AI 生成主任务和必要的子任务。
7. AI 建议负责人、参与人、标签和预计投入。
8. 用户修改或让 AI 帮助调整方案。
9. 用户最终确认后，系统正式创建任务。

最终确认之前，页面中的内容都是草稿，不能提前写入正式 Task。

### 3.2 创建任务 Skill

当前已有 `agentdoor-task-planner` Skill，用于生成和调整任务方案。

它负责：

- 判断用户是创建、调整、继续规划还是查询。
- 补问真正影响目标和交付的问题。
- 检查相似任务和已有关系。
- 生成主任务和子任务草稿。
- 建议负责人和参与人。
- 建议标签、依赖和预计投入。
- 输出调整前后的差异。

它不负责：

- 创建正式任务。
- 自动指派负责人。
- 自动邀请成员。
- 替成员接受任务。
- 自动修改已有正式责任。
- 自动验收或关闭任务。

### 3.3 任务内容

每个 Task 至少包含：

- 名称。
- 目标。
- 完成标准。
- 正式负责人或待接受负责人。
- 参与人。
- 状态。
- 时间。
- 标签。
- 父任务和前置依赖。
- 预计人类投入。

名称用于快速识别，目标用于描述希望达到的结果，两者不能写成相同内容。

### 3.4 子任务拆分

结果必须能独立交付、独立验收，并至少需要独立负责、单独交接或并行推进之一，才拆成子任务。详细判定见第 7.3 节；单纯需要复用资料，不构成拆分理由。

以下内容通常不拆成子任务：

- 普通操作步骤。
- 同一交付中的分析、执行和复核。
- 只需要一次咨询或资料补充的协作。
- 为了让方案显得完整而增加的阶段。

父子关系只表示范围包含，不自动产生前置依赖。

### 3.5 人员匹配

AI 按以下顺序推荐人员：

1. 检查成员是否可被发现，以及是否有权限参与当前工作。
2. 检查成员的正式责任是否覆盖整个任务结果。
3. 检查相关任务、文件和业务对象经验。
4. 检查成员主动公开的协作方式和可投入窗口。
5. 展示候选差异，由用户决定。

AI 不能通过任务数量、在线状态、回复速度或私人日历判断成员是否空闲。

没有合适人选时，任务可以保持未分配。不能默认把创建者、主管或首位成员填为负责人。

### 3.6 负责人规则

- 一个 Task 最多有一位正式 Owner。
- 用户选择自己负责时，可以直接成为正式 Owner。
- 用户选择其他成员时，先记录为待接受提议。
- 对方接受后，才成为正式 Owner。
- 待接受人不能进入“我的工作”。
- 已有正式 Owner 的变更不能通过普通编辑直接完成。

### 3.7 标签

AI 可以根据任务对象和交付结果建议已有标签。

- 标签可以修改或清空。
- 标签不是状态、目录或父子关系。
- 不创建主标签或标签组。
- 一个任务可以有多个标签，但在左侧列表中只出现一次。

### 3.8 工时和成本

当前只确定预计人类投入 EWD。

EWD 表示：在明示的估算条件下，完成当前范围预计需要多少人类投入；首版按常用工具及模板条件粗估，不假定用户实际采用了 AI。

**对任务的价值：** 预计投入人天表示完成任务预计需要的总人工工作量，帮助团队看清任务规模、投入主要花在哪里，并按工作量衡量完成进度。

**统一展示单位为人天，1 人天＝8 人时＝480 分钟。** 页面仍叫“预计投入”，例如“预计投入约 5 人天”；这是总人工投入的换算单位，不是日历工期，也不表示每位成员每天有 8 小时可用于此任务。40 小时的总人工投入应换算成 5 人天，不能直接改标签变成 40 人天。

首版根据任务名称、目标和完成标准生成任务 EWD 拆分明细，再按平台八个投入维度为每项进行三点估算；任务总 EWD 为各明细项之和。没有历史也能使用；规则、算例及后续学习方法见第 7.7 节「EWD 工时评估＋进度」。

计入：人工准备、操作、沟通、审阅、修改和验收。

不计入：等待时间、排队时间、无人值守的 AI 运行时间和自然工期。

- 未知不能按 0 计算。
- 子任务缺少估算时，不计算完整总投入。
- 父任务汇总叶子任务，不能重复累计。
- 目标、完成标准或工作方式变化后，需要重新估算。
- EWD 不等于工期、剩余时间、个人效率或任务优先级。

预计投入以 EWD 明细项为单位，记录对应完成标准、八维检查结果、三点估算、估算依据和 EWD；无法判断的工作保留待估。用户修改估算另存来源，不能当作实际耗时直接训练。

初期使用平台规则；后续积累团队历史任务的目标、完成标准、交付结果和投入反馈，逐步校准该团队的三点估算，供后续任务使用。数据不足时沿用平台规则；没有真实人工投入反馈时，不声称已校准真实工时，也不根据提交间隔设置个人效率系数。判断逻辑见第 7.7 节。

创建页在预计总投入下展开数字列表，按预计工时从高到低展示任务名称，右侧简写为“1.25 人天 · 25%”；不再重复“预计／占总投入”，也不展示饼图，避免信息冗余。占比的分母是当前全部叶子任务的有效 EWD；缺估或需重估时只显示已估部分，不计算占比。

金额成本暂不进入首版。人员费率、外部费用、币种和查看权限确认后，再设计金额公式。

### 3.9 创建确认

用户确认前，系统检查：

- 名称和完成标准是否有效。
- 人员是否属于当前团队。
- Owner 是否重复出现在参与人中。
- 日期是否合法。
- 依赖是否自指、悬空或形成循环。
- 子任务时间是否与父任务明显冲突。
- 预计投入是否仍对应当前任务范围。

无负责人不阻止创建。系统只统一提示一次未分配任务数量。

## 5. 我的工作

### 5.1 模块作用

“我的工作”回答：在我正式负责的任务中，现在应该先关注什么。

它不是第二套任务系统，也不创建新的待办。

### 5.2 展示内容

每条只显示：

1. 顺位。
2. 任务名称。
3. 一句优先原因。

点击任务名称进入原任务详情。

页面不展示 AI 内部评分、复杂权重、完整依据列表或其他任务的深层链接。

### 5.3 分析范围

本人负责/参与的，**只有待开始、进行中、已阻塞这三种状态的任务参与排序。**

### 5.4 推荐逻辑

产品规则采用“推荐权重＝重要度 × 60%＋紧急度 × 40%”，两维均为 0～100 分；比例是待验证的初始建议参数。程序按固定规则计算，AI 基于同一事实解释，具体分档、算例和同分规则见第 7.6 节。

1. **重要度：** 目标影响（0～50）＋已确认协作影响（0～30）＋标签参考（0 或 20）；任务没有独立的优先级字段。
2. **紧急度：** 期限压力、正在发生的损失或执行风险、当前待本人处理事项，三者取最高分，不重复叠加。
3. **排序：** 推荐权重降序，同分依次比较重要度、紧急度、可比较截止时间、稳定 Task ID。
4. **证据：** 每项分值必须有有效来源，资料缺失或过期不额外加分，按已知依据计算并提示待核对。仅有参考性前置未完成，不等于已阻塞，也不直接加分。

本节与第 7.6 节描述新产品规则，当前应用尚未接入，不代表只靠修改文档就已改变实际顺位。

没有截止时间是合法状态，不等于低优先级。

资料不足时，优先原因应表达“待核对”，不能推断任务正常或没有风险。

缺少真实日历、剩余工作量和个人可投入时间时，不输出忙闲率、完成概率或精确排程。

### 5.5 AI 分析规则

页面顶部保留默认收起的“AI 分析规则”，只说明：

- 哪些任务会进入分析范围。
- 重要度与紧急度的定义、权重、分档依据和同分规则，AI 如何据此解释原因；不在任务行展示内部打分。
- AI 不会自动修改任务。

只有分析输入真实变化时，更新时间才变化。打开页面或重新渲染不能制造新的分析时间。

#### 6.3.2 核心规则

| 区域 | 展示什么 | 主要规则 |
| --- | --- | --- |
| 完成进度 | 百分比与紫色 AI 预测，或用户确认 | AI 根据交付证据预测；已完成采用用户确认 100%；其他状态不直接映射百分比 |
| 完成时间（燃起图内） | 图内显示提前／按期／延期差值，图下列截止与预测／确认日期 | 灰色截止竖线、紫色预测虚竖线、蓝色确认竖线；同日来源用“｜”分隔，日期写一次 |
| 子任务进度 | 每项自己的状态、进度来源和日期 | 复用主任务样式并缩小；父子状态不级联，父任务确认完成不关闭子任务 |
| 燃起图 | 历史总工作量、完成量、未来预测趋势与完成日期对比 | 完成量注明来自 AI 预测或用户确认；新增范围、返工、确认各留记录，旧历史不改写 |

**状态与工作量独立：** 总量按工作范围评估，完成量按产出内容对照完成标准评估。即使仍为待开始，已有草稿或部分交付也计入 AI 预测；仅在待开始、进行中、已阻塞之间切换，不清零、不删历史、不隐藏有效完工预测，也不自动改状态。文件数量和状态本身都不能换算百分比。当前情况应提示核对已有文件，不能断言没有产出。

**布局：** 完成度 → 子任务（有子项时）→ 燃起图。移除“计算明细”入口及展开内容，不保留占位；进度说明仅展示公式和用户确认规则。历史评估与确认记录继续保存。主任务去掉独立时间轴；子项没有单独燃起图，保留较小的日期时间轴。燃起图横轴从任务创建日开始，覆盖截止及预测／确认日，提前在左、延期在右；仅有截止时间不产生预测。

**信息位置（2026-09-15）：** 进度行只保留百分比与来源。预测摘要统一标紫色「AI 预测」，具体子任务汇总口径保留在结果数据中；用户确认仍为 100% · 用户确认。燃起图依次是标题与图例、绘图区、截止／预测日期；提前／按期／延期差值只在图内显示。暂无图表时，已知日期和具体原因放空态下方。

**未来预测趋势（2026-09-16）：** 从当前完成点接紫色阶梯虚线，展示到预计完成日的后续交付变化。每个节点保存预测日期、累计完成量与依据；等待阶段持平，最后一个节点在预测完成日达到当日预计总量。未来总工作量从当前记录接灰色虚线，覆盖计划截止日与预测完成日；无预计范围变化时水平延续，有依据的预计新增时按节点上升。预计范围变化单独保存日期、总量与依据，不回写历史或当前进度的分母。悬停未来总量节点查看日期、预计总量及不变假设／变更依据。蓝色仍表示已记录的完成量，紫色节点不算已完成记录。只有完工日期、没有未来节点时只标日期，不从截止或两个端点插值。图内上沿「+N 天／−N 天／按期」只表达日期差。

预测节点关联同一次观察日、起始完成量和范围版本；任一不匹配时隐藏趋势，独立有效的日期仍保留。新增产出或剩余工作、依赖变化后更新预测；仅修改截止或切换待开始／进行中／已阻塞不改节点。用户确认完成或取消时退出当前未来曲线；重新打开后自动恢复有效的原预测日期与趋势。父任务逐日期分别汇总子任务的预计总量与完成量；缺少任一未完成子项的有效节点时不补造父级趋势。

**创建即有总量：** 横轴使用任务创建日期，不拿截止日或首次进度预测日作为起点。创建时保存预估人天、时间及范围版本，作为燃起图首条总工作量记录；有预测和无预测都展示。总量线从初始值连接后续范围记录，完成量线从首条有依据的记录开始；只有一次完成量观察也不能隐藏前段总量。后续估算、修改截止或重新预测不覆盖创建记录。暂无进度预测、负责人或截止时间，都不隐藏已知总量。未确认完成量时不补零，也不凭总量推算完工日期。已有工作量历史优先使用，不用今天的估算改写过去。

**燃起图如何画：**

| 已有记录 | 图中呈现 |
| --- | --- |
| 至少两次工作量记录 | 灰色总工作量阶梯线、蓝色完成量阶梯线，实线均止于最后一次评估；未来总量按不变假设或有依据的范围节点接灰色虚线至截止／预测完成日，有未来交付节点时接紫色完成量阶梯虚线 |
| 范围有增减 | 灰色总量线在变更日形成台阶；指向该日显示新增／缩减量。新增是总量的变化，不额外画一条线；没有变化时不显示新增项 |
| 只有一次工作量记录 | 显示总量点和完成量点，图下不追加说明文字；有独立未来节点仍可绘制紫色预测趋势；只有完工日期时只标日期，不补造过去的零值或平线 |
| 仅有创建时估算 | 显示初始总量点；范围未变时灰色总量线延续到当前。没有完成量预测不画蓝线，也不隐藏总量 |
| 仅有当前估算、创建估算不可追溯 | 显示当前总量点，不倒填历史；完成量与时间预测保持未知 |
| 创建估算和后续工作量记录均无 | 显示「尚无工作量估算」，保留已知日期，不造曲线 |

父任务按历史日期汇总各子任务截至当日最近的已知记录，保留范围变化与完成量变化，不压成最新单点。某子任务早期记录未知时，不用零或今天的值补齐；从所有必要子项都有记录的日期开始显示完整汇总。

**缺信息就说明原因：** 无进度证据仅用浅色正文显示“尚无进度预测”，取消大号横杠，保留中性轨道、不补 0%；没有时间依据则不画未来 AI 日期。高完成度不代表能按期，跨日不代表完成度增长。

**统一样式：** 主任务和子任务使用同一套来源样式。「AI 预测」「上次 AI 预测」「确认前 AI 预测」、预测日期及日期虚线标记均为紫色；摘要中的子任务汇总统一显示为紫色「AI 预测」，结果数据保留汇总公式与各项来源；用户确认和无数据提示保留原文案。百分比与当前完成条仍按统一规格展示；提前／延期结论分别用绿／橙色，不改变 AI 来源颜色。子任务仅缩小字号与间距。

**Demo 覆盖（2026-09-16）：** 220 个内置任务中，190 个展示 AI 预测完成日，18 个已完成、1 个已取消；7 个因明确依赖缺口暂无完工预测，另 4 个保留无进度数据场景。本次补齐 84 条独立完工预测，并对齐 3 条受前置依赖影响的旧日期；工作量、百分比、状态与 9/14 观测快照不变。

**历史 Mock 完整性（2026-09-16）：** 为原来只有最新快照的 144 个叶子任务补充独立的 9/8、9/10、9/12 演示观察，父任务按同日记录汇总。220 个内置任务中，215 个有多次历史，1 个保留单次观察（确认下周行动项与负责人），4 个保留无数据；190 个有效未来预测继续保留。9 个叶子样例包含有说明的范围增加，零完成量的等待任务保持 0；现有最新工作量、状态与预测日期不变。演示历史是固定样例，不从用户状态、截止或当前百分比在运行时反推。

图例直接显示最近记录的总工作量与完成量，单位为人天；即使历史线较短或只有一个点，也能读到已有数值。两条线重合时使用灰色外沿、蓝色内线，末点使用灰色外环和蓝色实心点；保持同一坐标。总量不等于新增，新增／缩减仍只在范围变更节点说明。

**趋势 Mock：** 190 个有完工日期的内置任务均有独立保存的未来预测节点；135 个叶子任务中，60 个配置中间交付／等待节点，其余在已说明的执行窗口一次收口。父任务使用子项节点汇总，创建流程中的防晒衣项目同样接入。库存核对当前 40%，9/15 等待仍为 40%，9/16 回复初核后预测 70%，9/17 差异与替代方案收口为 100%；这些均为演示假设，不是已发生记录。总量不变时灰色虚线延续；封面制作示例保留当前总量 4 人时，9/15 预计补充横版适配后总量变为 5 人时，9/16 预测完成量达到 5 人时。

**时间样例口径：** 常规任务同时维护完成度、预测完成日与时间依据，未开始不等于不能预测结束日。有前置任务时，预计完成不得早于前置完成；已阻塞但具有恢复时间假设时，可保留条件预测。演示执行窗口明确写成假设，保存在任务核对记录中，不从截止倒推，也不代表产品新增了工作排期。无日期仅保留达人档期待回复、安全风险处置时间未知、申诉无反馈时限、复验样件未定四个叶子场景及三个受影响的父级；取消和无数据另行处理。

<details class="progress-reference" id="progress-component-inputs">
<summary>数据来源与计算<span>预测进度、确认事实、完工日期、历史</span></summary>

| 数据 | 来源与有效性 | 用途 |
| --- | --- | --- |
| 用户事实 | 状态保存事件、操作者、事件时间、截止日期；开始时间仅在已有记录时使用 | 已完成确认 100%；对比截止日期；不拿普通更新时间补完成日期 |
| 进度预测 | 交付范围、完成标准、可读产出版本、子任务证据与权重；保存观测时间和输入版本 | 预测目前完成多少内容；单靠状态／截止日期无法预测 |
| 时间预测 | 剩余工作、有效执行速度或可用时间、依赖与等待；保存独立依据、时间和版本 | 预测何时完成；截止日期只是对比目标，不是预测答案 |
| 请求状态 | 首次读取、更新、失败、最近成功结果 | 真正在途才显示正在更新；无请求不能持续显示计算中 |
| 历史记录 | 原始总量、完成量、预测来源、确认／重开事件和范围变更 | 燃起图和依据；未知不补零，同日图可取末值但原始事件均保留 |
| 权限与覆盖 | 可读任务及证据范围、叶子覆盖是否完整 | 未覆盖部分不推算；无权限不展示缓存及受限名称、数量、数值 |

**进度计算。** 总工作量为 W，AI 基于完成标准判断各部分已覆盖的工作量 C；范围、证据和权重有效时，预测百分比为 C/W，最多一位小数。文件数量、消息数量、经过天数不能替代完成证据。W 未知或为零时不做除法；用户确认已完成仍可显示 100%，因为它来自声明。

**子任务依据。** 主任务需要汇总时，使用完整、去重的叶子工作量加权，不按个数平均；已完成叶子取确认值，其余取有效 AI 预测。汇总只是计算来源，不变成客观“实际进度”，也不自动改变父状态。缺少任一必要贡献时，不输出精确汇总。父级已有完成声明独立优先。

**截止与预测独立。** 用户截止日期 D 是要求，AI 预测日期 F 来自剩余工作和执行依据。修改、清空或恢复 D 不改变 F；只更新截止标记与 F−D。例：AI 预测始终为 9/18，截止从 9/18 改到 9/20 后图内显示「−2 天」（预计提前 2 天）；取消截止则保留紫色 AI 预测 9/18，不显示提前／延期。仅在交付范围、剩余工作、依赖或可投入时间变化等事件发生时，才重算受影响的预测。

**时间计算。** 未完成用有效 AI 预测结束日 F，已完成用用户确认日 R，分别与截止日 D 按团队时区的日历日期比较。只有 F 和 D 都有效才称“预计提前／按期／延期”。未完成且当前日晚于 D 是“已逾期 N 天”的事实；即使没有 F 也可判断。截止当天为“今天截止”，不是逾期 1 天。没有截止日，不输出提前／延期。

**各自更新时间。** 进度预测与时间预测分开记录 `observedAt`、`generatedAt`、输入版本、依据和失效原因；不能因为时间预测刚更新，就把旧进度标成今天的新结果。这些时间保留在结果数据中，摘要右侧不重复日期，燃起图横轴保留截至日。页面刷新不修改这些时间。


<a id="progress-ai-retention"></a>

**确认后保留 AI 预测。** 用户确认 100% 与 AI 预测分别记录。主界面只显示 100% · 用户确认；原 AI 值、时间与依据继续独立保存，不再通过计算明细展示。子任务仅呈现进度与时间，不增加第二条进度条或替代入口。

| 记录情况 | 独立保存的数据 | 判断边界 |
| --- | --- | --- |
| AI 09:30 预测 60%，用户 12:00 确认 | 确认前 AI 预测 60%；预测时间、当时依据；用户确认时间 | 旧预测可能尚未更新，差异不能直接说明用户确认有误 |
| 确认后有新证据并重新预测 | 确认后 AI 预测 N%；新预测时间和证据 | 有新证据支持缺项才提示核对；仍保留 100% 用户确认，不自动重开 |
| 同日但只记录日期，或缺确认时间 | 已保存 AI 预测 N%；保留已有时间精度，先后关系未知 | 不把旧记录当作确认后复核，不补造时分 |
| 没有可读 AI 历史记录 | 未保存 AI 预测记录 | 不用用户确认值或子任务汇总倒推 AI 的旧百分比 |

AI 记录保存当时的完成量／总量、范围版本、观测时间、依据与来源；用户确认另存状态事件、操作者和时间。确认、重开、子任务汇总或当前总量变化均不覆盖原 AI 数值。预测只按当时范围计算，不能用新总量重算旧百分比。同日燃起图可取末值，原始数据保留 AI 记录与确认事件。生产多次复核历史仍按正式账本接入，不把固定样例描述成已接通的实时服务。

</details>

<details class="progress-reference" id="progress-component-decisions">
<summary>状态变更与文案<span>AI 预测与用户确认如何切换</span></summary>

<a id="progress-state-rules"></a>

预设状态为 **待开始、进行中、已阻塞、已完成、已取消**。Mock 中原“待审核”统一为“进行中”，审核或等待确认保留在任务内容中；浏览器已保存的内置示例也做同样转换，仅改状态。用户已经设置的五种有效状态、截止时间、任务内容和历史记录保留；普通存量任务的旧状态仍兼容读取。加载、失败和预测过期属于数据状态。

状态选择使用单行菜单，每项显示语义色图标与状态名称，当前项右侧显示勾选；悬停仅高亮所在行，不改变勾选。选中后关闭菜单并同步列表、详情与子任务引用；确认已完成时，进度切换为 **100% · 用户确认**。支持方向键选择、Enter 确认及 Escape 关闭并返回触发按钮。列表标签复用同一状态颜色和图标，采用 22px 高、12px 字号的紧凑规格。

| 情况 | 完成进度怎么显示 | 时间怎么显示 | 后续处理 |
| --- | --- | --- | --- |
| 待开始，尚无预测 | 尚无进度预测 | 保留已知截止时间；无依据时不画预测节点与日期 | 不凭状态补 0%，不默认按期 |
| 进行中，有有效预测 | N% · AI 预测（紫色来源） | 独立有效的 AI 预测日期 | 更新证据后才可能改变百分比 |
| 已阻塞 | 有效进度保留；需复核时标上次 AI 预测 | 恢复时间未知则不报确定日期 | 阻塞本身不清零；恢复后复核时间 |
| AI 预测达到 100%，状态未完成 | 100% · AI 预测 | 等待完成确认；不画确认完成节点 | 可以建议用户核对，不自动改状态 |
| 用户标记已完成，保存成功 | 100% · 用户确认 | 用确认日期替代未来 AI 日期；对比截止判断按期／提前／延期 | 立即生效，不等待 AI；原预测留在历史 |
| 用户标记已完成，保存失败 | 保持原状态与原预测 | 保持原有日期 | 显示保存失败，可重试；不追加完成事件 |
| 已完成旧数据缺少确认日期 | 100% · 用户确认 | 完成日期未记录 | 不用今天或普通更新时间补日期 |
| 已完成后有新文件或 AI 发现缺项 | 保持 100% · 用户确认 | 保留确认日期 | 仅提出核对建议；需要继续执行时由用户重新打开 |
| 已完成／已取消后重新打开 | 自动恢复同范围的独立 AI 预测 | 截止保留，恢复有效预测日期及趋势；旧确认日期退出当前展示 | 保存状态即生效；缺少有效评估才显示缺口，不清零、不把用户确认当 AI 值 |
| 待开始，但已有产出与预测 | 有效 N% · AI 预测，历史总量与完成量照常展示 | 保留有效 AI 完工日期 | 无需先改为进行中；只改状态不清零、不重算、不新增历史点 |
| 已取消 | 保留取消前记录及来源，不补 100% | 已取消，停止未来预测与逾期跟进 | 历史保留；取消不等于交付或删除范围 |
| 父任务已完成，子任务未完成 | 父 100% 用户确认；子保持各自来源和状态 | 各用自己的截止与完成日期 | 不自动批量关闭子任务，后台汇总不撤销父确认 |

**优先顺序：** 权限 → 最新用户状态事实 → 预测有效性 → 请求状态 → 时间结论。用户刚确认完成时，旧 AI 请求即使随后返回 60%，也不能覆盖 100%。

**未知与旧值：** 首次无结果显示具体缺口；已有旧预测且可读，可标“上次 AI 预测 · 截至 M/D”。范围变化无法比较时只在原始记录中保留旧值；不能继续充当当前结果。单一区域失败不清空其他区域，完成声明不受历史加载失败影响。

<summary>预测更新节点与状态变更<span>什么触发、更新哪项、什么时候生效</span></summary>

| 更新节点 | 进度预测 | 时间预测 | 页面立即变化／不变 |
| --- | --- | --- | --- |
| 首次创建任务成功 | 有交付范围和执行证据才预测；无证据保持未知 | 有剩余工作、依赖及执行依据才预测；不默认等于截止日 | 显示用户状态与截止时间；不生成随机比例 |
| 待开始、进行中、已阻塞之间仅修改状态 | 不重算总量、完成量或百分比 | 保留有效完工预测，不因状态名变化失效 | 只更新状态；已有评估、观测时间和历史不变，不新增工作量点 |
| 阻塞原因、解除条件或恢复时间有新记录 | 仅在交付证据或范围变化时重算 | 执行依据确实变化时重算；恢复未知则说明无法预测 | 保留历史工作量；状态名本身不代表恢复时间未知 |
| 任意未完成状态 → 已完成，保存成功 | 停用本轮进度预测，以用户确认 100% 展示 | 停用未来日期预测，以完成事件时间记录确认日期 | 立即显示 100% 用户确认；不等待 AI，无新确认不重复记完成 |
| 已完成／已取消 → 执行状态 | 旧确认退出当前值，自动恢复同范围下独立保存的 AI 评估 | 自动恢复有效 AI 完工日期与趋势，旧确认日期留在历史 | 无需点击重新预测；没有有效评估才显示缺口，不归零、不把旧用户确认冒充 AI 100% |
| 进入已取消 | 停止新的执行进度预测 | 停止未来预测 | 保留取消前记录，不标完成、不删除历史 |
| 产出文件提交／换版本／删除、相关进展反馈保存 | 待开始也参与评估；内容可读取且确实影响完成标准时重新预测，解析失败不算新进展 | 剩余工作改变时重新预测 | 保留上次结果及时间；不是每个文件或每条评论都涨进度 |
| 完成标准、任务范围、交付数量改变；发现返工 | 失效受影响的旧预测，按新范围与证据重算 | 同步复核剩余工作与结束日期 | 标范围／依据已变化；已完成任务只提示核对，须用户重开后才恢复执行预测 |
| 子任务状态／预测／范围变化、增删或移动子任务 | 仅更新受影响父级的完整汇总或重新预测；移动涉及新旧父级 | 影响剩余交付或依赖时重算 | 子任务确认只改变该项；父级状态不自动完成，已有父确认不被撤销 |
| 修改、清空或恢复截止时间 | **不重算进度、不改变百分比** | **不重预测、不使原 F 失效**；仅用已保存 F 与最新 D 重算日期差 | 新截止立即显示；紫色 AI 日期与日期竖线保留。无截止则不显示提前／延期；原观测时间与依据不变 |
| 依赖、人员可用时间或执行方式变化 | 仅在交付内容／证据同时变化时重算进度 | 只更新受影响任务及后续依赖任务；缺少新依据则说明原因 | 改负责人姓名本身不增加进度 |
| 到截止日、跨过截止日、旧预测日期已过去 | **不调用 AI 制造新进度** | 代码更新今天截止／已逾期 N 天；过去的预测失效，不自动顺延一天 | 首版事件驱动，不每日无条件调用 AI；过期结果等待有效事件或手动重预测 |
| 用户点击完成进度右侧「重新预测」或通过助手提出请求 | 核对现有评估和当前子任务确认，重新计算并保存；数据不足返回具体缺口 | 汇总未完成子任务的有效日期与未来节点，不从截止反推 | 执行中禁用重复提交；成功刷新、失败保留原值并可重试，同依据可得到相同结果 |
| 只浏览、刷新、切页签、展开、悬浮历史，或编辑未保存 | 不触发新预测，只读取已保存结果 | 不触发新预测；可更新当前日期的轻量判断 | 不改结果时间、百分比和历史，不发送业务通知 |

**保存与并发。** 预测结果至少绑定任务、确认／取消事件及重开轮次、范围／完成标准、证据版本和可读范围；待开始、进行中、已阻塞之间的纯状态切换不使同一证据版本失效；时间预测另记录依赖／执行假设版本。截止日期作为独立比较目标保存，不属于预测失效条件；预测返回后与最新截止日期比较。执行中连续变更可合并，最终只采用覆盖最新输入的结果；迟到的旧版本结果不覆盖新结果、确认或取消。相同确认事件幂等，重复点击不刷新完成时间。

**更新中与失败。** 首次读取用骨架；有旧值时显示“上次 AI 预测 · 截至 M/D”。新结果成功后才替换相应区域；进度成功、时间失败可以分别展示。失败可重试对应请求，不能靠重试修改任务状态。若完成状态已保存，所有预测请求均不得将其降回旧百分比。

**历史。** 用户完成事件保存操作者、发生时间、确认时范围，原 AI 预测单独保留；百分比、时间与依据的展示见 [确认后保留 AI 预测](#progress-ai-retention)。燃起图按当时的范围和来源新增观察，过去的点不随今天改期、重估、返工而重写。按日显示最后值时，仍保存当日的原始预测与确认记录。

<a id="progress-state-acceptance"></a>

**验收重点：**

- AI 60% → 用户完成保存成功 → 100% 用户确认；原始数据保留确认前 AI 60% 和原时间、依据。AI 迟到返回 55% 仍保持用户确认 100%，按其证据观测时间区分旧预测与新复核。保存失败则保持原值。
- AI 100% 且状态进行中，仍标 AI 预测；子任务完成不自动完成父任务，父任务完成不自动关闭子任务。
- 重新打开后立即恢复同范围的独立 AI 评估、有效预测日期及趋势，无需再次点击；旧用户确认不作为当前 AI 100%。没有有效依据时明确缺口。
- 修改、清空或恢复截止日期不改变百分比、AI 完工预测日、观测时间和历史，也不触发重预测；只更新截止标记与日期差。浏览或跨日不增加百分比。尚未到截止且无完工预测，不显示预计按期。
- 进度与时间分开记录更新时间；任一请求失败不清空另一项，更不覆盖用户确认。
- 全无权限不渲染缓存与子任务信息；部分覆盖不生成精确父级汇总；所有入口可用键盘操作。

**实现范围：** Demo／PRD 共用组件，固定样例覆盖预测、确认、重开、逾期和失败；本地状态入口已有完成／重开时间。Demo 已支持手动重新核对固定评估、按当前子任务状态汇总、本地保存和失败重试；核对时间独立于原始观测时间，无新证据不生成更高进度或顺延日期。生产 AI 的事件队列、跨端版本竞争、独立预测时间与完整历史账本仍待接入；不将文档或 Mock 表现当作后台已运行。

### 6.5 讨论

#### 6.5.1 对象、范围与本次决策

用户需要围绕一条进展或一份文件持续沟通，能知道回复针对谁、附件在哪里、结论依据哪一版内容。本次所称“动态”指当前 Task 内成员主动发布的内容，复用现有“讨论”页签；不新增团队广播入口，也不将系统“活动”变成输入区。

- **用户明确方向：** 动态可以上传附件；文件内可以就内容讨论，确认后在文件右侧查看；补齐评论、回复、@ 人和回复某条回复的规则。2026-09-14 修订：动态及其回复不提供单独的“引用”操作，不重复展示原消息摘录；作者与回复对象同排且字号一致，例如“周岚 回复 陈默”；正文另起一段，点击回复对象可定位原消息。发布时间放在正文与附件下方、操作按钮上方，按保存时刻显示完整日期和时分（YYYY-MM-DD HH:mm），不显示“原时间”或相对时间；编辑保留原发布时间。文件讨论的原文锚点不受影响。
- **本次设计默认：** 发布成功的附件自动出现在本任务文件列表，同时允许在文件页手动上传、从已有文件中选择引用；不要求用户再执行一次归档。
- **对象分开：** 动态是任务讨论串的首条消息，评论和回复都属于该串；文件讨论串属于 `Task + File` 的上下文。同一条文件评论不自动再发布为动态。
- **计数分开：** 任务“讨论”数量统计任务讨论串中未删除、当前可见的人的消息（包含评论和回复）；文件评论不计入该数量。文件右侧统计可见讨论串数量，每串单列回复数；系统活动和 AI 建议均不计入。

以下操作与通知细节为设计建议，供实现和验收使用，不表示当前原型已经具备。

#### 6.5.2 评论与回复操作清单

| 用户操作 | 入口与行为 | 保存与边界 |
| --- | --- | --- |
| 发布动态 | 讨论页输入文字、粘贴图片、上传附件或选择已有文件，点击“发布” | 正文或至少一个可用附件必须存在；仅空格或仅 @ 人不能发布。纯附件动态允许发布 |
| 评论动态 | 动态下方“评论”，展开该串并聚焦输入框，点击“回复” | 保存到当前动态，不生成另一条顶层动态 |
| 回复评论 | 评论下方“回复”，在当前消息下展开输入框；已发布回复头部以相同字号显示“作者 回复 对象”；正文及附件在下方，随后显示实际发布时间与操作 | 保留被回复消息 ID；发送成功后仍停留当前串 |
| 回复某条回复 | 每条回复也提供“回复”；例如“林浩 回复 陈默” | 仍属于同一根讨论串，保存 `replyToMessageId`；界面只缩进一层，不无限套娃 |
| 查看回复上下文 | 点击“回复 姓名” | 展开并定位被回复消息；跨分页先加载目标。来源无权限时只显示不可用，不泄露摘录 |
| 取消回复 | 输入框“取消”，收起当前回复输入框 | 保留当前回复对象的会话草稿；再次点击该消息“回复”可继续，不发布为新动态 |
| @ 一位或多位成员 | 输入 `@` 后按姓名搜索，选择有权访问当前上下文的成员 | 使用稳定人员 ID；改名不失联。无候选显示空状态，待加入／无权限人员不作为可通知人选；不因 @ 自动邀请或授权 |
| 移除 @ | 删除完整提及标记，或在选择结果中移除 | 保存前移除的不通知；普通粘贴的“@姓名”文字不自动视为有效提及。首版不提供 @所有人 |
| 添加／移除附件 | 输入框“附件”下拉选择“上传本地文件”，或从“从文件列表选择”按文件夹逐级选择；选中文件即收起，也支持拖入文件、粘贴图片，草稿附件可移除 | 显示名称、大小、上传状态和失败重试；上传中或失败附件须完成、重试或移除后才能提交，文件规则见 6.8.4 |
| 查看／下载附件 | 点击附件打开文件预览，使用“下载”获取有权读取的版本 | 打开同一 File 及消息固定引用的 FileVersion；可从文件来源返回原动态或评论 |
| 编辑自己的内容 | 消息更多菜单“编辑”，编辑正文、提及或附件，点击“保存” | 保留作者、原发布时间与回复关系，增加“已编辑”和修订时间；失败保留草稿。不可编辑他人消息 |
| 删除自己的内容 | 更多菜单“删除”，说明影响后确认 | 已删除评论立即从列表隐藏，不展示作者、时间或“消息已删除”占位，不计入评论与展开数量；原关系保留，未删除回复继续显示，回复对象不可跳转已删除消息，已删除来源的引用摘录也不展示。整串无可见消息时隐藏该串及文件原文标记；删除不能连带删除他人回复或任务文件 |
| 展开／收起回复 | 动态下“查看 N 条回复”，文件串按需展开 | 根动态按创建时间从新到旧，串内按创建时间从旧到新；加载更多保留滚动位置，不因回复提升或打乱整条动态 |
| 复制链接 | 消息或讨论串更多菜单“复制链接” | 链接包含 Task、串和消息定位；文件串另含 File／版本信息，打开仍检查权限 |
| 连接个人 AI | 沿用当前讨论的“连接 AI” | 仅带入选定串、必要上文和有权访问的附件；文件讨论作为上下文不等于文件内容授权 AI 执行动作，AI 不自动回帖 |

文件右侧复用上述回复、@、附件、编辑、删除和定位规则，另保留文件原文锚点及文件讨论内的消息引用；新建文件讨论的按钮为“确认”，后续回复为“回复”。首版不扩展点赞积分、置顶、转发广播或全团队提醒。

#### 6.5.3 通知、草稿与发送状态

- 发布顶层动态不自动提醒所有参与人；首次文件讨论只通知明确 @ 的成员。评论动态通知动态作者；回复具体消息通知被回复者；回复文件根讨论通知根评论作者。每次再合并本条有效 @ 人员，剔除自己、不可见成员并按同一消息去重。
- 普通编辑不重复发提醒；编辑后新增的有效 @ 可产生一次新增提及通知。移除 @ 不撤回已发生的提醒。只有保存成功后才产生通知事件，投递失败独立重试，不能让用户重复发消息。
- 通知点击后直接进入原 Task 的讨论串，或文件右侧对应串并定位原文；已读只清除未读状态，不代表已回复、同意或解决。消息删除或权限撤回后，通知摘要与深链也遵守当前可见范围。
- 草稿按当前用户、团队、Task、串和回复对象隔离；切换文件或任务、收起面板、取消弹层不发布并保留会话草稿，显式“放弃草稿”才清空。首版不承诺刷新或跨设备恢复，界面说明保存范围。
- 正文输入 Enter 换行，`⌘/Ctrl + Enter` 提交；中文输入法组合中不提交。回复输入框不展示常驻快捷键提示，快捷键仍可使用。@ 菜单打开时方向键选择、Enter 选中、Esc 收起；点击或快捷键重复提交复用同一请求标识。
- 保存中禁用重复提交，失败保留正文／提及／附件并可重试；无回执显示“提交结果待核实”，先查询原请求，不立即再创建。并发编辑提示内容已变化，保留草稿供核对。

### 6.6 诊断

诊断回答：当前任务能否继续，依据是什么。

首版只检查两类问题：

- 执行阻塞：任务处于进行中或已阻塞，有正式依赖，当前阶段需要的前置交付尚未满足；未开始任务正常等待前置不直接判当前阻塞。详细条件见第 7.5 节。
- 决策冲突：根据任务已有文件内容和任务信息，检查同一事项是否存在相互矛盾或不能同时满足的地方，并指出内容和出处。

诊断范围包含当前 Task 和全部可见后代 Task。

每条诊断展示：结论、影响、建议和默认收起的依据。

诊断页只读，不提供一键修复、改期、改依赖、忽略或完成任务。

不可见或缺失的依赖只表示检查范围不完整，不能推断为阻塞、正常或已完成。

### 6.7 子任务

子任务列表每项只显示：

- 图标。
- 名称。
- 负责人或待接受负责人。

点击名称进入子任务详情。

- 手工新增至少需要名称和一条完成标准。
- 不自动继承负责人、参与人、文件或权限。
- 新增或删除后，父任务的直属子任务数量同步更新。
- 删除有下级的子任务时，必须说明影响范围。
- 子任务全部完成不自动关闭父任务。

### 6.8 文件

#### 6.8.1 文件内容讨论与“确认”

**本次决策：** 就文件内容讨论的完整记录和结论留在文件内，右侧查看，不自动发送到任务动态。截图里的“发起对话”改为“确认”，输入提示改为“补充对这段内容的讨论，可 @ 成员”。不先选择一排协作者，不将写评论包装为新会话或派发任务。

1. 打开文件，选择正文中的一段文字，点击轻量工具栏“评论”；文件顶部保留“查看讨论 N”，移除常驻“下载”“添加评论”入口及评论操作说明。整文件讨论从右侧面板内“评论整个文件”进入。顶部文件标题／路径与正文共用左侧边距，正文不再额外居中缩进。
2. 点击“评论”后在右侧打开输入区，展示来源版本、选中原文、PDF 页码、多行输入、@ 和附件，以及“取消／确认”。选区工具栏避让可视区边界，讨论输入与后续回复使用同一右侧面板。
3. “确认”只保存当前评论与来源引用；正文或可用附件至少一项。阅读态和编辑态都可选区评论。正文有未保存修改时，先提示“保存文件并评论”，用户点击后保存新版本，再打开评论输入；保存失败保留文件草稿与待评论选区，不创建评论。
4. 确认成功后清空已提交的输入，右侧“文件讨论”定位新串，正文显示可点击的讨论标记。点击原文标记打开对应串，点击串内原文摘录定位当前版本的片段；旧版讨论保留当时原文与版本提示，不将旧标记贴到新版正文。
5. 通过顶部“查看讨论 N”或正文标记打开右侧面板，每串显示回复数和完整回复，可点某条消息的“回复”继续回复或 @。关闭后重开、刷新后再次进入文件，讨论与回复继续保留，无需转到任务讨论页。

**确认内容如何体现：** 提交后的评论或结论作为文件右侧讨论记录保存，不自动插入或覆盖文件正文，不自动形成动态。需要把结论纳入正文时，由有文件编辑权的人使用现有“编辑 → 保存”形成新版本，讨论保留来源；需要主动向任务成员说明时，可在讨论页手动发布文字并引用文件／讨论链接，不增加自动同步或转发入口。

| 文案 | 含义 | 不代表 |
| --- | --- | --- |
| 确认 | 提交这条文件讨论及附件／引用 | 他人同意、正文已改、任务完成或交付验收 |
| 标记已解决 | 根讨论作者或具备本文件讨论管理权的人收起已处理议题，保留处理人和时间 | 删除历史、自动批准文件内容或自动关闭任务 |
| 重新打开 | 同样有处理权的人恢复该议题为未解决；其他成员可查看，并在开放后继续回复 | 撤销业务验收或还原正文版本 |
| 编辑 → 保存 | 有编辑权的人修改文件正文并形成新版本 | 自动解决相关评论或代表他人确认 |

“已解决／重新打开”属于本次设计建议；新回复不静默改变解决状态，已解决串需先重新打开才继续回复。

#### 6.8.2 最小布局与来源

桌面沿用“文件树 → 文件正文”，按需增加文件正文右侧讨论栏；正文始终是主区域。讨论栏默认展示未解决串，提供“未解决／已解决／全部”筛选，按最近回复时间排序；从通知／原文标记定位已解决串时切换筛选并提示其状态。面板标题为“文件讨论”，每串显示原文摘录、来源版本、PDF 页码、作者、评论、回复数及操作。作者与回复对象同排同字号，真实发布时间位于正文／附件下方。

| 组件 | 解决的问题与动作 | 数据来源／删除后的损失 |
| --- | --- | --- |
| 现有文件树与顶部路径 | 找到文件、切换版本、手动上传或引用 | TaskFilePlacement、File、FileVersion；删除会丢失文件归属与入口 |
| 正文与讨论标记 | 知道讨论指向哪句话，点击定位对应串 | 当前版本内容、锚点和有权可见的串；删除会失去原文上下文 |
| 右侧讨论输入区 | 在阅读位置写意见，确认保存 | 当前用户草稿、选区、文件版本；删除会增加跳页和重新找原文的负担 |
| 按需打开的右侧讨论栏 | 集中阅读、回复、查看已解决讨论 | 当前 Task + File 的讨论串及权限；删除会迫使用户离开文件找回复 |

串绑定创建时的 `fileVersionId` 和引用快照；移动或改名不影响关联。查看最新文件时仍可查看本 Task + File 的历史讨论，但标明“针对 vN”，不将旧标记硬贴到新版本。源片段被删除或无法唯一定位时显示“原文已变化”，保留有权读取的引用和原版本入口；不靠同名文字猜位置。

当前 Demo 的片段讨论覆盖 Markdown／纯文本及已提取正文的 PDF，阅读态和编辑态均可用；PDF 锚点保存页码、版本、原文和页内范围，相同文字不跨页匹配。图片、表格和未提取正文的二进制文件支持整文件讨论；其他局部标注需对应查看器提供可靠区域／单元格锚点，不宣称 Lexical 能直接处理所有二进制格式。讨论侧栏属于当前 Task 下该文件的上下文，同一 File 被另一 Task 引用时不自动合并或泄露其讨论。

#### 6.8.3 开源方案与接入边界

**当前 Demo 已接入 Lexical 0.50.0（Meta，MIT），实现状态同步于 2026-09-15；选型核实日期 2026-09-13。** 它是可扩展的编辑器框架，有官方 React 绑定；官方 Playground 的 CommentPlugin 提供选区评论、串式回复和评论面板的参考代码，适合当前 React／TypeScript 项目。选型依据：[官方介绍](https://lexical.dev/docs/intro)、[MIT 许可证](https://github.com/facebook/lexical/blob/main/LICENSE)、[CommentPlugin 源码](https://github.com/facebook/lexical/blob/main/packages/lexical-playground/src/plugins/CommentPlugin/index.tsx)。

| 接入部分 | 采用方式 | 仍由 TaskDoor 实现 |
| --- | --- | --- |
| 文字文件查看／编辑、评论输入 | 使用 `lexical`、`@lexical/react`；文字格式适配采用 `@lexical/markdown` | 保持文件格式与原版本；不能为接入评论静默改写原文件 |
| 选区标记、右侧讨论 | 基于 `@lexical/mark` 和官方 CommentPlugin 模式适配现有面板 | 稳定串 ID、版本锚点、解决状态、定位与移动端布局 |
| @ 成员 | 使用 Lexical 可扩展节点和输入候选能力 | 从现有成员查询读取可见人员；稳定 ID、权限和通知逻辑 |
| 附件与持久化 | 复用 TaskDoor File／FileVersion／任务文件关系 | 上传服务、评论存储、附件事务、幂等、访问控制、通知及审计 |

官方 Playground 是示例，不是可直接安装即完成业务闭环的评论服务。移植时保留许可证声明，选定并锁定同一兼容发行版本；验证 Markdown 往返、中文输入法、重叠标注、刷新后定位和只读评论。Lexical 运行时 NodeKey 不能作为持久化锚点，需保存版本内稳定位置／自定义块 ID、范围和引用上下文。首版不依赖实时协同编辑或 Yjs 服务。

对比：[Tiptap Comments 官方说明](https://tiptap.dev/docs/comments/getting-started/overview)要求试用／订阅、文档服务和私有 registry。Tiptap 核心开源不等于 Comments 扩展开源，本次不采用该付费能力。以下区分当前 Demo 与目标需求，不将框架接入等同于生产评论服务完成。

**当前 Demo（2026-09-15）：** Lexical 用于讨论输入、文本文件及 PDF 提取正文的按页阅读和划词评论；编辑态已接通，正文有修改时先“保存文件并评论”。顶部“查看讨论 N”、正文选区的“评论”及右侧回复数连接讨论入口，`MarkNode` 高亮连接原文与文件右侧讨论；点击“确认”只保存文件评论，不生成任务动态或可见活动。已支持稳定成员 ID 的 @、回复具体回复、文件内引用、作者编辑／删除、解决／重开，以及动态／回复附件自动进入文件列表、手动上传和选择已有文件。消息与文件列表共用 File ID，保留引用 vN；编辑移除附件或删除消息不删除任务文件。

消息、文件树、讨论串及本地通知记录按团队与 Task 组成同一份 `localStorage` 快照；上传原文件二进制保存在 IndexedDB，刷新后可恢复。新增或编辑消息与附件关系一次保存，失败保留输入，旧 revision 不覆盖新快照。文件评论保存源版本、PDF 页码、原文与版本内选择范围，不持久化 Lexical 运行时 NodeKey。

**当前缺口：** 未接入服务端 ACL、多人同步或外部通知；本地通知记录尚未连接现有全局通知 UI，编辑新增 @ 的提醒也未接入。旧版全文快照预览尚未实现：可见引用 vN 和当时原文，但预览明确展示当前最新正文，不能声称打开了旧版全文。真实上传的 DOCX／XLSX 等二进制文件尚未解析，仅支持下载原文件；未提取正文的真实 PDF 使用浏览器预览，仅支持整文件讨论；现有按页提取正文预览不代表已接入真实二进制解析。下文的生产事务、权限、通知和历史版本验收目标继续保留。

#### 6.8.4 动态附件与文件列表

1. **添加方式：** 动态、评论、回复及文件讨论统一使用“附件”按钮。下拉包含“上传本地文件”和“从文件列表选择”；后者按任务文件夹逐级展开，文件夹只导航，点击文件即加入草稿、收起菜单并恢复正文输入。支持多级嵌套，分组沿用任务文件夹。文件列表下拉顶部提供“搜索文件或文件夹”，按文件名和所属路径跨全部层级搜索；搜索结果显示文件名及完整文件夹路径，区分同名文件，根目录文件显示“任务文件”。清空搜索恢复层级浏览，无结果时显示“没有找到匹配的文件”。搜索不读取文件正文，也不把已归档分支或脱离当前文件树的文件加入结果。已添加文件显示勾选并禁用，移除使用草稿附件上的关闭按钮。草稿附件采用产品负责人指定的 File Card Collections（Faisal Amir / urmauur）组件，保留纸张缩略卡和不同格式的彩色色标；附件单元缩至 80px 宽，纸张缩略卡约 48 × 60px，下方只保留单行文件名；不显示大小或“待发布”等常驻状态，18px 移除按钮置于纸张卡内部右上角。多个附件并排并自动换行，图片在同一卡片内显示实际缩略图；其他格式显示类型示意，不冒充已解析的文件正文。长文件名省略并保留完整名称提示；添加中、失败及重试在原卡片内反馈。菜单浮于按钮附近，不在输入框内插入大块文件面板；长文件名省略并可查看完整名称，长列表在菜单内滚动。已有文件复用同一 File ID，不重复上传或增加副本；本地上传发布成功后自动进入任务文件列表。文件页保留“上传文件”和“引用已有文件”的手动入口，沿用原有文件夹规则，不提供自动／手动归档开关。
2. **默认入库：** 从讨论上传时先成为草稿附件；消息提交成功后，文件及指定版本与消息绑定，同时自动建立任务文件列表关系。尚未归属的附件默认放在本 Task 根目录，随后可移动；不强制新增“动态附件”文件夹。已有文件保留原位置。
3. **同一份文件：** 消息附件和文件列表共用 `fileId`，消息固定 `fileVersionId`；每个 Task 对同一 File 只有一个文件位置，重复引用不新增文件或数量。用户另传同名文件不按名称静默合并，也不自动变成原文件新版本；需显式选择更新版本。
4. **来源可回溯：** 文件详情显示“来自动态／评论／文件讨论”和可点击来源；同一文件有多个引用时均可定位。引用数和任务文件数不是同一计数，文件无权读取时不暴露标题、摘录或来源。
5. **提交一致性：** 上传未完成、扫描处理中或校验失败均不作为可用附件。先暂存二进制；服务端用一次幂等提交原子关联消息、附件、文件位置及待投递事件，成功回执前不显示“发布成功”。上传成功但消息保存失败不产生正式文件列表条目，也不通知他人；重试复用暂存结果，放弃草稿的暂存物按上传服务策略清理。
6. **删除语义：** 发布后移除附件或删除消息，仅移除该消息引用，文件仍保留在任务文件列表。删除任务文件须走单独操作并列出受影响引用；不能顺便删掉其他回复。文件被删除／归档／撤权时，历史附件显示不可用且无法下载，审计记录保留。
7. **权限与容量：** 只在当前 Task 范围归档，父子 Task 不自动继承，不扩大 File ACL；@ 和复制链接不授权。上传前展示服务端允许的类型、大小和数量限制；服务端再次校验。具体容量值由存储服务配置，接入前不得宣称任意大小或任意格式均可用。

| --- | --- | --- |

#### 6.8.6 状态与可验证验收

| 状态 | 必须呈现的行为 |
| --- | --- |
| 正常 | 选区评论“确认”后停留文件并打开右侧串；刷新后从已保存数据恢复；附件只登记一次 |
| 空／筛选空 | 显示“还没有文件讨论”及“添加讨论”；未解决筛选为空显示“暂无未解决讨论”，不冒充整个文件无讨论 |
| 加载 | 保留文件与讨论栏结构，标明正在加载；不把未加载数据统计为 0 |
| 保存／上传失败 | 原位置保留草稿及每个失败附件，可重试或移除；不生成动态、通知或正式文件关系 |
| 无权限 | 可阅读但无评论权时保留已授权正文，输入区说明不能评论；仅无正文编辑权不应阻止有评论权的人讨论。完全无文件权限时隐藏名称、引用和讨论内容 |
| 数据过期／并发修改 | 显示来源版本和“原文已变化／内容已更新”，保留草稿，重新加载后核对；旧请求不覆盖新内容 |
| 移动端 | 窄屏用全屏讨论面板和“返回文件”，回复键盘不遮住输入；返回恢复原阅读位置，不横向挤压三栏 |
| 键盘／读屏 | 选区评论可通过可聚焦工具栏打开；Esc 收起并恢复焦点、保留草稿，Tab 按原文→输入→操作顺序；原文标记可聚焦，状态变化可读出，触控目标至少 44px |

验收用同一场景串联：陈默在 v3 选中文字并 @ 林浩 → 点击“确认”后右侧显示评论、任务动态不增加 → 林浩回复 → 陈默针对该回复继续回复，能准确回到林浩的原话 → 有权人标记已解决，仍可在“已解决”找到且任务状态不变。另验收：

- 动态上传两份附件并提交，消息与文件列表都能打开同一 File／固定版本；再次引用后任务文件数不变；文件页手动上传／引用仍可用。
- 上传一份成功、一份失败时不提交；移除失败项后仅保存成功项。提交超时重试不重复消息、文件位置或通知。
- 删除动态／评论后文件仍可在列表找到；删除文件后原附件显示不可用，其他回复不丢失。
- 同一回复同时命中作者通知与 @ 只提醒一次，不提醒自己；没有访问权和未加入成员不会收到内容。
- 文件移动／改名后仍能定位原串；正文新版本删除原片段时显示版本差异，可查看有权访问的原版本，不错误指向其他同名片段。
- 两个 Task 引用同一 File 时讨论范围独立；文件评论不进入任务讨论计数，也不生成可见的活动条目。

**验收边界：** 上述为完整目标，当前可用范围以 6.8.3 的 Demo 说明为准。仍需接入生产上传与容量配置、服务端权限、多人同步和通知投递；历史版本全文预览、真实二进制格式解析及相应局部锚点能力尚未完成，不能将本机保存与框架接入视为生产验收通过。

### 6.9 活动

活动只记录已经真实发生并保存成功的变化。

活动分为三类：

- 任务信息。
- 讨论。
- 文件。

每条活动说明谁在什么时间做了什么。

- 没有真实变化时不生成活动。
- 未保存草稿不进入活动。
- AI 建议和诊断结论不进入活动。
- 活动只读，不能在活动页编辑或删除正式记录。
- 任务动态及其评论仍可形成只读活动摘要，原文留在讨论页。文件评论、回复和解决状态仅留在文件讨论及底层审计中，不自动生成任务动态或可见活动条目；本条局部替代此前“所有讨论／回复均形成可见活动”的规则。
- 动态附件上传、文件新版本等真实文件操作仍可形成“文件”类活动摘要，仅记录操作与链接，不复制讨论正文。一次附件提交使用同一来源事件去重；未提交的暂存上传不计入活动。

## 7. Skill 与判断规则

### 7.1 各自负责什么

本章按业务流程组织，不把每个判断步骤都建成一个 Skill。创建任务是完整 Skill，澄清、查重、拆分、人员匹配、依赖与时间安排是它的内部步骤。EWD 工时评估与进度作为独立规则模块：创建任务调用预计投入，任务状态分析引用完成度和燃起图。

人员责任分析是独立 Skill，负责持续校准当前用户的责任说明；创建任务中的成员推荐读取用户已确认的责任，不把责任分析重复做成创建时的必跑步骤。

| 所属流程 | 回答的问题 | 返回什么 |
| --- | --- | --- |
| 人员责任分析 | 我实际承担哪些工作，现有责任说明需要怎样校准？ | 有来源的责任新增、更新、废弃或不调整建议；组织用户确认后的更新并解释回执 |
| 创建与人员匹配 | 要拆成哪些交付，谁适合负责？ | 任务草稿、人员建议、依赖与预计投入 |
| 状态分析 | 当前情况怎样，下一步做什么，进度如何？ | 当前情况、下一步建议、进度（完成度与燃起图） |
| 任务诊断 | 哪项工作受阻，哪些要求互相矛盾？ | 问题、受影响任务、双方依据、处理建议 |
| 我的工作推荐 | 我负责或参与的任务先处理哪个？ | 固定规则计算的顺位和一句原因 |
| EWD 工时评估＋进度 | 预计投入多少，完成多少，是否在收敛？ | EWD、完成度与燃起图；供创建任务和状态分析引用 |

**模块划分：** 第 7.7 节集中维护工时评估维度、三点估算、完成度和燃起图；创建任务与状态分析保留调用说明。任务状态分析仍按当前情况、下一步建议、进度组织。

**当前实现：** 六类能力均有项目内 Skill 入口、判断规则和离线接入设计；创建规划保留 `agentdoor-task-planner` v0.2 契约，其余五类明确各自输入输出。入口与调用关系记录在 `skills/registry.json`，该清单不是运行时注册。前端已有责任建议查看与确认、本地工时、进度、诊断和排序逻辑；本轮更新 Skill 文件与 PRD，未修改应用运行代码，也未接通后台持续分析或责任写回服务。

**文件对应：** 人员责任分析 `agentdoor-responsibility-advisor`；创建任务 `agentdoor-task-planner`；状态分析 `agentdoor-task-status-analyzer`；诊断 `agentdoor-task-diagnostician`；我的工作 `agentdoor-personal-priority`；工时与进度 `agentdoor-ewd-progress`。各入口在 `skills/对应名称/SKILL.md`。产品规则从本章同步为各 Skill 的规则快照，避免两处独立修改。详细接入设计见 `docs/product-v2/14-agentdoor-skill-suite.md`。

### 7.2 判断前需要的数据

| 保存对象 | 必须保存的内容 | 用在哪里 |
| --- | --- | --- |
| 任务与完成标准 | 任务 ID、目标、交付物、数量、每条标准的 ID、状态、日期、负责人、父子关系、正式依赖、版本 | 拆分、工时、诊断、推荐 |
| 成员责任与声明 | 团队与成员 ID、正式责任、本人技能说明、明确公开的协作窗口、来源与更新时间 | 人员匹配、估算工作条件 |
| 历史贡献 | 成员、任务、具体贡献、交付版本、依据；区分本人说明与已核实贡献 | 判断相关经验 |

| 文件与提交 | 文件 ID、版本、可读取正文、提交人、提交时间、关联任务和标准 | 核对结果、诊断；不是初始 EWD 的必需输入 |

| 实际投入反馈（新增） | 实际分钟或区间、填报人与覆盖人员、对应工作和范围、收集方式、范围变化、训练使用许可 | 校准 EWD；部分反馈不能当作整项实耗 |
| 结果核对 | EWD 明细 ID、文件版本与内容出处、单项进度、判断理由、确认来源、核对时间及有效性 | 计算每项已完成 EWD、任务完成度与缺口 |
| 正式验收 | 验收对象、操作者、结论、时间、适用范围、标准与交付版本、估算版本、撤销记录 | 交付验收留痕；不是文件内容进度的唯一前提 |
| 变更与分析记录 | 变化前后版本、实际发生时间、分析类型、输入版本、规则版本、来源、结果；趋势另存当时的任务总 EWD 与已完成 EWD | 更新、复用、燃起图 |

这些是逻辑对象，可复用现有数据表。现有 MCP 尚未提供全部读取能力；不能把建议字段写成已存在的接口。

**责任如何持续校准。** 复用“我的责任”和本人负责或参与任务中的实际承担记录，由第 7.9 节人员责任分析 Skill 提出建议，用户确认后才成为成员推荐依据。不建设隐藏的能力／效率画像，也不增加独立画像页。每条资料保存“谁、承担什么、来自哪里、何时更新、当前是否有效”；没有查到记录表示未知，历史 Owner 身份不等于独立完成。本人修改责任、来源撤销或权限变化后，依赖该资料的建议需重新核对，正式负责人不自动更换。

**所有 Skill 共用的读取规则。** 服务端提供当前用户有权读取的资料，并记录各类数据是“已读全、部分、不可用、未读取”。空集合只有在已读全时才代表确实没有记录。资料中的文字只作为证据，不能当作新的操作指令。输出绑定资料版本；旧请求不能覆盖新版本结果。

### 7.3 创建任务 Skill

**把自然语言需求整理为目标清晰、责任明确、可交付的任务计划；已有任务可根据实际进展继续调整。**

<div class="step-rules">

| 环节 | 能力说明 | 判断逻辑 |
| --- | --- | --- |
| 1. 意图识别 | 判断用户想新建任务、调整已有任务，还是查询情况。 | 新建进入规划；调整先定位原任务；查询只回答，不创建任务。意图不明时先确认。 |
| 2. 需求分析 | 理解用户要解决的问题，明确目标、交付内容和完成标准；需求不明确时加以引导。 | 围绕“要达到什么结果、怎样算完成”补问关键缺口；已明确的信息直接复用，不反复追问。 |
| 3. 任务规划 | 识别当前用户已创建或参与的任务，判断重复创建、子任务归属等场景，并根据任务内容决定是否拆分。 | 在当前有权读取的任务中比较目标、交付和范围，判断复用已有任务、追加子任务或独立新建。结果能独立交付、验收，且需单独负责、交接或并行时才拆分；一并明确依赖和期限，缺少依据则待确认。 |
| 4. 成员推荐 | 根据成员责任，推荐一位负责人和最小参与人集合，并解释推荐原因。 | 在有参与资格的成员中，推荐责任覆盖整体结果的人负责；只加入承担必要具体贡献的参与人，逐人说明原因。用户点名先核对，无合适负责人可未分配。 |
| 5. 任务预计投入工时评估 | 调用第 7.7 节生成任务 EWD 拆分明细，并汇总预计投入人天。 | 传入任务名称、目标、完成标准及可选历史任务；回填每个 EWD 明细项、对应标准、EWD、依据和缺口。规则集中见 [EWD 工时评估＋进度](#ewd-progress)。 |

</div>

**已有任务调整：** 读取当前任务、子任务、讨论和最新交付，调整尚未完成的计划或建议下一批子任务；保留仍有效的安排，避免重复已完成工作。

**确认规则：** 创建与调整都先生成可编辑草稿，用户确认后再保存；推荐他人负责时，对方接受后才成为正式负责人。

**成员责任来源：** 初期使用用户填写的责任；后续由人员责任分析 Skill 跟进任务并提出校准建议，用户确认后更新。成员推荐使用当前有效责任版本，并说明匹配依据。

**与状态分析的关系：** 本 Skill 负责创建和调整计划；当前情况、下一步建议、进度由 7.4 任务状态分析负责。预计投入与进度规则统一见 7.7，页面展示说明见 3.8 与 6.3。

**Skill：** `agentdoor-task-planner`。

**草稿展示与换人：** 主任务、子任务均按完成标准、执行建议、前置依赖的顺序组织可编辑内容；前置依赖只作参考，不自动阻止任务执行或改变状态。卡片底部的匹配依据分别说明负责人覆盖的结果和参与人的具体贡献；人员选择或正式责任版本改变时重新核对，用户指定的人选不等于高度匹配，缺口如实提示。

### 7.4 任务状态分析 Skill

**任务状态分析分为三部分：当前情况、下一步建议、进度。进度包含完成度和燃起图。**

<div class="step-rules">

| 部分 | 回答什么 | 判断逻辑 |
| --- | --- | --- |
| 1. 当前情况 | 现在做到哪，发生了什么？ | 结合任务信息、讨论与交付记录，概括当前结果、缺口和近期变化；信息不足标待确认。 |
| 2. 下一步建议 | 接下来应该做什么？ | 根据当前缺口与诊断，有冲突先核对，有阻塞先解除，否则补齐尚未满足的结果。 |
| 3. 进度 | 当前完成多少，任务是否趋于完成？ | 引用 [7.7 EWD 工时评估＋进度](#ewd-progress) 的完成度与燃起图，解释当前进展和是否收敛；不另行生成一套数值。 |

</div>

相关交付、标准、反馈或验收发生变化时，重新核对受影响的结果。单纯经过时间或增加提交次数，不代表任务更接近完成。

**接入设计：** `agentdoor-task-status-analyzer` 组织这三部分；任务诊断复用 7.5，进度引用 7.7 的文件内容核对结果，不自动修改任务状态。

### 7.5 任务诊断 Skill

**任务诊断只分两类：执行阻塞、决策冲突。**

<div class="step-rules">

| 类型 | 判断什么 | 判断逻辑 |
| --- | --- | --- |
| 执行阻塞 | 当前任务为什么无法继续？ | 检查正式前置依赖与交付情况。任务已在执行，当前必须使用的前置交付尚未满足，导致无法继续，才判为阻塞。 |
| 决策冲突 | 任务里的文件内容与任务信息是否存在矛盾？ | 核对已有文件内容，以及目标、完成标准、时间等任务信息，找出同一事项上相互矛盾或不能同时满足的地方；指出冲突双方的具体内容和出处。 |

</div>

**例子一：执行阻塞。** 宣传海报正在设计，但依赖的活动文案还未交付，缺少标题和优惠信息，无法继续定稿。建议先推动文案交付。

**例子二：决策冲突。** 任务要求“活动预算不超过 10 万元”，但当前方案文件中的预算是 12 万元。建议确认是调整方案预算，还是修改任务中的预算要求。

**Skill：** `agentdoor-task-diagnostician`。

### 7.6 我的工作推荐 Skill

**作用：在本人负责或参与的任务中，综合重要度和紧急度，推荐现在应先处理哪一个，并说明原因。** 推荐权重是排序分数，不代表人员能力、完成概率或绩效；页面只显示顺位、任务名称和一句原因，完整计算规则放在“AI 分析规则”中。

#### 1. 哪些任务参与排序

本人负责/参与的，**只有待开始、进行中、已阻塞这三种状态的任务参与排序。**

#### 2. 排序权重：重要度 60%，紧急度 40%

**推荐权重 W＝重要度 I × 60%＋紧急度 U × 40%。**

重要度和紧急度均在 0～100 分之间，推荐权重也在 0～100 分之间。“权重”指这个最终综合分，不是第三个独立评分项。

| 维度 | 回答的问题 | 计算方式 | 在最终排序中的占比 |
| --- | --- | --- | --- |
| 重要度 I | 这件事对目标、交付和其他工作有多大影响？ | I＝目标影响 B＋协作影响 C＋标签参考 P，最高 100 | 60% |
| 紧急度 U | 如果现在不处理，会多快错过期限、持续损失或让别人等待？ | U＝max(D, H, Q)，取期限压力、当前风险、待本人处理三者最高分 | 40% |

**60%／40% 及以下档位都是初始建议参数，待产品验证，不是已验证的最优权重。** 重要度略高，是为了让关键交付、实际损失和影响他人的任务有机会超过低影响的例行逾期任务；时间不能独占排序。参数统一配置并记录规则版本，AI 不能每次自由调整分数。

#### 3. 重要度怎样计算

**I＝B＋C＋P。每个分项只取符合条件的最高一档，分项之间相加。**

**目标影响 B（0～50 分）：** 依据当前目标、完成标准、已确认的业务要求和目标关联判断，不以任务标题长短、金额大小或 AI 写出的“重要”二字判断。

<div class="priority-score-table">

| 分值 | 成立条件 | 必须能指出的依据 |
| --- | --- | --- |
| 50 | 已明确关联当前核心业务目标、关键外部承诺或必须满足的合规要求，交付失败将直接影响该目标或承诺 | 已确认的目标／要求、这项任务的具体交付，以及两者的直接关系 |
| 35 | 支撑明确的团队阶段目标或对外交付，但未被确认为核心目标或关键承诺 | 当前团队目标或交付要求，与任务完成标准的对应关系 |
| 20 | 有明确必要性的例行维护、内部支持或基础交付 | 已记录的需求与完成标准；不因“例行”判断其没有价值 |
| 10 | 已明确为可选优化，当前没有硬性交付要求 | 用户确认的可选范围，不能仅凭没有截止时间推断 |
| 0（待核对） | 目标、交付用途或关联信息不足，无法归档 | 标明缺什么依据；0 是暂不计分，不表示已确认没有价值 |

</div>

**协作影响 C（0～30 分）：** 判断“这项任务的结果会影响谁”，不是“这项任务在等谁”。

| 分值 | 成立条件 | 计数与边界 |
| --- | --- | --- |
| 30 | 已确认该交付是至少 2 项活跃下游任务的必需输入，或是一项已确认关键里程碑的必要条件 | 下游必须是待开始、进行中或已阻塞；按 Task ID 去重，每项关系有明确所需交付，不累计传递链 |
| 15 | 已确认该交付是 1 项活跃下游任务的必需输入，但不满足上档 | 只取 15，不按前置数、参与人数或评论数累加 |
| 0 | 没有上述影响证据，或只存在参考性关联 | 已知没有影响与资料未知分开记录；未知不能说“没有下游影响” |

父子归属不等于依赖，用户可编辑的前置依赖也只是参考。仅有关系边、上游还未完成，不能证明当前任务阻塞了别人；只有当前交付要求或有效协作记录明确证实“需要这个结果”，才能计入 C。

**标签参考 P（0 或 20 分）：** 任务没有独立的优先级字段，AI 可参考当前任务已有标签的名称和已知含义，辅助判断重要度。明确表示重要性的标签，如“高优先级”“重点任务”，取 20；普通业务分类标签、没有相关标签或含义不明确时取 0。多个符合条件的标签不叠加，最高 20 分；没有标签不等于任务不重要，仍正常计算 B 和 C。

只参考当前用户有权使用且实际关联到当前任务的标签，不借用其他人的私有标签，不按颜色、图标、标签数量或上级任务标签推断。含义不明或互相冲突时标待核对，不由 AI 猜测加分；仅写“紧急”的标签也不能代替 D、H、Q 所需的事实。记录命中的标签 ID、名称和判断依据；标签只作辅助参考，不能替代 B、C 的事实依据，不自动新增或修改标签，也不新增优先级设置。

例如：支撑团队阶段目标 B＝35，影响两项已确认下游交付 C＝30，任务已有“高优先级”标签，参考该标签取 P＝20，则重要度 I＝85。移除该标签后，P＝0，I 变为 65；任务状态不变，B、C 仍按原事实计算。

#### 4. 紧急度怎样计算：时间只是其中一项

**U＝max(D, H, Q)。三类信号各自取最高档，再取三者最高值，不相加。** 同一问题可能同时造成逾期、损失与等待，取最高值可避免重复放大；其他命中仍保留为解释依据。

**期限压力 D（0～100 分）：** 按团队时区计算，日期差 d＝截止日期与当前日期相差的日历天数。仅有日期时，以当地当天结束作为截止；明确时刻超过后才算逾期。先判断逾期，再选今天或未来档位。

<div class="priority-score-table">

| 条件 | D 分值 | 判断规则 |
| --- | --- | --- |
| 已逾期 | 100 | 早于今天的截止日期，或已超过明确截止时刻 |
| 今天到期 | 90 | d＝0，尚未超过明确截止时刻 |
| 未来 1～2 天到期 | 75 | d＝1 或 2 |
| 未来 3～7 天到期 | 60 | 3≤d≤7 |
| 未来 8～14 天到期 | 30 | 8≤d≤14 |
| 14 天以后到期 | 10 | d＞14 |
| 明确无截止时间 | 0 | 没有时间信号，仍正常计算 I、H 和 Q |
| 日期缺失、过期或无法识别 | 0（待核对） | 不猜年份、不补日期、不判逾期；推荐注明日期依据不完整 |

</div>

逾期天数不继续叠加分数。日期信息未知与用户明确不设截止时间是两回事；两者都不凭空增加 D，但解释必须区分。

**当前损失或执行风险 H（0～100 分）：** 除截止时间外，判断“拖延处理正在造成什么影响”。

| H 分值 | 成立条件 | 依据要求 |
| --- | --- | --- |
| 100 | 当前已有持续的关键服务中断、客户／交易损失或明确的合规、安全风险，且有需本人立即处理或协调的行动 | 当前有效事件、影响范围、未解除事实和本人行动；仅标题写“紧急”不成立 |
| 80 | 已证实执行阻塞或决策冲突正在持续造成停工、返工或扩大交付影响，需本人处理或协调 | 当前受影响的工作、阻塞／冲突内容及可采取行动，不只看状态名 |
| 60 | 有当前有效的决策冲突，继续按不一致要求推进会导致错误交付，但尚未证实持续损失 | 冲突两侧的具体内容和出处；失效的旧诊断不能使用 |
| 0 | 未证实以上风险，或没有当前需本人处理的行动 | 仅标“已阻塞”、很久没更新或前置尚未完成，均不自动给风险分；原因未知标待核对 |

**待本人处理 Q（0～80 分）：** 判断是否已有明确等待，而不是仅从任务状态猜测。

| Q 分值 | 成立条件 | 依据要求 |
| --- | --- | --- |
| 80 | 活跃下游工作已明确停等本人必须提供的结果、决定或确认，且本人现在有可执行的处理行动 | 当前等待方、所需内容、尚未回应／交付的记录；不是未来可能依赖 |
| 60 | 有指向本人的有效交付核对或决定请求，材料已提供且事项尚未处理，但未证实下游停工 | 请求、交付或反馈与本人责任的对应关系 |
| 0 | 没有上述当前等待 | 仅上传文件、没有验收记录、只有参与身份，均不构成等待；仅有参考性前置未完成不加分 |

例如：没有截止时间 D＝0，但本人需要立即协调处理持续的关键服务中断 H＝100，下游也在等待 Q＝80，则 U＝max(0, 100, 80)＝100。紧急度并不依赖是否填了时间。

#### 5. 证据、缺失数据和去重

- 每次命中必须保存事实内容、来源 ID／版本、适用任务和有效性。AI 可以从可访问记录中识别候选事实并解释，但分档必须符合上述条件；没有证据不能靠模型语气打高分。
- 不因资料缺失或过期加分；失效证据不再参与计算，未知分项暂取 0，不把剩余维度重新放大到 100。推荐注明“依据不完整，需核对”，不能写“低价值、没有风险”。资料恢复后重新计算。
- 同一维度中，同一事件、相同任务或重复文件只计一次；B、C、P 反映不同影响，允许相加；D、H、Q 反映当前处理压力，只取最高值。不要再额外叠加“阻塞＋20、资料过期＋25”等旧规则。
- 一个事实可同时支持重要度和紧急度，但必须分别解释：例如“会影响两个交付”支持 C，“两项工作现在已停等本人”才支持 Q。只证明前者，不能顺便计入后者。
- 不以 EWD 大小、提交次数、聊天活跃度、任务历时或人员历史速度加分；没有真实剩余工作量和可投入时间时，不计算忙闲率、完成概率或精确排程。
- 父任务与子任务可分别参与，但各自使用本任务的责任和行动。父任务不直接复制子任务的分数，也不因后代数量多而层层累加；父任务理由写统筹行动，避免重复推荐同一执行动作。

#### 6. 如何排序和解释

1. 先检查状态白名单及本人负责或参与的关系，再按 Task ID 去重。
2. 按当前有效事实分别取 B、C、P、D、H、Q。
3. 计算 I＝B＋C＋P；U＝max(D, H, Q)；W＝0.6×I＋0.4×U。
4. 按 W 从高到低；同分时先比较重要度 I，再比较紧急度 U，均从高到低；仍同分时，按可比较的截止时间从早到晚，无可比较截止时间排后；最后按稳定任务 ID 排序。
5. 排序使用未舍入的结果，展示或调试时最多保留一位小数。不能用传入数组顺序、随机数或重新生成的 AI 文案打破平局。
6. 一句优先原因说明最有贡献的重要度依据和当前紧急信号，再指出现在可做的事。无紧急信号时如实说明按目标或协作影响优先，不虚构截止压力。

有强依赖影响的任务可以比例行逾期任务靠前；已阻塞不必然第一，也不能被整体排除。**重要但不紧急的任务仍有排序权重，紧急但影响较小的任务也保留时间压力，两者通过固定比例综合，而不是先把所有逾期任务排完。**

| --- | --- | --- | --- |
| 1. 关键服务故障：无截止；关联核心承诺、影响多项交付、有“高优先级”标签；损失持续且下游停等本人 | 50＋30＋20＝100 | max(0, 100, 80)＝100 | **100** |

| 5. 团队常规交付：今天到期；支撑团队目标，仅影响本项交付，只有业务分类标签；暂无其他问题 | 35＋0＋0＝35 | max(90, 0, 0)＝90 | **57** |

第二项：W＝85×60%＋80×40%＝51＋32＝83。第三项：W＝70×60%＋60×40%＝66。没有日期的关键工作能够排在例行逾期工作前面，是重要度和非时间紧急信号共同作用的结果，不是遗漏了期限。

第一项的一句原因可写：“关键服务中断正在影响多项交付，需先协调恢复并回应等待方。”不能写成“未设置期限，所以不紧急”。

同分例子：任务 X 的 I＝80、U＝30，任务 Y 的 I＝60、U＝60，W 都为 60；按重要度，X 在前。若两项 I、U、截止均相同，则只按稳定任务 ID 决定顺序。

### 7.7 EWD 工时评估＋进度

**当前规则（2026-09-14，v13）：** 按第 6.3 节，用户设置状态与计划时间，不手填百分比；AI 预测当前完成度，用户完成声明优先显示 100%，同时保留来源。用户没有工作排期，不生成计划完成比例或工作量差；完工日期须有独立执行依据。每项先估算 EWD，再按相同范围加权；EWD 明细不会自动创建子任务。

#### 一、估算 EWD

**EWD 明细项：** 为满足任务完成标准，成员必须亲自投入时间的一项具体工作，例如整理资料、操作 AI、分析、制作、修改、沟通、审核或验收。每项同时写明可核对的完成结果；等待审批、排队和 AI 无人值守运行不列入明细。

1. AI 根据任务名称、目标和完成标准生成任务 EWD 拆分明细。每个 EWD 明细项是一项具体人工工作，同时对应一项可核对的完成结果；同级不重叠，并覆盖当前已确认任务范围的 100%。
2. AI 用八个投入维度检查任务，从已写明的信息中识别需要列入的 EWD 明细项、数量、条件与风险；同一项工作只列一次。
3. AI 为每个 EWD 明细项给出乐观值 O、最可能值 M 和保守值 P，程序按 `EWD＝(O＋4M＋P)÷6` 计算该项 EWD。
4. 任务总 EWD＝所有 EWD 明细项之和；共享工作只列一次，父任务只汇总叶子任务。
5. 初期使用平台维度与 AI 专家估算；后续根据团队历史任务的 EWD 拆分明细、完成标准和实际投入反馈校准估算。历史数据不足时继续使用平台规则。
6. 用户确认后保存 EWD 拆分明细、总 EWD 和规则版本作为本次估算基线；新增、删除或重估明细项时生成新版本，不回写旧基线和历史快照。

#### 平台初始 EWD 检查维度

八个维度是 AI 补全 EWD 明细项的检查清单，不打分，也不直接换算人天。每个维度必须回答“是否需要新增或调整明细、工作是什么、数量或次数、依据是什么”；同一项工作受多个维度影响时只保留一条明细，避免重复计时。

| 维度 | AI 检查什么 | 如何进入估算 |
| --- | --- | --- |
| 交付规模 | 结果数量、覆盖范围和适配版本 | 确定要制作、适配和交付几份结果 |
| 实现难度 | 完成结果所需的方法与专业判断 | 识别分析、设计、制作或开发动作 |
| 信息不确定性 | 需求、方法和结果是否明确 | 已识别风险进入 O／P 差异；关键条件未知则待估算 |
| 资料准备 | 输入资料是否可以直接使用 | 识别收集、整理、清洗、授权等准备动作 |
| 协作依赖 | 人工协调和外部输入有多少 | 识别沟通、等待前的人工跟进和交接动作；纯等待不计 |
| 修改迭代 | 已明确需要多少轮调整 | 按已明确轮次和受影响内容识别修改动作 |
| 核验验收 | 检查与验收要求有多重 | 识别自检、审核、复核和验收动作及人数 |
| 工具环境 | 工具、权限和环境准备工作 | 识别配置、接入、联调等 EWD 明细项；无人值守运行不计 |

AI 可以返回 `additionalFactor`，说明八个维度未覆盖的因素，并给出由此新增或调整的 EWD 明细项与三点估算。重复出现且有历史数据支持的因素，经团队规则评审后才能升级为团队扩展维度并记录版本。

#### 三点估算规则

**参考依据：** [PMI 的项目估算实践](https://www.pmi.org/learning/library/leveraging-new-practice-standard-project-estimating-6222)使用三点估算表达不确定性，并介绍常用的 PERT 加权平均公式 `(O＋4M＋P)÷6`。TaskDoor 将该方法用于每个 EWD 明细项；这些明细项在估算方法上对应 WBS 工作包。八个检查维度是平台规则，不是 PMI 规定的评分标准。

| 符号 | 名称 | 含义 |
| --- | --- | --- |
| O | 乐观投入 | 已确认的资料、工具和协作条件都顺利，没有额外返工时需要的人工时间 |
| M | 最可能投入 | 按当前已知条件正常完成时，最可能需要的人工时间 |
| P | 保守投入 | 已识别的不确定因素发生，但交付范围没有增加时需要的人工时间 |

**规则：** AI 只依据任务已写明的工作和风险，为每个 EWD 明细项估算 O、M、P，满足 `0≤O≤M≤P`；同一项工作只计算一次。程序计算 **单项 EWD＝(O＋4M＋P)÷6**，任务 EWD 为全部明细项 EWD 之和。关键条件不足、足以改变估算区间时标“待估算”。用户可以修改三点数值并补充依据；团队历史数据用于校准后续估算。

**数值来源：** 首版由 AI 根据任务名称、目标、完成标准、八个检查维度和已识别风险估算 O、M、P，单位统一为人天。它们不是固定分档，也不是 AI 随意打分；每个数值必须有对应工作和判断依据。用户可修正数值，后续再用团队历史任务的实际投入反馈校准。

**例子：制作一份方案。** 已知工作包括准备资料、操作 AI、人工修改和两人审核；任务同时明确存在“资料可能需要补充、审核后可能再修改一轮”的风险。

| EWD 明细项 | 对应检查维度 | O | M | P | 单项 EWD（人天） | 判断依据 |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| 准备资料 | 资料准备、信息不确定性 | 0.05 | 0.10 | 0.15 | 0.10 | 现有资料基本可用，但已明确可能需要补充 |
| 操作 AI | 实现难度、工具环境 | 0.05 | 0.10 | 0.15 | 0.10 | 使用现有工具生成一份方案初稿；保守情况包含一次提示调整 |
| 人工修改 | 实现难度、修改迭代 | 0.10 | 0.25 | 0.60 | 0.28 | 正常修改一轮；保守情况包含已识别的第二轮修改 |
| 两人审核 | 协作依赖、核验验收 | 0.10 | 0.20 | 0.30 | 0.20 | 两人分别审核；保守情况包含问题复核 |
| 任务合计 | 交付规模为一份方案 | **0.30** | **0.65** | **1.20** | **0.68** | 同一项工作虽对应多个维度，只计算一次 |

计算结果：`(0.30＋4×0.65＋1.20)÷6≈0.68`，**该任务 EWD≈0.68 人天**。

本规则采用面向交付的 WBS、范围覆盖、逐项估算、估算依据和版本基线。当前实现未记录按时间分配的计划值与实际投入。本次建议新增计划参考，不建设完整挣值管理，也不根据进度差推导实际成本或个人效率。

#### 二、进度预测与用户确认

用户仅设置状态与截止时间，没有工作排期，不计算计划应完成比例或工作量领先／落后。

有效工作量 W 与有交付依据的完成量 C 齐备时，AI 预测完成度＝C/W。完成标准、证据覆盖或权重不足时返回缺口，不从状态、截止时间、文件数量或经过天数生成百分比。用户标记已完成并保存成功后，以独立完成声明显示 100% 用户确认；AI 预测 100% 本身不改变状态。

主任务需要汇总时按完整、去重叶子工作量加权；叶子取其有效 AI 预测或用户确认。缺少必要贡献时不输出精确父级汇总。父子状态不级联；父级已有用户完成声明不被子项汇总撤销。

#### 三、截止日期与完工预测

截止日是用户要求的目标；AI 完工预测依据剩余工作、可用执行时间、依赖与已知等待，单独记录生成时间和输入版本。仅有截止与状态无法得出完工日期；不能用当前百分比或人天直接外推自然日。

用户完成后，确认事件日期替代未来预测。仅修改、清空或恢复截止日时，进度与 AI 完工预测日均保持不变，只重新比较日期差；不能为适配截止而修改预测，也不因此使预测失效。未完成且已过截止可由代码判断已逾期，无需 AI。

预测记录、完成确认、重开及范围变更分别保存。燃起图保留原时点总量和完成量及来源，不统一称为实际进度；新增范围与确认完成各有事件。生产预测队列、独立时间戳和正式历史迁移仍待接入。

#### 五、校准与实现边界

初始 EWD 采用三点估算；历史校准使用真实记录的投入和确认事实，不能将任意完成标记时间当作实际投入工时。当前展示修订不代表模型已实时运行或校准完成。进度来源与完成／重开、改截止、迟到结果、父子关系的验收统一维护于 [6.3 验收重点](#progress-state-acceptance)。

### 7.8 谁调用规则，什么时候更新

#### 创建任务的完整流程

| 流程步骤 | 归属 | 产物 |
| --- | --- | --- |
| 识别意图、明确目标和关键补问 | 创建任务 Skill 内部 | 有范围的需求 |
| 查重、拆分结果、判断父子与依赖 | 创建任务 Skill 内部，代码校验关系 | 任务草稿 |
| 匹配责任、安排必要协作与日期、建议已有标签 | 创建任务 Skill 内部 | 人员与时间建议 |
| 估算预计投入 | 创建任务调用 7.7 EWD 工时评估模块 | EWD、依据、假设与缺口 |
| 校验草稿、展示差异、用户确认 | 业务服务 | 确认后的提交 |
| 保存任务、估算和变更记录 | 业务服务统一事务 | 正式任务；选他人时负责人仍待接受 |

拆分、人员匹配不各开一个 Skill；规则表也不各开一个 Agent。创建时只调用需要的估算部分；执行中的结果核对和验收不是创建流程的必跑步骤。

#### 保存之后的更新表

进度与完工时间的具体触发、结果生效及失败规则统一见 [6.3 预测更新节点](#progress-component-events)。

| 保存的变化 | 更新什么 | 保留什么 |
| --- | --- | --- |
| 目标、交付数量或标准改变 | 检查受影响范围；相关估算依据和核对结论需复核；检查诊断和推荐 | 未受影响的结果与原始证据 |
| 子任务新增、移除、移动 | 更新新旧父级范围与汇总，相关诊断、进度和趋势；新增叶子按规则估算 | 已有历史点 |
| 本人责任、相关经验或公开窗口改变 | 刷新依赖这些资料的人员建议；实际工作假设改变才重估 | 正式 Owner 不自动更换 |
| 本人任务分工、实际贡献或责任建议反馈改变 | 调用人员责任分析，更新受影响的责任候选；用户确认后再刷新人员匹配依据 | 正式责任与原始来源，旧建议不覆盖新版本 |
| 正式 Owner 改变 | 更新新旧负责人的“我的工作”，核对相关工作假设 | 人名变化本身不改变工时 |
| 文件新版本、相关反馈或明确贡献记录 | 核对关联标准，更新已完成 EWD、完成度、燃起图、内容诊断与摘要；内容改变估算假设时才重估总量 | 仍适用的 EWD 和历史快照 |
| 用户确认完成／重新打开 | 按 6.3 更新用户确认 100% 或重开后恢复已有独立 AI 预测；受影响父级仅更新汇总，不级联改状态 | 原 AI 预测、确认与重开事件；不提供手填百分比 |
| TaskStatus 改变 | 按 6.3 更新进度来源、完成／重开记录、状态说明、关系诊断和推荐 | 不修改 EWD 估算；用户确认不伪装成 AI 验收，正式账本迁移待接入 |
| 仅截止日期改变 | 更新日期差和诊断，保留 AI 预测日期与观测记录，不触发重预测 | 百分比、AI 日期及日期竖线不因截止调整而改变 |
| 正式依赖改变 | 按 6.3 重新预测受影响的剩余工作与完工时间 | 依赖改变交付内容时才重新核对内容进度 |
| 已知执行时间或工作日历改变 | 复核受影响完工预测；没有这些数据时不虚构可用工时 | 已有进度不因时间假设改变而涨跌，历史不回写 |
| 内容核对或确认结果改变、撤销或失效 | 更新已完成 EWD、完成度、父级汇总和燃起图；读取失败时标待核对，不补 0 | 原始估算、历史点 |
| 实际跨日 | 按团队时区更新今天截止／已逾期及个人排序；过去的预测失效，不自动顺延、不每日无条件调用 AI | 进度不因时间流逝增长，结果截至时间与历史不改写 |
| 权限改变 | 清除当前用户不再有权读取的内容与分析缓存，重新核对覆盖 | 服务端受控历史保留，但不继续展示给无权用户 |

**运行方式：** 正式修改和变更记录一起保存；后台根据上表找受影响任务、祖先、后续依赖任务及相关负责人。代码能算的先算，需要理解文字的再调用对应 Skill。每次结果保存任务版本、证据版本、规则版本和读取范围；发布前重新核对，旧请求丢弃。

同一输入已有有效结果就复用。切页签、展开明细、尚未保存的输入不重算。失败保留有权限的旧结果并标“已过期”，用户可重试；刷新不伪造新的数据截至时间。同一页面的诊断、进度和摘要必须明确各自版本；不能将旧摘要包装成已解释新进度。

**规则维护：** 新规则发布要有编号、适用条件、参数来源、例子和版本。新版本使相关分析需复核，不自动改已采用估算或历史曲线。参数调整、模型理解错误和算术错误分别记录；当前未采集实际投入，不开展个人效率排名或声称估算已完成校准。

### 7.9 人员责任分析 Skill

**目标：持续跟进当前用户负责或参与的任务，识别本人实际承担的工作，结合用户确认和纠正，让责任说明越来越准确，为后续成员推荐提供更可靠的依据。** 判断“通常负责什么、责任边界在哪里”，不做能力、效率或绩效评分。

**Skill：`agentdoor-responsibility-advisor`。** 将第 2.5 节已有责任建议明确为独立的人员责任分析 Skill，复用“我的责任”的建议、依据和确认入口，不另建用户画像。

#### 1. 分析范围与输入

- 仅分析当前用户在当前团队中负责或参与、且当前有权读取的任务；不同团队的责任与证据分开保存。
- 输入责任文本与版本、任务目标与完成标准、本人分工、实际交付／贡献、相关讨论与确认、任务／交付来源及版本，以及历史建议和用户反馈。
- 已完成任务仍可作为历史依据；待开始任务只说明当前分工，不能当作已经执行。已取消任务只保留可证实的实际承担事实，不推断交付完成。本分析不套用“我的工作”的三状态排序范围。
- 输入注明数据覆盖、时间与权限；参与名单不等于实际承担，任务完成也不等于所有成果都由负责人独立完成。

#### 2. 分析步骤

| 步骤 | 判断什么 | 产物 |
| --- | --- | --- |
| 识别实际承担 | 本人在任务中具体负责什么结果、提供什么贡献，哪些记录可以证明？ | 带来源的承担事实；不能归属的内容标待核对 |
| 归纳责任范围 | 哪些是持续出现的工作，哪些只是一次临时协助或阶段性安排？ | 有范围、时效和依据的责任候选，不直接写“擅长”或“效率高” |
| 对照现有责任 | 已有描述是否覆盖实际工作，有没有缺失、过宽、重复或已确认的职责变化？ | 新增、更新、废弃或不调整，并指出对应原责任 |
| 用户核对 | 建议是否准确，责任边界需要怎样修改？ | 用户确认后才写入；保留修改、忽略与纠正记录 |
| 反馈校准 | 新任务事实和用户纠正改变了哪些判断？ | 更新后续建议的依据与范围，确认后的责任版本供成员推荐使用 |

一次临时协助不直接推成长期责任；多个独立任务的同类承担或明确的长期分工确认，可支持归纳。任务数量、在线时长和提交间隔不能代替实际承担证据；同一成果的多版本、父子引用不重复计数。没有近期任务或来源失效不代表职责消失；废弃建议需有明确职责调整依据。

#### 3. 输出与用户决定

每条建议包含操作、责任文本、原责任与基准版本、改变原因、任务与交付来源、数据时间、团队与范围、未确认事项。已有责任准确时输出“不调整”；证据不足保留原文并说明缺口。

复用“我的责任”：用户可查看依据、采纳、修改或忽略；旧建议不能覆盖新版本。未经确认的建议不进入正式责任匹配。Skill 不自动修改 Task Owner、参与人或权限；确认责任建议不等于接受具体任务。

**更新流程：** Skill 支持分析建议、准备更新、执行已确认更新三种模式。用户确认后才写入；确认绑定最终操作、责任文本、用户与团队、原责任及基准版本。业务服务独立校验权限、当前版本和幂等并返回回执；Skill 根据回执说明更新结果，不把候选的“可确认”当作写入授权。用户修改文本后须确认最终版本；旧建议或版本冲突时重新核对，不能覆盖新责任。写入接口未接通或回执未知时保留建议，明确待接入或待核实，不声称已更新。

#### 4. 何时分析，如何越来越准

- 本人任务分工、相关交付／贡献、确认记录或用户责任发生实际变化时，只重算受影响的责任候选；本人可主动触发重新分析。打开页面不制造新证据或新分析时间。
- 用户纠正需与被纠正建议及来源版本关联，例如“只是这次临时帮忙”“负责脚本，不负责投流”；后续判断复用该边界，新证据与之冲突时提出待核对，不静默覆盖用户说明。
- 忽略不等于否定，也不代表该用户拒绝承担工作；同一来源版本的已忽略建议不反复推送，实质证据变化后才重新判断。
- 来源撤销、权限变化、任务贡献被更正后，相关候选失效并复核；读取失败不等于没有责任。正式责任仍由用户决定是否调整，失效证据不得继续对外展示或用作新增推荐理由。
- 每次保留输入、来源版本、规则版本、建议与用户处理结果。同样输入和反馈复用有效结果；这里的持续校准是更新事实、责任边界与建议，不是重复刷新或默认开展模型训练。

**例子：** 用户原责任是“内容制作”，近期多次实际承担达人短视频脚本交付，可建议细化为“负责达人短视频脚本策划与交付”，附任务依据。用户纠正直播协助仅为临时安排后，不再凭同一记录归纳为长期责任。

**验证目标：** 看责任遗漏、错误归属和重复错误是否减少，成员推荐能否更准确地解释匹配原因；不以建议数量或文字长度代表准确，不对成员排名。

**实现边界：** 已设计项目内 Skill 文件，并同步更新 PRD、HTML 与 PDF。现有责任建议界面可复用；任务变更触发、贡献归属分析、反馈回读、受控责任写入与生产数据接入仍待实现，尚未启动后台持续分析。

## 8. MCP：工具与参数设计

### 8.1 用来解决什么

让个人 AI、MCP App 和普通页面操作同一份任务事实。REST 与 MCP 共用身份、权限、版本、幂等和事务服务，不能让 MCP 再存一套正式任务。

```text
页面 / 个人 AI → MCP 适配器或 REST → 同一领域服务 → 业务数据 / 变更回执
```

下面合并原《任务 REST API 与 MCP 工具契约》v0.1 的 **38 个候选工具**，并补齐阅读所需的参数类型和条件。它们仍是 Proposal；本次补充的必填性、枚举和字段白名单是待评审建议，不是现网 Schema。当前运行代码只有第 8.10 节的两个演示工具。

### 8.2 通用参数与回包

下表工具均使用完整 `agentdoor_` 名称。表中未标 `?` 的参数必填；`?` 表示可选。ID 均为非空 string；ID[] 为去重字符串数组；version 为正整数；null 是明确清空，不等于省略。

| 记号 / 参数 | 类型、默认值与校验 |
| --- | --- |
| `W` | 所有写工具共同带 `idempotency_key:string`；同一次业务操作及同一载荷重试用同一键 |
| `V` | 修改已有对象带 `expected_version:integer>=1`；从最近读取返回的 version 获取，不由模型猜 |
| `P` | 列表带 `cursor?:string, limit?:integer>=1`；默认 50，服务端限制最大值并回显；游标不跨查询条件复用 |
| 日期 | `YYYY-MM-DD`，日历日期校验；时间戳使用含时区的 ISO 8601，服务端记录 UTC |
| 未列字段 | 拒绝额外字段；不接受任意 JSON Pointer、SQL、任意本地路径或模型自报权限 |
| 身份 | team scope、真实 Principal、代表的成员和委托来自认证上下文；可选过滤参数不能扩权 |

**MCP → REST 映射**：`expected_version` 由适配器转换为 `If-Match`，`idempotency_key` 对应 `Idempotency-Key`；snake_case 工具参数转换为服务端 camelCase 字段。只在适配层映射，不能存两份不同字段。列表 `list_*` 对应 GET 集合，`get_*` 对应 GET 单资源，其余映射见各表。

成功返回 `content`（给人一两句话）和 `structuredContent:{data,receipt}`；错误为 `isError:true` 与 `structuredContent.problem:{code,message,retryable,recoveryAction}`。调用方解析结构化字段，不解析自然语言当作事实。

| 回执字段 | 意义 |
| --- | --- |
| `schemaVersion / operationId` | 写回执版本 `agentdoor.write-receipt.v0.1` 与操作标识；外层 meta 带 requestId、asOf |
| `outcome` | `succeeded / no_change / accepted_async / needs_confirmation` |
| `effect` | `none / proposed / applied`；只有 applied 才表示正式数据生效 |
| `replayed / atomic` | 是否幂等重放、是否整批原子成功 |
| `affectedResources[]` | 对象类型、ID、动作、beforeVersion、afterVersion；新建前版本为 null |
| `changeSetId / changeDigest / generatedActivityIds / committedAt` | 可追踪变更与实际提交时间；未应用不得伪造业务提交时间，Proposal 需细化各 outcome 的字段必填条件 |

默认 compact 返回 ID、状态、版本、关键差异和回执；长讨论、证据、文件正文分页获取。版本冲突或确认预览使用 standard。原契约的 detailRef / full 回传仍需补充具体资源读取地址，不能把一个不可读取的引用当作完整实现。

### 8.3 Task 与子任务：9 个工具

| 工具 / 操作 | 参数与返回重点 |
| --- | --- |
| `agentdoor_list_tasks` · GET /tasks | `filters?:TaskFilters, P` → 可见 Task 列表、nextCursor、asOf |
| `agentdoor_get_task` · GET /tasks/{id} | `task_id:ID` → 当前 Task、version；不可发现对象不透露其存在 |
| `agentdoor_create_task` · POST /tasks | `TaskCreateFields, W` → 正式 Task 与写回执；不是模型准备草稿步骤 |
| `agentdoor_update_task` · PATCH /tasks/{id} | `task_id:ID, V, updates:TaskUpdate[], W` → 更新后的对象或 no_change |
| `agentdoor_get_task_deletion_impact` · GET /tasks/{id}/deletion-impact | `task_id:ID` → 当前 taskVersion、可公开影响、impactDigest、requiresExplicitCascade |
| `agentdoor_delete_task` · DELETE /tasks/{id} | `task_id:ID, V, impact_digest:string, cascade?:none或descendants, W` → 逻辑删除回执；默认 none，有后代必须明确确认 |
| `agentdoor_change_task_status` · POST /tasks/{id}/status-transitions | `task_id:ID, V, to_status:TaskStatus, reason:string, evidence_refs:ID[], W` → 状态转换回执；证据必需性按转换规则校验 |
| `agentdoor_list_subtasks` · GET /tasks/{id}/subtasks | `parent_task_id:ID, P` → 仅直属、可见子 Task；继续按子 ID 获取下一层 |
| `agentdoor_create_subtask` · POST /tasks/{id}/subtasks | `parent_task_id:ID, TaskCreateFields, W` → 普通 Task，parentTaskId 由服务端绑定，不重复接收父级字段 |

`TaskFilters`：`team_id?:ID, status?:TaskStatus, owner_id?:ID, parent_task_id?:ID或null, label?:string, query?:string, updated_after?:ISO时间`。建议 parent_task_id 省略=不限制，null=根任务，ID=直属子任务；前端标签或状态查询不等于完整查重。

| TaskCreateFields 字段 | 类型与默认 / 规则 |
| --- | --- |
| `name` | 非空 string；正式接口统一用 name；planner 的 title 在适配层转换 |
| `goal` | 非空 string；子任务沿用已读取的主目标，不借子任务创建修改主目标 |
| `completion_criteria` | string[]，至少一项非空完成标准；对应 REST completionCriteria |
| `owner_id?` | ID 或 null，默认 null；选他人时产生责任提议，不伪造其接受；已有 Owner 变更不走普通更新 |
| `participant_ids?` | ID[]，默认 []；同团队有效成员、不重复 Owner；正式参与成立仍受现行接受规则控制 |
| `planned_start_on? / planned_end_on?` | 日期或 null，默认 null，不默认今天或 7 天后；校验前置和父级范围 |
| `depends_on_task_ids?` | ID[]，默认 []；禁止自指、循环和无效引用，父子关系不自动生成依赖 |
| `labels?` | string[]，默认 []；本 v0.1 原契约尚未确定标签字符串是稳定 ID 还是名称，接入标签模块前统一 |

`TaskUpdate` 为 `{field,value}`，数组至少一项；白名单及 value 类型：`name:string`、`goal:string`、`completionCriteria:string[]`、`participantIds:ID[]`、`dependsOnTaskIds:ID[]`、`plannedStartOn:date|null`、`plannedEndOn:date|null`、`labels:string[]`。这里 field 枚举沿用原文 camelCase；MCP 外层仍为 snake_case。数组整体替换，靠版本防止覆盖他人修改。

`TaskStatus` 使用 `open / in_progress / blocked / completed / cancelled`，分别对应待开始、进行中、已阻塞、已完成、已取消。不新增审核状态；交付核对是处理事项，不替代任务状态。状态转换图、正式验收、Owner Transfer 均未在本次补成可用接口。

**删除边界**：影响包括可见后代、依赖方、文件引用及草稿；确认绑定 impactDigest。影响变化报 `DELETION_IMPACT_CHANGED` 并重做预览；不可见影响由服务端判定能否操作，不透露隐藏名称、ID 或数量。逻辑删 Task 不删共享 File、正式 Commit 或审计事实。

### 8.8 安全、失败与重试

| 场景 | 服务端结果 / 客户端动作 |
| --- | --- |
| 超时或重复点击 | 用原幂等键和原载荷重试，返回同一 ID 和 replayed=true；不同载荷复用键返回 409 |
| 并发更新 | 版本不一致返回 412 VERSION_MISMATCH，保留用户草稿、读取新版本、重新确认；不自动覆盖 |
| 删除影响变化 | 409 DELETION_IMPACT_CHANGED；重新预览和确认，旧摘要失效 |
| 无权限 | 已知且可暴露存在的对象可报 403；不可发现对象统一 404；重放旧回执也要重新鉴权 |
| 验证不通过 | 400 结构错误，422 领域约束错误，428 缺版本前置条件；指出允许公开的字段问题，不写半份数据 |
| 文件仍扫描 | accepted_async，不当错误也不当可用；通过 upload status 查询后续状态 |
| 多任务计划 | 主任务与子任务创建需受控原子命令；当前 38 个工具没有整棵计划提交工具，不能逐项调用后宣称原子成功 |

annotations 只帮助调用方识别 readOnly / destructive / idempotent，不提供权限。删除、正式提交、状态变化的授权必须绑定实际对象和影响；不得把模型“用户已同意”的文字当作确认凭证。

### 9.3 诊断结果如何进入任务流程

会议指出“只展示诊断、没有后续动作”的问题。本节是对该方向的**最小闭环建议**，后台能力待接入：

1. **触发：** 任务状态、正式依赖、日期、文件版本或有关决策事实保存后，分析当前任务与受影响的可见任务；用户也可在常驻助手手动发起。无关浏览不重算。
2. **定位：** 一个发现使用同一标识，绑定实际受影响子任务、证据版本和待处理事实，在有权限的祖先任务中引用。子任务已阻塞或证据充分时显示“受子任务阻塞影响”，不直接将所有祖先 TaskStatus 改成已阻塞。
3. **触达：** 首次出现、影响实质扩大或解决后再次发生时，向有权限的受影响任务负责人、需采取动作的相关责任人及主任务负责人发送站内提醒，按接收人去重。持续未变不重复推送；没有负责人时按待确认接管规则路由，不能随便选一个成员。
4. **处理：** 通知打开原任务／原发现，带上下文进入助手；相关人可补充交付、澄清冲突或审阅改期／协调方案。修改按既有权限与确认机制执行，“提醒已发送／已读”不算问题解决。
5. **复核：** 相关事实改变后重新核对，条件不再成立才记录已解除与依据，更新父级聚合并向原接收范围反馈；通知发送失败可重试同一事件，不重复建问题。

通知文案只引用接收人有权看到的任务与证据；不可见范围说明覆盖不足。提醒、业务状态和诊断生命周期分开记录；手动关闭通知不能抹除仍成立的阻塞。具体通知时效、重复升级阈值与生产投递服务仍待接入评审，本次不替用户发送任何通知。
