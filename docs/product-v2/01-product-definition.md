# AgentDoor 产品定义

> 版本：V2 讨论稿  
> 核心主题：AI 原生的团队协作与责任基础设施
> 状态说明：产品方向、单 Owner 与人与人 Handoff 必须清晰等底层原则已确认；Proposal 边界、Owner 资格、文件发布协议、团队动态导航、Handoff Profile 和 AI 写入级别是建议默认，统一以决策台账为准。
> 当前产品投影：服从 `D-140 / PRODUCT-V2-2026-08-28-r125`。React 原型不提供 Task 创建流程；任务列表仅保留不提交、不附加文件、不生成 Proposal 或正式 Task 的任务意图输入壳。下文涉及创建 Proposal、拆分、人员与文件确认的设计均降为未来候选，不指导当前表面实现。

## 一句话定义

AgentDoor 是面向人类与个人 Agent 的团队协作层：它从用户真正想完成的事情出发，在必要时帮助补齐信息、找到合适的人、建立责任与权限边界，并把 Task、Task 内文件、活动、决策和 Agent 产出持续组织成可接续的团队上下文。

## 产品问题

个人 Agent 显著提高了个人执行速度，但没有自然解决团队问题：

- 一个人不知道自己缺少哪些知识、经验或授权。
- 知道需要帮助，却不知道团队里谁真正做过类似事情。
- 指派者容易过度拆解，使执行者失去自主权。
- 专家反复被找，忙闲和隐性协作成本不可见。
- 文件散落在任务、聊天和本地环境中，版本与权限不清楚。
- 工作发出后，双方常常没有形成相同理解；“发过了”和“接住了”之间存在责任空窗。
- 团队无法持续理解“谁实际负责什么、谁知道什么”。
- Agent 的洞察停留在私人对话，没有成为团队可以审查和接续的工作上下文。

AgentDoor 要解决的不是“怎样让 AI 自动管理所有人”，而是：

> 怎样让团队在保留个人主动性与人类责任的前提下，更容易知道需要什么、应该找谁、依据是什么、下一步如何继续。

## 产品定位

AgentDoor 不是 Jira、Asana 或飞书项目的完整替代品，也不是新的通用 Agent Builder。

它聚焦于传统协作工具最薄弱、而 Agent 可以显著增强的部分：

1. 从模糊需求中识别协作缺口。
2. 基于真实活动与权限，解释团队中谁可能提供帮助。
3. 让用户自主选择协作者和协作方式。
4. 为人和 Agent 提供稳定、最小且可追踪的上下文。
5. 在整个协作过程中发现阻塞、冲突、缺口和新的机会。

## 核心闭环

```text
用户表达想完成的事情
  → AI 先判断是否能由用户独立完成
  → 提醒缺失的信息、经验、权限或执行能力
  → 用户选择继续独立处理、比较协作者或团队广播
  → 形成由一位拥有者负责的任务
  → 人与 Agent 围绕 Task 状态、文件、活动和决定推进
  → 需要接续时，双方明确交什么、谁接、何时生效
  → 协作者回传结果与证据，由 Owner 验收和整合
  → AI 持续提供可解释洞察和下一步建议
  → 结果、证据和真实责任沉淀为团队上下文
```

## 核心产品对象

### 任务

需要持续跟进并由一个人对结果负责的工作对象。

- 每个正式任务恰好有一位拥有者；尚未确认的 AI 产物只是 Proposal，不算任务。本稿建议首版只允许正式人类成员担任 Owner。
- Task 创建者记录“谁发起并确认创建”的事实，Owner 记录“谁对当前 Task 的结果负责”，两者是独立关系。创建者不因发起自动永久成为 Owner，也不能被 Owner 变更重写。
- 任务可以有父任务和子任务，形成任意深度的任务树。
- 子任务可以有不同拥有者，实现逐层责任划分。
- AI 可以建议拆分，但用户与实际执行者决定是否拆分。
- 正式任务可以不设置计划周期。系统可按明确需求建议开始与结束日期，但成员可以在创建前或详情中清空整个周期，读取时不得自动补回；设置时必须是开始与结束成对的有效范围。它只是可选的完成承诺，不扩展为完整项目排期字段集合。
- 任务名称用于快速识别和导航，应是简洁的动作标题；任务目标用于表达完成边界与预期结果。AI 生成、Mock 和通用兜底都不得直接复制同一句文本填入两个字段。

### 按事务复杂度生长（未来创建候选）

以下条款只约束未来重新确认并接入的创建能力；当前 React 原型不呈现这些表面。

- 小事务直接创建一个单项 Task，不为了形式完整强制拆分。
- 复杂事务可以在创建 Proposal 中同时呈现一个父 Task 与一层可编辑子 Task；父子使用同一种 Task 对象，只以 `parentTaskId` 区分。每个子 Task 都要有独立名称、目标、唯一 Owner、按需选择的参与者和文件引用；不在创建阶段额外录入逐项 Responsibility 或验收标准。
- 只有一个 Task 时，创建 Proposal 直接使用单任务表单；Proposal 已经包含至少一个子 Task 时，才把父 Task 与一层子 Task 纵向平铺为可连续审阅的“任务”列表。创建确认页不显示父 / 子数量统计或追加入口，成员仍可编辑、展开、收起或删除已有子 Task。每个 Task 块只复用“任务信息、上级任务、[文件]”范式，方括号表示文件区仅在有候选或已有选择时出现。父 / 子只用层级标签、顺序编号和 `parentTaskId` 表达层级；每项可独立展开或收起，不使用弹窗、页签或压缩版编辑器。
- 子 Task 选择当前用户时可以直接由本人负责；拟交给同事时，只记录建议人选和待接受状态，在对方接受前仍由父 Task Owner 兜底，不能把“选择了同事”写成责任已经转移。
- Task 成员默认可见自己所在 Task 的协作信息；主 Task 与每个子 Task 分别维护文件候选和实际引用，父子 Task 的成员、候选与引用都不自动继承，引用文件也不因为拆分而扩大可见范围。分析中出现过的来源不等于必须进入创建候选；候选存在也不把文件变为必填。
- 创建入口必须让用户先看懂结构再确认；复杂拆分不自动附带阶段、通知、逐项责任或完整项目排期。
- 创建页右侧摘要只核对主 Task：主任务名称直接作为卡片标题，负责人和该主 Task 的参与者使用共享头像＋姓名组件；周期与子任务数量按存在性展示。新 Task 不选择或展示目录，创建者、文件和上级关系不在摘要重复；子 Task 人员不汇总成主 Task 参与者。

### 任务责任（Responsibility）

Task 内由成员明确接受的一项有界协作预期，用来表达 Reviewer、Advisor、Contributor 或 Coordinator 具体要承担什么。

- Responsibility 不拥有子任务树，也不是共同 Owner；同一 Task 可以有多项不同责任。
- 它适合短评审、咨询或持续但边界清楚的责任。需要独立结果、独立上下文、独立验收或继续拆解时，应创建子 Task。
- 接受邀请后才正式成立；已有 active Responsibility 换人时通过 Handoff 产生 successor，不改写历史持有人。
- Responsibility 不产生文件、批准或发布权限。
- 当前产品的 Task 创建与详情不录入、不展示逐项 Responsibility 分配；该对象只保留在已接受协作与 Handoff 的安全语义中，不能由参与关系或界面缺省值自动推断。

### 文件与文件夹

团队共享信息、证据和产出的稳定载体。

- 当前产品不提供独立团队文件模块；File 通过关联 Task 的文件页发现和使用。
- Task 内可以引用已有 File，也可以产生任务范围内的规范 File；退出独立模块不复制或删除文件真相。
- 文件引用不自动复制原文件，也不扩大权限。
- 版本、来源和可用权限必须清楚。

### 动态

协作过程中的讨论、求助、更新、提醒和系统事件。

- 任务活动围绕明确任务推进。
- 团队动态承载任务之外的求助、机会发现和跨边界协作。
- 动态可以转为 Task、文件引用或决定，不会默认全部沉淀为知识。

### Handoff（方向已确认 D-13；具体形态待确认 Q-11 至 Q-19）

Task 下用于让工作连续的双边接续协议，不是新的项目容器，也不是文件发送记录。

- 可承载上下文交接、已有责任移交、结果交回和整个 Task 的 Owner 转移。
- 新工作先走协作邀请或 Task Proposal；不是所有找人行为都叫 Handoff。
- 发出者说明目标、范围、现状、证据、未知和预期效果；接收者可以复述、澄清、改范围、接受或拒绝。
- 协议激活前，原责任关系不变；接受邀请、阅读文件和加入参与者都不等于责任已转移。
- Handoff 只引用有权限的 Task、FileVersion、Decision、Activity 与 ChangeSet，不复制完整聊天或文件树。

### 成员、Agent 与责任画像

人类成员、受委托 Agent 和受限外部协作者都是可审计的协作主体；责任画像由团队责任说明和平台可见证据共同形成，是可解释、但可能不完整的视图。首版是否只允许正式人类成员成为 Owner，保留在决策台账确认。

- 画像帮助回答“谁可能知道、做过或有权决定”。
- 画像不等于绩效评分。
- AI 推断不产生权限，不自动改变正式岗位。
- 每个 Team 只有一份纯文本团队责任说明，由本人和团队管理员查看、编辑并保留修订人；阅读界面可以按段落同权重呈现以便扫读，但不产生新的责任来源或主次；它不产生权限，也不改变 Task Owner 或 Task Responsibility。
- AI 可以依据平台内可复核、已验收的结果生成待新增或待更新的责任提议，但个人中心不设独立“AI 建议”区、右侧团队面板或建议第二栏。责任页只在标题区右侧提供紧凑 Team Select，复用应用当前 Team 并经过未保存草稿保护；触发器显示 Team Logo、当前团队名与下拉箭头，选项显示同构 Logo、团队名及当前项勾选，长名称视觉省略时可访问名称仍保留全文。下方单列责任清单使用内容区可用宽度。已有责任一行一条，行尾 Pencil 只把该行切换为 Textarea 与保存／取消，一次只编辑一行，人工新增／删除能力继续保留。有更新提议的条目在行尾显示 Sparkles 图标与可见“AI 建议”的推断黄色展开按钮，点击后才就地展示只读替换文本、逐行依据、忽略和“更新”。每条依据显示一个摘要和来源／时间等 meta；只有真实来源目标存在时才显示带箭头的“查看”动作。该入口不表示重新生成或已经更新，正式写入仍需点击“更新”。新增提议作为列表尾部的一条只读候选行，以虚线标记、轻量推断底色和行尾加号与正文区分，用户点击行尾加号即添加可见候选文本；具体依据仍可查看。提议文本不在候选行中编辑，需改写时使用对应责任行的单条编辑。人的按钮动作仍是正式写入前的明确确认；已处理提议与证据继续保留在记录中。AI 不能替人确认，也不能静默改写责任、权限或历史证据。
- 成员确认后仍可直接编辑团队责任说明；更新写入前必须校验基准版本、目标位置和原文快照，冲突时保留提议并提示重新核对，不得退化为追加。
- 当平台缺少邮件、会议、线下工作或外部系统证据时，画像必须显示覆盖范围，不能声称代表团队工作的全部事实。

## 一级产品模块

> 当前覆盖（D-139 / D-141 / D-146 / D-172 / D-177 / D-178）：下列六项保留为早期产品模块草案，不再作为当前可见导航契约。当前产品表面以 Task 为唯一行动模块；“连接 AI”一级页、顶栏入口与全局入口继续隐藏，仅“我的工作”头部保留局部连接按钮。该按钮按 D-177 复用既有四产品 `AiConnectionDialog`，并按 D-178 带入 `personalWorkbenchModel.ownedTasks` 的正式负责任务列表；每项仅含 Task ID、名称和真实状态，空列表以 `meta=0` 表达。

1. **首页 / 我的工作**：今天需要关注、决定、继续和等待的事项。
2. **任务**：不按 Folder 分组的单一 Task List、父子 Task、任务详情和一个不提交的意图输入壳；分类只使用无标签组的扁平标签，当前没有“新建任务”入口。
3. **团队动态**：任务外求助、广播、机会、经验与协作响应。
4. **设置**：头像菜单首项是主题切换，其下才是普通“设置”，最后提供危险动作“退出登录”；不展示个人信息卡，也不单列“我的责任”快捷入口。主题项复用现有状态与本机持久化，按当前主题显示“切换到深色／浅色”，顶栏不再另设主题按钮。点击“设置”打开统一大型 Dialog。左侧按个人设置和团队设置分组：个人设置依次为跨团队稳定的个人信息，以及仍属 Team-bound 数据的我的责任；团队设置为团队信息和成员。团队信息提供标志、名称及带确认的离开 / 删除本机 Team；成员提供邀请链接、邮箱邀请和管理员 / 成员角色管理，并保护最后一名在职管理员；我的责任在标题区右侧提供显示 Team Logo、当前团队名和下拉箭头的紧凑 Team Select，并继续以一份连续文本维护当前团队责任说明。上述团队管理能力是可持久化的本机功能原型，不发送真实邮件、不写生产 ACL，也不改变 Owner、Task Responsibility 或正式权限。
5. **连接 AI**：管理个人 Agent 连接、上下文范围与写入授权。
6. **设置与治理**：组织、权限、标签、审计和推断策略。

团队成员不作为本轮一级模块；找人、任务成员和协作关系仍可进入权限允许的成员信息，但他人资料页与观察责任的团队可见门槛继续服从 Q-07，不能由个人中心实现反推扩大。

全局通知入口（D-84、D-86、D-89、D-146、D-183）是跨模块 utility，不新增一级业务模块，也不要求用户先进入首页、Task 或 File。入口位于轻量顶栏右侧、头像之前；主题切换已收进头像菜单，不再占用通知旁的独立位置。点击通知后从视口右侧展开，轻量顶栏保持可见。列表只按“全部 / 未读 / 已读”筛选，铃铛数字表示未读数量；已读只表示成员看过通知，不等于接受、拒绝或处理完成。协作邀请与责任转交的通知快捷动作只保留接受和拒绝，完整协商回到来源对象。通知只引用原对象并提供最小充分上下文，正式责任、权限、Owner、Decision 与 Handoff 效果仍由对应对象和协议写入。

D-88 进一步规定，来源于 Task 的“AI 建议”在通知中只提供概览与“前往任务查看”。该动作关闭通知、打开来源 Task 并定位“AI 建议”区；具体处理继续在 Task 内完成。通知不得生成“已着手处理”等结果，也不得因打开或跳转而改变内部 Insight disposition 或 Task 数据。

当前已确认的 Task 详情按“概览 → [关联任务] → 文件 → 活动”排列，方括号表示存在直属父子关系时才显示。概览呈现目标、负责人、参与者、状态与按事实触发的 AI 建议，不再录入或展示逐项 Responsibility 分配、验收标准或 Todo。文件页直接展示当前 Task 有权可见的文件层级、正文与引用，不提供按人员切换；该收敛不改变 File / FileVersion、引用、ACL 或来源定位。Task 活动继续统一投影成员发布、AI 建议和 Commit。建议默认（Q-11 / Q-16）：真实 Handoff 不单独成为一级导航；其最终承载位置仍需在实现邀请、接受与 Result Return 前重新确认。

D-102 补充 Task 顶部人员投影：界面统一称“负责人”，负责人和参与者都使用共享头像＋姓名人员单元，负责人可通过共享 PersonPicker 修改。头像右下角以实心对勾 / 空心待勾选分别表达邀请已接受 / 待接受；拒绝者从当前人员列表移除。待接受只表示对方尚未同意，不能被文案或视觉解释为正式 Owner、Responsibility 或权限已经生效。

D-132 进一步明确创建文件按需出现：文件引用始终是 0..n；分析依据、当前 Task 文件候选与用户实际选择分别保存。当前 Task 没有候选且没有选择时，创建表单不渲染“文件”标题、说明、计数、空状态或添加入口；有候选但没有选择时仍显示候选并允许直接创建。父 Task 与每个子 Task 独立判断，正式 Task 仍只保存实际引用。

D-134 建立了 Task 父子关系的统一“关联任务”投影；顶部面包屑只保留当前 Task，不再承载 Folder 或父 Task。该呈现只使用既有 `parentTaskId`，不新增通用依赖关系，也不让父子 Task 继承 Owner、状态、成员、文件或权限；其原定概览位置已由 D-135 替代。

D-135 把“关联任务”移为紧随概览的条件页签：只有当前 Task 至少存在一个直属上级或直属下级时显示，页签数量为两类直属关系总数。概览不重复关系内容；其原定分组式 List 已由 D-137 替代。

D-137 将关联任务页内收敛为一个四列 List：任务名称、类型、状态、负责人。关系方向在每行“类型”列明确显示为“上级任务”或“下级任务”，不再拆分分组；任务名称列不附带目标、截止时间或其他元数据，整行继续进入对应 Task。

连接 AI 的本人可见性与紧凑图标样式由 D-101 在当时阶段确认；当前可见范围已由 D-141／D-146 收敛，并由 D-172 仅为“我的工作”头部增加局部入口。该入口的弹层以 D-177 为准，复用既有四产品 `AiConnectionDialog`；带入范围以 D-178 为准，只取 `personalWorkbenchModel.ownedTasks` 的完整正式负责任务列表，每项仅含 Task ID、名称和真实状态，不带 actions／priorities、讨论、文件或详情。上段同时列出的 D-99 仅对应复杂 Task 创建决定。

活动类型补充（D-78 / D-81 / D-119）：每条 Task 活动只显示动态、AI 建议、状态变更、周期变更、参与者加入、代码提交等具体动作，不增加事件分组或来源分类；其中“动态”专指成员主动发布的一条内容，回复仍单独标为“回复”，不会替代整个“活动”模块名称；“AI 建议”使用图标、文字和推断语义色形成特殊标识。

D-139 进一步收敛当前产品表面：Task 是唯一行动对象；一级团队文件、Todo、Task Folder、标签组、按人查看文件、逐项 Responsibility 分配和验收标准都不再占用入口或 Task 创建 / 详情界面。唯一 Owner、参与者、状态、活动、文件引用、父子 Task、Handoff 和权限边界保持不变。

## 产品原则

### 跟随需求，不强套规划

AI 输出的结构密度由需求决定。没有协作缺口时，不制造人员分工；没有必要拆分时，不生成任务树。

### 默认自己负责，协作由用户主动选择

创建任务时当前用户默认是拥有者。AI 可以指出独立完成的风险，但不能替用户邀请或指派同事。

### 一层任务，一位拥有者

共同参与不等于共同兜底。每个任务只保留一位最终跟进者；不同子任务通过不同拥有者表达责任划分。

### 建议必须能解释，也允许反驳

人员、文件、风险和下一步建议都要显示依据、数据新鲜度、权限限制与不确定性。

### 保护执行者自主权

委派者可以表达目标、约束和验收，不默认替执行者规定全部步骤。被邀请者可以接受、拒绝或协商责任范围。

### 交接必须双边完成（建议默认 Q-13）

系统不把“已发送”当成“已交接”。接收者需理解自己负责什么、不负责什么、第一步是什么；责任变化只在双方接受同一版本且权限、文件版本检查通过后原子生效。

### 权限先于智能

系统只能使用当前主体有权使用的信息。推荐某人不代表可以向其透露当前任务；加入任务也不代表获得所有引用文件权限。

### 动态数据不是监控数据

责任画像和工作量判断用于改善协作，不用于隐性绩效排名。候选比较只展示成员主动发布、可撤回且会过期的粗粒度协作窗口；精确任务数、审核队列和个人历史速度不向推荐发起人展示。禁止从私人沟通、非工作时间行为和敏感个人属性推断能力或态度。

## 当前不做

- 不建立通用 Agent 编排或 Agent 市场。
- 不强制迁移企业现有项目管理系统。
- 不以自定义看板、甘特图和复杂报表为早期重点。
- 不把员工活动量等同于产出或能力。
- 不把人模拟成后台进程，不展示或推断“几个人正在工作”、静默时长和在线投入度。
- 不自动分配成员，不自动扩大权限。
- 不要求本地 Agent 同步完整远程文件树。
- 不为所有任务强制阶段、日期、工时和里程碑。

## 成功标准

### 用户价值

- 用户更早发现自己缺失的知识、经验、权限和信息。
- 找到合适协作者所需的搜索、询问和解释成本下降。
- 被邀请者能够理解为什么找自己，并保有接受和协商空间。
- 交接双方能准确回答“现在谁负责、交了什么、还缺什么、下一位行动者是谁”。

### 团队价值

- 关键任务始终有明确的单一拥有者。
- 专家发现不再只依赖熟人网络和组织头衔。
- 文件、决定和责任能够被后续成员与 Agent 接续。
- 工作出去后能以结果、证据和剩余风险回到父 Task Owner，而不是停在一句“做完了”。
- 团队逐渐形成更准确的“谁知道什么、谁实际负责什么”。

### 治理价值

- 每次 AI 推荐和高风险动作有可查看依据。
- 文件访问与协作者邀请不发生隐式权限扩散。
- 成员可以理解并纠正系统对自己的画像。
