# 全平台 AI 协作洞察

> AI 的价值不只是“生成一份计划”，而是在协作全过程中持续发现人类容易忽略的缺口、联系、冲突和下一步。
> 状态说明：AI 覆盖完整协作过程已确认；首版默认停在 L3、L4 的授权方式是建议默认，见决策台账 Q-08。D-139 已确认当前产品以 Task 为唯一行动对象，不再投影 Todo；Task 创建与详情也不录入或展示逐项 Responsibility 分配和验收标准。

## 一、AI 介入分级（默认写入级别待确认）

| 级别 | 行为 | 默认权限 |
| --- | --- | --- |
| L0 观察 | 基于已授权上下文形成内部判断 | 不改变任何对象 |
| L1 提醒 | 展示缺口、风险、冲突或机会 | 用户忽略即可 |
| L2 建议 | 提供候选人、文件、下一步和比较 | 用户主动采用 |
| L3 起草 | 起草任务、广播、回复、决定摘要 | 用户编辑并确认 |
| L4 受限执行 | 在明确、可撤销且范围受限的授权内更新内部对象 | 记录 ChangeSet；撤销通过补偿记录完成 |
| L5 高风险动作 | 邀请、权限扩大、发布、批准、外部写入 | 必须由有权人明确确认 |

AI 不因建议准确率提高而自动升级权限。

首版默认停在 L3：AI 可以生成 Proposal，但创建正式 Task、改变 Owner、发出邀请或广播、扩大权限、确认 Decision、发布文件及执行外部写入都需要明确确认。L4 不是“AI 随时可写”，只适用于用户预先授权的低风险内部动作；授权必须限定对象、动作、期限并可撤销。不可逆外部动作永远不能用“之后可以撤回”包装。

D-17、D-26 与 D-35 对团队画像中的“观察责任”确认了一项有界 L4：AI 可以基于平台内可复核、已经人工确认的证据自动新增、刷新或过期观察建议，并记录来源、Coverage 和 ChangeSet。它不把其他对象的默认级别从 L3 提升到 L4，也不允许 AI 自行改写团队责任说明、权限、Owner 或 Handoff Effect；个人中心由人通过“采纳 / 忽略”处理建议。该画像能力不恢复 D-139 已移除的 Task 逐项 Responsibility 界面。

## 二、洞察的产品合同

每条洞察至少包含：

```ts
type CollaborationInsight = {
  type: string;
  summary: string;
  whyNow: string;
  evidenceRefs: string[];
  confidence: "low" | "medium" | "high";
  affectedObjects: string[];
  suggestedActions: SuggestedAction[];
  permissionNotes?: string[];
  coverageNotes?: string[];
  handoffRef?: string;
  expiresAt?: string;
};
```

前台必须回答：

- 发生了什么。
- 为什么现在提醒。
- 依据是什么。
- 系统不确定什么。
- 当前证据覆盖什么、缺失什么。
- 不处理会怎样。
- 用户可以做什么。
- 哪些动作仍需要谁确认。

### Task 概览的首版“AI 建议”投影（D-57 / D-119）

Task 概览不展示单独的“AI 判断分数”，也不复制 TaskStatus 字段。首版只把当前已有数据能够支持的建议投影为“类型 / 自然语言说明 / 建议动作”，并显示 AI 来源标识。可触发场景包括：

1. **任务态势**：用 Task 状态、未收口缺口、直属子 Task 和近期 Activity 说明任务正在发生什么。
2. **能力与判断缺口**：当前 Owner 独立完成仍缺少业务判断、专业知识或经验。
3. **证据、权限或独立结果缺口**：完成需要的依据、授权或可单独核对结果尚未形成。
4. **推进节奏**：有明确时间证据表明工作应关注，例如 Task 的承诺日期已过或显式依赖满足后仍没有对应 Activity。没有事件历史时不得笼统声称“推进缓慢”。
5. **前置依赖**：只读取显式依赖对象、输入 / Decision / FileVersion 或 Handoff 的返回事实；不得从静默或 Participant 身份推断等待状态。
6. **协作边界**：成员只是 Participant、Owner 仍唯一，或 Handoff 尚未激活；只能说明当前关系，不能推断或生成逐项责任。
7. **资源冲突**：已公开、可撤回且仍有效的协作窗口与任务周期冲突；不得用精确任务数或在线时长推断负载。
8. **结果证据风险**：缺少支持完成判断的文件、Decision、Activity 或 Result Return 依据。
9. **状态一致性**：例如 Task 已完成但仍存在未完成直属子 Task 或未解决缺口。
10. **结果回传准备**：子 Task 或有界交付已有可核对结果，等待父 Task Owner 整合。

只渲染命中条件的建议，不展示空分类；建议属于 L1 / L2，不自动改变 TaskStatus、Owner、Participant、Handoff、权限或通知。

D-123 进一步要求：当没有任何命中条件的建议时，整个“AI 建议”区不渲染，也不显示空状态占位；Task 概览的常规信息直接成为首块。若建议存在但当前成员已全部“已知晓”，界面只保留紧凑的重新显示入口，以维持 D-116 / D-122 的可恢复性。

### Task 概览“AI 建议”的数据—判断—动作矩阵

下面的“数据”只指当前成员有权查看、能够引用且仍在有效期内的结构化事实。模型生成的摘要、置信度和措辞不能单独成为触发依据；每条建议必须保留实际 `evidenceRefs`、Coverage 与新鲜度。首版动作的默认语义是“定位事实、展开处理面或起草跟进”，不是直接写入正式对象。

| 建议类型 | 读取的数据与必要字段 | 触发条件 | 前台应说明什么 | 主动作与落点 | 动作发生的实际变化 | 禁止自动发生 |
| --- | --- | --- | --- | --- | --- | --- |
| 任务态势 | Task `summary`、`status`；未解决协作缺口；未完成直属子 Task；近期 Activity | 进入概览时始终生成一条，但只汇总有权可见的数据 | 当前最需要关注的事实、未完成分支与未收口缺口，不重复展示状态字段本身 | “查看任务活动”或“查看关联任务” | 只定位 Activity、关联 Task 或文件，不写数据 | 自动改 TaskStatus、关闭子 Task、宣称任务已经完成 |
| 能力与判断缺口 | `CollaborationGap.kind=judgment`、`detail`、`evidence`、`state`、`recommendedAction`；Owner 与候选人的可复核经验 | 缺口未解决，且证据能说明当前 Owner 仍缺少哪项具体判断 | 缺的是什么判断、为什么需要、依据来自哪里；不能笼统评价人的能力 | “处理缺口”，展开既有缺口处理面 | 用户可选择自己处理、查看候选或准备邀请草稿；只有明确确认才继续 | 自动邀请、自动换 Owner、把“做过类似工作”写成 Task 逐项责任 |
| 证据缺口 | `CollaborationGap.kind=evidence`；Task 文件、FileVersion、引用、更新时间、可见权限 | 必需依据缺失、过期、版本冲突或不可访问 | 缺哪份依据、影响哪个结论、当前覆盖和未知是什么 | “处理缺口”并定位相关文件 / 缺口面 | 用户补充或固定文件版本、请求资料、记录待验证项 | 绕过权限读取文件、把 AI 产物直接当正式证据、静默替换版本 |
| 权限缺口 | `CollaborationGap.kind=permission`；PolicyDecision、AuthorizationGrant、所需动作、授权主体和有效期 | 下一步需要明确授权，而当前执行者没有相应权限 | 缺少哪项授权、谁有权确认、未授权时哪些动作不能执行 | “处理缺口”，展开授权相关的后续选择 | 只能准备请求、定位有权主体或缩小动作范围 | 自动授权、扩大文件 / 任务权限、用专业能力替代批准权 |
| 独立结果缺口 | `CollaborationGap.kind=independent-result`；独立结果名称、推进边界、结果证据、结果返回要求、`subtaskAssessment` | 结果可独立命名、相对独立推进并可回传 | 为什么留在父 Task 会造成 Owner 或接续歧义 | “处理缺口”；条件成立时显示“建议转子 Task” | 用户确认名称、父 Task 与初始 Owner 后才创建子 Task | 自动拆 Task、自动把候选设为子 Task Owner、把咨询或短评审拆成任务 |
| 推进节奏 | Task / 子 Task `status`、`due`；已明确的承诺时间 / 检查点；Activity 或 ChangeSet 的业务事件时间 | Task 超过明确承诺日期，或显式依赖满足后仍没有对应业务事件；没有事件历史时不生成“推进缓慢” | 哪项承诺在什么时间点需要关注，只描述事件，不评价投入程度 | “查看任务活动”或“查看关联任务” | 定位原 Task、Activity 或依赖；用户自行调整范围、日期或状态 | 根据静默时长催人、根据在线时长 / 任务数评价速度、自动改截止时间 |
| 前置依赖 | 显式依赖对象、所需输入 / Decision / FileVersion / Handoff、预期回传时间；受影响 Task | 至少一项显式依赖尚未满足并能够定位受影响 Task | 正在等什么、影响哪些 Task、已知回传时间与未知项 | “查看依赖来源” | 定位原依赖对象或关联 Task，由用户补充依赖或发起协调 | 从自然语言或静默推断依赖、自动催促、自动通知未确认对象、把个人描述成阻塞点 |
| 协作边界 | Task Owner、Participant、邀请与 Handoff 状态 | Participant 关系可能被误解为 Owner 或正式接续，或 Handoff 尚未激活 | 谁只是参与、当前唯一 Owner 是谁、哪些变化仍未生效 | “核对参与者”或“查看 Handoff” | 定位参与者或 Handoff 原对象；用户可保留或调整参与关系 | 从 Participant 身份推断责任、在 Task 详情创建逐项 Responsibility、自动移除成员 |
| 资源冲突 | Task 周期；成员本人公开、可撤回且未过期的粗粒度协作窗口；已接受的承诺范围 | 公开窗口与 Task 周期或已接受承诺发生可解释冲突 | 哪个时间范围冲突、数据由谁公开、何时过期；未知就显示未知 | “调整范围 / 时间”或“查看协作选择” | 进入相应编辑或协作确认面，由人缩小范围、改期或换一种协作方式 | 展示精确活跃任务数、推断空闲率、自动换人、把冲突变成绩效判断 |
| 结果证据风险 | Task 文件与 FileVersion；Decision、Activity、ChangeSet；Result Return 证据 | 没有支持完成判断的文件 / 结果，或证据版本不明确 | 缺少哪类结果依据、最终判断仍不能确认什么 | “查看结果依据” | 打开文件、Activity 或 Result Return；用户补充引用或请求结果回传 | 自动确认完成、自动发布文件、自动把 Task 标记完成 |
| 状态一致性 | Task `status`；未解决缺口；子 Task / Result Return / Handoff 状态；结果证据 | 例如 Task 已完成但仍有未完成子 Task，或状态与已有证据明显矛盾 | 哪些正式字段互相冲突，不替用户决定哪一个才正确 | “核对关联工作” | 打开关联 Task、Activity 或 Handoff；用户自行修正正式对象 | 静默修正任一字段、删除冲突记录、把一致性检查当成完成确认 |
| 结果回传准备 | 子 Task / 有界交付状态；Result Return 的产出、证据、决定、剩余风险与父 Task 引用 | 子结果已经可核对，但父 Task Owner 尚未接收或整合 | 哪项结果已准备、还缺什么、由谁接收 | “查看待整合结果” | 打开 Result Return / 子 Task 上下文，供父 Owner 接收、补充或退回 | 自动判定接收、自动关闭父 Task、自动改变 Owner 或 Handoff 状态 |

数据接入状态必须与产品能力分开表达：当前静态原型已经能基于 Task 基础字段、协作缺口、Participant、关联 Task、文件数量和 Activity 生成部分建议；真实 PolicyDecision / AuthorizationGrant、可撤回协作窗口、FileVersion 冲突与 Result Return 尚未形成完整生产数据链。在这些来源接入并验证权限前，相应行只能作为产品合同与测试目标，不能在界面中伪造已发生的事实。

AI 只能说明当前可见依据是否支持完成判断，不能代 Task Owner 确认完成。是否改变 TaskStatus 仍由当前 Task Owner 通过独立动作确认；该判断不恢复 Task 详情中的验收标准面板。

### “AI 建议”动作的统一语义

| 动作类型 | 用户看到的例子 | 默认级别 | 允许的副作用 | 确认边界 |
| --- | --- | --- | --- | --- |
| 定位事实 | 查看活动、查看前置项、查看结果依据 | L1 | 切换 Task 页签、设置 List 筛选、滚动到有权可见的来源 | 不需要写入确认，因为不改变正式对象 |
| 展开处理面 | 处理缺口、核对参与者 | L2 | 展开候选、文件、参与者或 Handoff 上下文 | 展开本身不写入；选择处理方式后再按具体对象确认 |
| 记录跟进 | 记录跟进 | L3 起草 | 由用户点击后，在 Activity 中追加一条包含建议标题与建议动作的跟进记录 | 点击即确认只记录 Activity；不代表建议已采纳或工作已完成 |
| 准备变更 | 调整范围 / 时间、补充结果依据、建议转子 Task | L3 | 预填编辑面、创建 Proposal 或打开确认 Dialog | 保存、创建、邀请、发布、Owner / 权限变化必须再次明确确认 |
| 高风险执行 | 授权、邀请、发布、批准、外部写入 | L5 | 仅在有权人确认后调用对应正式协议 | 建议卡不得直接执行，也不得把“记录跟进”包装成确认 |

同一条建议可以提供一个主动作和“记录跟进”，但两者语义必须分开：主动作负责定位或处理；“记录跟进”只留下可接续记录。忽略建议不得改变任何对象，也不得作为评价成员的负面信号。

### Task“AI 建议”类型与产品能力动作（D-110 / D-119）

Task 概览使用一个连续工作简报。任务态势是简报摘要，不作为需要“处理”的建议项。每项建议固定呈现类型与状态、结论、事实、影响、能力边界和动作；动作完成后从正式对象重算，不维护平行的建议完成状态。D-110 在 Task 概览范围内替代上一段固定提供“记录跟进”的要求。

| 建议类型 | 必须展示 | 与现有功能对应的动作 | 处理边界 |
| --- | --- | --- | --- |
| 协作边界 | 相关成员、当前参与关系、唯一 Owner、影响 | 核对并保存参与者；必要时查看 Handoff | Participant 不是 Owner；当前不能在此创建逐项 Responsibility 或改变 Handoff Effect |
| 判断 / 能力缺口 | 缺口、证据、影响、当前处理人 | 打开既有协作缺口处理 | 不自动指派，不改变 Owner |
| 证据缺口 | 缺失依据、来源、影响 | 查看任务信息；在已有协作缺口流程处理 | 不自动创建文件或催收请求 |
| 权限缺口 | 受限对象、现有依据、阻塞影响 | 信息提示；必要时只读查看依据 | 没有正式权限申请能力时不得显示伪申请按钮 |
| 独立结果缺口 | 预期结果、结果证据、与父 Task 的关系 | 复用既有创建子 Task 流程 | 仅满足独立结果条件时可创建，不冒充 Result Return 已完成 |
| 结果证据风险 | 缺失文件或结果引用、当前数量、影响 | 查看任务文件、Activity 或 Result Return | 不创建验收标准面板，不自动判定任务完成 |
| 状态一致性 | Task 状态、关联 Task / Handoff 状态、冲突 | 查看关联工作；使用现有 Task 状态控件 | 导航不代表问题已解决 |

Activity 仍可记录真实协作事件，但单独新增一条 Activity 不能证明建议来源事实已经改变。

多条 Mock 建议遵循 D-113：协作缺口按任务目标、标签、文件和状态组合生成，协作边界、结果证据与一致性继续从对象事实计算；不得为了“看起来丰富”给所有任务复制同一组风险。List 默认完整展示决定处理所需的信息，但使用连续短行压缩密度，单任务长期超过 6 条时再重新评估排序、分组或筛选，而不是先用折叠隐藏。

D-114 与 D-122 将每行收敛为左右两区。左侧信息只保留类型与状态、结论、关注原因和一条可复核依据；右侧用分隔线集中放置现有功能动作和一句必要边界，不逐行重复“可用操作”。影响不再作为独立字段重复展示，而是写入“关注原因”；处理边界不再占用信息区。没有产品内动作的权限缺口只显示“提示”和“已知晓”，不重复说明当前无申请能力。该收敛不允许删除证据或把无能力事项变成动作。

D-116 与 D-122 补全信息提示型建议的退出机制：当产品没有对应处理能力时，左侧状态显示“提示”，右侧提供“已知晓”。“已知晓”按稳定成员标识保存，是当前成员在当前 Task 下对当前证据版本的个人展示偏好，不得使用可编辑显示名称作作用域；它不改变协作缺口、权限或其他正式对象，不写 Activity，也不影响其他成员。界面需提供短时撤销和可发现的重新显示入口。建议的结论、状态、关注原因、依据、能力边界或可用动作发生变化时必须作为新版本重新出现；任何已有正式动作的建议始终显示，不得以旧隐藏记录替代对象闭环。当前 Mock 可用本机持久化模拟个人偏好；若浏览器拒绝写入或移除偏好，当前会话仍可更新投影，但反馈必须说明刷新后可能恢复原状态，不能把持久化失败报告成成功。该 Mock 不能据此宣称已经具备生产级跨设备同步或 Insight disposition Schema。

D-124 规定“已知晓”使用共享实心 Button，作为右侧唯一动作时仍有明确的可点击外观；该视觉权重不改变上一段的个人展示语义，也不表示用户接受 AI 结论或来源事实已经解决。

信息承载遵循 D-59：查看活动、查看前置项和查看结果依据等定位动作直接切换到对应页签；“核对参与者”“处理缺口”等同时需要背景、人员、依据、资源和多个后续动作的处理面使用 Dialog。打开 Dialog 只是查看和准备，不等于确认任何正式变更。

### “需要关注的信息”与“AI 建议”的边界

Task 文件与 Activity 中的“需要关注的信息”不是新的“AI 建议”类型，也不是 AI 生成的摘要。它是可复核的上下文投影：从 Task 已有的直接关系出发，引用当前成员有权查看的 File、Activity、Commit、Decision 或 Result Return。

| 投影位置 | 关系来源 | 展示内容 | 点击动作 | 空状态与边界 |
| --- | --- | --- | --- | --- |
| Task 文件 | Task 显式引用的 File / FileVersion 及其用途 | 类型、原对象标题、格式、版本与更新时间 | 切换到文件页签并定位原对象 | 没有显式关系时显示任务文件空状态；不得用语义相似度偷偷补齐 |
| Activity | Task 内显式引用的 File、Commit、Decision、Result Return 等已有对象 | 类型、原对象标题或摘要、作者与更新时间 | 切换到活动页签并定位原 Activity 或引用对象 | 没有显式关系时不生成个人化关注列表；不得由 Participant 身份推断个人应关注内容 |

该投影只帮助成员快速找到执行上下文，不证明成员已阅读、接受、理解或完成任何工作。Task 文件引用不自动等同于某位 Participant 的个人义务；权限过滤发生在聚合之前，原对象不可见时不显示其标题或摘要，也不能用 AI 转述绕过权限。

## 三、按协作生命周期整理洞察点

### 1. 表达需求

- 目标过于抽象，无法判断完成状态。
- 输入中混合了多个应独立负责的结果。
- 用户实际上只需要一条信息，不需要创建任务。
- 与已有任务高度相似，可能重复工作。
- 输入引用了用户尚未授权 Agent 读取的内容。

AI 动作：复述目标、提出一个高信息增益问题、推荐已有任务或直接信息答案。

### 2. 创建与规划

- 当前用户独立完成是否缺少信息、经验、权限或执行范围。
- 哪些内容留在当前 Task 的 Activity / 文件上下文，哪些结果需要独立子 Task 与 Owner。
- 计划是否过度拆解，侵占执行者自主权。
- 哪些文件是必要输入，哪些只是可能相关。
- 当前任务是否应先探索而不是立即执行。

AI 动作：保持最小草稿、给出协作缺口、按需展开结构。

协作缺口进入正式 Task 后仍保留其证据、影响和处理状态。AI 必须先判断缺口类型，再决定是否建议人员或子 Task：

- 单一判断、咨询、短评审、权限确认和资料补充留在当前 Task，不制造子 Task。
- 只有可独立命名的结果、相对独立推进和结果返回同时成立时，才输出“建议转子 Task”。
- 建议必须列出触发依据和不产生的副作用；AI 不自动创建子 Task、不自动把候选写成 Owner。
- 用户可以暂不分配任何缺口；未分配不是失败，也不阻止主 Task 推进。

### 3. 找人协作

- 谁具有正式授权，谁只有经验。
- 谁做过相似工作，证据是否足够新。
- 候选人本人公开的粗粒度协作窗口是否适合短评审或共同执行；未公开时只能显示“未知”，不能从任务数或活动节奏推断。
- 是否总在找同一位专家。
- 是否需要独立视角而不是最熟悉现状的人。
- 不知道找谁时，广播到哪个范围最合适。

AI 动作：硬过滤权限，提供多维候选比较，起草邀请或广播。

### 4. 信息准备

- 哪些信息已经具备，哪些仍缺失。
- 文件是否过期、互相冲突或引用了不同版本。
- 当前任务成员是否真正拥有文件访问权。
- 是否存在可复用的 Task 文件、历史决定或类似任务。
- 是否在重复上传同一文件。

AI 动作：形成 File List，解释缺口，申请而非绕过权限。

### 5. 执行协作

- 某个 Task 或直属子 Task 错过双方明确约定的检查点，或其显式依赖条件已经满足但仍没有对应业务事件；不能仅以无事件时长判断。
- 多个后续事项依赖同一权限、文件、决定或稀缺角色；先描述结构性依赖，不默认把个人标成“阻塞点”。
- 成员讨论出现相互矛盾的假设。
- 已有人做了相同工作，存在重复劳动。
- 目标、范围或约束在动态中发生漂移。
- 执行者提出的方案与原计划不同，但可能更合理。

AI 动作：聚合证据、指出影响、建议澄清或调整，不自动责备成员。

### 6. 决策与审批

- 讨论已经形成候选结论，但尚未明确记录。
- 当前确认者没有相应授权。
- 结论缺少关键证据或仍存在反例。
- 新决定与历史决定冲突。
- 决定影响其他任务或固定版本文件。

AI 动作：起草 Decision，标记冲突与权限，通知受影响 Owner。

### 7. 文件协作

- Task 引用的文件发布了新版本，但当前 Task 仍固定在旧版。
- Agent 产物尚未经过人类审核就被当成正式依据。
- 文件中的标注已被新版本移动或失效。
- 同一结论散落在多个文件，存在真相分裂。
- 文件权限比任务权限更窄。

AI 动作：提示差异、建议固定或升级版本、请求维护者确认。

### 8. 推进与阻塞

- 当前任务达到了进入下一状态的证据条件。
- 状态显示“进行中”，实际等待外部决定。
- 父任务的关键子任务已改变范围或 Owner。
- 当前 Task 中浮现出一个需要独立 Owner、独立推进和结果回传的结果。
- 有动作被阻塞，但等待的对象、条件或治理路径不明确；具名下一响应者只在直接协作者需要协调时显示。

AI 动作：建议状态变更、创建关联子 Task、澄清协作边界或求助；由人确认高影响变化。

### 9. 交接

- 用户真正需要的是求助、新工作委托、知识交接、责任移交、Owner 转移，还是结果交回。
- 新成员缺少哪几份必要文件和关键决定。
- 当前上下文中哪些是事实、推断、过期结论和未决问题。
- 双方是否接受同一 Handoff Revision；source、recipient 与引用证据之间是否仍有未解决分歧。
- 接收者是否缺少下一步所需权限，关键 FileVersion 是否在等待期间漂移。
- 当前是否正处关键操作，不适合立即切换责任；是否需要重叠支持。
- 是否存在汇报 / 考核关系，需要提供重新排优先级、第三方协调或缩小范围，而不是重复催促。
- 结果交回时是否包含产出、证据、决定、剩余风险和下一项依赖。
- 本地 Agent 产出是否可安全带入团队。

AI 动作：区分协作类型，生成最小 Handoff 包和接收者视角预览；把 source、recipient、共同 Revision 与证据相互比较，检查权限与版本，起草 Result Return。AI 只能 Facilitator，不能替任何成员接受、拒绝或转移 Owner。完整协议见 [11-human-handoff.md](./11-human-handoff.md)。

### 10. 完成与沉淀

- 完成判断是否有文件、Activity、Decision 或 Result Return 证据，不只是状态被切换。
- 哪些未完成结果应成为后续 Task。
- 哪些产出适合保留为 Task 文件或引用。
- 唯一 Owner、Participant 与 Handoff 关系在推进中有何变化。
- 哪些洞察可更新成员责任画像。

AI 动作：起草完成摘要、后续任务和 Task 文件整理建议；对满足 D-17 / D-26 / D-35 门槛的团队画像观察责任可自动更新候选建议，并立即向本人显示准备写入的文本与证据。人只选择“采纳 / 忽略”：采纳原子地写入团队责任正文并记录 accepted，忽略记录 hidden；AI 无权代替人确认，权限、Task Owner 与 Handoff Effect 仍由有权人确认。

### 11. 跨任务与组织洞察

- 多个任务依赖同一成员、文件、外部团队或决定。
- 同一类问题反复发生，应该沉淀规则或模板。
- 某正式职责与实际承担长期偏离。
- 某类权限或经验只集中在极少数成员，形成结构性单点风险。
- 团队有未被利用的经验或协作者。
- 不同团队正在独立探索相同问题。

AI 动作：在权限安全的聚合层面提出组织洞察，不公开敏感任务细节。

## 四、洞察优先级

建议使用四个维度，不以模型置信度单独决定：

1. 影响：不处理会造成多大损失。
2. 紧迫：最晚什么时候需要响应。
3. 可行动：用户是否有明确可执行动作。
4. 打扰成本：现在提醒是否值得中断用户。

只有“高影响 + 高紧迫 + 可行动”的建议可以中断式提醒。其余进入任务摘要、每日 Brief 或相关对象侧栏。

D-84、D-86 进一步限定全局通知：只有影响对象、为何现在提醒和可执行动作都明确的建议才进入全局通知；普通总结与低紧迫建议留在原对象摘要。通知列表只按“全部 / 未读 / 已读”筛选，用户查看建议只会改变已读状态，不会使其完成；处理、稍后、暂不处理、事实不准确、依据过期或无权限仍是独立 disposition。通知动作继续服从本文件的 L1–L5 边界，不能借全局入口直接改变 Owner、Responsibility、权限或状态。

D-88 与 D-119 收窄 Task“AI 建议”在全局通知中的动作：通知只展示最小概览并跳转来源 Task 的“AI 建议”区，不在通知内改变任何 disposition。处理、事实反馈与证据补充只能在 Task 的既有建议流程中发生；跳转本身不是处理结果。前台改名不改变内部 Insight 类型或其处理边界。

## 五、洞察反馈

用户可以选择：

- 有帮助并采用。
- 事实不准确。
- 依据已经过期。
- 我知道但暂不处理。
- 不要再提示此类情况。
- 缺少权限，无法行动。

反馈用于调整提醒策略，而不是给用户或成员打分。

## 六、AI 不应该做的洞察

- 从措辞推断成员情绪、人格、忠诚度或离职风险。
- 根据在线时长判断努力程度。
- 把任务数量直接等同于负载或绩效。
- 使用成员不可见的私人消息解释推荐。
- 公开推断个人关系好坏。
- 在没有业务授权时自动改变 Owner、扩大权限或发布结果。
- 根据“已读”、静默时长或回复快慢判断 Handoff 已完成或成员是否投入。
- 生成个人交接质量分、接受率和响应速度排行。
- 根据没有新事件自动催促个人，或把结构性资源不足表述成某个人的长期“瓶颈”。
- 向发出者或管理者披露私密拒绝原因、响应耗时和个人历史模式。
- 向推荐发起人展示候选人的精确活跃任务数、审核队列、个人历史交付时长，或把这些信号折叠成隐含效率 / 空闲评分。
- 在 `declined` 保护期内通过换入口、改文案、人工代发或 Agent 代发重复请求同一 scope。
- 为了显得主动而持续制造低价值提醒。

## 七、建议实施顺序

### 第一组：基于当前对象即可验证

- 信息缺口。
- 文件版本与权限缺口。
- 单点阻塞。
- 决定未记录。
- 已有相似任务。
- 从当前 Task 的 Activity / 缺口中建议创建独立子 Task。
- Handoff 权限 / 版本预检、最小上下文包和接收者视角预览。

以上洞察也必须建立在统一 Principal、PolicyDecision 与 append-only ChangeSet 之后；当前静态 Mock 只能演示话术，不能证明安全执行。

### 第二组：需要统一事件与责任证据

- 动态责任画像更新。
- 专业知识或正式授权集中在单一角色的结构性风险；成员忙闲只使用本人公开窗口，不以任务数推断个人负载。
- 实际责任漂移。
- 交付周期估计。
- 跨任务依赖。
- Handoff Revision、Consent、激活与 Result Return 的事件洞察。

### 第三组：需要真实多人数据后谨慎验证

- 团队协作模式建议。
- 跨团队机会发现。
- 组织责任缺口。
- 长期工作设计与专家梯队建议。
