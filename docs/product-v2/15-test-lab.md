# TaskDoor 测试工作台

## 启动与入口

在项目目录运行 `npm run dev -- --host 127.0.0.1`，打开 <http://127.0.0.1:5173/test-lab.html>（`/test-lab` 会跳转）。与原 TaskDoor 页面并存，不使用它的 LocalStorage 或业务写入接口。

本版是本机、单管理者测试工具，不是生产登录、权限服务或对外部署平台。团队围绕行业交付场景构建，人员视角用于测试任务与资料可见范围，不评价个人能力或效率。

## 使用顺序

1. **团队沙箱**：新增或复制团队，编辑成员、责任、主子任务、五种状态、前置依赖、标签与证据正文。管理视角下，每位成员旁提供“编辑责任”，可单独修改责任范围，保存后用于后续测试，历史报告不变。数据经关联校验后保存；归档可恢复。切换人员会从服务端读取过滤后的任务和证据（模拟视角及历史快照保持只读）。
2. **用例库**：选择团队与执行成员，配置一个或多个 Skill 步骤、目标任务、输入、自动断言和人工核对项。可搜索、分类、复制、归档，以及导入／导出 JSON。
3. **运行**：确认后调用真实 API。每批最多 5 例、20 个步骤，串行执行；不自动重试或用 Mock 替换失败。停止排队用例不会发请求；活动取消不保证上游停止计费。
4. **运行报告**：查看原始输入／输出、结构检查、自动断言、人工结论、耗时、Token、版本和前后沙箱。重跑使用当前已保存用例，产生新报告，不覆盖历史。

多轮步骤可携带前轮实际输出。高级事件支持 `task_status`、`responsibility`、`evidence`，事件在每一步调用前应用，只改变本次运行沙箱。模型返回的任务或责任建议不会自动写回团队，也不等于正式创建、接受或更新成功。

事件示例（使用当前团队的真实沙箱 ID）：

```json
[
  { "type": "task_status", "taskId": "script", "status": "已阻塞" },
  { "type": "responsibility", "memberId": "lin", "responsibilities": ["脚本策划与交付；直播仅临时支援"] }
]
```

## API 与存储

沿用项目 `.env.local` 的 `PPIO_API_KEY` 和 `PPIO_MODEL`。默认模型为 `pa/gpt-5.5-pro`，默认接口为 `https://api.ppinfra.com/openai/v1/responses`。可用 `PPIO_BASE_URL` 配置其他既有 PPIO API 根地址；必须为不带凭据或查询参数的 HTTPS 地址。

可选服务端参数：`TEST_LAB_MAX_OUTPUT_TOKENS`（默认 8000，最大 32000），`TEST_LAB_TIMEOUT_MS`（默认 180000，最大 600000）。环境变更后重启服务；页面只展示脱敏配置，不接收或回传 Key。Key 仅用于模型服务的授权头。

数据保存在 `data/test-lab/state.json`，已排除 Git。原子文件替换，保存使用修订号防覆盖；任务、成员、证据和用例改动由服务端增加版本。冲突返回 409，编辑器保留草稿，可导出后重新合并。不要用多份服务进程同时写同一个数据目录。

服务只接受本机连接，校验 Host、Origin 和写入 CSRF；没有 CORS 放开。运行报告含完整测试输入和模型输出，应按测试资料敏感度保管。模型请求不携带预期答案、断言、其他团队数据或当前视角不可见的任务／证据。

## 内置资料及验证边界

- 新规则核心库：7 个用例覆盖 6 类 Skill，包括多轮责任纠正。
- “导入内置库”：迁移旧库 60 个单轮、4 个多轮资料，全部默认停用待复核。旧期望单独保留，绝不发给模型。
- 历史转换只提取兼容任务字段、成员责任及团队成员讨论。原始来源、文件、历史、固定时钟、约束、确认字段、ACL 情节留在只读原始输入。未知状态任务不转换；异常任务图不当作合法运行图，并保留原始资料说明。补齐当前沙箱上下文和断言后再启用，不声称等价回归。
- 当前不模拟旧版草稿提交、业务幂等、权限撤回、责任写回或生产 MCP 工具。真实 API 指模型 API，不表示接通生产任务服务。
- 自动检查包括协议、身份／版本绑定、引用、部分数值不变量及用户配置的断言；不证明业务语义正确。缺字段的比较断言标记“未判定”，不当作通过。人工结论单独保存，不洗掉自动失败。
- 服务重启时，未结束的记录标记“已中断”，不恢复付费队列；原团队保持不变。

## 定向验证

只检查测试工作台模块：

```sh
node --import tsx --test server/testLabStore.test.ts server/testLabRunner.test.ts server/testLabHttp.test.ts server/testLabValidation.test.ts server/testLabUi.test.ts
npm run build
```

单元测试的网络 transport 为可控测试替身，不能当作真实 API 成功依据。真实调用记录需单独在运行报告中核对；本版不会自动运行全量用例或生成全库准确率。

### 场景验收与自动化流程

180 个行业场景已补充验证目标、初始条件及逐步目标结果；十个行业各提供四条流程。流程先预检资料与版本，再沿用现有队列串行执行，最后汇总自动断言、结构检查和人工核对结果。CLI 支持仅预检、显式模型运行、读取已有批次以及 JSON/JUnit 导出。完整场景、操作步骤与判定边界见 [场景验收与自动化流程](16-test-workflows.md)。
