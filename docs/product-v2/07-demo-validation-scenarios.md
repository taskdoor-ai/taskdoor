# 跨行业 Demo 验证场景

> 目标：用真实团队协作压力验证同一套架构，而不是为每个行业制作一套孤立演示。场景中的人、任务、文件、活动、团队画像证据和权限状态都必须相互关联。
> D-140 当前投影：Task 是唯一行动对象，React 原型不再提供 Task 创建流程；列表输入壳不提交、不生成 Proposal 或正式 Task。下文的创建夹具与创建序列退出当前验收并保留为历史场景素材；既有 Task 的 Owner、Participant、Activity、Task File、父子关系、Handoff 与 ACL 继续验证。

## 已退出当前验收的任务创建夹具

这些夹具记录 D-140 之前的创建演示，不再对应当前代码或测试入口；`src/data/taskCreationScenarios.ts` 已随 React 创建流程删除。若未来重新接入创建能力，应先重新确认合同，再决定是否复用这些场景素材。

| 示例 | 快速测试标记 | 分析来源 | 创建文件候选 | 结构 / 人员 | 关键约束 |
| --- | --- | ---: | ---: | --- | --- |
| 日常安排 | 单项任务 · 自己处理 | 1 | 0 | 一个 Task，Owner 直接处理 | 分析有连续上下文，但创建不展示文件，也不强造协作者 |
| 会员规则 | 单项任务 · 只咨询 | 3 | 3 | 一个 Task，Owner + Participant 苏禾 | 不改变 Owner，财务判断有依据 |
| 发票方案 | 单项任务 · 短评审 | 3 | 3 | 一个 Task，Owner + 苏禾评审 | 限定材料，保留税务接口契约 |
| 门店验证 | 单项任务 · 有界交付 | 3 | 3 | 一个 Task，Owner + Participant 林洁 | 结果返回 Owner 核对与整合 |
| POS 故障 | 复杂拆分 · 3 个子任务 | 3 | 父 3；子 3 / 2 / 2 | 一个父 Task + 3 个子 Task | 修复实现、离线回归与现场灰度分别形成独立结果；规则判断与最终整合留在父 Task |

POS 复杂示例的三个子 Task 固定覆盖：完成修复实现与自测、完成离线重放回归验证、完成门店灰度验证。三项分别交付代码与自测记录、回归证据、门店级结果，均有不同目标、唯一 Owner、资料子集、Participant 和至少一项真实协作缺口。退款与撤单规则由父 Task Owner 判断，最终发布结论也由父 Task Owner 整合；限定技术说明和质量复核使用有界协作，不再拆成重复子 Task。拟由他人拥有的子 Task 在邀请接受前仍由创建者兜底，不伪造 Owner 转移。

数据约束：来源 ID 唯一；类型必须诚实保留为 `document / data / task / change`；分析来源、Task 级文件候选和实际引用分别维护。没有候选且没有选择时文件区为 0；有候选时允许 0 选择创建。每个 Task 只维护目标、唯一 Owner、Participant、按需文件候选 / 引用和父子关系；父 Task 与子 Task 的文件候选和选择状态分别维护，不能因为存在任务树就清空父 Task，也不能把同一组来源固定传给全部子 Task。创建入口不出现逐项 Responsibility 或验收标准；候选人未接受前不改变 Owner，也不自动获得 Participant、权限或通知。
> 阅读说明：下文完整任务树通常仍是“用户选择协作、候选人接受后”的目标状态。创建入口默认呈现由当前用户拥有的最小 Proposal；只有明确满足独立结果、独立推进和结果回传边界的复杂测试夹具，才在首次确认前呈现一层可编辑子 Task 草稿。它不代表 AI 已经替同事接受 Owner 或 Handoff。

## 一、统一验证基线

所有行业场景都必须验证：

- 新任务默认由创建者作为唯一 Owner。
- AI 先理解需求和缺口，不一次生成完整任务树。
- 用户可以不邀请任何人继续推进。
- 一个任务只有一个 Owner；不同层级任务可以有不同 Owner。
- Task 是唯一行动对象；当前 Demo 不创建、不展示也不操作 Todo。
- Task 列表不按 Folder 分组，只使用无标签组的扁平标签。
- 没有独立团队文件模块；文件从所属 Task 的文件页查看，File / FileVersion、引用和 ACL 真相不复制。
- 团队动态支持任务外求助、广播、表达可帮助、引荐和贡献信息；响应本身不等于认领责任。
- 推荐分别展示经验、上下文、权限、本人公开的粗粒度协作窗口和协作成本。
- AI 不自动邀请、授权、广播敏感信息或完成高风险决定。
- AI 默认只生成 Proposal；正式创建、Owner 转移和外部动作都需要明确确认。
- 邀请、Handoff 与关联工作状态分开；每队至少验证一次“工作经邀请或 Handoff 出去，并以 Result Return 或反向 Transfer 回来”的闭环。
- 协作区优先显示工作关系和对象依赖；具名下一响应者 / 最新证据仅向直接协作者按需显示，不展示“几个人在线 / 正在工作”。
- 同一文件分别验证 hidden、metadata-only、content-readable，以及 Agent 委托撤销。

### 创建过程

输入：“帮我规划 9 月无糖气泡茶的上市传播，我先做一版，周五拿给管理层看。”

AI 先问：

> 目标人群和“0 糖”宣传口径已经确认了吗？这决定现在先做传播框架，还是先补洞察与合规依据。

回答后再给出：程夏适合前期共创、罗曼适合短时媒介评审、唐梨适合主张成形后审核，也允许沈言先独立完成第一版。

### 端到端渐进状态序列

1. **输入**：沈言表达需求；系统只读取他已经授权的上市背景和概念测试摘要。
2. **一个追问**：AI 询问目标人群与“0 糖”口径；此时不出现任务树和人员分工。
3. **最小 Proposal**：生成“形成无糖气泡茶上市传播第一版”，建议 Owner=沈言，只有目标、已有信息、缺失信息和一个“创建任务”按钮。
4. **缺口提示**：AI 显示两个重要缺口——目标人群证据需要洞察判断，正式对外主张最终需要法务确认；二者都描述为任务缺口，不评价沈言能力。
5. **用户主动比较**：沈言点击“看看协作者”。候选卡分别显示程夏的相似研究证据、乔木的创意经验与本人公开的“只做节点评审”、唐梨的正式审核权；没有综合排名，也没有精确任务数或个人历史速度。
6. **先创建、后邀请**：沈言确认创建根 Task，自己保持唯一 Owner；随后选择邀请程夏做 45 分钟共创，并预约唐梨在主张成形后审核。系统只发送用户确认过的最小上下文。
7. **协商而非指派**：程夏接受共创，并主动提出承接“明确目标人群与消费场景”子 Task；唐梨接受未来审核，但要求先看到证据清单。乔木暂不被邀请。
8. **逐步正式创建**：程夏接受邀请且沈言确认子 Task Proposal 后，系统才创建该子 Task；唐梨作为 Participant 提供有界评审，不成为根 Task 或子 Task Owner，也不在 Task 详情生成逐项 Responsibility。
9. **后续生长**：第一版策略形成后，AI 再建议是否增加创意、媒介与合规子 Task。下面的完整树是多人逐项接受后的状态，不是创建首屏输出。

- 创意希望使用“喝了没有负担”，法务认为证据不足。

### Task 文件与引用

```text
重复扣款定位、修复与灰度（Task 文件）
├─ 架构与 ADR
├─ 支付业务规则
├─ 运行手册
├─ 事故记录 / INC-2026-0826 重复扣款
│  ├─ 脱敏样本
│  ├─ 调查记录
│  ├─ 修复方案
│  └─ 复盘
├─ 发布记录
└─ 生产日志索引（受限、按需读取）
```

### 冲突与洞察

- 加数据库锁可以快速止血，但可能扩大延迟。
- API 文档写重试两次，实际网关配置三次。
- 最匹配的人最忙，最有空的人缺生产权限。
- AI 应分别展示经验、权限、响应窗口，不能把它们合成“最佳人选”。
- AI 不能向团队广播订单号、客户、金额或原始日志。

加盟店店长可查看操作与培训文件，不能查看配方成本、总部毛利和其他门店经营数据。

### 冲突与洞察

- 培训视频使用配方 v7，POS 使用 v6。
- 原料只够八家店，却计划灰度十二家。
- 三家门店尚未确认培训。

## 七、智能制造：衡川质量联合组

### 创建过程

输入：“B41 新批次出现异响，下午前给我一个判断。”

AI 先询问该批次是否仍在生产或出货，以判断先围堵还是先调查。质量经理赵衡保持 Owner；工艺工程师林川掌握追溯上下文；供应商质量吴启有相似经验但正在处理停线；设计工程师何真了解公差却无出货批准权。

```text
└─ 形成出货或继续冻结决定｜Owner 赵衡
```

### 文件与权限

```text
B41 异响批次围堵与出货决策（Task 文件）
├─ 产品与图纸（研发受限）
├─ 批次追溯
├─ 检验与实验
```

- 采购希望维持交付，质量要求冻结。
- 供应商判断是装配问题，产线判断是材料问题。

- AI 把冲突整理为待验证假设，不宣布根因。
- AI 不解除批次冻结、不代替有权人发布客户通知。

### 可执行 Given / When / Then

#### A. 不知道找谁的团队广播

- **Given**：衡川 Task 已有唯一 Owner；画像中没有满足“异响频谱诊断”证据门槛的可见候选；原始文件含客户与供应商敏感信息。
- **When**：Owner 主动选择“向质量联合组求助”，确认 AI 生成的脱敏卡和可见范围。
- **Then**：创建 `help-request Activity`，只包含批次类别、需要的判断和投入区间；回复者可以提供线索或推荐人，但不加入 Task、不获得文件权限。Owner 后续发出邀请且对方接受后，才按范围成为 Participant；若形成独立结果，则另建有唯一 Owner 的子 Task。

#### B. 责任画像纠正

- **Given**：乔木的观察职责显示“持续参与上市全流程”，证据来自两次高可见项目，但 Coverage 不含线下创意评审。
- **When**：乔木将该 Claim 标为“不准确：我只负责概念与终审节点”并选择团队可见。
- **Then**：原 Claim 进入 `disputed`，纠正作为新证据保留；推荐方式改为节点评审，不删除历史 Task，也不把纠正当成负面能力信号。

#### C. 文件版本冲突

- **Given**：鹿岛培训 Task 跟随配方 File 最新版，POS Task 固定 v6；维护人发布 v8。
- **When**：新 FileVersion 生效。
- **Then**：AI 生成带证据的版本影响 Insight；培训引用自动看到 v8，固定 v6 的 POS Task 只收到提醒。Owner 可以继续固定、比较差异或申请升级；系统不替其改版本。

#### D. 高风险决定

- **Given**：衡川证据支持“继续冻结”，但当前分析者没有出货决定权。
- **When**：用户采用 AI 建议并尝试确认结论。
- **Then**：系统只创建 `Decision.status=proposed`；PolicyDecision 拒绝当前用户确认，并路由到有权人。获授权者查看同一证据后明确确认，才更新 Decision 与 Task 状态，并在同一事务追加 ChangeSet。

#### E. Agent 按需读取与撤权

- **Given**：OrbitPay 江南连接个人 Agent，只获准读取事故 Task 的脱敏 File List 和固定日志版本。
- **When**：Agent 请求正文，随后江南撤销连接。
- **Then**：首次请求按“用户 ∩ AgentConnection ∩ FileVersion ∩ Task”放行并记录 actor/on-behalf-of；撤销后的下一次请求立即拒绝，已产生的摘要仍按原权限受控，不能被自动发布。

#### F. 人际责任 Handoff 的有条件接受

- **Given**：鹿岛总部培训负责人休假前拟把“12 店现场异常收集”责任交给区域督导；发出者对督导有考核输入权，根 Task Owner 不变，且两家店的配方文件对接收者不可读。
- **When**：接收者选择“先重新排优先级并补齐权限”，复述自己只能承担 6 店范围，并请求区域经理作为中立协调人。
- **Then**：Handoff 保持 `clarification-requested`，原 Responsibility 继续有效；发出者只看到范围 / 依赖状态，不看到私密理由或响应耗时。区域经理须先通过无直接考核 / 利益冲突校验；若有冲突则更换协调人。接收者拒绝后，人工与 Agent 都不能直接重发同一 scope，只能由接收者重开、无冲突协调人确认实质变更或正式应急策略解除保护。协调、权限补齐后生成新 Revision，双方接受同一 digest，系统再 supersede 原 Responsibility、创建 successor 并追加 ChangeSet。

#### G. 结果交回与父 Owner 整合

- **Given**：OrbitPay 技术子 Task 已进入 Review，子 Task Owner 准备交回修复结论、固定日志版本和一项未决业务规则。
- **When**：直接父 Task Owner 查看 Result Return 并复述“技术结果可接收，业务规则仍待授权人决定”。
- **Then**：系统先记录结果交付；父 Owner 对当前 Revision 明确接收后，激活事务才关闭子 Task。未决规则成为 Decision Request，父 Task 的整合另记为后续事件；系统不把“已交付”自动写成“已接收”，也不把子 Task Owner 变成父 Task Owner。

#### H. 品牌假设争议与贡献归属

- **Given**：南栀洞察负责人拟把“核心人群证据”Context Handoff 给创意负责人；其中“夜间饮用者最在意零糖”仍是假设，且两人存在专业地位差异。
- **When**：接收者复述后把该结论改标为“待验证”，只接受基于已确认访谈开展概念探索，并要求保留原洞察作者署名。
- **Then**：系统生成双方共同编辑的新 Revision，不以 source 为真值；Context 激活不改变传播根 Task Owner。创意结果另建子 Task，完成后用 Result Return 逐级交回，历史贡献和被否决假设都保留。

#### I. 影视外部反提范围与限权交回

- **Given**：雾港后期 Owner 邀请外部调色供应商完成一个新子 Task；在 Q-05 当前建议默认下，实际承接 Owner 的供应商负责人已先经过组织邀请，成为 tenant 内受限 guest Member，而不是直接用 external Principal 冒充 Owner；他只能访问代理素材与锁片版本，授权将在交付夜到期。
- **When**：供应商反提“只交 HDR 主版本，国际版次日补交”，内部 Owner 接受缩小范围；期间锁片 FileVersion 变化。
- **Then**：新工作通过 Proposal / 邀请正式创建子 Task，不重复一次 Handoff 接受；版本变化使旧 Task Brief / 接受失效并重新确认。HDR 通过 Result Return 被父 Owner 接收，国际版成为新子 Task；供应商看不到合同和其他供应商目录，权限到期后正文读取立即拒绝。

#### J. 制造应急接管与接回失败

- **Given**：衡川质量 Owner 在客户现场失联，出货冻结仍在；具备接管授权的值班 Steward 准备自己成为临时 Owner，但尚未看过最新图纸。
- **When**：Steward 补齐固定版本，以 recipient 身份接受临时责任，并记录应急授权、原 Owner 不可用事实与 source Consent 例外；原 Owner 回归后暂时拒绝接回，要求先完成客户通知复盘。
- **Then**：系统不伪造原 Owner Consent，应急激活前后始终一位 Owner；回归只触发关联原协议的反向 owner-transfer Handoff Offer，不自动切回。未满足接回条件时现 Owner 继续负责，系统路由对象依赖而不持续催促原 Owner。
