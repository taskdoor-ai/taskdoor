# AgentDoor 项目工作宪章

> 状态：项目级规范。产品负责人已确认需要用统一工作流程、规则与原则把控项目基调；本文的具体执行细则作为当前默认，后续调整必须进入决策台账。  
> 当前治理 Revision：`GOVERNANCE-2026-08-28-r2`（精简、风险驱动执行）。
> 适用对象：产品、设计、研发、测试、研究、Reviewer、人类协作者与 Agent。  
> 项目基调：**安静、清晰、有依据、尊重人、可接续。**

## 一、这份宪章解决什么

AgentDoor 不缺想法，真正需要控制的是：每次讨论、设计和实现是否仍在解决同一个问题，是否尊重已经确认的产品原则，是否留下下一位成员能够接续的事实、决定和证据。

这份宪章负责统一：

- 什么可以直接推进，什么必须先由产品负责人确认。
- 小改动和大型改造分别需要多重的流程。
- 产品、设计、工程、AI 和数据判断发生冲突时以什么为准。
- 一个工作分支如何开始、完成、验收和 Handoff。
- 什么才算“完成”，而不是只算“做过”。

它不是额外的项目管理对象，也不要求每件小事都写长文档。规则的目标是减少返工和误解，而不是制造仪式。

精简执行规则与按需记录模板见 [工作记录规范](../workflow/README.md)。默认在任务回复中闭环，不为每一步创建独立文件；正式产品 Handoff 另按领域规范创建。

## 30 秒执行摘要

- **先判动作，再判影响**：回答 / 诊断默认只读；改造按 C0–C3 路由，轻事走短路径，高影响工作先确认。
- **先有事实，再有方案**：事实、推断、未知、建议和决定必须分开；代码存在、会议提过和 Agent 建议都不等于产品已确认。
- **人的承诺由人作出**：AI 可以准备和提醒，不能替人接受责任、改变 Owner、扩大权限或执行不可逆外部动作。
- **每层只有一位结果负责人**：产品对象使用 `Task Owner`；项目交付分支使用 `Work Owner`，二者不得混用。
- **完成必须可验证、可接续**：普通工作在当前回复中说明结果与验证；只有确实转移既有上下文、工作或责任时，才进入长期记录或产品语义的 Handoff。
- **拿不准时看影响**：会改变产品语义、人的选择、权限、数据或恢复成本，就升级而不是靠改动行数降级。
- **轻事只走一遍**：清晰请求直接实施，连续反馈在任务边界统一验证；不重复读、重复确认、重复建档或默认跑全量回归。

## 二、规范用语与事实状态

本文使用三种强度：

- **必须**：不满足就不能进入下一阶段或宣称完成。
- **默认**：没有明确反例时照此执行；偏离必须说明理由和影响。
- **可以**：团队按任务规模选择，不构成放行门槛。

任何文档和沟通都要区分四类内容：

| 状态 | 含义 | 能否直接据此实现 |
| --- | --- | --- |
| 已确认决定 | 产品负责人明确同意，并进入决策台账 | 可以 |
| 设计默认 / Proposal | 为了闭合方案提出，仍可编辑 | 不可冒充已确认 |
| 当前实现事实 | 从代码、数据或界面核对得到 | 只能说明现状，不自动成为产品方向 |
| 历史方案 | 曾讨论或实现，但已被替代 | 不可继续作为依据 |

事实、推断、未知和建议必须分别表达。模型置信度、界面完成度和代码已经存在，都不能把一项推断升级成决定。

本文区分两种 Owner：

- **Task Owner**：AgentDoor 正式 Task 的唯一结果负责人，服从产品领域规则。
- **Work Owner**：一次设计、研究、开发或文档交付的整合负责人，可以是当前执行 Agent；它不自动获得任何产品 Task 的 Owner 身份或权限。

## 三、单一事实源与冲突优先级

发生冲突时，按以下顺序处理：

1. 安全、隐私、法律、平台权限和不可逆外部影响的硬约束。
2. 产品负责人最新的明确决定，并以 [09-decision-register.md](./09-decision-register.md) 为记录。
3. 本项目工作宪章。
4. `docs/product-v2/` 中当前标记为 canonical 的产品、领域和场景文档。
5. 已确认工作的具体要求、持久 Decision Revision 与可观察完成证据。
6. [AgentDoor Design System](../agentdoor-design-system.md) 与组件研究记录；其中产品结构若与 V2 冲突，以 V2 为准。
7. 当前代码、Mock、旧会议纪要和历史文档。

补充规则：

- 当前任务中会长期约束后续工作的明确新决定即时控制本次工作；Work Owner 必须在交付前同步台账、Revision 和受影响文档。局部可逆反馈只控制本次实现，不逐条登记。表述不清或范围不确定时必须停下确认。
- 临时任务说明不能静默改变产品原则；需要改变时，先更新决策台账和受影响文档。
- 代码是“现在怎么做”的事实，不是“以后必须怎么做”的依据。
- 同一领域对象只保留一份规范 Schema；其他文档只能引用或定义投影。
- 会长期约束后续工作的产品 / 治理决定不能只埋在聊天、会议纪要、提交信息或代码注释中；局部可逆反馈不需要逐条登记。
- `AGENTS.md` 负责约束 Agent 的执行行为；若它与本文或决策台账冲突，Agent 必须停止并报告，不自行选择方便的一边。

## 四、不可动摇的产品原则

当前产品表面服从 `D-139 / PRODUCT-V2-2026-08-28-r124`：Task 是唯一行动对象；当前产品不创建或操作 Todo，Task 创建与详情不提供逐项 Responsibility 分配或验收标准。唯一 Task Owner、Participant、Activity、Task File、父子 Task、Handoff、ACL 与接受前不生效等安全语义继续有效。

### 1. 从用户想完成的事情出发

先理解目标、现状和真正缺口，再决定 Task 需要哪些参与者、文件引用、父子关系或阶段。不能先拿系统模板套用户。

判断题：如果删掉系统预设流程，用户的目标和下一步是否仍然清楚？

### 2. 结构按需生长

小事允许保持轻量；只有出现独立结果、持续上下文或继续拆解时，才升级为 Task 或子 Task。复杂度必须由真实需求产生，不能由 AI 的表现欲产生。

判断题：这个新增对象是否解决了现有对象无法表达的稳定语义？

### 3. 默认自己负责，协作由人主动选择

AI 可以发现经验、知识、信息、权限、容量和利益相关缺口，但不能自动邀请、指派或把用户变成计划的执行机器。

判断题：用户是否可以不找人，仍然继续完成当前可做的部分？

### 4. 一层 Task，一位 Owner

共同参与不等于共同兜底。每个正式 Task 恰好一位结果 Owner；不同层级可以有不同 Owner。Reviewer、Advisor、Contributor 和 Approver 通过 Participant、邀请范围、Activity、子 Task 或 Handoff 表达清楚，不在 Task 详情另建逐项责任分配。

判断题：出现问题时，团队能否在十秒内回答“这一层结果由谁持续跟进”？

### 5. 承诺来自接受，不来自界面指派

邀请、已读、加入成员、文件分享和 Handoff 发出都不等于责任成立。接收者必须知道目标、范围、非目标和第一步，并能拒绝、改范围或请求协调。

判断题：接收者是否知道自己没有接受什么？

### 6. 工作出去，结果必须回来

独立工作用子 Task 表达，并由直接父 Task Owner 整合；已有工作接续使用 Handoff。完成必须带回结果、证据、剩余风险和未决问题，不能停在“做完了”。

判断题：父 Owner 能否不重读全部历史，就判断接收、补充还是拆出后续工作？

### 7. 证据先于推断，权限先于智能

推荐、画像、洞察和 AI 行动必须能回到有权可见的来源、版本、Coverage 和新鲜度。能力、责任、访问权和批准权是四件不同的事。

判断题：如果隐藏模型结论，只看证据，人是否仍能理解为什么这样建议？

### 8. AI 是 Facilitator，不是隐形管理者

AI 负责理解、比较、起草、检查、提醒和解释；人负责承诺、授权、Owner 变化、高风险决定与不可逆外部动作。

判断题：界面是在帮助人作决定，还是在用“智能”包装已经替人做好的决定？

### 9. 协作数据不能变成绩效监控

系统展示对象、责任、依赖和证据，不展示或推断在线投入、静默时长、个人速度、接受率和伪精确空闲率。忙闲只使用本人主动公开、可撤回且会过期的粗粒度协作窗口。

判断题：如果这项数据被直属管理者看到，是否可能改变成员拒绝或协商的安全感？

### 10. 一份真相，引用而不是复制

Task 是当前产品唯一行动对象；File、FileVersion、Decision、Activity、Handoff 与 ChangeSet 各自承担稳定语义，底层 Responsibility 只服务已确认的协作与 Handoff 安全边界，不在 Task 创建或详情中形成逐项分配面。Task 引用文件和版本，不复制第二份真相；Handoff 引用上下文，不克隆文件树和聊天。历史 Todo 合同已由 D-139 替代，不得继续指导当前产品面。

判断题：同一事实变化后，团队是否需要手工维护两处以上内容？

## 五、项目标准工作流

统一闭环按影响展开，默认短路径是：

```text
需求进入
  → 定位必要事实与直接相关规则
  → 判断影响级别
  → 需要时一次确认具体决定
  → 实施最小完整改动
  → 针对性验证
  → 简短结果；仅在持久决定、高风险或真实接续时留长期记录
```

### 1. 需求进入：先判断用户要什么动作

- **回答 / 评审**：只读核对并给结论，不推断授权去修改。
- **诊断**：查明原因和影响；除非请求包含修复，否则不顺手改代码。
- **改造 / 构建**：在已确认范围内实施并验证。
- **探索 / 产品讨论**：先形成可编辑 Proposal，不把建议写成已决定或直接实现。

### 2. 上下文核对：开工前先读什么

按影响读取，先搜索再打开直接相关部分；已经在同一连续工作中读过且来源未变时复用，不做形式化重复：

- **C0 / C1**：读取触达文件、直接相关决定 / 规则与必要当前事实；纯拼写、局部样式或失效链接修正无需遍历无关文档、代码、数据和测试。
- **C2**：读取本宪章和决策台账的相关章节、相关 canonical 文档与当前实现事实。只有治理本身、跨域核心合同或发现冲突时才完整通读。
- **C3**：完整核对触发风险所属的规范、决定、代码、数据和测试事实；不因高风险而加载明显无关领域。
- **任何级别**：发现范围升级、来源变化或语义冲突时，立即补读并重新分级。

常规 UI 工作读取设计系统的相关章节并优先复用现有组件；新页面、实质重做或新共享交互原语再执行完整设计准备与按需组件发现。

### 3. 最小 Brief：先把问题说对

执行者必须能回答三件事；用户请求已经清楚时，无需再生成或复述一份 Brief：

- **目标**：希望产生什么用户或业务结果。
- **范围**：本次改变什么，不改变什么。
- **完成证据**：如何知道它真的完成。

中大型工作只补与决定或风险直接相关的当前事实、未知、取舍、权限 / 数据影响和恢复方式。

### 4. 路由与确认：什么时候必须停下来

遇到以下任一情况，必须停在 Proposal / 决策确认，等待产品负责人明确确认：

- 新增或删除一级模块、核心对象或正式状态。
- 改变 Task 作为唯一行动对象、Task Owner、Participant、Responsibility / Handoff 安全边界的语义或不变量。
- 改变协作创建、找人、邀请、拒绝、交接或结果接收的核心流程。
- 新增人员数据采集、画像用途、监控指标或更宽的可见范围。
- 改变权限、授权、Agent 写入范围、外部发布或不可逆动作。
- 有两个以上合理方向，选择会显著改变用户体验、数据模型或迁移成本。
- 与已确认决定、本文或 canonical 文档冲突。

以下情况可以在用户已要求实施后自主推进，不必为低风险细节反复确认：

- 不改变语义的缺陷修复、测试补充和可逆重构。
- 在现有 Token、共享组件和确认交互内完成的小范围一致性调整。
- 用户已明确要求、且不改变核心对象 / 状态 / 权限 / 导航合同的局部文案、布局、样式、Mock 和交互修正。
- 把已确认决定补写到相关文档，或修正文档内部矛盾和失效链接。
- 为验证已确认行为补充 Mock、边界场景和自动检查。

### 5. 实施准备：只在必要时形成记录

技术评估是判断工具，不是每个任务的必需产物。C2 只有存在实质方案取舍、跨模块不变量或恢复风险时才写；C3 必须覆盖相应风险。需要跨会话保留时，把决定、实现范围、验证和恢复合并在一份 Work Note 中：

- **`pre-decision`**：只读核对可行性、选项、影响和未知，用来帮助人作决定；不能预设某个 Proposal 已获批准。
- **`implementation-ready`**：产品方向确认后，绑定已确认 Revision，补齐必要的实现范围、验证与恢复；达到相应 DoR 后才可进入代码。

需要书面评估时，进入代码前至少回答：

- 当前实现事实、相关文件和依赖。
- 要改变的领域对象、状态与不变量。
- 权限、隐私、版本、并发和审计影响。
- 数据迁移、兼容、失败恢复和撤回方式。
- 验收场景、自动测试和人工验证范围。
- 哪些仍是 Mock，哪些是真正安全能力。

涉及 UI 时，只覆盖本次实际改变的对象 / 状态、键盘路径、响应式和复用选择；外部候选研究按设计系统的触发条件执行，不是普通调整的默认步骤。

### 6. 实施：最小完整纵切

默认优先完成一条从用户动作到持久状态、权限、反馈和验证的完整路径，不一次铺开大量半成品页面。

- 复用统一领域对象、Command Gateway、Token 和共享组件。
- 不把正式状态只存在前端文案或 `localStorage` 中却声称已经安全落地。
- 不顺手改无关模块，不覆盖团队成员未完成的工作。
- 大改拆成可独立验收的分支；每条分支有明确 Work Owner、输入、输出和回传目标。

### 7. 验证：最小充分证据

- 默认先验证本次改变的行为与最可能受影响的相邻路径，不跑与改动无关的全量回归。
- 每项检查先绑定一条可观察验收并复现目标场景；构建只证明可编译，截图只证明该视口状态，不能替代行为、权限或产品语义证据。
- 文档只检查触达链接、术语、决定状态与结构；代码按触达范围选择构建、类型检查或具体场景。
- 常规 UI 检查实际受影响的视口、交互与键盘 / 焦点路径；新页面、重大重做或发布级工作再扩大到完整桌面 / 移动和跨页面一致性。
- `npm run verify` 只执行前端生产构建；设计债务基线由 `npm run verify:design` 按需执行，仅用于全局 Token、共享基础组件、全局样式、设计检查本身或发布级验收。
- 领域、权限与数据只在相应边界被触达时验证不变量、拒绝、并发、幂等、撤权和恢复；C3 增加必要独立架构、安全 / 隐私或人性 Review。
- 连续小步反馈合并到任务边界验证一次；检查失败时再基于原因扩大范围。

测试通过只证明被测行为没有失败，不自动证明产品决定正确、权限模型完整或用户真实接受。

### 8. 交付与 Handoff：让下一位不需要重新考古

普通回答、文档、设计或代码交付默认在当前回复中用三项收口：**结果、实际验证、仍有的实质问题 / 风险**。没有剩余项就省略，不列无关 `N/A`、完整终端输出、已读清单或虚构下一步。只有跨多人 / 跨会话、高风险或真实接续需要时才保存 Work Note。

只引用必要上下文，不粘贴完整源码、聊天、密钥或与接收者无关的数据。普通结果说明不代表双边 Consent，也不自动改变责任。

只有出现以下情形才使用 AgentDoor 产品语义的 **Handoff**：既有上下文需要正式接续、Responsibility / Task Owner 需要转移，或子 Task 需要 Result Return。接收者需要独立新结果时创建子 Task；只需短评审时使用有界协作范围，并通过 Participant、Activity 或邀请上下文表达，不在 Task 详情新增逐项 Responsibility 分配面。正式 Handoff 的责任变化服从 [人与人 Handoff 规范](./11-human-handoff.md) 和已确认决定，普通结果说明绝不等于责任已经生效。

### 9. 沉淀：完成后更新团队真相

- 会长期约束后续工作的产品决定进入决策台账。
- 领域、流程或权限改变时同步更新 canonical 文档。
- 可复用视觉决定进入 Token、共享组件或设计系统。
- 当前实现差距进入路线图，不伪装成已完成能力。
- 被真实验收的工作可以成为责任画像候选证据；活动量本身不能。

## 六、按规模选择流程，而不是一刀切

| 级别 | 典型工作 | 必需产物 | 放行方式 |
| --- | --- | --- | --- |
| C0 只读 | 回答、审查、代码核对、原因诊断 | 结论、依据、未知 | 可直接进行，不产生外部变更 |
| C1 轻量 | 文案、小缺陷、局部可逆 UI / Mock、测试、无合同重构 | 改动 + 针对性验证 | 用户已要求修改即可推进 |
| C2 产品 / 治理合同 | 核心流程、对象、状态、一级导航、跨模块不变量 | 具体决定确认；持久决定入台账；评估按风险 | 产品负责人确认具体方向后实施，不重复确认低风险细节 |
| C3 高影响 | 权限、人员数据、Task Owner / Handoff、持久化或外部契约 Schema、数据迁移、外部或不可逆动作 | 一份合并 Work Note、安全 / 隐私与恢复方案 | 明确逐项批准并独立 Review |

规模由影响决定，不由改动行数决定。一个按钮若会发布外部消息属于 C3；一份很长的 Mock 数据若不改变正式语义仍可能只是 C1。

内部 TypeScript shape、测试 fixture 或无语义重命名不因出现 `Schema` 一词自动成为 C3；静态原型也不能因“没有落库”自动降为 C1。原型按它准备验证或影响的产品语义分级，并必须显著标注尚未真实落地的权限、数据和写入能力。

## 七、决定与 Revision 规则

需要确认的工作在对话中使用以下最小结构；清晰请求不重复生成，只有持久决定才进入台账：

```text
要解决的结果：
当前事实与实质未知：
建议方案及主要取舍：
会改变 / 不会改变：
需要确认的一项决定：
完成证据：
```

决定规则：

- 一次确认绑定具体 Revision；实质范围变化需要重新确认。
- 用户对具体方案的明确指令或同意就是该 Revision 的确认；同一决定不再要求一次同义确认。
- 沉默、已读、继续讨论和代码已写都不等于批准。
- 会议纪要中的推测、总结者评论和行动项不自动成为产品决定。
- 被否决方案保留理由，避免团队下一轮重新争论同一问题。
- 决定记录必须包含日期、决定人、受影响文档和重新审视触发条件。
- 紧急决定可以先缩小处置范围，但不能绕过权限、Consent、单 Owner、审计和数据最小化。

## 八、Definition of Ready

### C1 最小开工条件

- 目标、范围和完成证据清楚。
- 不改变未确认的产品语义。
- 相关文件和当前事实已经核对。

### C2 开工条件

- 具体产品 / 治理方向已确认；若为持久决定，已分配当前 Revision。
- 受影响合同、不变量、范围和验收证据清楚。
- 存在跨模块、共享基础或难恢复风险时，Reviewer 与恢复方式已明确。

### C3 开工条件

- 具体高风险动作、权限 / 数据范围与恢复方式已逐项确认。
- Work Owner、必要 Reviewer、失败 / 拒绝路径、迁移和审计证据明确。
- 验收能够区分界面演示与真实安全落地；新增依赖或外部动作另有明确授权。

### 没有 Git baseline 时的放行边界

| 工作 | 可以做什么 | 不能宣称什么 |
| --- | --- | --- |
| C0 | 正常只读分析和审查 | 不能声称核对了不存在的历史 diff |
| C1 | 可修改明确文件；交付时列完整文件、验证结果并注明“无可靠历史 diff / 回滚” | 不能声称已经完成版本级回滚验证 |
| C2 / C3 产品与治理 Proposal | 可研究、写按需 Work Note、更新明确获准的规范，并以完整文件内容、after-state hash 和必要独立内容 Review 固定当前结果 | 不能把它包装成已具备代码变更追溯和回滚能力 |
| C2 / C3 功能实现 / 发布 | 只能停在研究、Proposal 和必要的 `pre-decision` 评估 | 没有经人类批准的 Git 初始 baseline，或具有 before / after、不可变存储和恢复验证的等效快照前，不能实施或宣称 Done |

人类若选择暂不建立 Git baseline，必须同时选择等效版本证据和恢复方式；“不做任何版本固定”不是 C2 / C3 功能实现的可放行选项。Agent 不得自行创建首个 commit。

未 Ready 的工作可以继续研究和起草，但不能把 Proposal 物化成正式实现决定。

## 九、Definition of Done

以下条件按**本次确认范围与触达区域**判断。不适用项直接省略；只有本应执行却未执行的检查才说明原因和风险。仓库已有债务不自动阻断一个局部交付，但本次不能复制、扩大或把它冒充已解决。版本 / 发布级工作另需证明整个发布范围满足相应门槛。

一项工作只有同时满足所有适用条件才算完成：

- 实际结果与确认过的目标和范围一致。
- 关键不变量、权限、拒绝路径和失败恢复有证据。
- 所选的最小充分检查通过；与本次结果直接相关但无法执行的检查明确说明原因和风险。
- 本次声称完成的范围内没有调试词、意外暴露的内部枚举、未标注 Mock、不可达入口或只做了一半的交互状态。
- 代码、文档、设计系统和决策台账没有产生新的双重真相。
- 新增复用模式已经进入共享层，而不是复制在单页。
- 达到本级要求的 Reviewer / 自审者能回答“改了什么、为什么、怎么验证、还剩什么”。
- 已在当前回复中给出足以接收的结果与验证；跨会话或正式责任接续时，另有 Work Note、Handoff / Result Return。

“代码写完”“页面能打开”“构建通过”“Agent 说完成”都只是完成证据的一部分，不是 Done 的同义词。

## 十、协作与多 Agent 规则

- 只有可以独立产出、边界清楚并能并行的工作才拆给协作者或 Agent。
- 每个分支必须写明目标、输入范围、禁止事项、期望输出、Work Owner 和回传对象。
- 子 Agent 可以成为其交付分支的 Work Owner；子 Task 可以有不同 Task Owner。两种 Owner 不互相继承，整合责任始终留在直接父级 Work Owner / Task Owner。
- 多个协作者不能分别创建同一领域的“最终版本”；主 Work Owner 负责合并、消歧和形成单一结论。
- Reviewer 应尽可能独立于作者，重点检查意图与实现差异、架构不变量、人性风险和证据充分性。
- 协作者结果未经父级 Work Owner / 直接父 Task Owner 验收，不能直接标为整个任务完成。
- 不为了显得忙碌而拆分；协调成本高于独立产出价值时，不拆。

## 十一、AI 行动边界

### AI 默认可以

- 读取有权范围内的代码和文档，核对事实与冲突。
- 起草 Proposal、按需 Work Note、Handoff 和测试场景。
- 在用户明确要求的范围内实施可逆改动并运行验证。
- 指出权限、版本、责任、Coverage、设计一致性和验收缺口。
- 调度 Agent 并行完成有界研究，由主 Work Owner 统一整合。

### AI 默认不可以

- 把建议、会议推断或当前代码包装成已确认产品决定。
- 替人接受邀请、Handoff、Owner 变化、批准或不可逆动作。
- 自动扩大任务、数据、文件、成员或外部系统作用域。
- 以成员活动量、回复速度、静默和私人数据推断态度或能力。
- 为了“完成更多”顺手修改无关模块、安装依赖、发布、发送或提交。
- 隐藏验证失败、未知、Mock 限制或与原需求的偏差。

AI 输出涉及判断时，默认使用以下表达顺序：

```text
结论 → 依据 → 不确定性 / 风险 → 建议动作 → 需要谁确认
```

## 十二、产品、交互与视觉基调

产品与正式文档统一使用名称 `AgentDoor`；代码包名、CSS 前缀和文件路径可以继续使用小写 `agentdoor`。不得在同一用户界面混用 `Agentdoor / Agent Door / agentdoor`。

### 产品性格

- 像一份准备充分的工作 Brief，而不是监控驾驶舱。
- 像可靠的协作伙伴，而不是居高临下的自动经理。
- 主动发现问题，但把最终决定留给有责任、有权限的人。
- 面对复杂度时逐步展开，不用大量表单证明系统很专业。

### 交互规则

- 上下文和证据在前，人员推荐和动作在后。
- 一个决策区域只突出一个主要下一步，同时保留返回、拒绝和改范围路径。
- 默认展示对象状态、依赖和责任，不展示人的“在线 / 正在工作”。
- 建议、已确认、已接受、已生效、已交付和已验收使用不同语言和状态。
- 错误说明什么失败、什么仍安全、如何恢复；不能只显示“操作失败”。
- 轻任务保持轻，复杂任务才展开结构、权限和 Handoff 细节。

### 文案规则

- 使用用户认识的业务名词，不暴露实现枚举、内部 ID 和模型术语。
- 按动作效果命名按钮，例如“邀请王敏评审”“允许读取日志 v3”，不用模糊的“确定”“继续”。
- AI 使用“我发现 / 依据是 / 我不确定 / 建议你”，不用“已替你分配 / 最佳人选 / 保证完成”。
- 不使用制造焦虑、羞耻、服从和排名感的话术。
- 不把推断写成事实，不把未回复写成阻塞，不把接受邀请写成责任已转移。

### 视觉规则

- 默认白色和安静中性色；蓝色承担单一主要路由动作，语义色只表达事实、推断、冲突、未知和确认。
- 视觉层级依靠构图、排版、间距和对比，不靠巨大标题、彩色卡片墙和无意义分割线。
- 重要页面应有 AgentDoor 特有的“问题 → 证据 → 责任 / 权限 → 决定 → 验收”路由关系，而不是通用后台模板。
- 同一对象、动作和状态跨页面使用同一组件、文案与 Token。
- 动效只解释状态变化与连续性；不做空转、庆祝或装饰性干扰，并支持 reduced motion。
- WCAG AA、键盘焦点、移动端信息完整性和 44px 触控目标是基线，不是加分项。

完整视觉数值、Token、组件和研究流程以设计系统为准。

## 十三、真实 Demo 与 Mock 原则

Demo 要像已经有人使用过的团队，不像为了填页面生成的数据。

- 有历史任务、当前任务、失败尝试、被否决决定、版本冲突、权限不足和未决问题。
- 成员有正式职责、实际责任证据、Coverage、公开协作窗口和可以纠正的错误推断。
- 文件有文件夹、版本、来源、权限、任务引用和发布 / 衍生关系。
- 场景覆盖轻任务、多人协作、外部成员、高风险决定、拒绝、Handoff 和 Result Return。
- Mock 数字必须有来源说明；不能用伪精确工时、能力分和空闲率制造“生产感”。
- 静态 Mock 只能证明表达和交互可以演示，不能证明权限、安全、预测或审计已经实现。

## 十四、Review 与放行规则

按风险选择 Reviewer，不要求每个小改动开完整评审会：

| 级别 | 最低 Review 要求 | 最终整合者 |
| --- | --- | --- |
| C0 | 作者事实自检；用户明确要求独立审查时除外 | Work Owner |
| C1 | 作者自审；若发现实际改变持久产品合同或敏感边界则升级 | Work Owner |
| C2 | 产品负责人确认具体方向；跨模块不变量、共享基础、难恢复选择或实质不确定性时增加一位针对性非作者 Reviewer | Work Owner 汇总单一结论 |
| C3 | 非作者 Review 必需；产品、架构、人性、设计、安全 / 隐私中所有触发视角都要有具名结论。同一人可覆盖多个胜任视角，但不能由作者一人包办 | Work Owner 汇总；有权人分别作决定 |

| Review 视角 | 必答问题 | 触发条件 |
| --- | --- | --- |
| 产品 | 是否仍解决原始用户目标？是否引入未确认语义？ | C2 / C3，或范围发生变化 |
| 架构 | 是否保持单一真相、领域不变量、权限、版本和事务边界？ | 数据、状态、跨模块、Handoff、Owner |
| 人性 | 是否伤害自主、心理安全、公平、贡献归属或形成监控？ | 找人、画像、忙闲、上下级、拒绝、通知 |
| 设计 | 是否符合信息层级、共享组件、Token、无障碍和产品一致性？ | 新页面、重大重做、共享基础或发布级 UI |
| 安全 / 隐私 | 是否扩大采集、可见范围、授权、外部动作或重识别风险？ | C3 |

正式 Review 被触发时，放行结论使用以下统一枚举之一：

- **`approved`（通过）**：证据满足当前范围。
- **`approved-with-follow-up`（带后续项通过）**：当前范围可以接收；每个后续项的 Work Owner、期限或明确触发条件、验证方式都已记录，且不违反硬约束。
- **`changes-required`（修改后复审）**：存在必须修复的问题；修复前保留原状态。
- **`blocked-pending-decision`（等待决定）**：证据无法替代尚缺的产品、权限或风险决定；不得用“先上线看看”绕过。

问题级别与结论强制对应：

- 未决决定类 `Blocker` → `blocked-pending-decision`。
- 任一未修复 `Must fix` → `changes-required`。
- `approved-with-follow-up` 只能包含 `Follow-up`，每项必须有 Work Owner、期限或触发条件和验证方式。
- `approved` 不能遗留 Blocker 或 Must fix；多个视角结论冲突时由 Work Owner 汇总为更保守的结论，不能投票抵消风险。
- 只要存在尚未关闭的 Follow-up，最终结论就必须是 `approved-with-follow-up`；只有没有任何未结问题时才使用 `approved`。

## 十五、偏离、例外与紧急路径

任何偏离默认规则都要记录：编号、原因、范围、风险、批准人、有效条件、恢复方式和复查触发点，并登记在 `docs/workflow/deviations/README.md`。未登记、无到期条件或由 Agent 自行批准的偏离无效。

批准权按被偏离规则归属：

- 产品语义、交互和文案原则：产品负责人。
- 架构、构建、测试和工程流程：人类技术负责人。
- 同时跨产品与技术，或涉及人员、权限、隐私、安全和外部动作：产品负责人 + 对应人类技术 / 安全责任人；角色不存在时不能偏离。
- Agent 可以提出和起草 Deviation，不能批准自己的偏离。

以下原则不能以“紧急”为由豁免：

- 正式 Task 始终恰好一位 Owner。
- 人不能被 Agent 代为 Consent。
- 权限与数据最小化不能靠前端隐藏代替。
- 不可逆外部动作不能伪装成可撤回。
- 审计事实不能被静默改写或删除。
- 敏感数据和成员行为数据不能因 Demo / 调试扩大可见范围。

以上清单是全项目 canonical 非豁免集合；其他文件只能引用，不得缩短成更宽松版本。另有法律、平台和组织安全硬约束时自动并入，不需要等本文更新才生效。

紧急路径可以减少表单、缩小目标和延后非关键文档整理，但必须保留最小 Brief、当前 Work Owner、适用时的 Task Owner、授权依据、ChangeSet / 证据和事后复查。

## 十六、宪章如何维护

- 修改本宪章属于 C2 产品治理变更，需要产品负责人明确确认。
- 变更后同步更新决策台账、总入口、`AGENTS.md` 和受影响规范。
- 每次修改都要说明替代了什么，不能让新旧规则并存。
- 重大治理或发布版本进行一次与实际风险匹配的独立审查；不为未触发的视角制造空报告。
- 如果规则长期被绕过，先判断规则是否过重或目标是否错误，不把所有问题归因于执行者不自律。

## 十七、十秒基调检查

在提交方案、页面、代码或文档前，快速回答：

1. 这是从用户目标出发，还是从系统模板出发？
2. 事实、推断、未知和决定分开了吗？
3. 用户和接收者仍有真实选择吗？
4. 这一层结果只有一位 Owner 吗？
5. 权限、版本、证据和回传路径清楚吗？
6. AI 是在辅助判断，还是已经越俎代庖？
7. 这是协作信息，还是可能变成绩效监控？
8. 小任务是否被不必要地复杂化？
9. 下一位成员能否不重新考古就接续？
10. 这个结果看起来、读起来、用起来都像 AgentDoor 吗？

任何一题无法回答，都不应直接宣称完成。
