# 任务规划方法与示例

用于把真实需求变成任务树、人员安排和基础信息。示例说明判断方法；不提供固定团队、默认负责人或可用于写入的虚构 ID。

## 从用户原话形成需求清单

先提取这几类信息，再一次生成任务清单：

| 信息 | 需要确定什么 | 缺失时如何处理 |
| --- | --- | --- |
| 交付结果 | 最终交付什么、用于什么目的、交给谁 | 只说“做好宣传”等无法界定范围时补问交付物 |
| 对象与数量 | 产品、渠道、版本、份数、时长等 | 保留已给数字；不猜型号、渠道规格或额外版本 |
| 质量与限制 | 必须包含的内容、预算、不做的工作、已有材料 | 限制进入对应目标或标准；已有材料优先复用 |
| 分工 | 点名人选、按职责安排、必要协作 | 用真实成员身份与已确认职责，不能凭名字或角色猜能力 |
| 时间与投入 | 明确截止日期、人工分钟、方法与依据 | 未提供截止不自造；需要估算时注明假设 |

只补问会改变范围、可行性、负责人或硬期限的缺口。问题尽量合并，问业务信息而不是 `workspaceId` 等接口参数。“标题没给”“执行步骤没给”通常不阻止方案生成：可以根据明确的交付结果生成。专业参数不明且会影响承诺时不能猜；例如活动预算是否包含制作费、指定“周五”究竟指哪一天。

已有资料只读取与本次交付有关的部分。区分已读全、部分可读和读取失败；没有读取到资料不能直接说资料不存在。用户已明确新增一个独立任务时，无需为了防重遍历全部历史。

## 按交付边界拆分

先列出交付物，再判断各项是否能单独验收。只有能独立交付、独立验收，且需要独立负责、交接或并行推进之一时才拆分。

| 情况 | 任务结构 | 说明 |
| --- | --- | --- |
| 一份脚本，含调研、撰写、校对 | 一个任务，步骤放执行建议 | 工作步骤不是独立交付物 |
| 同一次发布需要脚本、海报、活动方案 | 一个父任务，三个交付子任务 | 父级汇总本次范围，子级各有负责人和标准 |
| 两个渠道各有独立交付与交接 | 按渠道或交付物分组 | 选择最容易验收与负责的层级，避免同一结果在两处重复创建 |
| 多个互不相关的请求 | 多个根任务 | 不强行建没有共同目标的父任务 |
| 只需同事核对一处表述 | 原任务的必要参与者 | 不把一次咨询拆成独立“审核任务” |
| 需要单独确认且供后续使用的业务口径 | 可独立验收的确认任务 | 与普通校对区别在于它是用户要求单独交付的确认结果 |

层级按业务需要决定，不规定必须两层或三层。避免只为分类增加空父任务；中间节点应有明确的汇总范围。父任务标准说明整体交付如何完成，子任务标准说明各自交付如何通过；每个节点都要生成标准。

多阶段需求要把用户列出的每项结果落实到节点。比如“先确认口径，再做文案和海报，最后整理交接清单”，对应口径确认、文案、海报、交接清单四项交付；不要只写三项制作任务，在 summary 中提及清单却遗漏实际交付。确认结果供文案和海报使用，清单汇总最终文案、海报及其版本和交接信息；无需凭空增加受众版本或重复海报。若用户只要求现有资料分别交接，交接标准可归入各分支，不必额外拆清单任务。

任务结构只表达父子归属，所有 `dependsOnClientIds` 固定为空数组。材料确认后才能制作等明确要求写入相关目标、标准或执行建议；同一已确认资料下的文案和海报可以并行，不把叙述顺序或材料使用关系转成依赖链。

“发布前确认”不是“制作前确认”。例如用户只要并行制作的网站内容、宣传图和问答，发布前再由业务侧确认价格：仅规划三份内容，价格处保留待核对；不新增价格确认任务，也不把价格未提供扩大为制作整体阻塞。只有本轮明确请求独立确认结果，才把它作为独立交付处理。

## 生成可以验收的基础信息

| 字段 | 写法 | 避免 |
| --- | --- | --- |
| 名称 | 动作或交付物＋业务对象，能够区分渠道或版本 | “任务一”“完成相关工作”、堆叠全部要求 |
| 目标 | 说明交付后可以达到的结果或用途 | 复制标题、只写“按时完成” |
| 完成标准 | 可检查的交付物、内容、数量与质量要求 | “高质量”“领导满意”、无依据的数值阈值 |
| 执行建议 | 帮助执行的具体步骤、可用资料或注意点 | 把建议包装成额外验收门槛，扩写用户已指定条目 |
| 截止日期 | 保留明确日期，按真实当前日期和时区解释相对时间 | 生成开始时间，用估算工时反推截止 |

例如“完成产品介绍”可写成：名称“编写新品介绍文案”；目标“交付可用于发布、帮助读者理解产品用途的介绍文案”；标准“包含产品用途”“明确适用对象”“说明已确认的核心特点”。逐条标准尽量只核对一类要求，但不把每句话机械拆成一条，也不固定要求三条。

把要求与其适用对象对应：整体预算约束整个项目；脚本时长仅约束脚本；文案与海报的卖点一致性仅约束这些物料；活动方案的步骤和检查清单仅约束活动方案。父级标准汇总这些各自成立的结果，不把局部要求升级成所有子任务的共同门槛。职责中列出的常规源文件、格式或多渠道适配，仅用于分工及可选执行建议；只有用户要求或本次交付确实必需时才成为完成标准。

预算、数量等整体限制保留在父任务的验收范围；没有分项预算就不擅自分配或给每个子任务重复算一份总预算。已有素材可直接作为执行条件，不创建重复制作素材的任务。“不拍摄、不投放”等明确排除项贯穿拆分和标准，不能在建议里重新增加。

截止日期按各节点分别生成。用户分别给父任务与子任务日期时不统一覆盖；只给整体日期时可让范围内子任务遵守该截止，不自造提前几天的硬期限。缺失日期用 null 表示，不影响明确任务方案的生成。

## 选择负责人和参与者

根据调用方提供的有效成员目录排除未加入、已停用或无法参与该工作区的成员。再按以下依据比较：用户明确选择；职责语义是否与核心交付合理相关；可核实的相关经验；成员主动公开、与本次交付有关的协作条件。缺少的依据如实保留，任务数量、在线状态、回复速度和职位都不能代替忙闲或能力证明。

- 内容制作的负责人应能承担内容交付；业务口径确认看谁对业务信息有责任，不能自动给制作人。
- 现场执行、检查清单、渠道交接应按运营或执行职责匹配；最终内容核查按确认的核查职责匹配。
- 父任务负责人负责范围、协调和整体交付，不必与全部子任务同人。用户指定且身份有效时保留，不用“更合适”自行覆盖。
- 渠道分组含实际交付与交接时，也推荐合理相关的负责人，并明确谁承担交接；接收方未知可保留为待补资料，不因此把交付责任留空。运营可承担渠道交接，统筹可承担分支协调，不要求职责逐字列出渠道名。
- 每个任务只有一个负责人。参与者承担具体补充贡献，例如文字表述核查；不重复添加负责人，不为凑齐角色添加全员。
- 若交付本身是审核结果，审核人可以是负责人；若审核只是制作中的协作，制作人仍为负责人，必要审核人是参与者。

宽泛职责也能支持推荐，不要求逐字匹配。例如“品牌运营”可以合理承担门店活动执行清单、渠道交接；“内容制作”可以承担产品介绍文案；“项目统筹”可以承担范围整理、协调和整体交付。职责未逐项列出这些工作，不代表成员不承担。相关制作中的常规自检也不必有单独的审核岗位描述；用户要求独立审核或有明确专业资质要求时再区别处理。

优先推荐关联较强的人；多个选择都合理时，选择一位并在需要时用 summary 或 warnings 简要说明关联依据，不为这种常见选择阻塞方案或机械留空。不编造效率分数、个人经验或已取得资质。成员资料缺失、无人具有合理关联、明确排除该工作或缺少必需资质时，负责人保留 null 并说明具体缺口，不能用创建者、主管或首位成员兜底。方案中的 `ownerMemberId` 是推荐人选，不能宣称对方已接受任务。

## 估算人工投入

用户已给出的预计投入优先保留，不能用模型数字替换。需要生成估算时，以当前完成标准为范围，列出不重叠的人工工作明细，再汇总。写清使用的资料、工具或模板条件；用户未说明采用 AI 时，不假定其工作会被 AI 自动完成。

考虑交付数量和规模、专业难度、材料完整度、工具准备、协作与沟通、核验质量、修改轮次及不确定性。不要把“审核较严格”等描述直接转换为无依据的固定倍率，也不因负责人姓名不同调整个人效率。

同一明细用同一单位的乐观 O、最可能 M、悲观 P，满足 O≤M≤P，预计投入为 `(O+4M+P)/6`。例如在已知模板与资料齐全的条件下，一项人工工作 O=30、M=45、P=90 分钟，预计为 50 分钟；依据应说明该条件下包含哪些人工动作，而不是只写公式。按统一口径取整数分钟，1 人时=60 分钟，1 人天=480 分钟。

人工准备、操作、沟通、审阅、修改和核验计入；等待回复、排队和无人值守运行不计入。多人同时工作仍按各人的实际人工投入相加，不能把墙钟时间当总投入。父任务不再次计入已由叶子覆盖的工时；有独立统筹工作才另估该部分。未知或部分待估就说明缺口，不用零填满、不把已估部分声称完整总量。写入 `effortEstimate` 的分钟、工作方法和原因要相互一致。

估算依据绑定当前方案范围与标准。用户修改范围或标准后，保留其指定投入；需要重新估算时只更新被要求重算的部分，并说明依据变化。方案值不是服务端已保存的估算，也不生成保存回执。

## 三个典型请求

**单一交付。** 用户：“帮我建个新品介绍脚本任务，30秒，讲清容量和可拆洗杯盖，不拍摄、不剪辑。”生成一个脚本任务；根据已确认职责选择内容负责人。容量数字未提供则不编造。标准覆盖时长、容量说明、杯盖特点及纯脚本交付；校对通常放步骤，确需核查才添加有具体贡献的参与者。

**多个交付与分工。** 用户：“安排新品首发，需要一份介绍脚本、一张主视觉、一份门店活动执行方案，预算不超过两万元，不拍摄、不投放。”生成一个汇总任务和三个子任务；文案职责承担脚本，视觉职责承担主视觉，现场执行职责承担活动方案，统筹职责承担父任务。所有人员均须来自输入中当前可选成员；缺少其中某项能力不能把不存在的岗位当成员。整体预算标准放在父级，各子项保留对应内容要求。

**材料确认与差异日期。** 用户：“先确认商品卖点，再做官网文案和海报。文案12月20日完成，海报12月25日完成，整个发布准备12月31日完成。”在日期年份和工作区明确后，父任务汇总发布准备；卖点确认、文案、海报各自按职责安排，相关标准写明使用已确认卖点。每项生成各自日期和标准，所有 `dependsOnClientIds` 返回空数组；这里只输出带稳定临时 ID 的预览任务树，不调用创建或字段设置工具。
