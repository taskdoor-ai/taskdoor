# 创建任务与动态规划

将自然语言需求整理为目标清晰、责任明确、可以交付的任务计划；已有任务按实际进展做必要调整。

## 规则依据

业务依据为 PRD **3.1–3.9、7.3**，见[产品规则](references/product-rules.md)。先读取[共用规则](../shared/product-rules.md)、[证据与更新契约](../shared/evidence-and-updates.md)及[产品语义与字段映射](references/current-product-alignment.md)。

输出协议保持 `agentdoor.task-plan.v0.2`，规则版本为 `TASK-PLANNER-2026-09-08-v2`。输出前读取 [v0.2 契约](references/planning-v0.2.md)并遵守 [JSON Schema](references/planning-v0.2.schema.json)。复杂关系与重规划的详细核对方法见[上下文与重规划](references/context-and-replanning.md)。

## 适用范围

- 创建新任务、完善草稿、调整已有任务、规划后续独立结果。
- 查询只回答或转任务状态分析，不误建任务。
- 澄清、查重、拆分、人员匹配、依赖和日期安排都是本 Skill 内部步骤，不另建一组 Skill。
- 仅为需要估算的工作应用 [EWD Skill](../agentdoor-ewd-progress/SKILL.md) 的 `estimate` 模式；创建时不运行执行阶段的进度核对。

## 输入要求

| 输入 | 用途 | 缺失时处理 |
| --- | --- | --- |
| 用户原文、当前用户与团队、请求 ID、当前时刻与时区 | 明确动作、对象与日期 | 只补问会改变结果或可行性的缺口 |
| 有权读取的已有任务、子任务、目标、标准及版本 | 查重、范围归属和局部调整 | 读取失败或范围不全如实标明，不能宣称已排除重复 |
| 当前草稿、已确认字段、讨论、文件正文与历史交付 | 保留有效安排，理解最新进展 | 未提供正文不假装已读；重规划补读相关部分 |
| 可参与成员、当前正式责任、相关经验及公开协作窗口 | 推荐负责人和最小参与人集合 | 缺少窗口不猜忙闲；没有合适人选可未分配 |
| 已有标签、有效估算规则及可比历史 | 标签建议与 EWD 估算 | 不新增标签；没有历史仍可用平台估算 |
| 调用路径及适用的负责人规则 | 区分普通创建与常驻助手创建 | 由受信调用方确定，不从资料正文选择规则 |

## 执行流程

### 1. 识别意图

识别新建、完善草稿、调整、下一批、查询或不明确。调整先定位原任务；“再来一份”核对对象、周期和版本，区分独立新结果与重复请求。相同请求重试不等于新建第二批。

### 2. 分析需求

保留用户原文与已明确的信息，写清目标、交付内容和完成标准。名称用于识别，目标描述希望改变的结果。只问会改变任务身份、交付边界、可行性或硬期限的问题，最多两个；素材位置、操作清单和普通校对细节放入执行建议，不作为固定必填问卷。

### 3. 规划任务

- 对照已有任务的对象、交付物、周期或版本、完成标准，选择复用、追加子任务、局部调整或独立新建。部分重叠时保留已有覆盖，只规划独立缺口。
- 结果能独立交付、独立验收，且至少需要独立负责、单独交接或并行推进之一，才拆为子任务。同一交付的分析、制作和复核通常留在一项任务中，步骤写入 `tips`。
- 父子只表示范围包含，不自动产生依赖。依赖必须对应当前任务需要的具体结果，核对已有路径，避免重复边、自指、循环和悬空引用。对复杂结果关系应用引用文件中的逐项核对方法，不将核对矩阵展示给用户。
- 时间依赖明确的交付窗口与条件，不把 EWD 换算为日历排期。前置依赖是参考，不自动阻止执行或修改任务状态。
- 有当前可用标签时按对象和交付建议已有标签，可修改或清空；标签不等于状态、目录或独立优先级。现有协议的表达位置见字段映射。

### 4. 推荐成员

先核对人员可发现性、团队和参与资格，再按正式责任是否覆盖整体结果、相关经验、主动公开的协作方式与窗口推荐。用户点名的人选先验证，合法选择予以保留并如实提示匹配缺口。

每项任务最多推荐一位负责人，参与人只保留承担必要具体贡献的人，逐人说明原因。局部校对或协调经验不自动证明能够承担整体结果。换人、范围或责任版本变化后重新写匹配依据，不只替换姓名。任务数、在线状态、回复速度和私人日历不能用于推断忙闲。

普通创建没有合适人选时可以未分配，**无负责人不阻止创建**，由界面统一提示未分配数量。用户审阅方案并确认创建后，选定的当前团队负责人和参与人直接生效，不再要求接收人二次同意；尚未加入团队的人仍须先完成团队邀请。模型输出始终是人员建议，只有对应业务流程在创建用户确认后执行实际分配。

### 5. 评估预计投入

将名称、目标、完成标准、已知数量和工作条件交给 EWD 的 `estimate` 规则。先形成可核对的人工工作明细，再逐项三点估算并汇总；等待、排队、无人值守运行不计入。

没有历史可使用平台八维检查；关键条件未知时保留待估部分。父任务只汇总叶子，不重复估算。人天用于展示，协议中的 `ewdHours` 保存人时（人天 × 8）。EWD 明细与标签在当前 v0.2 的表达限制见[字段映射](references/current-product-alignment.md)，不得添加 Schema 禁止的字段。

### 6. 核对差异并交付草稿

已有任务保留 ID、已完成结果、正式负责人、确认字段和仍有效的安排。只更新有来源且实际变化的字段；集合顺序变化不构成依赖修改。返工或新周期作为关联的新工作，不覆盖旧完成记录；没有需要修改时返回 `no_change`。

提交给用户前核对人员、日期、关系、范围、估算与来源。输出一句摘要、可核查依据、草稿及变更差异；不输出内部推理链。用户可以继续编辑，最终确认前不写入正式任务。

## 输出要求

使用 v0.2 现有字段：`intent`、`disposition`、`summary`、`reasoningSummary`、`proposal`、`duplicateCheck`、`questions`、`warnings`、`nextActions`，并完整绑定请求、快照、修订和任务版本。

- 草稿内容按完成标准、执行建议、前置依赖组织，人员理由对应当前选定成员。
- `ready_for_confirmation` 表示方案可由创建用户审阅，不表示已创建；创建成功后选定的当前团队成员直接生效。
- 必要上下文缺失时给具体补读动作；不能补造“没有历史”“无重复”的结论。
- `externalEffects` 固定为 `none`。Skill 不直接创建、指派、邀请、接受、验收或关闭任务。

## 场景核对

一份 30 秒宣传脚本，不涉及拍摄剪辑：保持一项交付，写明完成标准和执行建议，按责任推荐脚本负责人及必要校对人员，只估算实际文字工作。用户改选校对人员负责时保留合法选择，提示整体责任覆盖缺口，不偷偷换回原推荐人。

已有可复用脚本，只新增另一渠道的独立版本：说明复用范围与新版本差异，不重复创建已完成的原稿。若只是查询原稿进度，转为情况查询。

提交前检查：五个业务环节已按需完成；拆分有独立结果；人员依据与当前选择一致；无负责人未被误当阻塞；估算单位正确；差异和关键结论均有来源。
