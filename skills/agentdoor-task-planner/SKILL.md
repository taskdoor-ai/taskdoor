# AgentDoor 任务创建与动态规划 Skill

把用户想达成的结果与团队正在做的工作接起来：判断应新建、复用、局部调整，还是继续下一批工作。输出有依据的候选计划，不直接创建、指派、邀请、验收或运行任务。既能供 agent 执行，也可由未来解析服务加载。

## 先读取

先读 [当前产品规则](references/product-rules.md)、[当前产品语义与字段映射](references/current-product-alignment.md) 和 [证据与更新契约](../shared/evidence-and-updates.md)。产品规则版本 `TASK-PLANNER-2026-09-03-v1`，输出仍为 `agentdoor.task-plan.v0.2`；规则版本由调用方保存，不增添旧 Schema 不允许的字段。

执行前读 [v0.2 输入输出与判断契约](references/planning-v0.2.md)，输出遵守 [v0.2 JSON Schema](references/planning-v0.2.schema.json)。涉及既有任务、重复候选或讨论时，再读 [上下文判断与重规划](references/context-and-replanning.md)。设计界面或接入服务时读 [呈现与接入](references/presentation-and-integration.md)。

[v0.1 契约](references/contract.md)、原 Schema 与三个 examples 保留用于旧接口迁移和回归，不把两种版本混装。行业测试资料在 [行业场景说明](evals/industry-scenarios.md)；只有对应合成场景可以使用其中的成员、时间与任务，不把模板灌进真实用户上下文。

本次升级是可执行的规划指令、合成案例与离线验证，不是生产接入。当前 React 创建仍只有五个明确 Mock 场景与有限局部调整，最终确认仅写入当前浏览器；真实模型、服务端 ACL、历史检索与版本化提交尚未接入本协议。截图的“已实现”不构成这些能力的验证。不要修改正式 Owner／验收语义或恢复隐藏入口。

## 执行顺序

1. **明确本轮动作。** 识别 create／refine／replan／next_batch／query／unclear。查询不误建；“再来一份”先判断新周期、新对象还是重复提交。需要读取的资料缺失时请求具体上下文，不拿行业模板假装历史。
2. **先核对现有事实。** 只读授权快照：任务与多层子任务、状态和交付证据、文件目录及已读取节选、人工确认字段、讨论线程、相关历史及成员职责。文件名、目录元数据或“已上传”状态不等于正文已核对；判断使用文件内容时引用对应版本的 sourceRef。区分正式字段、已确认决策、发言人的报告和未接受提议；较新的发言不自动覆盖既有确认，状态与讨论冲突保留并提出核对，不自行裁定。凡文件正文或讨论冲突直接支撑 disposition、阻塞判断，或“不能视为完成／批准”的关键边界，必须在 reasoningSummary 的 evidenceRefs 中显式引用该来源；凡安全、隐私、合规、权限或最小披露边界实际限制了候选范围，也引用输入中对应的正式边界来源，不能只写一句通用免责声明。warning 只陈述风险，不能作为唯一证据承载位置。检索未查、失败、截断不等于没有历史或没有重复。
3. **确定最小交付范围。** 目的描述希望改变的状态，注明明确要求或推断，不新增 KPI／预算。轻任务只建一个 Task，把操作步骤放 tips；复杂任务按可独立核对的结果拆分，每项有明确标准。多人参与、翻译、复核或先后步骤本身不构成拆分理由；若它们共同完成同一份交付，且复核只是该交付的常规检查，就留在同一 Task 的贡献、tips 和完成标准里。只有结果能独立交付、验收，且需单独负责、交接或并行时才拆分；仅可复用不是拆分依据。缺少某类成员只形成责任缺口或问题，不靠创建占位子任务解决。子任务继承主目的，父子不是默认依赖。
4. **建议责任与协作。** 显式指定者先校验；否则按职责与相关证据推荐唯一候选 Owner，允许 null。Owner 的职责证据必须覆盖整项结果的责任边界；只适合版本管理、协调、翻译或复核其中一部分的人保留为参与贡献，不能因为“总得有个人”就提升为整项 Owner。没有人覆盖完整结果时用 `unassigned`／null 并说明缺口。参与者只列不可缺的贡献，不能把全团队塞进每个任务。Creator 不自动负责；主管不自动执行全部工作。容量缺失说未知，不从任务数、在线或消息量推断闲忙；新候选不等于已接受。
5. **先冻结关系算法，再检查时间与投入。** 查重按业务对象、交付物、周期／版本和完成标准判断；请求重试先核对 requestId 与既有结果。父子只表达范围，不自动产生依赖。涉及既有任务时，起草任何候选字段前必须按 [上下文判断与重规划](references/context-and-replanning.md) 完成以下六步，不能边写候选边补理由：

   1. **拆结果并计数。** 对每个语法作用域列原子结果集合 `Rᵢ` 与消费者集合 `Cᵢ`；`Cᵢ` 除用户点名对象外，也包括现有标准、消费者专属正文、受信决定，或共享交付物正文与审核标准共同证明会直接消费**同一原子结果**的任务。隐式纳入前先过同结果门：“批准数字／必要证据／保持待决／可追溯／版本一致”等泛称、父子关系、裸 sourceRef、linkedTaskIds、草稿尚未纳入新事实或仅处于下游，都只说明相关，不建立覆盖。`Rᵢ` 不是用户表层名词数：逐个表层结果检查输入中是否已有任务生产“当前对象／版本的适用性、范围、批次要求或批准结论”；若消费该表层结果必须先知道这项结论，就把它连同原始规则、实际实例／回执／核对状态拆成独立结果并留在同一作用域。尤其把“承诺／预计／已提交”和“实际收到／生效／完成／核对通过”分开。计算 `expected = Σ(|Rᵢ| × |Cᵢ|) − 明确排除数`。冻结矩阵以 `(consumerId,resultId)` 为唯一键，实际行数必须等于 expected，重复数与未分类数必须为 0，否则不得起草候选。批量点名建立“需要该结果”的覆盖，不直接指定图路径。
   2. **锁定生产者。** 为每个 resultId 只用输入建立 `resultType／producerKind／producerId／evidenceRefs`。对每项被使用的规则、参数或文件固定分列 `authorityValue／applicabilityDecision／instanceState`：原始来源只生产权威值；若现有任务标准记录当前对象／版本的适用范围、批次要求或批准边界，该任务生产 applicabilityDecision；收件／核对任务只生产实际实例状态。输入正文准确点名某消费者把该规则用于当前对象时，该消费者也需要 applicabilityDecision；不能用原始规则 source_only 或另一任务的 instanceState 代替。生产者的现有标准必须生成消费者等待的**同一个原子结果**；仅使用同一来源、字段或业务对象不算。现有任务标准负责形成范围、批准、验收或核对状态时，该任务是生产者；已完成或被要求“不重开”只约束修改动作，不会让它失去生产者身份。外部上传状态只提供原始事实，不能替代团队核对结论。任务生产者为 0 或多于 1 时先补读、拆结果或提阻塞问题。候选新文字不能扩张生产者结果、创造生产者或独立复核职责。
   3. **逐对选路径。** 必须逐 `(consumerId,resultId)` 判定，并在“现有图 + 本轮全部候选边”上重新收敛。权威原始事实且没有同结果的任务加工结果为 source_only；只要求索引／引用／附上外部原始文件时也不改依赖。任务结果若有输入证明的最近中间交付路径则为 transitive；否则覆盖已成立的消费者直接依赖锁定生产者，分类为 direct，不要求原文另写“直接”。本轮因结果 A 建立的 `consumer → middle` 边只能证明 A 的路径，不能自动证明 middle 也承载其其他上游结果 B；只有消费者自身标准、专属正文或受信讨论明确消费 middle 的整项组合交付时，才展开其全部已证实上游结果。输入若准确点名该消费者需要某任务生产的适用性、范围、批次或批准结论，而没有**同一结果**的专属中间路径，该行必须 direct。消费者自身生产该结果时不自依赖；无覆盖证据或输入明确排除才是 unrelated。已有核对／聚合任务若只核对当前直接前置、版本一致性、批准缺口或“上游事项保持待决”，共同源头仍为 transitive 或 source_only；只有标准明确审核生产任务形成的同一结果，或共享交付物正文与审核标准共同锁定该结果，才 direct。消费者专属证据优先于泛称、linkedTaskIds 和裸 sourceRef。
   4. **做依赖差分。** 对每个消费者取全部 direct producers 的并集，满足 `final = old ∪ requiredDirectProducers − obsoleteProducers`。逐行做防漏与防冗余反事实。旧边默认仍代表独立消费；只有输入来源明确说旧结果已被取代或消费者不再需要，才能列入 obsoleteProducers。新增中间任务或矩阵改判本身不是删边证据。
   5. **检查合并图与日期。** 在“现有快照 + 候选”图上检查跨分支路径、循环、全部直接依赖和祖先。前置交付不得晚于消费者窗口，候选 dueOn 不得晚于未同步调整的祖先 dueOn；recommended 日期不能机械平移，原日期仍可行时只修关系。
   6. **检查投入边界。** 调用 [EWD Skill](../agentdoor-ewd-progress/SKILL.md) 的 estimate 模式，先生成可核对的任务 EWD 拆分明细，再按有效团队规则或平台八维明细检查与三点估算；无历史仍可使用平台规则，范围不清的部分保持 unknown。EWD 只算人类投入，等待、排队和外部审批历时不计入，不从任务数、在线状态或默认每日工时推断排程。
6. **只提出必要差异。** 重规划保持原 ID、已完成结果、正式 Owner 和确认字段；新需求用新增／局部更新候选，完成后返工是关联的新工作，不覆盖旧完成记录。部分重叠且新增边界已明确时，引用既有覆盖，用契约中的 resolution 把独立缺口绑定到新增操作；不因找到旧任务就丢弃新需求，也不改称“不同实例”绕过查重。“下一批”以已完成产出和明确后续缺口为起点，已有进行中工作直接复用。先在合并后的依赖图上检查现有传递链；未改任务已能通过现有链或本轮新增的中间边消费新结果，且目标、标准、日期仍准确时保持不变，不为展示影响重复改写下游标准或添加冗余依赖。影响闭包不等于 update 集合：source_only、已有／本轮形成的 transitive 行和 unrelated 行不因“受到影响”获得更新资格；只有最终字段相对快照确实变化的 direct 缺口或其他有来源的字段差异才能更新。每个 update 先过资格门：输入必须证明目标、结果定义、验收边界、日期或依赖中的至少一项确实不同；出现新事实、状态变化、成为生产者、被称为“消费者”或新增交接关系，本身都不授权改写已经充分表达同一结果、等待条件或确认边界的标准。输出前将每个 update 与输入快照逐字段比较，dependsOnTaskIds 按无序集合比较；删除等价字段，fields 为空则删除该 update 并将任务列入 preservedTaskIds。没有需要改的内容输出 no_change，拒绝为了展示 AI 动作制造变更。
7. **输出可决策结果。** 一句摘要、最多四条可核查依据、结构化差异与可执行下一步。输出前做“决定性主张 → 输入来源”证据闭包：每个变更字段、保持不变的硬期限、真实等待、被拒绝／撤回方案、完成／批准冲突，以及实际限制范围的安全、隐私或合规边界，都至少在 reasoningSummary 或相关 change 中显式引用一个正式任务、权威来源或完成历史。凡以“已完成／已发布／不受影响／不重开”保留某基线，也必须引用基线证据；baseTaskVersions、preservedTaskIds 和无 evidenceRefs 的 warning 不算证据。最多问两个会改变任务身份、结果边界、可行性、安全性或硬期限的阻塞问题；执行者可在任务内发现或补齐的素材位置、操作清单和普通校对细节，不阻塞候选审阅，写进 tips 或完成标准。其余未知留在相应字段与说明中。不输出内部思维链、伪造工具调用或演示百分比。计划可审阅不等于已创建；新一轮仍保留用户原文与已确认内容。

### 重规划提交前的影响清单

这四项只用于核对，不输出为思维链；算法细节不在这里重复：

1. **计数门：**逐语法作用域记录 `Rᵢ、Cᵢ、明确排除、expected`；矩阵唯一行数等于 expected，重复与未分类均为 0。
2. **生产者与路径门：**每个 resultId 的生产者锁表完整；每个 `(consumerId,resultId)` 恰有 direct／transitive／source_only／unrelated 之一及输入证据；批量覆盖已成立且有唯一任务生产者、又无中间路径的行必须是 direct。
3. **差分与可行性门：**每个 update 写 `taskId／字段／快照值／目标值／来源`；依赖满足集合公式，合并图无环，全部直接依赖与祖先日期可行；等价值和空 update 删除并改为 preserved。
4. **证据闭包门：**硬期限、真实等待、冲突、被拒绝方案、安全边界和被保留的完成基线都有显式 evidenceRefs。更新依赖时，每条仍保留的已完成旧前置至少引用该任务、正式交付物或完成历史之一；一句“不重开／不受影响”同时点名多项基线时逐项闭包，不能用其中一项的证据代替其余项。外部承诺不冒充团队核对结论，warning、dependsOnTaskIds 与 preservedTaskIds 本身不能代替证据。

最后枚举状态冲突表 `conflictPairs = 非正式完成／关闭／批准主张 × 正式任务状态／确认字段／签发证据`。凡影响本轮变更、保留或 disposition 的每一对，都必须映射到一条 reasoningSummary，且该条同时引用冲突两侧；映射数少于应处理的冲突数时不得输出。完成这一步后再做逐字段差分并输出。

## 常见偏差纠正

| 偏差 | 正确处理 |
| --- | --- |
| “发起人就是最稳妥负责人” | 依据明确指定或职责推荐，不以创建者身份替代判断 |
| “加一个子任务比较完整” | 与主任务相同的单子任务删去；操作步骤变成 Tips |
| “多人参与就按角色拆任务” | 先看是否产生可独立交接的结果；同一交付的翻译、复核和协作写入一项任务 |
| “局部贡献者最适合当整个任务 Owner” | 只有职责覆盖整项结果才推荐 Owner；版本、协调或单环节贡献保留为参与者，必要时 Owner 留空 |
| “细节没列全就不能给草稿” | 只有影响身份、结果边界或可行性的缺口才阻塞；执行中可核对的细节留在任务内 |
| “没有查到就是没有重复” | 先看服务状态、ACL 和覆盖范围 |
| “历史没提供就是没有同类历史” | 只说本次快照未读取或未提供可用历史；不能推断企业内不存在同类记录 |
| “有人选、日期就可自动创建” | 只输出草稿；确认、接受、提交由独立流程处理 |
| “心跳中断所以任务停滞” | 只报告数据过期，不推断人的投入和任务停滞 |

## 验证与交付边界

用 `scripts/validate_plan.py --input input.json --output output.json` 验证 v0.2 输出。该脚本离线检查结构、来源引用、ID、版本、受保护任务与依赖，不是生产 ACL 或真实语义判定器。高密度合成数据另用 `scripts/validate_realistic_data.py` 检查团队、任务树、文件、讨论、历史、依赖图与评分证据的引用完整性。行业 case 输入和期望分开；独立 agent 先读 Skill 与输入并生成输出，之后才评分，不能用参考答案回填声称模型通过。

服务端仍须独立校验身份／ACL、当前版本、确认绑定、依赖 DAG、成员有效性、提交幂等和原子事务；Skill 的 `ready_for_confirmation`、`externalEffects` 或文字声称不能授权写入。真实读取、模型质量、写回及用户闭环分别验收，不把合成案例通过率宣传为生产准确率。
