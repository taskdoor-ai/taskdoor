# 任务创建与动态规划 Skill：设计及离线试跑

2026-09-01。已将原规划 Skill 升级为 v0.2，并构建 **6 个行业团队、36 名成员、24 个业务案例**。数据来自公开流程启发下的合成情境，不是真实企业或个人记录。

本次实际运行了独立 Codex agent；当前页面仍是 Mock，未连接生产模型、真实团队数据或任务写入服务。离线规划可执行与产品已经接入，是两件分别验收的事。

## 实际结果

首轮由3位无上下文继承的独立执行 agent 分别处理8例；每例只看执行指令与输入，不看期望、校验器或评分意见。每组内连续处理8例，并非24次完全独立模型上下文。随后由其他 agent 作语义复核，主 agent 核对关键问题；**没有行业用户或人工标注员参与**。

| 轮次 | 样本 | 结构及机器断言 | 独立 agent 语义复核 |
| --- | --- | --- | --- |
| 首轮原始结果 | 全24例；无缺失 | 24/24 | 23满足、1不满足、0未知 |
| 窄修后重测 | SAAS-03、ECOM-03、CONTENT-03 | 3/3 | 3满足、0不满足、0未知 |

首轮原始证据：[输入及输出](runs/2026-09-01-first/manifest.json)、[结构报告](runs/2026-09-01-first/structural-report.json)、[逐例语义汇总](runs/2026-09-01-first/semantic-summary.json)、[执行环境](runs/2026-09-01-first/execution-metadata.json)。每份输出及每条输入均校对原始 SHA-256；首次失败未删除、未修补后替换。

重测证据：[所选案例与版本](runs/2026-09-01-retest/manifest.json)、[结构报告](runs/2026-09-01-retest/structural-report.json)、[独立语义评审](runs/2026-09-01-retest/semantic-review.json)。重测输入与首轮完全相同，由新的执行及评审agent分别处理；这是3例定向回归，没有重跑其余21例，不能把首轮结果改写成24/24语义通过。

这些数字描述本次有目的挑选的案例，不是产品准确率或行业泛化指标。真实模型快照、温度和随机种子未提供；脚本运行环境为 macOS arm64、Python 3.12.0、jsonschema 4.26.0。实际调用的是会话内 agent，不是应用中的 AI 接口。

### 首轮发现：只新增任务还不够

[SAAS-03 首次输出](runs/2026-09-01-first/outputs/SAAS-03.json)没有重做已完成迁移，也保留了负责人和12条已确认UAT标准，但新增字段核对的截止日建议为9月12日。它又要求现有9月9日UAT和9月10日培训使用这份新结果，既未调整相关依赖／交付边界，也没有问清是否确实影响它们，仍标为可确认。

它通过了结构校验，却没有形成可用的衔接方案。因此补强三条通用规则：

1. 新增／改变产出时，检查哪些已有未完成任务要使用它。
2. 若是必要输入，一并协调受影响任务的依赖和交付边界；不能只写在执行建议中。
3. 影响关系不明确时，只问具体阻塞问题；不机械顺延全部任务，也不把主期限复制给所有前置项。

原版指令已保存在 [首轮协议快照](runs/2026-09-01-first/protocol-snapshot.json)。重测使用相同输入和新的独立执行 agent，并加入“第二批复用已有产出”“局部受众变更”两个对照，避免只修好一个案例。

重测中，[SAAS-03](runs/2026-09-01-retest/outputs/SAAS-03.json)保留已完成及确认内容，将新增核对的日期留空，明确询问是否为UAT／培训必要前置以及相应窗口，状态为需澄清。另两例保持可审阅：[ECOM-03](runs/2026-09-01-retest/outputs/ECOM-03.json)只建第二批独立后续根及三个必要结果；[CONTENT-03](runs/2026-09-01-retest/outputs/CONTENT-03.json)局部更新主交付标准、文案和渠道适配，未重建已完成任务。修订没有让这两类已有充分依据的局部规划一律变成补问。

### 同时纠正了一处评分误锁

旧评分把“保留培训任务”编码成该任务完全不可更新。但输入只锁定了负责人和UAT标准；培训还未完成，其期限与依赖未锁。正确的局部重规划应能保留原ID而调整必要字段。

经独立复核，只移除这项过强限制，保留禁止重建、完成记录和确认字段保护，并增加人工复核项。见 [勘误记录](runs/2026-09-01-first/grading-erratum.json) 与 [当时评分快照](runs/2026-09-01-first/expectations-snapshot.json)。**这不改变首轮失败结论**：首次答案本来就通过旧评分，失败来自它未处理业务衔接。

## 用户应该看到什么

不用向用户展示24个测试标签或整份JSON。同一任务页面上，左侧保留任务列表；右侧最新生成过程可展开依据，“AI 帮你改”保留一个入口，继续接收需求。结果区显示一句结论、必要候选差异和下一动作。

下面是依据实际试跑结果整理的**呈现建议文案**，不是已经实现的新界面：

| 真实情况 | 默认呈现 | 展开后与下一动作 |
| --- | --- | --- |
| 五处错字修改 | “只需1项任务，由已指定的颜北负责。” | 显示修改边界与完成标准；不拆策划、设计或投放子任务。 |
| 同一首发重复提交 | “这项首发准备已在推进，建议继续原任务。” | 列SKU、渠道、周期和已有记录，提供“查看已有任务”；不再创建一套。 |
| 第二批沿用旧素材 | “沿用已确认图片，只补第二批包装、库存与页面核对。” | 展示可复用版本和本轮新增范围；旧批次完成记录不变。 |
| 客户改变受众 | “保留已审图片，仅调整文案和渠道适配。” | 原任务卡上显示标准前后差异及客户确认来源，不重复整棵树。 |
| 前置晚于硬期限 | “当前条件下，原交付安排存在冲突。” | 并列真实窗口与期限，只问日期／范围的必要取舍；不自动承诺加班或换人。 |
| 查重失败或无权限 | “还未核对完整的已有工作。” | 说明缺哪个范围、可重试什么；不会说“没有重复”，也不展示无权信息。 |

每个步骤展示可核查的来源摘要、版本与缺口，不展示内部思维链。时间和投入缺依据时保留未知；已有完整事实可以读到，就不要求用户再次填写。细节见 [状态与动作表](../references/presentation-and-integration.md#2-复用现有页面呈现决策而非增加流程页面)。

## 验证范围与剩余工作

本轮检查 Skill 格式、JSON Schema、来源引用、版本、成员与候选范围、完成／确认字段保护、依赖图，以及每例业务语义。验证器11项测试、评测工具10项测试全部通过；旧 v0.1 的4项测试通过，覆盖三个例子及13种非法变异。Skill格式检查通过。

另在临时副本中重查首轮24例：仍全部通过结构检查，报告如实显示Skill和契约已变化、Schema未变，并继续使用首轮原始期望。归档中首轮118处及重测77处语义证据指针已通过路径映射核对，原始报告未覆盖。

尚未验证：真实服务身份与ACL、真实历史检索召回与分页、实际模型延迟、多轮连续会话、并发创建与幂等事务、成员接受、生产回写、真实用户提效。24例也未覆盖所有行业、语言及任意任务输入；查询和无变化等协议分支还需追加独立业务试跑。

后续接入应分别验收“授权读取 → 候选规划 → 用户确认精确差异 → 服务端重验版本并提交”。重复任务的语义判断不能替代写入幂等，模型建议不能替代正式责任接受。当前工作没有改变这些产品边界。
