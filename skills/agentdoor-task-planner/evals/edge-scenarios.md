# 任务规划边缘案例集

整理日期：2026-09-01。共 16 个独立案例，ID 为 `EDGE-01` 至 `EDGE-16`，补充六行业原料中的意图、身份、时间、责任与对抗边界。

**全部业务数据均为合成。** 团队与稳定成员 ID 复用 `industry-fixtures.json` 的 6 个团队、36 名成员；不访问真实业务，不调用外部 API，不创建、指派、通知、邀请、发布、验收或启用循环任务。本文件只说明测试原料和使用边界，不报告输出、通过率或生产能力。

## 文件分工

- [edge-fixtures.json](edge-fixtures.json)：来源目录、原有合成团队及 16 个原始输入。`scenarios[].input` 不含预期计划、标准答案或评分项。
- [edge-expectations.json](edge-expectations.json)：独立的可接受意图、状态范围、保护对象、必需证据与人工语义检查项。只供评估侧读取，不能发给被测规划模型。
- 本文件：案例索引、装配规则和契约边界。盲跑时不把本文件当作模型输入。

两个 JSON 沿用行业集的 `sources / teams / scenarios` 和 `globalAssertions / expectations` 结构；分别使用 `agentdoor.edge-fixtures.v1` 与 `agentdoor.edge-expectations.v1` 标识本组原料。它们不是运行时接口，也不修改旧行业夹具或任何已冻结运行。

## 输入装配与保真

1. 每次只取一个 `scenario.input` 的深拷贝。默认按该案例的 `teamId` 从 `teams` 注入成员，前提是 `acl.status=verified` 且该团队同时在 ACL 与授权团队列表中。保留输入本身已有的 `members`，不能覆盖 EDGE-11 的目录快照。
2. `teams` 和 `sources` 从现有行业集逐项复用。来源目录记录的是行业集原核对结果；本轮没有重新联网核对，也不把官方页面当成合成业务决定、人员能力或客户确认的证据。
3. 每案都有稳定请求 ID、候选 revision、快照 ID、截至时间、ACL 与四类读取覆盖。Task 记录具有稳定 ID、父子关系、状态、版本、更新时间、正式 Owner 和来源；本组新增来源与讨论也保留版本及出处。
4. 任务、讨论、历史和其他来源只包含本案相关快照。`coverage=complete` 的空集合表示此范围确实为空；不把其他案例的历史补入当前输入。查重匹配必须指向本次可见任务。
5. EDGE-11 的共享团队没有改名。只有该案 `input.members` 中 `content-m3`、`content-m5` 的显示名变成“阿宁”，并追加目录 v2 证据及原姓名映射。两人的稳定 ID、职责、边界与原记录保持。目的是测试显示名不能替代唯一 ID，并非新增两名真实成员。
6. EDGE-13 的 `timezone=null`、UTC 时钟和原期限文字必须保留。旧成员窗口不是当前日期的排期依据。EDGE-14 的非法日期以原始文字保留，不能在送给模型前默默纠正。
7. EDGE-15 的旧 `estimate.ewdHours=72` 是有明确来源的历史导入错误；它与“预计总历时”的来源原文冲突，正是要检测的输入事实。不要预先修掉旧记录或替模型推导纯人时。
8. EDGE-16 中的不可见证据与外部成员 ID 都是合成占位字符串，未附真实隐藏资料。引用这些字符串的讨论自身可见且可引用；字符串所指对象并没有因此进入授权证据集合。

## 评估方式

准备一份新的冻结运行，保存本组夹具、期望、Skill、契约、Schema 和校验器版本；不得覆写旧行业运行。将模型输入与评估期望放在不同位置，独立执行者只读取 Skill、契约和被分配案例的装配输入。生成输出后才运行结构检查和独立语义复核，不用预期检查项回填答案。

`requiredEvidenceRefs` 要求引用本轮决策不可忽略的事实来源，不要求固定句子。标题禁建项只用于本来不应再次创建的既有结果；同名但不同实例不能只因标题一样判错。机器检查覆盖结构、ID、版本与确定性约束，人工检查覆盖是否抓住主意图、是否保留最小可用候选、是否误用人员与期限，以及重复关系理由是否成立。

本组包含应路由、应不变更、必须澄清和能够给出候选的情境。不能靠所有案例都返回一句“信息不足”通过：例如混合请求中的明确主创建意图、新周期一次性任务、已允许人选留空的草稿，以及合法范围明确的对抗输入，都保留了实际规划空间。

## 发现的契约边界

以下来自整理时读取的 v0.2 契约，不在本次文件中修改 Skill、Schema 或校验器。后续若修订协议，应另存运行版本并复核期望，不能重写旧输出宣称原版本通过。

- **已解决的部分重叠。** EDGE-07 的用户与来源已明确已有覆盖、新增缺口和不受影响的后续任务。整理原料时发现原输出只有重复关系，没有表达“重叠已按范围消解”的字段。此缺口在本组首次盲跑前通过可选 `overlap.resolution` 补齐，冻结协议明确新增范围、对应 create 操作和既有覆盖证据。旧协议及首轮输出仍保留；本案不接受为了过检把同一实例伪装成不同客户或周期，也不要求旧 FAQ／培训重做。
- **混合意图只有一个主分类。** EDGE-05 可将创建作为本轮主意图，并把附带查询结论放入摘要、依据和已有任务入口；当前结构没有独立的次意图或结构化查询答复。评估应看实际行为是否覆盖明确主请求，不能要求新造 Schema 字段。
- **精确时刻的表达。** EDGE-13 的相对日期需要先明确时区；即使后续用户补足“收工”的钟点，当前 `schedule` 仍只有 `startOn/dueOn` 日期，没有精确时间字段。应保留原文字与待确认项，不伪装为协议已支持时刻级承诺。
- **专业参与者缺口。** EDGE-12 的已知成员候选数组只能列出有 ID 的人，未配备的翻译/复核贡献只能写进 warnings、理由或完成标准。候选 Owner 可为 null 是当前契约明确允许的可审阅状态，不能与可提交的正式责任条件混淆。
- **重试回执仅作输入事实。** EDGE-09 可通过真实可见来源理解旧回执并路由到已存在任务，但输出没有事务回执类型。本例不模拟提交幂等、竞争请求或数据库唯一约束，只检查模型不要将重送解释成新批次。

本文件不把上述边界视为新增产品能力，也不改变现行创建入口、正式 Owner、验收、循环任务、ACL 或写回限制。
