# 高拟真合成协作场景

这组案例用于验证任务创建与动态规划 Skill 在“已有工作很多、资料互相影响、用户只要最小差异”的情况下是否仍能做出可审阅计划。所有企业、姓名、客户、文件、任务、讨论和历史均为合成资料，不来自生产，也不代表任何真实组织。

## 数据规模

- 12 个行业场景、12 支团队、88 名可指派成员、5 名不可指派的外部发言人。
- 179 个已有任务；每案 13–16 个任务，均有 4 层父子树；合计 106 条产出依赖，包含跨分支依赖且图无环。
- 84 个版本化文件目录项，每项含 MIME、版本、状态、64 位合成 checksum、关联任务和来源；同 ID `sourceRefs` 只提供本次决策需要的正文节选。
- 105 条讨论，覆盖 decision／proposal／report／question、线程回复、撤回提议、状态与报告冲突；68 条历史事件。
- 历史读取同时覆盖三种语义：10 案完整丰富历史、1 案完整查询且确实为空、1 案分页只读到部分历史。
- 39 个人工确认字段和 35 个已授权查重候选，用于检查“保持不变”、重复创建、不同实例和部分重叠。

## 真实性如何表达

团队成员不是姓名列表。每名成员都有角色、职责、责任边界、职责证据和可用窗口；外部客户、审计、候选人、物业和业主使用 `context.stakeholders`，明确 `assignable:false`，只能解释讨论作者，不能成为 Owner 或 Participant 候选。

任务同时表达父子归属和产出依赖。父子关系不自动产生依赖；只有下游消费上游交付时才写 `dependsOnTaskIds`。场景包含完成、进行中、阻塞和开放状态，也包含已完成工作依赖旧版本、文件已上传但尚未批准、口头承诺与正式回执不同等常见脏状态。

文件目录不冒充正文读取。目录项说明版本、状态和任务关联；只有同 ID 的最小 `sourceRef` 节选可以被计划引用。讨论保留 threadId/replyToId、作者、时间、kind、authority 和 state，能区分提议、报告、确认与撤回。历史覆盖完成、阻塞、版本变更、期限确认和证据关联；完整空集与未读到历史分开。

## 验证方法与边界

先运行 `scripts/validate_realistic_data.py` 检查数据密度、外键、文件配对、回复线程、父子树和依赖 DAG，再用 `evaluate.py prepare --suite realistic` 冻结输入、协议和评分哈希。盲测执行者只读 Skill、契约和分配到的输入；首次输出原样保留。机器评分只判断结构、允许动作、受保护对象、必要依赖和来源，随后由不同执行者逐案复核业务语义。

该套件没有真实二进制附件、生产 ACL、分页服务、并发写入、任务提交、通知或真实行业用户。它可以证明离线规划协议在这些合成输入上的表现，不能证明生产准确率、安全性或写入可靠性。
