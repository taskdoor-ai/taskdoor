# TaskDoor PRD 更新规则

目标是让不同对话都维护同一份可追溯 PRD：Markdown 是唯一内容源，当前事实有证据，语义变更有日志，历史版本可保留。

## 1. 先定位唯一内容源

1. 当前检出包含 `docs/prd/README.md` 时，以当前检出为 PRD 根目录。
2. 否则使用仓库根目录下的 `.worktrees/full-product-prd`；其内必须存在 `docs/prd/README.md`。
3. 两处都不存在时停止修改，报告缺少正式 PRD 内容源。不得只改 `public/prd/` 或另建一套 PRD。

进入 PRD 根目录后，先完整读取 `docs/prd/README.md`，再读取目标模块及与本次事实有关的 `source-map.md`、`current-implementation-matrix.md`。跨对话摘要按 `docs/prd/INTAKE.md` 核验，不能直接覆盖正式需求。

## 2. 区分事实和目标

- 当前 MVP：必须由当前代码、测试或真实运行页面支撑，并写入来源映射或实现矩阵。
- 已确认目标：正式模块直接说明产品如何工作；尚未实现的差异仅在实现矩阵中登记，不能用界面示例证明能力已实现。
- 待确认或设想：保留在交接／审计材料中，不写成正式产品能力。
- 已移除能力：从当前设计中删除；如相对已发布 PRD 发生语义变化，仍需记录变更日志。

工作区之间不可见的未提交代码不能靠猜测补齐。需要当前实现证据时，回到摘要指定的代码基线核验。

## 3. 更新正文

每个模块只固定四个一级区块：

1. 目的
2. 范围和边界
3. 详细功能设计
4. 功能验收标准

按功能说明核心用途、用户能做什么及操作结果。优先用一小段讲清，必要时用短列表。

- 用功能小标题组织正文；连续操作使用有序列表，并列规则使用短项目符号，关键动作、限制和结果适度加粗。复杂功能按“流程／规则与限制／异常处理”分组，简单功能不强行套齐小节；避免一段混写多个主题，也避免将整段文字全部加粗。
- 正文只写最终功能、用户操作、系统响应与必要规则；不得写入对话过程、修改指令、方案辩解或“取消旧设计”的叙述。修改原因归变更日志，实现差异归实现矩阵。正文、范围、图注及验收不得混入 Mock、本地演示、测试数据、尚未接入等开发状态说明；图片用于呈现界面与流程，来源及实现证据仅登记在来源映射、实现矩阵和截图清单中。
- 不逐项复述页面标题、按钮、字段排列、位置、尺寸或颜色；只有影响理解与操作的关键交互才写。
- 同一规则只在归属模块说明一次，其他模块引用；正文、图注和验收不重复铺陈。
- 目的只写用户价值，范围只写产品能力与业务边界，功能只写能力与关键规则，验收只补可验证条件。
- 技术校验细则按需引用参考文件，不将长篇细则搬到验收区；精简表达不取消已确认约束。
- 保留影响结果的期限、权限、确认及异常规则；区分当前实现与后续目标。
- 用户任务的达成条件统一称“任务完成标准”；模块第四区块“功能验收标准”用于研发和测试判定软件行为，两者不可混称。

### 详细功能设计的组织顺序

默认按 **整体流程 → 分步处理 → 生成或展示的内容 → 规则与异常 → 界面案例** 编写：

1. **整体流程**：有分支、补问或回退的流程先给流程图；写清判断条件、分支结果和结束点。
2. **分步处理**：按操作顺序写“用户输入／系统处理／结果”，用有序列表或步骤表，避免按零散控件组织。
3. **内容结构**：用字段表说明输出包含什么、哪些可编辑、哪些可为空或由系统计算。
4. **规则与异常**：集中说明跨步骤的权限、数量、保存和提交规则；异常表写“触发情况 → 系统响应与下一步”。
5. **界面案例**：放在核心规则之后，用于对照典型分支，不重复整段功能说明。

简单功能可省略不适用的小节，不强行补图表。流程图负责看路径、表格负责查规则，正文只解释图表未表达的细节；同一规则只维护一处。示例轮数、人数和任务数不得变成通用限制。

模块发生语义变更时同步更新 frontmatter 的 `last_change`。只有需要发布新版本时才修改模块 `version`，不能用版本号代替变更日志。

## 4. 判定并记录变更

以下属于语义变更：功能范围、操作流程、规则、状态、权限、数据边界、验收标准，以及“当前已实现／目标能力”的判断发生变化。

语义变更必须在同一次修改中完成：

1. 更新对应模块 Markdown；
2. 在 `docs/prd/CHANGELOG.md` 表格顶部追加一个未使用的 `PRD-NNNN`，写清日期、当前产品版本、影响模块、类型、变更内容、原因与影响、相关链接；
3. 如当前事实或证据变化，同步更新 `source-map.md` 和 `current-implementation-matrix.md`；
4. 如页面表现或截图证据变化，同步处理图片与 `screenshot-manifest.json`。

变更日志只追加，不改写或复用旧 ID。错别字、措辞润色、排版和纯视觉样式调整不写日志，但仍须重新构建。治理规则本身发生变化时，影响模块写“PRD 维护机制”。

## 5. 管理截图

- 当前页面截图必须来自主工作区当前运行时，不得用旧 worktree UI 冒充。
- 图片放入 `docs/prd/assets/<module-id>/`，并登记 `screenshot-manifest.json`。
- `current-page`、`current-component` 和 `state-illustration` 必须明确区分；状态示意不能作为已实现证据。
- UI 变化使旧截图失效时，将其恢复为待采集或重新采集，不能继续标记为当前证据。

## 6. 构建与最小验证

正文、日志或图片更新完成后，在 PRD 根目录运行：

```bash
node scripts/build-agentdoor-prd.mjs
```

然后至少确认：

- 构建成功，`public/prd/index.html` 与模块索引已同步；
- 生成页包含本次修改和变更 ID；
- `git diff --check` 对本次改动无格式错误。

构建失败时修改源 Markdown，禁止手工修补生成文件。默认只做与改动风险相称的最小验证；用户未明确要求时，不运行全量测试或双重审查。

## 7. 发布历史版本

普通更新继续写入当前版本并追加日志，不自动创建新版本。只有用户明确要求发布新版本时，才读取 `version-manifest.json`，使用 `scripts/release-agentdoor-prd.mjs` 按用户确认的版本号和标题归档；不得自行猜测版本号，也不得覆盖既有版本。

## 8. 完成时报告

最终说明本次更新的模块、变更 ID（如需要）、主要证据、构建结果，以及正式 Markdown 和生成页路径。若本次仅为非语义修正，明确说明未新增变更日志的原因。
