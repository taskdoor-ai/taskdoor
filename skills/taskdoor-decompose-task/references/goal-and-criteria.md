# 目标与任务完成标准生成规范

每次生成或优化子任务建议都读取本模块。已有父任务是上下文，本Skill不改写父任务目标、标准或日期。它规定 `title`、`goal`、`acceptanceCriteria` 的语义及检查方式；拆解规则归[本Skill的一层拆解规则](../SKILL.md#只拆下一层)。以下内容用于模型内部判断，不要求用户填写额外表单，不增加协议字段。

## 1. 三个字段各回答一个问题

| 字段 | 回答的问题 | 应承担的内容 |
| --- | --- | --- |
| 标题 `title` | 这是什么工作？ | 简短识别动作、对象或交付物，方便找到任务 |
| 目标 `goal` | 为什么做？希望什么情况变好，或使谁能够做到什么？ | 真实用途、要解决的问题、任务完成后希望具备的状态或能力 |
| 任务完成标准 `acceptanceCriteria` | 如何核对本次承诺是否达成？ | 可以检查的结果、交付要求、质量及范围边界 |

标题“制作新品商城主视觉”不能直接扩写成目标“完成并交付一张高质量的商城主视觉”。后者仍然只说明产物，没有回答为什么需要它。给标题加“按时”“顺利”“高质量”“确保完成”也不能形成目标。

目标可以涉及交付物，但句子的重心要落在用途或期望改变上，例如“让商城访客清楚理解产品容量和清洁特点，支持选购判断”。目标没有数字也可以真实；有数字也未必有意义。

**用途前缀也可能只是换称。**“为新品宣传提供一份表述准确、结构清晰、可供后续宣传使用的脚本”仍把重心放在产物与质量，没有说明使用者或下游工作因此获得何种具体能力。首次生成或本轮授权优化目标时，应再回答一层：例如“让宣传受众获得准确清晰的新品介绍”，或在输入已说明制作交接场景时“使宣传制作人员能按统一、已核对的信息制作后续内容”。选择本次场景有依据的用途，不默认增加受众细分、用户测试、发布活动或业务收益。用户把“形成准确清晰的脚本”称为目标，也要保留准确清晰的要求作为标准，并据现有场景整理真实用途；实质用途不能判断时补问。不要仅加“用于、支持、便于、为……”就认为目标已经合格。

## 2. 先找目的依据，再写目标

按下列顺序使用信息：

1. **用户明确目的**：保留原本要解决的问题、受益对象及期望结果，不擅自换成更宏大的战略。
2. **当前任务上下文**：使用已给的场景、使用方、父任务目标及材料中与本次任务直接相关的用途；父目标只提供上下文，不证明子任务独自承担整个业务结果。
3. **最近一层合理用途**：信息不足但用途清楚时，可提出紧贴场景的目标建议。例如商城图片支持理解商品信息、验证码修复恢复身份验证能力。不能由此推出销量增长、成本降低或注册率提升等未经提供的承诺。
4. **实质目的仍未知**：若不同目的会改变交付或验收，只补问最关键的问题，例如“这些文件整理后主要给谁、用来做什么？”；保留已知内容，输出 `needs_clarification`。已有候选节点的 `goal` 可以明确写“目标待确认：……”并配合具体问题，不能把待确认内容标为最终目标或 `ready`。

最近用途属于模型推断时，通过 `warnings` 简短说明其依据和待核对性，不包装成用户已明确说过的话。依据充分就直接整理，不因用户没亲口说“目的是”而机械补问。

**禁止补造：** 不把参考案例、成员职责或管理书籍中的常见收益，写成本任务已确认的业务目的；不声称当前用户已经存在某种痛点，除非输入提供了事实。可写“帮助理解”，不能无依据声称“解决已经导致大量退单的问题”。

## 3. 目标怎么写

内部检查对象、场景与期望状态是否清楚；无需把所有要素强塞成固定句式。通常用一到两句话说明最关键的目的，具体数量、格式和字段清单优先放完成标准。

| 任务情形 | 目标重点 | 避免 |
| --- | --- | --- |
| 业务改善 | 用户明确要改变的业务状态；已有基线、目标及适用周期保持 | 从制作活动自行推断增长承诺 |
| 内容或材料制作 | 内容将帮助谁理解、判断或继续做什么 | “交付一份材料”换称标题 |
| 系统修复 | 恢复哪种可用能力或消除哪种已知异常 | “完成问题修复”“代码已提交” |
| 会议或协调 | 形成什么决定、共识或可执行安排 | “顺利召开会议”“加强沟通” |
| 调研或验证 | 消除哪种不确定性、支持什么判断 | “完成调研报告”“证明方案一定有效” |
| 持续维护 | 持续保持的可用状态或服务价值 | 虚构整体结束点，或把“坚持维护”当目的 |

### 目标的四项自检

- **动机检查**：读完目标，是否知道为什么需要这项工作？若只知道做什么，重写。
- **换称检查**：若删掉“完成／制作／交付／按时”后只剩标题近义词，目标通常仍不合格；这是语义检查，不用关键词禁令误伤正常表达。
- **真实性检查**：目标里的对象、问题、数字和预期改变能否追溯到本次输入或紧邻用途？模型建议是否已说明？
- **范围检查**：目标是否把用户的小交付升级成另一个业务项目？若是，收回到本次工作确实能贡献的用途。

## 4. 从目标和原始要求生成标准

先在内部对应“本次目的 → 必须得到的结果或交付 → 怎样检查”，再保留真正决定完成的标准。用户原话中的数量、质量、交接和排除项必须落在对应范围，不能只留在 `summary`。

标准应让相关协作者能据此核对，通常说明检查对象、需要成立的条件，以及必要时的检查方式。不要把每条写成一份验收操作手册，也不要求固定条数。

| 标准类型 | 可以写什么 | 依据要求 |
| --- | --- | --- |
| 结果标准 | 某种可用状态恢复、决定明确、业务指标达到用户目标 | 结果属于本次承诺；指标口径及阈值有来源 |
| 交付标准 | 本次需要的文件、内容、数量及交接对象 | 用户明确要求，或本次用途不可缺少 |
| 质量标准 | 内容准确、关键信息可读、指定行为正常、资料一致 | 条件能核对，直接服务本次用途 |
| 范围约束 | 不改哪些部分、预算上限、只交付哪一个版本 | 保留原约束的适用对象，不扩大到无关分支 |

### 五项质量检查

1. **可判定**：去掉“高质量、充分、专业、领导满意”等无口径评价，改成可观察条件。用户确实要求特定人审核时保留该审核，不默认新增审核人。
2. **有依据**：数字、格式和通过条件来自用户或必要的可用性要求；不从行业习惯、参考书或成员职责扩出硬门槛。
3. **必要且覆盖**：每条都支撑本次目标或明确要求；合起来没有遗漏关键承诺，也没有为了凑条数重复表达。
4. **能由当前交付证明**：一张图已经生成只能证明制作结果，不能证明访客已经理解，更不能证明销量增加。若本次不含用户测试或效果观察，标准只检查信息呈现等可交付条件，不暗中增加实验。
5. **层级正确**：只约束该节点负责的范围；脚本的时长不约束海报，项目总预算不重复分给每个子任务。

## 5. 常见不合格标准与修正

| 不合格写法 | 问题 | 修正方向 |
| --- | --- | --- |
| 高质量完成海报 | 不能据此判断 | 按实际用途核对指定卖点、可读性和商城展示要求 |
| 先调研、再设计、最后自检 | 是路径，不是完成证据 | 必要步骤放 `executionTips`，标准核对最终内容 |
| 保证转化率提升20% | 数字和因果可能无来源 | 只保留已提供指标；制作任务不附加业务效果承诺 |
| 完成主任务要求 | 没有说明本节点的交付 | 写该子任务实际贡献及其可检查条件 |
| 未经用户要求补做访谈和测试 | 把验证方法扩大为额外工作 | 用当前交付可证明的条件核对；需要扩大时作为建议 |
| AI判断已达成，用户无需确认 | 混淆生成标准和执行事实 | 只生成标准，不输出完成状态、人工确认或成功回执 |

操作动作并非一概不能成为标准：用户要求的独立操作结果，例如“完成指定文件迁移且目标目录可读取”，可以核对；仅“点击迁移按钮”不能证明迁移结果。

## 6. 目标、可控交付与业务效果的关系

真实目标可能超出单次交付的直接控制范围，这不构成把目标降格成标题的理由。应同时保留真实目的、说明本次贡献，并让标准对应本次实际承诺。

- 用户明确“把支付成功率从68%提高到75%”时，保留该业务目标；若本次任务确实承担结果改善，标准保留目标值及必要统计口径，关键窗口不清时补问。
- 用户只是为同一目标制作一张图时，图的目标说明帮助用户理解信息，标准检查这张图的内容与可用性；不要求该制作人独自保证整个支付成功率。
- 探索任务的目标是减少不确定性；标准检查观察数据及可支持的结论。观察完成与假设成立分别表达，小样本不外推为整体效果。
- 持续工作没有整体结束点时，以实际维护范围、有效信息和可用状态核对；不强行添加整体截止或最终一次性收益。

## 7. 拆解后如何承接父目标

按[一层拆解规则](../SKILL.md#只拆下一层)在用户明确要求时拆分。父任务保留真实整体目的，不能只用子交付物列表替代；每个子任务说明自己的结果怎样服务该目的。

- 覆盖：用户明确要求的结果都有承载节点，不在父目标里承诺一项却没有对应交付。
- 不重做：父任务负责整体结果或汇总判断，不再制作一次所有子任务产物；同一结果不放进多个分支重复执行。
- 有边界：子任务标准检查自身交付；不能把父级全部标准和业务指标原样套给所有子任务。
- 不强造不同：父子或不同渠道可以服务同一真实目的，允许复用适用的目标表述；必要时补充本节点贡献。文字必须不同不是验收条件，也不能因此发明不同业务目标。
- 不把步骤当任务：调研、起草、自检通常是同一交付的执行路径；只有用户要求且结果可独立交付、负责和验收时才成为子任务。

## 8. 对照示例

### A. 商城主视觉：从制作动作到选购用途

输入：“商城展示要让用户看清新品350ml容量和温和清洁的特点，帮我做一张主视觉，别加其他物料。”

- 标题：制作新品商城主视觉。
- 不合格目标：交付一张高质量的新品商城主视觉。
- 合格目标：帮助商城访客清楚理解产品容量与清洁特点，支持选购判断。
- 完成标准：交付一张用于商城展示的主视觉；350ml容量和温和清洁特点清楚可读；按已提供的商城展示要求核对，关键信息不被裁切。
- 边界：不增加销量指标、额外物料或用户访谈；未提供商城规格时不编尺寸或称已核验线上效果。

### B. 文件整理：已知问题决定目标

输入：“新同事总分不清现行流程和历史版本，把入职目录整理一下，让他能找到当前规则。”

- 标题：整理入职流程目录。
- 目标：让新同事能找到并辨别当前有效流程，避免把历史版本当作现行规则。
- 完成标准：现行流程有明确入口与版本标识；历史版本可辨别且不冒充现行；所需链接可打开。

只有“整理文件”且无用途时，不直接套用这个目标；应核对是检索、交接、归档还是其他目的。

### C. 会议：决定是目标，会议是方法

输入：“用一小时定下下季度最优先的一项结账改进方向，会后明确推进人，不制作PPT。”

- 标题：召开结账改进决策会。
- 目标：明确下季度唯一优先的结账改进方向及推进责任，使团队能够据此安排后续工作。
- 完成标准：形成一项明确决定及对应推进人；会议不超过用户指定的一小时；不增加PPT制作。

### D. 拆解：共享目的，局部贡献各自可查

输入：“新品发布要让潜在客户理解用途与卖点，文案和海报都要有，请拆开负责。”

- 父目标：支持新品发布时清楚传达产品用途与已确认卖点。
- 文案目标：帮助潜在客户通过文字理解产品用途和特点。
- 海报目标：在发布的视觉呈现中清楚传达已确认卖点。
- 父标准核对整体信息一致及两项交付齐备；文案、海报分别检查自身内容和用户指定要求，不重复要求每项单独保证销量增长。

## 9. 输出前最后核对

只做一次简短内部检查：目的有依据且没有换称标题；标准可检查且覆盖本次要求；步骤与额外交付未混入；父子贡献对应；未知和建议没有变成用户承诺。发现问题修正对应字段，不为一次目标优化重写人员、日期或已有层级，也不为满足标准偷偷增加任务。
