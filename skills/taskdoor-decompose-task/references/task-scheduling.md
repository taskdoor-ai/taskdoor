# 新增子任务建议的截止日期

仅为本轮新增的直属子任务判断日期，不改父任务与已有子任务；父任务硬期限与建议冲突时提示并补问，不隐瞒冲突。不得不加判断地复制父日期。

这是 TaskDoor 的规划规则，不是从管理书籍推导出的统一估时算法。只输出现有 `dueDate` 与文字依据，不输出开始日期或新增字段。日期使用调用方 `currentDate` 和 `timezone`；新给出的 AI 建议不得早于调用方当前日期。用户明确或既有的过去日期保留为候选并提示过期风险，不静默改成未来日；须补问或要求修正后再创建，不能视为可提交安排。日期不存在、年份或相对日期有关键歧义时再补问。

## 先保留用户选择

1. 用户给定截止日：按原要求解析；过紧时提示范围／容量风险，不能擅自改到“更合理”的日期。
2. 用户明确不设截止、长期持续，或要求清空：`dueDate: null`。不在优化时补回。
3. 有 `previousPlan`：没有要求重排时保留每个节点当前日期，包括 `null`。仅凭 `null` 不能知道是未估还是人工清空，所以不猜；明确要求推荐日期后才重算对应节点。
4. 用户主动改名、人员或文案，不等于请求重排。范围变化但没有授权调整日期时保留原值，必要时提示新范围可能影响计划。

## 未给日期时，判断是否适合建议

| 情形 | dueDate 与文字处理 |
| --- | --- |
| 有限、交付明确、可以合理规划的小任务 | 默认给 AI 建议日期；把依据和未核实条件写入 `warnings` |
| 有结束点的长任务，范围／资源／窗口充分 | 可以给建议，但不用固定六周、季度末或“长任务一律无日期” |
| 长期愿景、持续运营／维护，没有整体结束点 | 整体留空；如有必要，可在执行建议提出阶段回顾，不自动另建任务或给整体硬截止 |
| 外部招募、审批、供应等关键等待无可判断窗口，或整体范围不足 | 留空并说明缺口；不把默认工时换算成确定日期 |
| 研究只需收集证据，尚无成功阈值 | 可先生成研究交付；阈值未知本身不阻止方案，日期仍按窗口是否可判断处理 |

## 如何形成有条件的建议

- **先区分可补规格与关键等待。** 单张图片只缺商城尺寸、纪要只缺共享渠道等普通制作规格，若交付对象、规模与用途已明确，不自动归类为“关键外部等待无法判断”。首次仍可给有条件的建议日期，并明确假设这些规格能在制作前补齐；若未补齐则需重新评估。不能仅以“尺寸未提供”取消初始日期建议。用户已说明规格须等待外部确认、回复时间未知，或缺口会实质改变交付规模且不能合理假设时，才按关键等待或范围不足留空；不把假设写成已经取得承诺。
- 以本次范围对应的人工工作估算为起点，分别考虑可用容量、已知工作窗口、等待、沟通和核验；不直接使用“人工分钟÷480”作为日历历时。
- 输入提供可比历史、成员可用时间或已确认安排时优先使用；缺少时可提出**明确标为模型假设**的轻量安排，不能写成已经读取团队日历、成员有空或对方已承诺。关键外部等待无法合理假设时留空。
- 没有团队工作日历时，不声称排除了法定节假日或已落实周末工作；若按周一至周五规划，要写明这只是工作日假设。缺少具体时间点，不制造当天几点开始的安排。
- 资料、素材和既有环境可用只是估算条件；未实际提供时写“假设可用”，不能在完成标准写成已经核实。
- 不套统一“加20%缓冲”“每个任务3天”等参数。确需考虑修改或核验时，说明实际动作及影响，而非无来源的倍率。
- 父子节点有各自明确日期时分别保留；只给整体日期时不强加内部提前截止。建议日期出现明显矛盾时说明并调整候选，不用日期生成已移除的依赖边。

## 输出与采纳边界

AI 建议可进入预览节点 `dueDate`，并在 `warnings` 用任务名称／`clientId`、建议日期、关键假设说明来源和可修改／清空性；多个节点应能分别对应。不要添加 `dateSource`、`confidence`、`schedule`、`startDate` 等 Schema 未定义字段，也不伪造输入证据 ID。

例如：`任务「制作商城主视觉」(draft-visual) 的 2026-10-16 为 AI 建议：假设现有产品资料与商城规格可用、接下来有半天设计及核对窗口；人员实际可用时间未核实，可修改或清空。`

日期来源及依据属于候选说明，应由应用与最终方案一并提供核对；本 Skill 不声称当前页面已经展示这些说明或服务端已保存来源元数据。没有真实确认或写入工具时，不能说“截止已设置”。

创建建议是初始规划；用户确认后的计划截止、执行中根据事实产生的 AI 完工预测分别处理。后续预测不得静默覆盖计划截止，创建方案不输出已创建任务的进度或预测快照。
