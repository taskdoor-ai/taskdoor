# AgentDoor 产品 PRD（文字简版）

> 版本：1.1  
> 日期：2026-09-03  
> 用途：产品流程、五个 Skill 与 MCP 参数设计；同步提供 HTML 与 PDF

> 算法修订：`EWD-PROGRESS-2026-09-03-r2`。第 7.7 节详细定义 EWD、历史与人员经验的作用、AI 候选完成度及正式验收完成度。算法是待接入的产品设计，当前运行代码仍按本地估算与账本投影。

## 1. 产品流程

```text
加入团队
  → 维护个人责任
  → 创建任务
  → AI 分析并生成任务方案
  → 用户确认任务、人员和投入
  → 任务进入左侧列表
  → “我的工作”推荐当前优先事项
  → 在任务详情中持续协作和跟进
```

AgentDoor 中只有一种工作对象：Task。

子任务也是 Task。标签、文件夹、讨论和活动都不能代替 Task，也不能代替父子关系或依赖关系。

## 2. 团队成员、邀请与个人责任

### 2.1 团队成员

用户可以在“设置 → 成员”中：

- 查看当前团队成员。
- 查看成员的责任说明。
- 通过链接或邮箱邀请新成员。
- 管理管理员和普通成员角色。

邀请只表示邀请对方加入团队，不表示对方已经参与任务或负责某项工作。

### 2.2 邀请规则

- 负责人和协作人使用同一人员弹层，保留“暂不分配”与“没找到合适的人，邀请更多同事进来协作 · 立即邀请”。
- 邀请成功后，不自动写入 Task Owner。
- 邀请成功后，不自动写入 Participant。
- 被邀请人加入团队后，仍需接受具体的任务责任提议。
- 团队至少保留一名管理员。

### 2.3 我的责任

“我的责任”记录成员在当前团队中通常负责什么。

用户可以：

- 手工新增、修改或删除责任。
- 查看 AI 对已有责任的更新建议。
- 查看 AI 建议新增的责任。
- 查看建议所依据的任务或交付记录。

### 2.4 AI 责任建议

AI 可以根据已确认的任务责任和交付记录，建议新增、更新或废弃一条责任。

AI 只生成建议，不直接修改责任。

- 更新建议默认收起。
- 用户点击“更新”后，才替换原责任。
- 新增建议通过候选行展示。
- 用户点击加号后，才写入责任。
- 原责任已经被修改时，旧建议不能继续覆盖。
- 权限不足或证据不足时，AI 不生成确定结论。

### 2.5 责任建议 Skill

需要建立一个责任建议 Skill，暂定名：`agentdoor-responsibility-advisor`。

输入：

- 当前成员和团队。
- 当前责任文本及版本。
- 有权限查看的任务、交付和活动记录。
- 证据时间和来源。

输出：

- 新增、更新、废弃或不调整。
- 建议文本。
- 对应的原责任。
- 建议依据。
- 数据时间和信息缺口。

Skill 不负责写入责任，也不能修改 Task Owner、参与人或权限。

## 3. 创建任务

### 3.1 创建流程

1. 用户点击左侧“新建任务”。
2. 用户输入希望完成的事情。
3. AI 判断信息是否足够。
4. 必要时提出最多两个关键问题。
5. AI 检查已有任务、成员责任和可用资料。
6. AI 生成主任务和必要的子任务。
7. AI 建议负责人、参与人、标签和预计投入。
8. 用户修改或让 AI 帮助调整方案。
9. 用户最终确认后，系统正式创建任务。

最终确认之前，页面中的内容都是草稿，不能提前写入正式 Task。

### 3.2 创建任务 Skill

当前已有 `agentdoor-task-planner` Skill，用于生成和调整任务方案。

它负责：

- 判断用户是创建、调整、继续规划还是查询。
- 补问真正影响目标和交付的问题。
- 检查相似任务和已有关系。
- 生成主任务和子任务草稿。
- 建议负责人和参与人。
- 建议标签、依赖和预计投入。
- 输出调整前后的差异。

它不负责：

- 创建正式任务。
- 自动指派负责人。
- 自动邀请成员。
- 替成员接受任务。
- 自动修改已有正式责任。
- 自动验收或关闭任务。

### 3.3 任务内容

每个 Task 至少包含：

- 名称。
- 目标。
- 完成标准。
- 正式负责人或待接受负责人。
- 参与人。
- 状态。
- 时间。
- 标签。
- 父任务和前置依赖。
- 预计人类投入。

名称用于快速识别，目标用于描述希望达到的结果，两者不能写成相同内容。

### 3.4 子任务拆分

只有结果可以独立负责、交付、验收、并行推进或复用时，才拆成子任务。

以下内容通常不拆成子任务：

- 普通操作步骤。
- 同一交付中的分析、执行和复核。
- 只需要一次咨询或资料补充的协作。
- 为了让方案显得完整而增加的阶段。

父子关系只表示范围包含，不自动产生前置依赖。

### 3.5 人员匹配

AI 按以下顺序推荐人员：

1. 检查成员是否可被发现，以及是否有权限参与当前工作。
2. 检查成员的正式责任是否覆盖整个任务结果。
3. 检查相关任务、文件和业务对象经验。
4. 检查成员主动公开的协作方式和可投入窗口。
5. 展示候选差异，由用户决定。

AI 不能通过任务数量、在线状态、回复速度或私人日历判断成员是否空闲。

没有合适人选时，任务可以保持未分配。不能默认把创建者、主管或首位成员填为负责人。

### 3.6 负责人规则

- 一个 Task 最多有一位正式 Owner。
- 用户选择自己负责时，可以直接成为正式 Owner。
- 用户选择其他成员时，先记录为待接受提议。
- 对方接受后，才成为正式 Owner。
- 待接受人不能进入“我的工作”。
- 已有正式 Owner 的变更不能通过普通编辑直接完成。

### 3.7 标签

AI 可以根据任务对象和交付结果建议已有标签。

- 标签可以修改或清空。
- 标签不是状态、目录或父子关系。
- 不创建主标签或标签组。
- 一个任务可以有多个标签，但在左侧列表中只出现一次。

### 3.8 工时和成本

当前只确定预计人类投入 EWD。

EWD 表示：在约定的 AI 或工具使用方式下，完成当前范围预计需要多少人类投入。

**对任务的价值：** 预计投入人天表示完成任务预计需要的总人工工作量，帮助团队看清任务规模、投入主要花在哪里，并按工作量衡量完成进度。

**统一展示单位为人天，1 人天＝8 人时＝480 分钟。** 页面仍叫“预计投入”，例如“预计投入约 5 人天”；这是总人工投入的换算单位，不是日历工期，也不表示每位成员每天有 8 小时可用于此任务。40 小时的总人工投入应换算成 5 人天，不能直接改标签变成 40 人天。

内部继续保存整数分钟，汇总、占比与完成度都使用未舍入原值；最终显示除以 480，保留最多两位小数并去掉末尾零。0 显示“0 人天”，大于 0 且小于 0.01 人天显示“<0.01 人天”，未知保留“待估算”。估算区间显示下界向下、上界向上取两位小数，避免舍入缩窄范围；各项显示值相加可能与总显示值略有差异，总计以原始分钟求和后换算为准。底层既有小时字段保留原单位，不能把人天数直接写入 ewdHours 等字段。

计入：人工准备、操作、沟通、审阅、修改和验收。

不计入：等待时间、排队时间、无人值守的 AI 运行时间和自然工期。

- 未知不能按 0 计算。
- 子任务缺少估算时，不计算完整总投入。
- 父任务汇总叶子任务，不能重复累计。
- 目标、完成标准或工作方式变化后，需要重新估算。
- EWD 不等于工期、剩余时间、个人效率或任务优先级。

历史任务与人员经验通过有证据的工作差异影响估算，例如可复用材料、熟悉业务、额外学习或核查。当前历史只有提交修改记录与状态变更时间，不据此设置个人效率系数或声称已校准真实工时。单项估算、上下界、去重汇总与更新规则统一见第 7.7 节。

创建页在预计总投入下展开数字列表，按预计工时从高到低展示“任务名称 · 预计 1.25 人天 · 占总投入 25%”；不再展示条形或饼图，避免将投入占比误读为完成度。占比的分母是当前全部叶子任务的有效 EWD；缺估或需重估时只显示已估部分，不计算占比。

金额成本暂不进入首版。人员费率、外部费用、币种和查看权限确认后，再设计金额公式。

### 3.9 创建确认

用户确认前，系统检查：

- 名称和完成标准是否有效。
- 人员是否属于当前团队。
- Owner 是否重复出现在参与人中。
- 日期是否合法。
- 依赖是否自指、悬空或形成循环。
- 子任务时间是否与父任务明显冲突。
- 预计投入是否仍对应当前任务范围。

无负责人不阻止创建。系统只统一提示一次未分配任务数量。

## 4. 左侧任务列表

### 4.1 页面结构

```text
搜索 ｜ 筛选 ｜ 新建
我的工作
按标签分组的本人任务
待确认负责人
```

### 4.2 标签分组

- 默认使用任务的第一个标签作为展示分组。
- 没有标签的任务进入“未打标签”。
- 一个任务只在一个分组出现。
- 标签筛选时，按第一个命中的已选标签临时归组。
- 清除筛选后，恢复默认分组。

### 4.3 列表范围

- 本人任务通过稳定成员 ID 和正式 `ownerId` 判断。
- 创建者身份不能代替负责人身份。
- 参与人不能代替负责人身份。
- 待接受负责人不进入本人正式任务列表。
- 本人创建但尚未分配的任务进入“待确认负责人”。

搜索、状态和标签筛选只影响左侧列表，不影响“我的工作”的分析范围。

## 5. 我的工作

### 5.1 模块作用

“我的工作”回答：在我正式负责的任务中，现在应该先关注什么。

它不是第二套任务系统，也不创建新的待办。

### 5.2 展示内容

每条只显示：

1. 顺位。
2. 任务名称。
3. 一句优先原因。

点击任务名称进入原任务详情。

页面不展示 AI 内部评分、复杂权重、完整依据列表或其他任务的深层链接。

### 5.3 分析范围

- 当前用户全部正式负责任务。
- 相同 Task ID 只出现一次。
- 待接受和未分配任务不进入。
- 已完成和已取消任务不生成当前优先事项。
- 左侧搜索、筛选和折叠不改变分析范围。

### 5.4 推荐逻辑

AI 主要检查：

1. 是否逾期或当天到期。
2. 是否存在正式阻塞或未完成前置。
3. 是否等待审核、验收或关键决定。
4. 任务状态与现有记录是否冲突。
5. 关键资料是否缺失、过期或无权读取。
6. 当前用户在任务中承担什么正式责任。

没有截止时间是合法状态，不等于低优先级。

资料不足时，优先原因应表达“待核对”，不能推断任务正常或没有风险。

缺少真实日历、剩余工作量和个人可投入时间时，不输出忙闲率、完成概率或精确排程。

### 5.5 AI 分析规则

页面顶部保留默认收起的“AI 分析规则”，只说明：

- 哪些任务会进入分析范围。
- AI 使用哪些事实判断顺序。
- AI 不会自动修改任务。

只有分析输入真实变化时，更新时间才变化。打开页面或重新渲染不能制造新的分析时间。

## 6. 任务详情

### 6.1 任务头部

头部展示：

- 名称、目标和完成标准。
- 正式负责人、待接受负责人和参与人。
- 状态、时间和标签。
- 任务属性编辑入口。

字段保存成功后才形成活动记录。没有真实变化时，不生成活动。

### 6.2 当前情况

任务头部下方展示三部分：

| 区域 | 内容 |
| --- | --- |
| 当前情况 | 当前摘要、已完成事实、差距、风险和近期变化 |
| 下一步建议 | 有依据的候选行动 |
| 完成进度 | 完成百分比、进度条和燃起图 |

下一步建议只是一项建议，不自动修改状态、负责人、时间或子任务。

没有足够记录时显示未知或“尚无可核对记录”，不能显示“运行正常”。

### 6.3 完成进度和燃起图

“完成进度”的说明图标支持悬浮、键盘聚焦和点击。说明必须匹配当前读数来源：正式口径说明“按当前有效 EWD 加权，以有效验收记录为准，不代表实际耗时”；AI 候选口径明确标“AI 估算完成度”，说明“根据当前交付证据核对完成标准，仅供参考，不代表正式验收”。历史任务只帮助理解标准和工作方式，不能证明当前交付已完成。当前原型继续说明本地记录计算、尚未接入 AI 评估服务；不能给正式验收百分比统一套用 AI 估算提示。完整算法见第 7.7 节。

完成百分比同一行右侧显示“预计投入 8.75 人天”，无需展开即可查看。主任务汇总当前范围的叶子工时，独立任务显示自身估算，不重复累计父级；使用当前有效估算，不沿用历史快照中的旧总量。缺估时显示“已估部分 2.5 人天”，无估算显示“预计投入 待估算”，过期／异常分别显示“需重估／待核对”。总工时代表预计投入，不代表已花费时间；下方子任务明细不变。

燃起图标题不再显示 `EWD · h`。有可绘制历史时，图例为虚线“当前总工作量”与实线“已完成工作量”；空状态不补图例。“查看数据”内说明按 EWD（预计人类投入）加权、已完成以验收为准且不代表实际耗时，统一以人天展示，1 人天＝8 人时＝480 分钟。既有 scopeHours 等字段仍按原小时含义读取并除以 8 展示，不改历史数值、不将工作量解释为工期。

现有正式完成进度使用以下口径；未来 AI 候选使用独立字段、标签与证据规则，不静默替换当前读数：

```text
当前范围内已验收叶子 Task 的有效 EWD
÷ 当前范围全部叶子 Task 的有效 EWD
```

- 不按已完成任务数量计算。
- 不根据 TaskStatus 推导。
- 范围 EWD 完整、有效且大于 0，且确认验收记录集合为空时可显示 0%；验收记录未读取不能视为 0。
- 没有历史不伪造趋势；单个真实快照只显示一个点，不补画过去的线。
- 父任务只汇总叶子 Task，不重复计算。
- 进度达到 100% 不自动关闭父任务。
- 状态与进度记录冲突时，显示“待核对”。

有子任务时，在整体进度条下默认收起一行“子任务投入与进度 · 展开”，不重复百分比旁的总工时，也不显示“已验收 / 范围”图例。展开后按预计工时从高到低排列；同值保持原序，未知项置后，不改变实际任务顺序。

- 每项第一行显示黑色加粗的任务名称，可点击进入该子任务详情；暗色主题使用对应主文字色。
- 第二行左侧显示“预计 1.25 人天 · 占总投入 25%”，右侧显示“已完成 60%”。预计投入不等于实际耗时。
- 下方进度条只表示该子任务自身的完成度：本项有效已验收 EWD ÷ 本项当前有效 EWD，不再乘以投入占比。
- 缺少或未读取验收记录时显示“进度未知”和灰色空进度条，无彩色填充，不补 0%；明确记录为 0 时显示 0%。过期估算、非法验收值或零分母提示“进度待核对”，同样保留空轨道，不生成伪百分比。
- 部分任务缺估时百分比旁显示“已估部分 2.5 人天”，明细保留未知项，不把已估部分当完整分布；其中已有有效估算和验收值的单项仍可展示自身完成度。
- 仅一个子任务也支持展开；没有子任务不显示此入口。多层任务只统计叶子，不重复累计父级。
- 窄屏明细允许换行，展开按钮和任务名称支持键盘操作；燃起图继续独立表达时间趋势。

### 6.4 页签顺序

```text
讨论 ｜ 诊断 ｜ 子任务 ｜ 文件 ｜ 活动
```

### 6.5 讨论

讨论只承载人的交流：

- 发布消息。
- 回复。
- @ 成员。
- 引用文件和讨论上下文。
- 从讨论连接个人 AI。

任务变更、诊断结果和自动 AI 建议不计入讨论数量。

### 6.6 诊断

诊断回答：当前任务能否继续，依据是什么。

首版只检查两类问题：

- 执行阻塞：任务存在正式依赖，且可见前置尚未完成。
- 决策冲突：至少两个正式来源存在互不相容的记录。

诊断范围包含当前 Task 和全部可见后代 Task。

每条诊断展示：结论、影响、建议和默认收起的依据。

诊断页只读，不提供一键修复、改期、改依赖、忽略或完成任务。

不可见或缺失的依赖只表示检查范围不完整，不能推断为阻塞、正常或已完成。

### 6.7 子任务

子任务列表每项只显示：

- 图标。
- 名称。
- 负责人或待接受负责人。

点击名称进入子任务详情。

- 手工新增至少需要名称和一条完成标准。
- 不自动继承负责人、参与人、文件或权限。
- 新增或删除后，父任务的直属子任务数量同步更新。
- 删除有下级的子任务时，必须说明影响范围。
- 子任务全部完成不自动关闭父任务。

### 6.8 文件

文件页用于管理当前任务有权查看的文件和引用。

- 引用已有文件时复用同一 File ID，不复制内容。
- 文件夹只用于组织，不改变文件身份和权限。
- 父子任务的文件不自动继承。
- 固定版本和跟随最新版本必须区分。
- 文件无权限、已删除或缺失时，明确显示不可用。

### 6.9 活动

活动只记录已经真实发生并保存成功的变化。

活动分为三类：

- 任务信息。
- 讨论。
- 文件。

每条活动说明谁在什么时间做了什么。

- 没有真实变化时不生成活动。
- 未保存草稿不进入活动。
- AI 建议和诊断结论不进入活动。
- 活动只读，不能在活动页编辑或删除正式记录。

## 7. 五个 Skill：核心设计

### 7.1 分工、核心设计与当前实现

Skill 负责判断和生成建议；MCP 负责受控读取、执行已授权操作。五个 Skill 都不自行改变任务事实。

| Skill | 解决的问题 / 页面 | 核心设计 | 当前情况 |
| --- | --- | --- | --- |
| 创建任务 `agentdoor-task-planner` | 把一句需求变成可确认的任务方案；创建页 | **先识别再查重**：确定新建、调整或查询；按业务对象、交付物、周期和完成标准比对授权团队任务，区分复用、部分重叠、子任务和独立新建。<br>**按结果拆分**：只拆能独立负责和验收的结果，普通步骤留在执行建议；父子归属与前置依赖分开判断。<br>**按责任匹配人**：先校验显式人选，再按完整责任覆盖、相关交付经验和已公开协作窗口比较；局部贡献者作参与人，无合适人选则未分配。<br>**形成可确认方案**：关键缺口每轮最多补问两项；估算叶子任务的人类 EWD，核对依赖、时间和范围，只更新实际变化字段，最终由用户确认创建。 | 已有 v0.2 Skill 和离线契约；前端仍是有限 Mock，未接入完整生产链路 |
| 状态分析 `agentdoor-task-status-analyzer` | 不翻完讨论也能知道进行到哪；详情头部 | **同源归纳现状**：读取当前任务、后代、讨论和交付记录，区分正式状态、已确认结果与成员自述，对照完成标准总结已做、未做和信息缺口。<br>**给出可执行下一步**：复用同一快照的诊断，优先建议核对冲突、解除阻塞或补齐关键交付，说明对应责任人，不自动改状态。<br>**由代码计算进度**：以已验收叶子 EWD / 当前范围叶子 EWD 计算完成度，模型只解释；缺估或记录未读取则未知，不按任务数量或状态猜百分比。<br>**分开展示当前与历史**：子任务分布呈现当前工作量和验收进度；燃起图只用真实历史快照，范围或记录变化后使旧分析失效。 | 名称及契约为本次建议；现有 `taskSituation`、进度模块提供本地规则投影 |
| 任务诊断 `agentdoor-task-diagnostician` | 找到任务为何受阻、哪些决定冲突；诊断页签 | **覆盖可见任务树**：检查当前任务、全部可见后代和正式前置，不把父子关系当依赖。<br>**阻塞有明确条件**：执行中的消费者存在正式依赖，且可见前置尚未完成，才形成执行阻塞；依赖不可读只说明检查范围不完整。<br>**冲突保留双方证据**：至少两个不同正式来源相互矛盾，例如消费者已完成而前置未完成；单条发言不足以判定。<br>**问题归到实际对象**：同一问题使用稳定 ID，向主任务聚合时去重；呈现结论、影响、建议和可展开依据，源事实变化后重算，不另建“忽略 / 已解决”状态。 | 名称及契约为本次建议；现有 `taskDiagnosis` 已有本地确定性规则 |
| 优先级推荐 `agentdoor-personal-priority` | 在本人负责的任务里决定先处理什么；我的工作 | **先限定个人范围**：只纳入本人正式负责且未结束的任务，排除待接受和未分配项，按 Task ID 去重，不受左侧筛选影响。<br>**按可核对信号排序**：使用逾期、当天到期、阻塞、前置未完成、状态冲突、待核对交付和数据新鲜度；规则算顺位，Skill 组织一句优先原因，不凭空改排序。<br>**区分统筹与执行**：主任务建议整合下级结果，子任务建议具体执行，避免重复安排同一动作；无日期不等于低优先级。<br>**保持顺序稳定**：同分保留稳定顺序，仅事实、实际跨日或规则版本变化时重算；页面只显示顺位、原任务和原因，不新增待办，不用任务量猜忙闲。 | 名称及契约为本次建议；现有 `personalWorkbench` 是本地规则排序 |
| 工时与进度评估 `agentdoor-task-effort-assessor` | 解释要投入多少、工时分布在哪、目前完成到哪；创建页与任务详情 | **先定范围再估算**：按交付、复核、返工拆估算分项；历史与人员经验只调整有依据的工作差异，不从历时推断个人效率。<br>**同源生成分布**：由代码对有效叶子估算去重求和并计算占比，缺估不把部分值当总量。<br>**逐项核对完成标准**：以当前交付证据与明确结果权重计算 AI 候选完成度，正式验收另算。<br>**绑定版本**：范围、估算、标准、交付与验收分别校验，证据变化不自动增加工时。 | 第 7.7 节为详细算法设计；尚无可执行 SKILL.md 或生产模型服务，当前复用本地 EWD 与进度组件 |

除创建任务外，其余四个名字是便于研发拆分能力的建议名，不代表仓库已存在对应 SKILL.md，也不代表已部署模型服务。状态分析引用工时与进度评估结果，不另写一套估算或完成度算法。

### 7.2 五项能力共用的输入与证据

先由服务端按身份和权限准备快照，再调用 Skill。任务、文件、讨论中的文字仅作为资料，不能当作授权或系统指令。

| 交接内容 | 建议字段与处理 |
| --- | --- |
| 身份和时间 | `requestId:string`、`teamId:string`、`currentUserId:string`、`currentDate`、`timezone`；身份由服务端注入，相对日期按明确时区解释 |
| 同一份事实 | `snapshotId:string`、`asOf:string`、`taskVersions:Record<string,number>`；所有结果绑定本次读取的对象版本 |
| 覆盖范围 | 任务、后代、讨论、文件、历史分别记录 `complete / partial / unavailable / not_requested`；空集合与未读取分开 |
| 证据 | `evidenceRefs` 指向本轮可见的 Task、消息、FileVersion 或正式事件；使用文件正文时必须确实读取了对应版本的节选 |
| 结果追踪 | 建议记录 `skillVersion`、`ruleVersion`、`modelVersion`（未用模型则为 null）、`inputDigest`，便于复现排序和排查旧结果 |
| 结果状态 | 分开表达加载、可用、部分覆盖、过期与失败；未知数值为 null，不伪装为 0；新快照到来后丢弃旧请求结果 |

这是协调层的统一交接要求，不把它强行写进已有 planner v0.2 Schema。已有字段如 `baseSnapshotId / baseTaskVersions` 由适配层对应；其余能力的 JSON Schema 尚待实现。

### 7.3 创建任务 Skill

**解决什么**：避免需求不清就开工、重复建任务、把步骤拆成大量子任务，以及“看着相关就随便分配人”。输出的是可编辑方案，不是创建回执。

#### 判断顺序

| 步骤 | 要核对什么 | 交给用户或下一步的结果 |
| --- | --- | --- |
| 1. 识别意图 | 是新建、修改草稿、调整已有任务、追加下一批，还是只问情况？是否来自已有主任务？ | `create / refine / replan / next_batch / query / unclear`；查询不误建 |
| 2. 定义任务身份 | 为哪个业务对象、哪个周期或版本、达成什么结果？交付物和完成标准是什么？哪些日期和范围不能动？ | 明确目标与硬约束；目标说明结果，名称用于识别，不能相互抄写 |
| 3. 判断是否要补问 | 缺口是否真的改变任务身份、交付范围、可行性、安全边界或硬期限？ | 每轮最多两个关键问题；普通操作细节进执行建议，不阻塞生成 |
| 4. 检索并判断关系 | 在当前授权团队任务中比对业务对象、目标、交付物、周期和范围，包含其他成员建立的任务及同级子任务 | 复用已有任务 / 部分重叠 / 作为子任务 / 独立创建 / 关系待核对 |
| 5. 确定最小拆分 | 能否独立负责、交付、验收、交接或并行？只是同一结果的操作步骤吗？ | 单任务只建一个 Task；复杂任务按结果拆分，避免同义的“主任务 + 一个子任务” |
| 6. 匹配责任 | 显式人选是否有效？谁的责任覆盖整个交付，谁仅贡献一环？ | 一个候选 Owner 或未分配；必要参与者及各自贡献 |
| 7. 分析依赖和时间 | 本任务必须消费哪项前置产出？已有传递链能否覆盖？日期是否与前置、主任务冲突？ | 依赖差异、日期建议或需要用户选择的冲突；父子关系不自动等于依赖 |
| 8. 估算与归类 | 调用工时与进度评估 Skill，传入候选叶子、完成标准及人／AI 分工；有哪些已存在的合适标签？ | 回填叶子 EWD、估算依据和未知项，再给标签建议；不捏造金额成本 |
| 9. 校验并交付 | 引用、版本、任务树、依赖环、人员有效性、已确认字段、重复候选是否处理完？ | 草稿卡片和最小变更清单；用户最终确认后才由提交服务写入 |

#### 五类场景必须走通

| 场景 | 具体处理 |
| --- | --- |
| 单任务 | 一个结果一张卡片，准备、执行、复核可放执行建议，不强行拆阶段 |
| 复杂任务 | 生成主目标、可独立核对的子结果、贡献人、必要依赖及叶子 EWD；汇总不重复计算父项 |
| 需求不明确 | 一次展示一道单选题，每个选项一行：三个预设选项，最后一行自定义输入；自定义内容非空才可继续。标题如“再明确两个关键信息（1/2）”，选完点“下一步”，最后点“开始生成方案”；返回上一题保留答案 |
| 相似 / 重复任务 | 相同结果优先打开已有任务；部分重叠只规划未覆盖的部分；不同周期可独立建，但必须说清区别。检索失败或范围不完整不能说“没有重复” |
| 已有任务下创建子任务 | 明确主任务 ID，读取主目标与已有子任务，核对是否已覆盖；上方路径为“任务 / 主任务名 / 新建任务”，卡片内不重复放关联路径；完成后进入新子任务详情 |

**成员交叉重复**是重点：A、B 因沟通不及时分别创建同一事项，不能只搜索本人任务。展示“在你参与的任务中发现……”前必须确认参与关系；否则写“在你有权查看的团队任务中发现……”。随后列具体依据，如“业务对象均为 9 月新品发布会，交付均为媒体邀请名单，执行时间重叠；请确认是否是同一项工作”。只有标题相似时，只说标题相近，不编造目标或时间命中。

#### 人员匹配：先过门槛，再比较

1. **有效性门槛**：只推荐授权可发现、当前团队有效且可被选择的成员；外部发言人不是可指派成员。
2. **显式人选优先**：用户点名后先校验资格；若责任不匹配，说明差异让用户决定，不能悄悄换人。
3. **Owner 完整性门槛**：正式责任必须覆盖整项结果，而非仅命中某个词。只会维护版本、协调或复核的人，不自动成为完整交付的 Owner。
4. **候选比较顺序**：责任范围吻合度 → 同业务对象或同类交付的可核对经验 → 当前明确承诺的协作窗口。证据不足保持未知，不推断私人忙闲。
5. **参与者按贡献选择**：每个人都写“承担什么贡献”。Owner 不重复出现在参与者列表，不把全团队塞进去。
6. **无人匹配**：返回 `memberId:null` 和责任缺口，允许用户暂不分配；创建者、主管、列表首人都不是兜底负责人。选他人只形成待接受提议。

匹配百分比是推荐强弱，**不是胜任概率或绩效评价**。建议生产端只在有校准规则和可追溯依据时输出 `matchScore:0..100`，否则为 null 并显示“待评估”。颜色按 ≥80 绿色、50–79 橙色、<50 红色；同时保留数字和理由，不只依赖颜色。

当前原型实际算法：任务文本与角色、责任文本的关键词交集数量为 n；n>0 时 `min(98,58+8×n)`，无命中为 52。它不检查整项责任覆盖，也不会产生低于 50 的结果；不能将它作为生产匹配质量依据，红色分档仍需独立覆盖。

#### 依赖判断的核心

按“消费者 Task × 必须交付的结果”逐项核对。每个结果先锁定实际生产者，再分类：直接依赖、已有中间任务传递、仅引用原始资料、无关。文件被引用不必然形成任务依赖；前置任务已完成也不意味着应删掉依赖。

最终依赖 = 原有依赖 + 本轮必要的直接生产者 − 有证据已失效的旧依赖。检查“已有图 + 候选变更”无环且日期可行；不能为了展示 AI 做了事而改写没有变化的下游任务。

#### 输入与输出契约

| 方向 | 关键字段 |
| --- | --- |
| 输入 | `requestId / message / currentUserId / teamId / currentDate / timezone`；`revision / confirmedFields / currentTaskId`；`context.tasks / members / discussions / files / history / sourceRefs` 及真实读取覆盖；`duplicateSearch` 和硬约束 |
| 输出头 | `schemaVersion:agentdoor.task-plan.v0.2`、`requestId`、`baseSnapshotId`、`baseRevision`、`baseTaskVersions`、`intent`、`disposition`、`summary` |
| 方案 | `proposal:{rootTaskId,complexity,changes,preservedTaskIds}`；每项 change 有 `id / action:create或update / targetId / parentId / fields / reason / evidenceRefs` |
| 候选字段 | `title / goal / acceptanceCriteria / tips / ownerRecommendation / participantRecommendations / schedule / estimate / dependsOnTaskIds`；标签由现有页面承载，v0.2 Schema 未定义标签字段，接入时须显式扩展或单独适配 |
| 人员与投入 | Owner 为 `{memberId,basis,reason,evidenceRefs}`；参与者为 `{memberId,contribution,evidenceRefs}`；兼容估算为 `{ewdHours,basis,assumptions,evidenceRefs}`，ewdHours 仍为小时，显示人天时除以 8，未知 null |
| 分流 | `ready_for_confirmation` 可审阅；`needs_clarification` 补问或补读；`route_required` 转已有任务或查询；`no_change` 无需变更。附 `duplicateCheck / questions / warnings / nextActions`，`externalEffects` 固定为 `none` |

**提交边界**：用户确认绑定草稿 revision、对象版本和具体差异摘要。服务端重验权限、成员、依赖、幂等并原子创建整棵树；双击或网络重试返回同一结果。成功直接进入任务详情，不停在“任务已创建”中间页。Mock 场景只演示并复用演示对象，不反复持久化新任务。

**接入差异**：界面已确认“允许未分配创建”，planner 参考文档仍有“不能创建无人承担的正式结果”的旧句；接入前应以本 PRD 的现行规则统一，不能把无 Owner 当成硬校验失败。澄清题的三项候选、当前题号和自定义答案也需在协调层补充，现有 planner questions 只包含问题文本等字段。

### 7.4 任务状态分析 Skill

**解决什么**：把散落在任务属性、子任务、讨论和交付记录中的事实，整理成“现在怎样、下一步做什么、完成多少”。它不等于诊断报告，也不改 TaskStatus。

#### 分析顺序

1. 读取当前 Task、目标和完成标准版本、可见后代、正式依赖、相关讨论、FileVersion / Commit、有效 EWD 与验收快照。
2. 分清事实层级：正式状态、正式确认、成员自述、AI 推测分别保存。讨论“我做完了”只能表述为某人报告完成。
3. 对照标准归纳已核对产出、尚缺结果和最近变化；优先引用同快照的诊断结果，不重新发明另一套阻塞结论。
4. 生成一句当前状态摘要和少量必要要点；缺资料就写缺口，不写“进展顺利”。
5. 推荐下一步可执行动作：核对冲突 / 解除阻塞 / 补齐关键结果 / 继续交付；说明谁以什么正式责任处理，不替人接受或承诺。
6. 引用同快照的工时与进度评估 Skill 结果及代码汇总，接入完成百分比、子任务分布和燃起图。状态模型只能解释这些结果，不能另行生成或改写数值。

#### 完成进度：由代码计算

有效范围 S = 当前范围中叶子 Task 的有效 EWD 总和；已验收 A = 同一范围、同一口径下有正式验收依据的叶子 EWD 总和；完成度 P = A ÷ S。

| 条件 | 输出 / 展示 |
| --- | --- |
| EWD 全覆盖、S>0、验收记录读取完整 | 展示 P；完整空验收集合可得到 0%，不是从“待开始”状态推出来 |
| 部分缺估、范围已变、记录未读或不可用 | `progressRatio:null`，显示缺估或待核对；不能把缺失部分按 0 补齐 |
| S=0 或 A>S 等非法关系 | 不计算百分比，提示口径异常；不强行截到 100% |
| 子任务标记已完成但无验收 | 可以总结“标记已完成”，不能计入 A |
| 只有一个历史快照 / 没有历史 | 单点 / 无趋势，不用当前估算补造过去历史 |
| 达到 100% | 表示有效范围的已验收比例，不自动关闭父任务 |

**页面**：百分比旁显示预计投入；说明图标区分正式验收与 AI 候选来源，采用第 6.3 节文案。总进度条下不放“已验收 0 / 范围”图例，有子任务时改为一行“子任务投入与进度 · 展开”，不重复总工时。展开后名称黑色加粗，可进入详情；第二行左侧“预计 1.25 人天 · 占总投入 25%”，右侧显示同一口径下的完成度。下方条宽只表示该子任务自身完成度，不再乘以投入占比。缺估不补占比，验收记录未知不补完成百分比；无记录时显示“进度未知”和灰色空进度条，无彩色填充。父级只汇总叶子且不重复计数，燃起图继续使用正式验收快照，不混入 AI 候选值。

#### 建议输出契约

| 字段 | 含义 |
| --- | --- |
| `taskId / snapshotId / asOf / sourceVersions` | 当前对象与分析依据版本；时间来自真实数据，不因重渲染更新 |
| `summary:string` | 一句状态总结，明确“标记完成”和“已验收”的区别 |
| `facts[] / gaps[]` | 每项 `{text,evidenceRefs}`；缺口不伪装为已证实风险 |
| `nextActions[]` | `{text,targetTaskId,responsibleMemberId:null或string,evidenceRefs}`；用于展示建议，不是可直接执行的命令 |
| `progress` | 计算服务返回 `state / progressRatio:null或0..1 / scopeHours / acceptedHours / coverage / breakdown / history`；Skill 不改变原始数值，小时字段在展示时除以 8 转为人天 |
| `diagnosisRefs[] / freshness / coverage` | 链接同快照诊断、标记有效性和读取范围 |

触发：首次打开，相关事实保存或同步后，或用户明确刷新。字段、讨论、交付、验收或范围版本变更时失效；仅切页签、展开图条、输入未保存草稿不触发重分析。当前原型没有生产验收事实服务；有估算就回落到 0 的本地行为不能替代“验收集合已完整读取”的生产条件。

### 7.5 任务诊断 Skill

**解决什么**：指出当前任务和可见后代中的具体执行障碍与相互冲突的决定，并给用户可核对依据。首版只有以下两类，不增加健康分、人员评价或完成概率。

| 类型 | 成立条件 | 示例与不成立情况 |
| --- | --- | --- |
| 执行阻塞 | 有正式 `dependsOnTaskIds`，且可见前置尚未完成；当前消费者不是已完成或已取消 | “上线执行依赖素材审核，审核仍未完成。”只有父子归属不算依赖；看不到前置只算覆盖缺口 |
| 决策冲突 | 至少两个不同的正式来源表达不相容事实，保留两侧来源和版本 | “消费者标记完成，前置仍未完成”；“主任务已完成，仍有未完成且未取消后代”。单条发言不能独立判定冲突 |

分析步骤：先建可见任务树及依赖图 → 检查执行前置 → 比对有正式来源的冲突 → 去重并定位实际受影响 Task → 给出影响、建议和依据。日期比较仅在两端日期明确可比时进行；前置交付晚于消费者窗口才提示时序问题。

**不归入诊断**：缺少负责人在属性栏处理；缺验收证据在状态分析中说明，待标准与证据可靠关联后再决定是否扩展诊断类型。任务长期无消息不能自动判定停滞。

#### 建议输入与输出

| 方向 | 字段与约束 |
| --- | --- |
| 输入 | `taskId / tasks / visibleDescendants / dependencyRefs / confirmedDecisions / sourceRefs / sourceVersions / coverage / asOf`；不可见依赖不把缓存名称、状态或数量交给模型 |
| 单条诊断 | `{id,affectedTaskId,type,conclusion,impact,suggestion,evidenceRefs,sourceVersions}`；type 为 `execution_blocker` 或 `decision_conflict`（建议协议名） |
| 证据 | 阻塞含消费者的正式依赖与前置状态；冲突至少包含两个不同源对象的完整事实句；每个引用都能定位本轮可见版本 |
| 报告 | `{taskId,snapshotId,asOf,coverage,findings,countsByType}`；ID 绑定实际问题与受影响对象，聚合到祖先时沿用同一 ID |

页面只读：问题结论作标题，展示影响和建议，依据默认收起。不提供“一键修复、忽略、改期、完成”等操作，也不另建一个问题关闭状态；源事实修正后诊断自然变化。

重算触发：状态、日期、正式依赖、后代增删、前置可见性、正式决定及证据版本变化。空结果只说明“当前可见范围内未发现这两类问题”，不等于任务无风险或已通过验收。

### 7.6 任务优先级推荐 Skill

**解决什么**：为当前用户从其正式负责的 Task 中排出处理顺序。排的是原任务，不生成新的待办，也不把其他人的执行任务转给当前用户。

#### 候选与排序

1. 从当前团队授权快照读取全部正式 `ownerId=currentUserId` 的 Task；排除待接受、未分配、已完成和已取消项，按 Task ID 去重。
2. 不受左侧搜索、标签筛选或折叠影响。父任务体现统筹责任，本人同时负责子任务时分别表达整合与执行，不重复安排同一个动作。
3. 复用状态分析和诊断中的可信信号：截止压力、阻塞、前置、状态冲突、待核对交付、信息过期。每个优先原因必须能回到本 Task 的事实。
4. 先用确定性规则排序，再由 Skill 压缩成一句原因；模型不能凭个人偏好覆写输入顺位。
5. 同分保持稳定顺序。业务日期按团队时区计算；实际跨日或任务数据变化才重新计算，而不是每次打开页面随机洗牌。

#### 当前原型的可复现规则

以下是现有 `agentPriorityScore` 的真实内部加分，用于解释原型，不是已经验证有效的生产权重。生产采用前须用真实案例校准；分值不向用户显示。

| 信号 | 当前内部值 / 避免重复规则 |
| --- | --- |
| 截止状态（取一项） | 逾期 +400；今天到期 +300；未来到期 +20；日期无法解释 +35；无日期 +0 |
| 主要问题（取一项） | 阻塞 +110；状态冲突 +100；前置依赖 +80；交付依据 +60；关键信息未知 +50 |
| 其他条件 | 关联前置处于阻塞 +20；待审核且主要问题不是交付依据 +40；信息过期 +25；信息缺失且主要问题不是未知 +10 |
| 排序方式 | 总分降序，同分保持传入顺序；上游先按期限、日期和原顺序稳定排列 |

例：两个任务都今天到期，A 存在前置依赖而 B 无其他问题，则原型为 A=300+80、B=300，A 在前；页面只显示“A：今天到期，前置交付尚未完成，需先核对可推进范围”。无日期 +0 只表示没有时间压力加分，不意味着任务不重要。

不使用：任务条数推断忙闲、聊天频次、在线状态、私人日历、EWD 倒数、没有证据的商业价值或精确完成概率。不能把“工作量小”直接等同于“应该先做”。

#### 建议输出契约

| 字段 | 用途 |
| --- | --- |
| `userId / teamId / snapshotId / asOf / ruleVersion` | 绑定个人、范围、真实分析时间与算法版本 |
| `items[]` | `{taskId,rank,priorityReason,evidenceRefs}`；前端只展示顺位、任务名、一句原因，点击回原 Task |
| `coverage / freshness / excludedReasons` | 内部解释数据是否齐全、为何排除；不得通过数量或文字泄露隐藏任务 |

有部分数据缺口时保留可核对任务并提示分析范围有限；请求失败不把旧顺序冒充最新。页面“AI 分析规则”默认收起，只解释候选范围、信号和不自动改任务，不展示内部加分表。

### 7.7 工时与进度评估 Skill

**建议名称**：`agentdoor-task-effort-assessor`。本次完成技术设计，不表示模型服务或可执行 Skill 已上线。

**解决什么**：创建方案时回答“预计投入多少、主要花在哪里”；执行中回答“哪些结果已经有证据、还缺什么”。同一套叶子估算供总工时、分布和进度使用，避免三个位置各算一遍。它不负责拆建 Task、分配人员、生成状态摘要或改变正式验收。

#### 核心判断步骤

| 步骤 | 判断与处理 | 结果 |
| --- | --- | --- |
| 1. 固定本轮范围 | 读取当前目标、完成标准、任务树及版本；多层任务展开到有效叶子，按 Task ID 去重。取消或删除项不计入当前范围，独立任务视为一个叶子。树不完整时不能报完整总工时。 | 本轮叶子集合、范围摘要、读取缺口 |
| 2. 检查历史能提供什么 | 当前只有用户提交修改记录与状态变更时间，没有人类实际投入记录。时间戳仅用于还原事件先后与历时；有权读取的具体修改内容才能帮助识别工作步骤、范围差异或返工原因。不能将记录间隔、提交次数或状态持续时间换算为人类工时。 | 实际可用的历史上下文；明确未用实际工时校准 |
| 3. 估每项人类净投入 | 在每个叶子内部评估资料准备、制作／执行、校验、合理返工的时间；这些是估算分项，不自动新建子任务。AI 生成、工具运行、等待反馈只计算人类实际参与的部分，多人协作先累计人工分钟，再换算人天、共享工作只算一次。 | 预计分钟、上下界、分项依据、假设、信心等级 |
| 4. 汇总投入分布 | 由代码验证非负整数分钟、范围与估算版本；完整覆盖时求总和并计算每项占比。部分缺估只给已估部分，不将已知子集重新归一为 100%。 | 总工时、覆盖率、按工时降序的子任务分布 |
| 5. 核对当前完成情况 | 对每项完成标准匹配当前有效交付物、文件版本、正式验收和成员自述。AI 判断“证据支持／未达成／未知／冲突”，历史样本只能帮助理解交付难度，不能证明当前结果已完成。 | 标准级候选判断、来源、缺失项；无记录不当作未完成 |
| 6. 计算并发布分析 | 有有效标准权重和完整证据覆盖时，由代码汇总 AI 候选完成度；正式验收完成度另按验收记录计算。返回绑定版本的只读分析，失效结果不覆盖新版本。 | 候选评估、正式进度、更新时间与待核对项 |

#### EWD 预计工作量计算规则 v0.2

**对任务的价值：** 预计投入人天表示完成任务预计需要的总人工工作量，帮助团队看清任务规模、投入主要花在哪里，并按工作量衡量完成进度。

**单位统一：** 预计投入及燃起图数据以人天展示，1 人天＝8 人时＝480 分钟；典型值显示最多两位小数。计算与保存继续使用原始分钟，区间及微量显示规则见第 3.8 节。兼容的 ewdHours、scopeHours 等旧字段保留小时语义，在展示时除以 8，不将字段名不变而数值偷偷换成人天。

> 2026-09-03 算法设计。产品负责人已明确要求将历史与人员经验的作用、EWD 和完成度评估详细写入 PRD；具体字段与校验为本节实现建议。用途是帮助用户理解预计工作量及其分布，下列算法尚未接入运行代码，未使用实际工时校准；不改变现有正式验收数据来源。

**对象与成功标准。** 为创建或查看任务的用户估算当前范围预计需要的人类总投入。用户应能看懂工作主要花在哪里、数字依赖什么假设；研发应能从同一份估算分项复算出相同的总数。EWD 不用于推断员工效率、个人容量、实际耗时、剩余投入或交付日期。

**1. 先确定能否估算。** 每个末级任务至少需要：交付物、数量或可界定的规模、完成标准、材料准备情况及人／AI 分工。优先读取现有任务和授权上下文，不新增必填工时表单。非关键缺口可提出显式假设，例如“按已有资料、一次审核估算”；交付边界、规模或关键制作方式无法界定时返回未知和具体缺口，不套固定工时。只知道“做一份方案”不足以估算。

**2. 在叶子内部拆估算分项。** 根据实际工作保留资料准备、制作执行、必要沟通、审核、修改、验收中的相关项，不强制每项齐全，不因此自动新建子任务。每个分项必须对应当前交付或标准，并记录：工作内容、计量单位、数量、单次人类耗时、参与人数、轮次及依据。固定的一次性工作可以写作“1 次”；没有依据不能假设所有参与人全程投入，未知的审核人数或轮次也不能悄悄设为 1。

**3. 单次耗时来自明确的估算假设。** 接入后由模型结合分项内容、资料量、质量要求和工具分工，给出单次人类投入的下界、典型值与上界，单位整数分钟，满足 `0 ≤ 下界 ≤ 典型值 ≤ 上界`。典型值代表在列明假设下模型认为通常需要的投入，不是从时间戳计算出的事实，也不采用区间中点冒充实测均值。

- 每个数值必须能解释对应的人工动作。例如“逐页核对事实与改写”需要人工时间，“AI 后台生成”不计人工时间；阅读材料、准备提示与检查生成结果分别计入相应分项。
- 范围一致时，材料是否齐备、是否已有模板、是否需独立核查等具体差异通过对应分项的增删、数量或单次耗时体现；不叠加统一的“复杂度系数”“紧急系数”“AI 提效折扣”或默认返工百分比。
- 预计审核和修改分别列出有边界的轮次。已包含的一轮修改不能再乘一次返工系数；无限修改、未知审批轮次不得用任意固定上界隐藏。
- 当前纯模型耗时均标为低信心、未经实际工时校准。上下界是工作假设下的粗估范围，不是统计置信区间或交付承诺。模型自述“很有把握”不能提高数据可信度。
- 若用户主动提供适用于当前范围的投入估计，可以明确引用为用户估计；已有历史估算只能标为“参考历史估算”。未来有真实人类投入记录时，另行校验可比性并设计校准，不能提前宣称当前已经支持。

**4. 确定性计算。** 模型只提供带依据的分项参数，由代码执行以下运算：

```text
分项人工投入分钟 = 工作数量 × 每单位每人每轮耗时分钟 × 必要参与人数 × 轮次
叶子 EWD 分钟 = 该叶子所有分项人工投入分钟之和
任务总 EWD 分钟 = 当前范围全部有效叶子的 EWD 分钟之和
展示 EWD 人天 = 任务总 EWD 分钟 ÷ 480
子项投入占比 = 子项后代有效叶子 EWD 之和 ÷ 任务总 EWD
```

下界、典型值、上界分别代入并求和，典型值作为 EWD 点估算。总区间只表示这些假设组合下的粗估范围，不能声称具有统计覆盖概率。无需以 PERT 加权、简单平均或取上界替换典型值。任一参数未知时，该分项和所在叶子的完整估算为未知；可保留已有分项，但不能把它们的和当作完整叶子 EWD。

参与者耗时不同时分别建分项，例如起草人与审阅人分开计算；只有同一工作、同等参与时长时才能乘人数。相同人的同一段投入不能在重叠分项重复计算。数量可以按页、份、条、批或一次性工作计量；只有各单位工作近似同质时才可线性相乘，固定准备投入单独列出，复杂内容不机械按页数估时。最终结果保存为非负整数分钟；不可精确得到整数分钟的参数需修正并注明，不能静默截断。合计与占比使用原始分钟，仅展示时格式化。

**5. 汇总边界。** 展开至叶子并按 Task ID 去重，父级旧估算不再另加；共享工作只归入一个明确分项或拆分实际贡献，不能在多个叶子重复记整份投入。若有必要的父级统筹工作尚未被任何叶子覆盖，标记范围缺口，待明确归属后再报完整总量，不擅自加到父级或自动新建任务。明确退出当前范围的任务不计入。任何叶子缺估、过期、读取不完整或无权限，均不报完整总数和投入占比；可以显示有权限且仍有效的“已估部分”，不将已知子集重新归一为 100%。确有依据的零投入保留为 0，总量为 0 时占比为空。

**6. 更新规则。** 交付规模、材料假设、完成标准、必要参与方式、审核轮次或人／AI 分工变化后，原估算需核对并生成新候选版本。普通状态变更、单次提交、修改次数增加或时间流逝本身不自动增加 EWD。只有修改内容证明范围或估算假设变化时才触发重估；实际执行的一轮修改若已在原估算中，不重复加算。父级在叶子变化后重新汇总。相同输入、规则版本和已有候选复用同一结果，避免每次打开页面重新生成数字；新候选不静默覆盖已采用版本，不回写历史进度。

**7. 最小呈现。** 复用现有“预计投入”和说明入口，展示点估算及“粗估”提示；说明中提供范围、主要工作假设和“未使用实际工时校准”。无需新建估算页面或要求用户逐项填工时。分项用于复算和依据，不新增常驻投入明细区。

| 情况 | 呈现规则 |
| --- | --- |
| 范围完整、估算有效 | 例如“约 0.5 人天 · 粗估”；说明中显示“粗估范围 0.31–0.75 人天，按已有资料、10 页内容、一轮修改与两人审核估算” |
| 无足够范围信息 | “待估算”，说明具体缺口，不显示 0 |
| 部分缺估 | “已估部分约 X 人天”，有完整计数权限时可说明已估项数；不显示完整总量或占比 |
| 加载 / 失败 | “估算中”或“暂无法估算”；失败保留已有输入，可重试，不将旧值标成新结果 |
| 过期 / 数据异常 | “需重估”或“待核对”；旧值仅作为注明过期的历史参考 |
| 无权限 / 范围未读全 | “完整投入暂不可用”；不泄露隐藏任务的数量、名称或估算 |

说明入口继续支持鼠标、触屏与键盘聚焦，移动端允许文本换行，不能只依赖悬停读取假设。示例估算必须标明示例，不能只换成“模型粗估”就宣称已接入模型。

**算例（参数均为演示假设，不是通用标准或产品默认值）。** 假设材料齐备，整理成 10 页内部方案，AI 辅助起草，人工逐页核查并改写，包含一次整体修改和两名审核人各审核一轮。

| 分项 | 数量 × 人数 × 轮次 | 单次耗时：下界 / 典型 / 上界（分钟） | 人工投入分钟：下界 / 典型 / 上界 |
| --- | --- | --- | --- |
| 整理已有材料 | 1 次 × 1 人 × 1 轮 | 20 / 30 / 45 | 20 / 30 / 45 |
| 逐页制作与核查 | 10 页 × 1 人 × 1 轮 | 6 / 10 / 15 | 60 / 100 / 150 |
| 整体修改 | 1 次 × 1 人 × 1 轮 | 30 / 50 / 75 | 30 / 50 / 75 |
| 审核 | 1 份 × 2 人 × 1 轮 | 20 / 30 / 45 | 40 / 60 / 90 |
| 合计 | — | — | **150 / 240 / 360** |

得到 EWD 典型值 240 分钟，即约 0.5 人天；原始范围为 0.3125–0.75 人天，页面显示 0.31–0.75 人天。“每页 10 分钟”等仍是模型假设，公式只保证可解释与可复算，不把假设变成测量事实。等待审核两天不加工时；若只知道提交时间与完成时间，就无法得到此算例中的任何单次耗时。

**最小验收项。** 上述算例可复算为 150 / 240 / 360 分钟；同一工作两人各审核 30 分钟计 60 分钟；仅增加两天等待不改变估算；只有时间戳和模糊标题时返回未知；任一叶子缺估时不显示完整总量和占比；范围或假设变化使旧估算失效，普通状态更新不自动改估；有相同输入的已保存候选时复用结果。以上为文档规则的验收要求，不表示模型准确率或运行代码已通过验证。

待后续确认的实现事项：模型服务接入方式、现有点估算字段与区间分项的保存兼容。当前阶段不依赖用户新增打卡数据，也不承诺估算已达到可用于人员排期的精度。

#### 历史任务与人员经验如何进入 EWD

**先区分数据含义。** 目前的“历史完成效率”只能描述任务事件与历时，无法拆出人工执行、等待、并行处理和他人贡献。模型不能将创建到完成的时间、进入进行中后的时长、提交间隔、提交次数或按时完成率当作人类工时标签。记录一周没有变化也不能推出没有工作或能力不足。

| 可见数据 | 允许影响的估算内容 | 禁止推断 |
| --- | --- | --- |
| 提交或状态变更时间戳 | 事件先后、对应版本、可追溯来源；必要时单独解释历时 | 单次人工耗时、个人速度、默认每日有效工作时长 |
| 可读取的修改内容、交付物、明确反馈 | 当前可能需要的工作步骤、遗漏检查、返工原因；辨认哪些内容可复用 | 一次提交等于一轮业务修改；修改越多越低效 |
| 已存在且适用于当前任务的模板或材料 | 对应分项的工作数量、准备或制作方式，并写出仍需校验的内容 | 整项任务统一打折；所有历史成果默认可复用 |
| 与当前交付相关的本人经验说明或有来源的历史贡献 | 判断是否确需上手、培训、额外核查；必要时提出单次耗时调整假设 | 只因是历史 Owner 就认定由其独立完成；形成跨任务的个人效率分 |
| 旧任务的预计工时 | 在范围、标准与工具方式可比时引用为历史估算参考 | 将旧估算当实际耗时，将旧完成状态当作估算准确性验证 |
| 未来明确采集的实际人类投入 | 经过来源与可比性校验后，另行设计估算误差分析 | 用当前时间戳补造该数据；提前启用个人速度系数 |

**历史参考处理顺序。**

1. 只读有权限且与当前交付物、规模、质量标准、材料条件、人／AI 分工相关的任务；同名不代表可比，行业不同也不必然不可比。
2. 每条参考标记具体 Task ID、版本、实际读到的内容、相同点与差异；没有读取正文就不能引用为工作依据。历史不可用时仍可按当前范围粗估，不把历史读取失败当作已完成校准。
3. 先提取可以迁移的工作事实，例如“已有可编辑模板”“历史确有两轮合规反馈”；它们只是当前工作假设的参考。历史两轮不自动等于本次两轮，还需核对当前完成标准与审核约定。
4. 将差异落到第 7.7 节既有分项：增删工作、改变数量或轮次、调整指定分项的单次耗时范围。多个历史记录指向同一复用成果或返工原因时去重，不累加多次修正。
5. 无法落到具体工作的“这类任务通常很慢”“这个人效率很高”不进入数值计算。保留估算假设及缺口即可，不展示没有数据基础的精确效率系数。

**人员相关调整。** 只处理当前任务已经明确的能力与工作条件，不根据职级、聊天活跃、任务数量或在线状态猜速度。可以依据本人明确说明“首次使用该系统，需要先熟悉操作”，增加有边界的学习分项；不能因为没有查到相关历史，就默认是新手。可核实的经验说明可以支持“无需重复上手”的假设，但并不能直接证明每项人工动作快 30%。Owner 变更只在相关工作假设确实改变时触发重估，人员名字本身不是系数。

```text
当前分项参数 = 原范围下的估算参数 + 有依据的局部工作调整
当前 EWD = 对调整后的完整分项重新求和
```

这里的“+”表示修改相应工作参数，不是额外附加一层分数。若把准备工作从 30 分钟改成 15 分钟，就只替换该分项一次，不能再对总量乘模板折扣。每条调整保存 `componentId、before、after、reason、evidenceRefs、assumption`；变化后的工时仍是估计，来源事实不等于时间差已经实测。

**接续 0.5 人天算例。** 下列也是演示假设：已确认适用模板可复用，将材料整理典型值从 30 改为 15 分钟，其他项不变，则为 225 分钟，即 0.46875 人天，页面显示约 0.47 人天；另一种场景中，执行人明确需要熟悉新工具，并假设需要 45 分钟，则在原 240 分钟基础上新增学习分项，得到 285 分钟，即 0.59375 人天，页面显示约 0.59 人天。两种情况是不同工作条件，不是给两个人分别评为高效或低效。生产候选必须同步给出受影响分项的上下界；只得到新的典型值时不能沿用旧区间冒充完整新估算。

**暂不纳入的后续算法。** 有真实投入记录后，才可以比较同等范围、质量与工具条件下的估算误差；需区分本人投入与协作者投入、排除等待、控制范围变更并保留未完成样本。个人化时间系数的样本量、适用期限和误差要求需另行设计，本版不启用，也不以 EWD 自动评价绩效。

#### EWD、AI 候选完成度与正式验收完成度

| 数值 | 计算口径与边界 |
| --- | --- |
| 预计总工时与占比 | `totalMinutes = Σ leaf.estimateMinutes`；`share = leaf.estimateMinutes / totalMinutes`。全部当前叶子有效且 total>0 才有占比；有效零投入保留为 0，但零总量不计算比例。 |
| AI 候选完成度 | 先把完成标准拆成可核对的结果单元，并分配合计为本叶子 EWD 的权重分钟；只支持二值或明确的数量型达标比例，不凭文字情绪输出任意百分比。`suggestedCompletionRatio = Σ(权重分钟 × 证据支持比例) / 本叶子 EWD`。权重未明确、证据未读、未知或冲突时返回 null 和缺口，不默认等权或取 50%。 |
| 正式验收完成度 | `acceptedCompletionRatio = 正式已验收 EWD / 当前有效 EWD`；正式验收必须绑定相同范围与估算版本。候选完成度不得写入该字段，不替人确认验收，也不自动更新 TaskStatus。 |
| 主任务完成度 | 同一口径下按叶子 EWD 加权汇总，不平均子任务百分比；不混用部分 AI 候选与部分正式验收。范围变化需形成新快照，不能用新分母配旧分子，也不回写旧燃起图。 |

例如三项子任务的精确投入为 0.375、0.25、0.25 人天，总投入 0.875 人天（页面分别显示 0.38、0.25、0.25，总计约 0.88），占比为 42.9%、28.6%、28.6%。若中间一项有正式完整验收，其余两项的完整验收集合为空，则正式完成度为 0.25÷0.875=28.6%。AI 仅凭一条“已做完”的讨论不能把该任务计为已验收；若记录尚未读取，则显示未知与空条，不补 0%。百分比只在展示时四舍五入，内部保留精度。

#### 完成度评估算法：从证据到百分比

**用途与限制。** 完成度回答“当前范围的结果已有多少得到支持或验收”，与预计要花多少时间分别计算。EWD 是权重，投入时间、工作难度、人员熟练程度、历史完成速度都不是完成证据。相同结果和权重下，换执行人或多花一天不会提高完成度。

**A. 固定评估快照。** 读取当前任务树、范围、每个叶子的 EWD 版本、完成标准、相关交付版本、正式验收及读取覆盖。取消或删除的范围退出本次集合；范围未读全则不计算总体比例。同一快照分别计算候选与正式口径；某一口径不可用，不自动切换为另一个口径，状态模型也不重新输出独立百分比。

**B. 形成可核对的结果单元与权重。** 结果单元是叶子内部的分析结构，不自动创建 Task、检查清单或新验收流程。先按完成标准明确“什么结果算达标”，再将估算分项的典型分钟分配给对应结果：

- 每个结果关联一个或多个完成标准、可核对的交付对象和质量要求。一个结果必须同时满足几条标准时作为组合条件，不将每条描述分别当独立完成信用。
- 每个分项可全部分配给一个结果，也可明确拆分给多个结果，但同一分项的分配分钟之和必须恰好等于其典型分钟；所有结果权重之和必须等于该叶子 EWD。不得重复计量，也不得为了让当前进度更高而临时调整权重。
- 准备、沟通与学习等投入通常归入它们服务的交付结果；不因为开完会、学习完或操作过 AI 就单独认定交付完成。若这些活动本身就是明确约定的独立结果，可按其实际完成标准处理。
- 权重映射先随范围和估算形成候选，并记录采用的版本；每次进度刷新复用该版本。缺映射时输出标准级判断和“权重待明确”，不能按完成标准条数默认等权。
- 必须满足的整体质量或验收条件标为 `requiredGate`。有权重的结果支持比例可能为 100%，但只要必需条件未达标、未知或冲突，候选总体比例就不发布为 100%，返回 `null` 和未关闭的条件，不用 99% 掩盖。

**C. 根据当前证据判断达标比例。** 模型逐项返回判断、引用、缺口和可支持的比例，代码校验范围与数值。每条引用需要有可定位的对象及版本；模型只能判断实际读取的内容，文件名、附件数量或提交标题不足以证明内容符合标准。

| 结果类型或证据状态 | 比例规则 | 示例 |
| --- | --- | --- |
| 二值结果，完整证据支持全部条件 | `r = 1` | 当前方案与数据来源一致，指定核查条件全部得到证据支持 |
| 二值结果，有证据明确尚未达标 | `r = 0` | 已读交付明确缺少必需的预算章节；不能按写了一半给 50% |
| 数量型结果，固定范围内各单位可独立且同等验核 | `r = 达标单位数 / 总单位数` | 10 条独立规则中 5 条已逐条符合标准，r=0.5；同一单位重复提交只算一次 |
| 数量型单位工作量不同 | 为各单位明确权重后计算；没有权重则不可算 | 复杂接口与简单接口不能仅按条数平均 |
| 只读到“完成了”的讨论或完成状态 | `r = null`，记录为完成声明 | 可以总结成员自述，不能替代交付证据或正式验收 |
| 证据未读取、不可见、失效或内容不足 | `r = null`，标明具体缺口 | 没找到附件不等于工作尚未做；已读完整交付确实缺必需部分才属于明确未达标 |
| 同一结果有互不相容的有效证据 | `r = null`，标记冲突 | 一方确认预算冻结，另一有效版本要求修改预算；不取平均或选最新消息覆盖 |

数量型分母来自本轮约定范围，不能根据已经交付的数量倒推。只支持可独立判断且质量可核对的单位；“写了 5 页 / 计划 10 页”本身不代表完成 50%，必须明确这些页是否对应同等工作量的独立达标单元。分母未知、为 0 或达标数量超出分母时返回异常，不静默截断。除计量型比例外，不能从“基本完成”“还差一点”等文字生成 70%、90%。

**D. 计算 AI 候选完成度。** 使用点估算的典型分钟作权重，不用区间下界、上界或人员速度再加权。

```text
E_i = 叶子 i 的当前有效 EWD 分钟
w_ij = 叶子 i 的结果 j 分配到的权重分钟；Σ_j w_ij = E_i
r_ij = 当前证据支持的达标比例；取 0、1 或明确的数量比例
C_i = Σ_j(w_ij × r_ij)
P_i_AI = C_i / E_i
P_AI = Σ_i C_i / Σ_i E_i
```

任一影响结果的标准、权重或证据未知、冲突、过期，均不得把该项按 0 填入完整候选比例；该叶子候选为 `null`，总体候选也为 `null`，但其他可独立计算的子项仍可显示。只有所有必需条件均已判定、有效权重完整且分母大于 0 时才可发布数值。完整证据明确各项均未达标时可以输出 0%。加权后的中间分钟可为小数，计算保留精度，不把它当成实际工时记账；百分比只在展示时舍入。`requiredGate` 的阻断规则在发布 100% 前再次校验。

**E. 计算正式验收完成度。** 当前延续整叶子验收：同一范围、完成标准及估算版本下有合法有效的完整验收记录时 `a_i=1`；已完整读取并确认没有有效验收时 `a_i=0`；未读取、不可判断或记录版本冲突时为未知。提交交付物、修改 TaskStatus、AI 判断 100% 均不能生成验收记录。

```text
A_i = E_i × a_i
P_accepted = Σ_i A_i / Σ_i E_i
```

只有全部当前叶子估算有效、验收资格可判定且分母大于 0 时，才发布正式百分比。当前不为叶子内部的部分 AI 达标结果写正式验收工时；如未来支持部分正式验收，需要另定结果单元验收权限与账本，不从本节候选公式自动推导。中间层任务可能是 60%，它来自后代叶子加权，不代表单叶子已支持任意正式百分比。

确有依据的零 EWD 叶子不增加工作量分母，也不产生完成信用；自身加权比例为空，必需交付与验收仍需独立核对。因此加权进度达到 100% 也不能自动关闭任务。EWD 本身是粗估时，正式比例表示“按当前估算权重的验收覆盖”，不代表实际投入已完成同样比例。

**F. 已知、未知和冲突分别返回。** 无生产验收读取能力时正式比例是未知，不能假设验收集合为空从而显示 0%。整叶子已验收，但某条新交付证据否定当前标准时，候选评估标冲突；正式验收投影依据独立的有效性规则处理，不能由 AI 自行撤销。旧范围验收不能与新 EWD 拼接，需明确复核并绑定新版本后才能用于新的正式投影。

#### 完成度算例与变化后的结果

**同一叶子，两种读数。** 沿用方案任务 EWD=0.5 人天（240 分钟），演示性地将工作映射为三个不重叠结果。映射假设先固定，不根据当前完成情况调权重。

| 结果 | 分项权重如何分配 | 证据支持比例 | 加权支持分钟 |
| --- | --- | --- | --- |
| 范围与资料结论明确 | 准备 30 + 制作中的 30 = 60 | 1 | 60 |
| 10 个同等工作量的内容单元符合各自标准 | 剩余制作 70 + 修改 50 = 120 | 5 / 10 | 60 |
| 完整方案通过约定审核条件 | 审核 60；必需条件 | 0，证据明确待修正 | 0 |
| 合计 | 240 | — | 120 |

因此 AI 候选完成度为 `120/240=50%`。这里的 10 个内容单元是假设可独立验核的结果，不是仅根据页数计数。若正式验收集合已完整读取且为空，则正式完成度为 0%；若未能读取验收，正式完成度是未知。若第三项只有“等待审核”的文字而没有足够证据判定是否达标，第三项应为未知，不能套用表中的 0，整体候选也暂不可算。

**父任务加权。** 另有一个 0.25 人天（120 分钟）的叶子，候选达标与正式验收均为 100%。范围只有这两个叶子时：AI 候选为 `(240×50%+120×100%)/360=66.7%`；在前一项正式验收已确认是 0 的前提下，正式完成度为 `120/360=33.3%`。不能将两项候选简单平均成 75%，也不能将第一项的 AI 50% 混入第二项的正式验收来显示“正式完成 66.7%”。

**范围与返工。** 若新增一个 0.25 人天（120 分钟）的叶子，已有两项的范围、权重和验收仍有效，且新增项验收集合已确认为空，则正式进度由 `120/360=33.3%` 变为 `120/480=25%`，原因是范围扩大。新增项缺估时新总进度为未知。若已完成结果发生明确返工，候选按新证据重评；正式线只有有效验收撤销或失效事件才减少，普通修改记录不直接扣减。

#### 刷新与失效矩阵

| 变化 | EWD 处理 | 完成度处理 |
| --- | --- | --- |
| 交付数量、完成标准或任务范围变化 | 受影响叶子需重估，父级重汇总 | 受影响权重与判断失效，重新核对证据及验收适用版本 |
| 模板可复用、人／AI 分工或人员工作假设改变 | 只调整有依据的分项；候选保存新版本 | 原始证据可保留，权重需重新绑定；不把重估本身解释为完成了更多工作 |
| 提交新的交付版本、出现相关修改或反馈 | 内容改变范围或估算假设时才重估 | 重新核对关联标准；旧文件结论不能自动覆盖新版本 |
| 仅状态变化、截止变化或等待时间增长 | 不自动改变 EWD | 可以触发状态冲突检查，不从状态或时间推导百分比 |
| 有效验收、撤销或正式有效性变更 | 不自动增加 EWD | 按受控记录更新正式投影；候选可引用有效证据，但不覆盖正式记录 |
| 历史参考读取失败 | 已采用且范围未变的估算保持；新估算注明未参考历史 | 不影响已有当前交付证据的效力，不伪称校准完成 |
| 当前范围或必需证据失去读取权限 | 不泄露历史缓存；完整汇总不可用 | 相应比例不可用，显示缺口，不把不可见当作未完成 |
| 重复打开页面或收到相同输入 | 复用同版本结果 | 复用结果，不刷新数据截至时间或重复生成历史点 |

燃起图沿用正式验收与范围事件形成的版本化快照，每个点的分子、分母来自同一时点和口径。新增范围、改估、撤销验收分别记录原因；不将 AI 候选写成验收历史，不使用今天的估算重算并覆盖过去的曲线。人员或方法调整可能改变工作量权重，即使交付数量未变也会使百分比变化，说明应写“估算口径调整”，不能说“工作效率提高”。

#### 输入、输出与接入

| 方向 | 建议字段 |
| --- | --- |
| 输入范围 | `mode:create或review`、`taskId`、`snapshotId`、`sourceVersions`、`scopeDigest`、`leafTasks[]`；每个叶子含完成标准、数量、材料条件、工具方式、人员相关工作假设及已有估算版本。 |
| 输入证据 | `historySamples[]`、`personContext[]`、`deliverables[]`、`discussions[]`、`acceptanceRecords[]`、`evidenceRefs[]`；历史类型区分 `event_only / content / estimate / actual`，当前没有 actual 数据时不得生成该类型；personContext 只含授权的任务相关事实与明确声明，不含推导的效率分。 |
| 读取覆盖 | `coverage:{scope,history,personContext,deliverables,acceptance}`；各类为 `complete / partial / unavailable / not_requested`，配来源版本及缺口。只有 complete 才能将空数组解释为完整空集合；scope 不完整时总叶子数量保持未知，不能暴露隐藏计数。 |
| 叶子估算 | `estimates[]:{taskId,state,estimateMinutes,estimateRangeMinutes,components[],adjustments[],assumptions[],sampleRefs[],basis,confidence,estimateVersion,scopeDigest}`；分钟或区间可为 null。basis 区分 `model / user_estimate / historical_estimate / mock / unknown`，是分析来源，接入时映射现有存储类型，不直接改写既有 enum。当前纯模型为低信心，mock 始终显示示例。 |
| 投入分布 | `distribution:{state,totalMinutes,knownMinutes,estimatedCount,totalCount,rows:[{taskId,estimateMinutes,share}]}`；完整总分钟、总项数或 share 无法确定时为 null。合计、占比和排序由代码生成，模型不返回另一套总数。 |
| 完成情况 | `completion:{suggested:{state,ratio,reasonCodes[],gaps[]},accepted:{state,ratio,reasonCodes[],gaps[]},resultUnits[],criteriaAssessments[],evidenceRefs[]}`；两种口径各自有状态，不因正式记录不可用而清空有效候选，也不以候选填正式未知值。映射旧字段时分别输出 suggestedCompletionRatio 与 acceptedCompletionRatio，不混入 progressRatio。 |
| 结果版本 | `assessmentId,asOf,inputDigest,skillVersion,ruleVersion,modelVersion,sourceVersions,estimateVersion,criteriaVersion,weightVersion,scopeDigest`；协调层校验引用真实、版本适用、输入未变后才允许发布，候选尚未采用与已采用版本分别保存。 |

字段名是协调层的建议合同，不代表当前 MCP 或数据库已有对应字段。具体分项与结果结构至少保留以下信息：

| 结构 | 最小字段及约束 |
| --- | --- |
| `components[]` | `id, work, unit, quantity, people, rounds, unitMinutes:{low,typical,high}, assumption, evidenceRefs[]`；计量参数有限且非负、人数及轮次为正整数，单次分钟为非负整数；零工作量必须有依据。未知参数为 null，不代入默认值。 |
| `adjustments[]` | `componentId, before, after, reason, evidenceRefs[], assumption`；同一事实不重复修正，对应分项原值与新值可追溯，保留区间变化。 |
| `resultUnits[]` | `id, taskId, criterionIds[], kind:binary或quantity, requiredGate, allocations:[{componentId,minutes}], weightMinutes, assessment, supportedRatio, numerator, denominator, evidenceRefs[]`；quantity 需明确单位身份与去重规则；binary 不接受任意小数。 |
| `criteriaAssessments[]` | `criterionId, resultUnitId, assessment:supported或not_met或unknown或conflict, evidenceRefs[], explanation, gaps[]`；标准编号稳定，同一标准关联多个对象时说明组合关系，不能重复算权重。 |
| 验收读取投影 | `taskId, outcome, sourceRef, scopeDigest, criteriaVersion, estimateVersion, validAsOf`；由正式验收服务或显式本地示例提供，不由模型填充“已验收”。 |

**代码校验与调用次序。**

1. 校验身份和读取覆盖、任务树结构、叶子去重及当前范围；范围不全不发布总体比例。
2. 模型生成估算分项和证据引用，代码校验数值、单位、有限值、整数分钟及上下界顺序；汇总超出安全数值范围则拒绝，不静默截断。模型不直接决定总工时。
3. 采用或复用估算版本后，校验分项到结果的权重映射：逐分项分配守恒、逐叶子总权重等于 EWD，且完成标准均有核对路径。缺口返回明确原因，不自动均摊。
4. 模型只返回当前标准的证据判断及可核实的计数；代码执行数量去重、比例界限和必需条件校验，再计算候选比例。
5. 独立读取验收投影，校验资格与版本，计算正式比例。完整空集合与读取失败不同；候选有效不构成正式读取成功。
6. 按同一口径汇总父级，并检查 `inputDigest` 和来源版本是否仍然一致；仅发布与当前输入一致的结果。重试复用相同输入的已保存结果，旧异步响应不得覆盖新范围。

状态建议统一为 `available / partial / unknown / stale / invalid`，口径分别保存。原因码至少区分 `scope_incomplete、estimate_missing、estimate_stale、weight_unresolved、evidence_unread、evidence_conflict、gate_unmet、acceptance_unavailable、version_mismatch、zero_total、invalid_number`，供界面转换成简短中文说明，不直接把技术码展示给用户。单项可算而总量不可算时保留单项，不伪造总体值。

创建 Skill 完成候选拆分后调用本 Skill，把估算回填到原草稿，最终用户确认才保存。状态分析 Skill 引用同快照评估并组织现状与建议，不重新估工时；诊断和个人排序仍沿用自己的规则，不因工时小就提高优先级。

MCP 复用第 8 章已有任务、后代、讨论、文件版本读取能力，不新增能直接“写完成百分比”的工具。EWD 粗估不以实际工时为前置，AI 候选需要当前交付证据与已采用的权重映射，正式比例需要独立有效的验收读取。相关生产契约未齐全时只使依赖该数据的输出不可用，不伪装成现有 MCP 已支持。若需新读接口，另行确认参数与权限，当前 38 个候选工具清单不变。

#### 刷新、页面与验收

- 创建方案生成后首次估算；后续依照本节刷新矩阵分别更新估算、权重、候选判断或正式投影，交付及验收变化不默认触发工时重估。只展开明细、切页签、输入未保存草稿不触发；相同 `inputDigest` 复用结果。
- 调整范围或方法时新建估算版本，原值及历史快照保留。异步返回先核对版本，过期响应丢弃；失败保留输入，旧分析注明过期，不冒充最新。
- 页面总投入只在整体百分比旁展示一次；子任务名称黑色加粗，每项保留预计工时、占比和自身进度条，未知保留空轨道。说明图标兼容鼠标、键盘与触屏，按正式、候选或示例来源分别说明。加载与失败显示对应提示，过期不冒充当前；无权限不泄露内容，窄屏允许说明换行。
- 当前页面继续使用本地估算与账本计算的 `progressRatio`，不因为加了提示就宣称 AI 已上线。本次新增的 `suggestedCompletionRatio` 为未来接入候选字段，不覆盖现有正式口径；未来若用它作为主读数，必须显式标“AI 估算完成度”，不能无标识替换。
- 最小验收：同一叶子不重复计入；0.875 人天（显示约 0.88）示例各处一致；无样本可降级、缺估不补 0；AI 自述与正式验收不混；旧范围响应不能覆盖新结果；未知进度有空条；历史不可见时不泄露任务信息。

**算法验收矩阵（研发接入要求，不代表已运行生产模型测试）。**

| 输入或事件 | 必须得到的结果 |
| --- | --- |
| 0.5 人天算例四个分项 | 区间及典型总量为 150 / 240 / 360 分钟 |
| 原始算例准备项 30 改为 15，其他典型值不变 | 225 分钟，只修正一次；新上下界缺失时不能沿用旧区间 |
| 原始算例新增明确的学习投入 45 分钟 | 285 分钟，依据是工作差异，不产生个人效率分 |
| 同一任务仅历时从 1 天变为 3 天 | EWD 与证据支持比例不自动改变 |
| 240 分钟叶子，结果权重 60 / 120 / 60，证据比例 1 / 0.5 / 0 | 候选 50%；正式完整空验收时为 0%，验收未读时为未知 |
| 其中任一结果证据未知或冲突 | 候选为 null，有效的其他结果判断保留 |
| 所有正权重结果支持 100%，另一个必需条件未达标或未知 | 不发布候选 100%，返回 null 和条件缺口 |
| 一个分项被重复完整分配，或权重合计不等于叶子 EWD | 拒绝计算，返回权重异常，不自动平均或缩放 |
| 240 分钟叶子候选 50% / 正式 0%，120 分钟叶子两者 100% | 总候选 66.7%，正式 33.3%，不简单平均或混算 |
| 上述范围新增已估 120 分钟且明确未验收的叶子 | 正式 25%；原历史快照仍保留 33.3% 及原分母 |
| 新增叶子缺估、范围未读全或总量为 0 | 完整总比例为 null；部分已知值不冒充总体 |
| 成员说完成、仅状态变为已完成、历史同类任务已完成 | 均不生成当前正式验收，也不单独证明候选 100% |
| 验收绑定旧估算版本，或旧模型响应晚于新范围返回 | 当前结果不可直接采用，标版本不匹配或忽略旧响应 |
| 仅历史参考缺失，当前范围、交付及权重完整 | 允许未校准的 EWD 粗估与当前候选判断，不伪称用历史工时校准 |

### 7.8 五个 Skill 如何串起来

```text
授权快照 → 创建 Skill 拆分与匹配 → 工时与进度评估 Skill → 用户确认 → 受控写入
任务事实变化 → 诊断 Skill + 工时与进度评估 Skill（同快照）→ 状态 Skill 总结 → 任务详情
同一批任务快照 + 本人正式责任 → 规则排序 / 优先级 Skill → 我的工作
```

验收重点：相同输入可复现判断；每项结论有来源；无权限不泄露；无验收不当完成；同一请求不重复创建；状态摘要、诊断、排序不出现不同版本的矛盾结论。这里描述的是接入验收要求，不是本次已执行生产验证。

## 8. MCP：工具与参数设计

### 8.1 用来解决什么

让个人 AI、MCP App 和普通页面操作同一份任务事实。REST 与 MCP 共用身份、权限、版本、幂等和事务服务，不能让 MCP 再存一套正式任务。

```text
页面 / 个人 AI → MCP 适配器或 REST → 同一领域服务 → 业务数据 / 变更回执
```

下面合并原《任务 REST API 与 MCP 工具契约》v0.1 的 **38 个候选工具**，并补齐阅读所需的参数类型和条件。它们仍是 Proposal；本次补充的必填性、枚举和字段白名单是待评审建议，不是现网 Schema。当前运行代码只有第 8.10 节的两个演示工具。

### 8.2 通用参数与回包

下表工具均使用完整 `agentdoor_` 名称。表中未标 `?` 的参数必填；`?` 表示可选。ID 均为非空 string；ID[] 为去重字符串数组；version 为正整数；null 是明确清空，不等于省略。

| 记号 / 参数 | 类型、默认值与校验 |
| --- | --- |
| `W` | 所有写工具共同带 `idempotency_key:string`；同一次业务操作及同一载荷重试用同一键 |
| `V` | 修改已有对象带 `expected_version:integer>=1`；从最近读取返回的 version 获取，不由模型猜 |
| `P` | 列表带 `cursor?:string, limit?:integer>=1`；默认 50，服务端限制最大值并回显；游标不跨查询条件复用 |
| 日期 | `YYYY-MM-DD`，日历日期校验；时间戳使用含时区的 ISO 8601，服务端记录 UTC |
| 未列字段 | 拒绝额外字段；不接受任意 JSON Pointer、SQL、任意本地路径或模型自报权限 |
| 身份 | team scope、真实 Principal、代表的成员和委托来自认证上下文；可选过滤参数不能扩权 |

**MCP → REST 映射**：`expected_version` 由适配器转换为 `If-Match`，`idempotency_key` 对应 `Idempotency-Key`；snake_case 工具参数转换为服务端 camelCase 字段。只在适配层映射，不能存两份不同字段。列表 `list_*` 对应 GET 集合，`get_*` 对应 GET 单资源，其余映射见各表。

成功返回 `content`（给人一两句话）和 `structuredContent:{data,receipt}`；错误为 `isError:true` 与 `structuredContent.problem:{code,message,retryable,recoveryAction}`。调用方解析结构化字段，不解析自然语言当作事实。

| 回执字段 | 意义 |
| --- | --- |
| `schemaVersion / operationId` | 写回执版本 `agentdoor.write-receipt.v0.1` 与操作标识；外层 meta 带 requestId、asOf |
| `outcome` | `succeeded / no_change / accepted_async / needs_confirmation` |
| `effect` | `none / proposed / applied`；只有 applied 才表示正式数据生效 |
| `replayed / atomic` | 是否幂等重放、是否整批原子成功 |
| `affectedResources[]` | 对象类型、ID、动作、beforeVersion、afterVersion；新建前版本为 null |
| `changeSetId / changeDigest / generatedActivityIds / committedAt` | 可追踪变更与实际提交时间；未应用不得伪造业务提交时间，Proposal 需细化各 outcome 的字段必填条件 |

默认 compact 返回 ID、状态、版本、关键差异和回执；长讨论、证据、文件正文分页获取。版本冲突或确认预览使用 standard。原契约的 detailRef / full 回传仍需补充具体资源读取地址，不能把一个不可读取的引用当作完整实现。

`TaskFilters`：`team_id?:ID, status?:TaskStatus, owner_id?:ID, parent_task_id?:ID或null, label?:string, query?:string, updated_after?:ISO时间`。建议 parent_task_id 省略=不限制，null=根任务，ID=直属子任务；前端标签或状态查询不等于完整查重。

| TaskCreateFields 字段 | 类型与默认 / 规则 |
| --- | --- |
| `name` | 非空 string；正式接口统一用 name；planner 的 title 在适配层转换 |
| `goal` | 非空 string；子任务沿用已读取的主目标，不借子任务创建修改主目标 |
| `completion_criteria` | string[]，至少一项非空完成标准；对应 REST completionCriteria |
| `owner_id?` | ID 或 null，默认 null；选他人时产生责任提议，不伪造其接受；已有 Owner 变更不走普通更新 |
| `participant_ids?` | ID[]，默认 []；同团队有效成员、不重复 Owner；正式参与成立仍受现行接受规则控制 |
| `planned_start_on? / planned_end_on?` | 日期或 null，默认 null，不默认今天或 7 天后；校验前置和父级范围 |
| `depends_on_task_ids?` | ID[]，默认 []；禁止自指、循环和无效引用，父子关系不自动生成依赖 |
| `labels?` | string[]，默认 []；本 v0.1 原契约尚未确定标签字符串是稳定 ID 还是名称，接入标签模块前统一 |

`TaskUpdate` 为 `{field,value}`，数组至少一项；白名单及 value 类型：`name:string`、`goal:string`、`completionCriteria:string[]`、`participantIds:ID[]`、`dependsOnTaskIds:ID[]`、`plannedStartOn:date|null`、`plannedEndOn:date|null`、`labels:string[]`。这里 field 枚举沿用原文 camelCase；MCP 外层仍为 snake_case。数组整体替换，靠版本防止覆盖他人修改。

`TaskStatus` 沿用候选 API：`open / in_progress / blocked / completed / cancelled`。界面“待审核”目前没有对应 API 枚举，需确定是扩展状态还是交付核对标记；不能无声映射为 completed。状态转换图、正式验收、Owner Transfer 均未在本次补成可用接口。

**删除边界**：影响包括可见后代、依赖方、文件引用及草稿；确认绑定 impactDigest。影响变化报 `DELETION_IMPACT_CHANGED` 并重做预览；不可见影响由服务端判定能否操作，不透露隐藏名称、ID 或数量。逻辑删 Task 不删共享 File、正式 Commit 或审计事实。

#### 文件参数展开

| 结构 | 具体字段与条件 |
| --- | --- |
| `UploadTarget` 新文件 | `{kind:new_file,task_id:ID,folder_id?:ID|null}`；文件夹必须属于目标任务且有权限 |
| `UploadTarget` 新版本 | `{kind:new_file_version,file_id:ID,expected_file_version_ordinal:integer>=1}`；准备和完成阶段都校验当前基准，避免覆盖新版本 |
| `content_digest` | `sha256:<内容摘要>`；服务端对实际上传字节再算，不能信客户端声明；本页示例不是真实摘要 |
| `version_mode / version_id` | pin_version 必须有 version_id 且版本属于该 File；follow_latest 时 version_id 省略或 null，不携带过期固定版本 |
| `PlacementUpdate` | `{field,value}`；仅 `folderId:ID|null`、`versionMode:pin_version或follow_latest`、`pinnedFileVersionId:ID|null`；组合校验同上 |
| `FileMetadataUpdate` | 本次建议先仅开放 `{field:name,value:string}`；原契约未列具体白名单，maintainer / visibility 等先不开放，不能借元数据更新改权限 |

读取 File 正文必须再次校验 Agent 委托、用途和内容权限；Task 可见不代表 File 可读。上传令牌与地址只给受信 App，不放模型可见的 content / structuredContent；模型不能指定本地绝对路径让服务读取。文件版本 availability 为 `processing / available / quarantined / failed`，只有 available 可显示可用；内容更新必须新建 FileVersion。

| 工具 / 操作 | 参数与返回重点 |
| --- | --- |
| `agentdoor_list_task_commit_drafts` · GET /tasks/{id}/commit-drafts | `task_id:ID, P` → 有权可见的提交草稿 |
| `agentdoor_get_task_commit_draft` · GET /task-commit-drafts/{id} | `draft_id:ID` → 草稿、version、basedOnTaskVersion |

`message / result_summary` 为非空 string；两个 refs 数组显式传入，可为空但不能伪造引用。`CommitDraftUpdate` 建议白名单为 `message:string`、`resultSummary:string`、`fileVersionRefs:ID[]`、`evidenceRefs:ID[]`；禁止修改 taskId、作者、基准版本和 consumed 状态。

正式提交同时校验 Task、草稿、文件版本与证据权限，版本一致后在同一事务创建 Commit、消费草稿并记录事件。`supersedes_commit_id` 仅指同任务需要更正的旧 Commit；更正产生新的 Commit，不覆盖旧记录。**提交成功不等于完成或验收**，不自动调用状态转换。

### 8.8 安全、失败与重试

| 场景 | 服务端结果 / 客户端动作 |
| --- | --- |
| 超时或重复点击 | 用原幂等键和原载荷重试，返回同一 ID 和 replayed=true；不同载荷复用键返回 409 |
| 并发更新 | 版本不一致返回 412 VERSION_MISMATCH，保留用户草稿、读取新版本、重新确认；不自动覆盖 |
| 删除影响变化 | 409 DELETION_IMPACT_CHANGED；重新预览和确认，旧摘要失效 |
| 无权限 | 已知且可暴露存在的对象可报 403；不可发现对象统一 404；重放旧回执也要重新鉴权 |
| 验证不通过 | 400 结构错误，422 领域约束错误，428 缺版本前置条件；指出允许公开的字段问题，不写半份数据 |
| 文件仍扫描 | accepted_async，不当错误也不当可用；通过 upload status 查询后续状态 |
| 多任务计划 | 主任务与子任务创建需受控原子命令；当前 38 个工具没有整棵计划提交工具，不能逐项调用后宣称原子成功 |

annotations 只帮助调用方识别 readOnly / destructive / idempotent，不提供权限。删除、正式提交、状态变化的授权必须绑定实际对象和影响；不得把模型“用户已同意”的文字当作确认凭证。

### 8.9 Skill 与 MCP 如何对接

| 能力 | 可复用工具 | 尚缺的数据能力 |
| --- | --- | --- |
| 创建与人员匹配 | list_tasks、get_task、list_subtasks、list_task_discussions、read_file_version_content | 授权成员与正式责任读取、语义查重服务、计划确认绑定和原子提交；现有工具不能仅靠名字搜索完成全部判断 |
| 状态分析 | get_task、list_subtasks、讨论 / 文件 / Commit / Activity 查询 | 版本化 EWD、验收事实与进度快照服务；不能从 Commit 自动推算验收 |
| 任务诊断 | Task 与后代 / 前置查询、讨论 / 文件版本 | 有授权确认依据的决策来源、可见范围完整性声明；须递归读取可见后代而非只查一层 |
| 个人优先级 | list_tasks 的 owner 过滤、上述状态与诊断结果 | 当前用户身份注入、同快照聚合与过期策略；左侧筛选结果不能当作个人全集 |
| 工时与进度评估 | get_task、list_subtasks、list_task_discussions、read_file_version_content；按权限读取历史候选任务 | 实际人类投入、版本化估算、标准权重、正式验收与评估快照；由协调层补齐，不能用创建至完成的时间差冒充工时 |

表中工具名为去掉 `agentdoor_` 前缀的简称。缺项属于后续接口设计，不伪装为已有 MCP。最先对接的是受控读取与统一回执，再接单任务写入、文件和正式提交；验收与责任转移规则确认后再增加相应命令。
