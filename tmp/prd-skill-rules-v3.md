## 7. Skill 与计算规则

### 7.1 各自负责什么

本章按业务流程组织，不把每个判断步骤都建成一个 Skill。创建任务是完整 Skill，澄清、查重、拆分、人员匹配、依赖与时间安排是它的内部步骤。预计投入、完成度和燃起图是多个流程共用的规则，单列便于复算，不需要额外建立一个工时 Agent。

| 所属流程 | 回答的问题 | 返回什么 |
| --- | --- | --- |
| 创建与人员匹配 | 要拆成哪些交付，谁适合负责？ | 任务草稿、人员建议、依赖；调用 7.7 得到预计投入 |
| 状态分析 | 当前做到哪里，下一步做什么？ | 当前事实、缺口、下一步；引用同一份进度和诊断 |
| 任务诊断 | 哪项工作受阻，哪些要求互相矛盾？ | 问题、受影响任务、双方依据、处理建议 |
| 我的工作推荐 | 我正式负责的任务先处理哪个？ | 固定规则计算的顺位和一句原因 |
| 共用计算规则（非独立 Skill） | 要投入多少人天，结果完成多少？ | 分项估算、投入分布、候选完成度、正式完成度、燃起图数据 |

**本次新增规则：** 第 7.7 节用固定参数表替代“让模型自行给每项分钟数”的旧写法，先覆盖普通文字资料和 AI 辅助内部方案；未覆盖的工作保留缺口或使用用户明确给出的估算。参数是产品初始设定，未经实际工时验证。完成度按明确结果和权重逐项计算，不采用固定的“开始 20%、审核 80%”阶段比例。

**当前实现：** 创建规划已有 `agentdoor-task-planner` v0.2 文档和离线契约；状态分析、诊断、我的工作三个 Skill 名称是接入设计。前端已有本地工时、进度、诊断和排序函数，但本章的新参数表、结果核对和更新服务尚未接入生产。此前单列的 `agentdoor-task-effort-assessor` 在本版归为共用评估模块，不要求创建独立 Skill 文件。

### 7.2 判断前需要的数据

| 保存对象 | 必须保存的内容 | 用在哪里 |
| --- | --- | --- |
| 任务与完成标准 | 任务 ID、目标、交付物、数量、每条标准的 ID、状态、日期、负责人、父子关系、正式依赖、版本 | 拆分、工时、诊断、推荐 |
| 成员责任与声明 | 团队与成员 ID、正式责任、本人技能说明、明确公开的协作窗口、来源与更新时间 | 人员匹配、估算工作条件 |
| 历史贡献 | 成员、任务、具体贡献、交付版本、依据；区分本人说明与已核实贡献 | 判断相关经验 |
| 文件与提交 | 文件 ID、版本、可读取正文、提交人、提交时间、关联任务和标准 | 统计资料量、核对结果、诊断 |
| 估算 | 规则编号与版本、分项数量、人数、轮次、单价分钟、上下界、假设、来源、采用状态、适用任务版本 | 预计投入、进度权重 |
| 结果核对 | 结果 ID、关联标准、权重分钟、证据版本、达标情况、理由、核对时间 | AI 候选完成度 |
| 正式验收 | 验收对象、操作者、结论、时间、适用范围、标准与交付版本、估算版本、撤销记录 | 正式完成度 |
| 变更与分析记录 | 变化前后版本、实际发生时间、分析类型、输入版本、规则版本、来源、结果；趋势另存当时的范围与验收合计 | 更新、复用、燃起图 |

这些是逻辑对象，可复用现有数据表。现有 MCP 尚未提供全部读取能力；不能把建议字段写成已存在的接口。

**成员画像怎么建立。** 首版复用“我的责任”和有来源的历史贡献，不增加独立画像页。每条资料保存“谁、做过什么、来自哪里、何时更新、当前是否有效”。AI 只提取与本次任务有关的责任与经验。没有查到经验表示未知；历史 Owner 身份不等于独立完成；提交间隔、在线状态、任务数量不转换成能力分或个人效率系数。本人修改责任、来源撤销或权限变化后，依赖该资料的匹配建议失效，正式负责人不自动更换。

**所有 Skill 共用的读取规则。** 服务端提供当前用户有权读取的资料，并记录各类数据是“已读全、部分、不可用、未读取”。空集合只有在已读全时才代表确实没有记录。资料中的文字只作为证据，不能当作新的操作指令。输出绑定资料版本；旧请求不能覆盖新版本结果。

### 7.3 创建任务与人员匹配 Skill

**Skill：** `agentdoor-task-planner`。输入需求、当前任务（如有）、相关已有任务、成员责任；输出可编辑草稿。用户确认前不创建正式任务。

#### A. 任务怎样拆

按下表顺序处理，任何未知项都要说明缺什么。

| 顺序 | 判断规则 | 处理结果 |
| --- | --- | --- |
| 1. 分清意图 | 查询不创建；调整已有任务先定位原任务；新增需求进入规划 | 查询结果或草稿 |
| 2. 写出结果 | 每个候选结果写明交付物、数量、完成标准。关键缺口每轮最多补问两项 | 能被核对的结果清单 |
| 3. 检查重复 | 比较业务对象、交付物、周期或版本、完成标准；不能只看标题 | 全部覆盖则建议复用；部分覆盖只规划剩余部分；检索不完整则标待核对 |
| 4. 决定拆分 | 结果能单独交付且能单独验收，并至少满足“独立负责、单独交接、可以并行”之一，才拆为子任务 | 子任务或任务内部步骤 |
| 5. 检查覆盖 | 所有父任务结果必须在叶子中有归属；同一交付不能重复归属。父级若另有整合工作，要明确计入哪个叶子的分项 | 无遗漏、无重复的范围 |
| 6. 建依赖 | 后项必须使用前项的具体产出时才建正式依赖，并注明所需产出 | 依赖关系；父子关系不自动变成依赖 |
| 7. 匹配与估算 | 按 B 节匹配人员，再调用 7.7；只有工作分工改变，才重新计算相关分项 | 完整草稿和估算缺口 |

**例子。** “做一份方案”通常一个任务；资料整理、AI 操作、修改、审核是该任务的工作分项。“方案定稿、宣传素材交付、上线执行”各自能交付和验收，且需要交接，才拆成三个子任务。不要为了展示步骤而创建三个没有独立结果的子任务。

**代码检查：** 任务 ID 和引用有效；每个任务有名称和标准；父子及依赖无环；重复候选已处理；日期合法；不会覆盖用户已确认且未要求修改的字段；提交绑定草稿与对象版本。同一提交重试只创建一次，整棵树一起成功或失败。

#### B. 人员怎样匹配

先列出该任务必须承担的责任，再对候选成员逐项核对。模型只能返回“覆盖、部分覆盖、未知”和依据，不能仅凭关键词就认定胜任。

| 顺序 | 明确规则 |
| --- | --- |
| 1. 资格 | 只使用当前团队有效、当前用户可发现且有参与资格的成员；无资格者不进入候选 |
| 2. 用户点名 | 先校验指定人选；责任不符或资料不足时显示差异，让用户决定，不自动换人 |
| 3. 责任 | 候选 Owner 的正式责任需覆盖整项结果；仅覆盖审核、设计等一环的成员作为对应参与者 |
| 4. 经验 | 责任均覆盖时，按“有核实的同业务对象同类贡献 → 有核实的同类交付贡献 → 本人说明有相关经验 → 未知”比较；同一贡献引用多个文件只算一次 |
| 5. 窗口 | 前面相同时，优先采用本人明确表示符合本次要求的有效窗口；未填写表示未知，明确无法参与者不自动推荐 |
| 6. 并列 | 条件相同保持稳定成员顺序，展示差异，不由模型随机选人；无人有依据覆盖整项结果则返回未分配 |

**例子。** 任务要求“编写并交付活动方案”。甲的责任是活动策划且有同类编写贡献，乙只负责视觉审核，丙责任未填写：甲可作为 Owner 候选，乙作为审核参与者，丙资料不足。推荐甲的依据是责任和贡献，不是“甲历史任务完成得快”。选择他人只形成待接受提议，对方接受后才成为正式 Owner。

**保存：** 任务必需责任、候选成员 ID、各项判断、来源、缺口、资料版本。首版不生成匹配百分比；既有关键词分数 `min(98,58+8×命中数)`、无命中 52 属原型，不能用作生产评分。

#### C. 返回与更新

返回任务树、每项完成标准、Owner 候选、必要参与者及贡献、依赖、时间建议、叶子估算、假设和待核对项。已有 planner v0.2 的 `requestId / baseSnapshotId / baseRevision / baseTaskVersions` 继续由适配层衔接；标签、资料计量和新估算字段需显式扩展，不能声称旧 Schema 已支持。

需求范围或完成标准变化时检查受影响结果；成员资料变化只刷新依赖该资料的建议；输入相同复用草稿。已创建任务的调整返回具体差异，经相应授权提交。允许未分配创建，以当前 PRD 为准，不沿用旧 planner 参考文档中“必须有人承担才创建”的约束。

### 7.4 任务状态分析 Skill

**Skill：** `agentdoor-task-status-analyzer`。读取当前任务、交付和讨论，以及同版本的 7.5 诊断、7.7 进度。它组织说明，不另算百分比。

| 判断 | 输出规则 |
| --- | --- |
| 有有效正式验收 | 写“已验收”，引用验收对象与时间 |
| 只有 TaskStatus 为已完成 | 写“任务已标记完成”；验收未知则同时写“验收情况待核对” |
| 只有成员说完成 | 写“某成员报告已完成”，不改为客观已完成 |
| 当前标准有核对结论 | 列出已达标结果和明确未达标项；未读到的证据写缺口 |
| 下一步 | 优先说明需核对的冲突，其次解除当前阻塞，再处理明确未达标或待核对的交付，最后继续既定工作；按实际责任说明动作 |
| 展示进度 | 原样引用 7.7 的数值与口径；未知仍为未知，不按状态补百分比 |

**例子。** 成员说“方案做好了”，TaskStatus 为待审核，系统未读取到验收：输出“方案已提交审核；成员报告制作完成，正式验收待核对”。不能输出“完成度 90%”。若 7.7 已计算 AI 候选为 50%，必须带“AI 估算完成度”标识。

**保存与更新：** 保存摘要、事实与缺口、下一步、引用结果 ID、来源版本和数据截至时间。任务属性、相关交付、讨论、诊断或进度变化后刷新；切页签、展开明细不刷新。失败保留仍有读取权限的旧结果并标为过期。页面现有“当前情况”使用本结果，不新增概览页签。

### 7.5 任务诊断 Skill

**Skill：** `agentdoor-task-diagnostician`。首版只输出“执行阻塞”和“决策冲突”。代码查正式关系，AI 查文字内容；每个问题都要能定位到当前有效来源。

| 编号 | 成立条件 | 不成立或未知时 |
| --- | --- | --- |
| D1 执行阻塞 | 有正式依赖；消费者处于进行中或已阻塞；依赖所需交付尚未满足，且该阶段确实需要它。未记录阶段条件的整任务依赖按开工前必须满足处理 | 未开始任务正常等前置不直接判当前阻塞；依赖不可读只报检查不完整 |
| D2 状态冲突 | 消费者已完成，但其仍有效的必需依赖未满足；或父任务已完成，仍有纳入范围且未完成、未取消的后代 | 只存在父子关系不能推断执行依赖；已明确移出范围的后代不算 |
| D3 日期冲突 | 有正式依赖和明确的产出需要日期，前置交付日期晚于该日期；只有截止日期时，只能确定前置晚于消费者截止的冲突 | 日期不明确或时区不明时不比较，不猜开工日 |
| D4 内容冲突 | 两个不同的当前有效正式来源，对同一对象、同一适用范围提出不能同时满足的要求；AI 给出两侧具体内容 | 单条发言、旧版已被替代、适用范围不同，只列资料或缺口，不判冲突 |

D1 对外归为执行阻塞；D2、D3、D4 归为决策冲突。前置取消不自动等于交付完成，必须核对依赖是否解除或已提供有效替代。若现有依赖暂以 TaskStatus=已完成作为满足依据，需要明确这是状态规则，不等于正式验收。

**例子。** 当前有效标准要求“预算不超过 10 万”，已确认方案写“预算 12 万”，适用范围相同且两者均有效，D4 成立。仅讨论说“可能要 12 万”不独立成立；标准已正式改为 15 万后，原冲突消失。

**返回：** 稳定问题 ID、实际受影响 Task ID、类型、结论、影响、建议、双方来源及版本。D1 ID 绑定消费者和依赖关系；D4 ID 绑定受影响任务及相冲突的要求，不能随文案变化生成新问题。向父级展示时沿用同一 ID 并去重。

**更新：** 状态、正式依赖、日期、后代范围、正式要求、交付版本或权限变化后重算。无需另外维护“忽略／已解决”状态，源事实修正后问题自然消失。空结果写“当前可见范围内未发现这两类问题”。

**当前差异：** 本地诊断对未完成消费者的依赖检查较宽，且把取消前置排除在未完成集合之外；接入时应按 D1 和取消处理规则修正。此处是规则设计，尚未改动应用代码。

### 7.6 我的工作推荐 Skill

**Skill：** `agentdoor-personal-priority`。代码先排序，Skill 根据同一组事实写一句原因；不另建待办。

**第一步：选任务。** 只读取当前用户正式 `ownerId` 对应、未完成且未取消的任务。排除待接受和未分配项，按 Task ID 去重，不受左侧搜索、标签或折叠影响。父任务保留统筹动作，子任务保留具体执行动作，不能重复安排同一个动作。

**第二步：计算分数。** 沿用现有原型的可复现加分作为初始参数，不代表已证明是最佳排序；上线前用真实任务案例核对。公式为“时间分 + 主要问题分 + 补充分”。

| 分项 | 取值规则 |
| --- | --- |
| 时间分，只取一项 | 逾期 400；今天到期 300；未来到期 20；有日期但无法解释 35；无日期 0 |
| 主要问题分，只取一项 | 当前阻塞 110；状态或决定冲突 100；前置未满足 80；交付待核对 60；关键信息未知 50；没有这些问题 0。多项命中取最高分，并使用对应理由 |
| 关联前置已阻塞 | 加 20，一次 |
| 本任务待审核 | 加 40；主要问题已为交付待核对时不重复加 |
| 本任务数据过期 | 加 25 |
| 本任务关键信息缺失 | 加 10；主要问题已为未知时不重复加；与过期为互斥的数据状态 |

**第三步：排序。** 总分从高到低；同分按明确截止日期从早到晚，无法比较日期的排在后，再按稳定 Task ID 顺序。日期按团队时区判断，每次打开不随机洗牌。数据读取不全时说明范围有限，不引用隐藏任务名称或数量。

**例子。** A 今天到期且前置未满足：300+80=380；B 今天到期且无问题：300；C 未来到期且当前阻塞：20+110=130。因此 A、B、C。A 的原因写“今天到期，前置交付尚未完成，先核对可推进范围”，不建议直接执行被前置卡住的动作。

**保存与更新：** 保存候选任务 ID、命中规则、各分项、总分、顺位、理由、来源版本、规则版本和业务日期。本人任务集合、日期、诊断、待审核信息或实际跨日变化时更新。无日期只代表没有时间压力分；预计投入小、聊天活跃、任务多不加分。当前前端同分保留传入顺序，生产接入须固定上游顺序或按上述规则补齐。

### 7.7 共用规则：预计投入、完成度与燃起图

[初始参数表](#effort-baseline) · [准备资料怎么算](#effort-preparation) · [完整投入算例](#effort-example) · [完成度怎么算](#completion-example) · [燃起图规则](#burn-up-rules)

创建任务调用 A 节估算规则，把结果放入草稿；执行中调整范围继续复用 A 节；状态分析调用 B 节核对结果；C 节由代码保存并绘制趋势。创建时不需要执行诊断、个人推荐和历史进度评估的完整流程。

**对任务的价值：** 预计投入人天表示完成任务预计需要的总人工工作量，帮助团队看清任务规模、投入主要花在哪里，并按工作量衡量完成进度。

#### A1. 预计投入的计算方式

预计投入是当前范围从开始到完成的总人工工作量。已完成一部分工作，不从原预计投入中扣除；范围变化才重新核对。等待、排队、无人值守 AI 运行不计入。

```text
分项分钟 = 数量 × 每单位每人每轮分钟 × 人数 × 轮次
叶子任务分钟 = 所有分项分钟相加
任务总分钟 = 当前范围内所有叶子任务分钟相加（按任务 ID 去重）
预计人天 = 任务总分钟 ÷ 480
子项投入占比 = 该子项全部叶子分钟 ÷ 任务总分钟
```

所有数值由代码计算。模型只返回规则编号、数量、适用依据和假设；命中下面的固定参数时，不能另编单价或总数。保存整数分钟；显示最多两位小数，去掉末尾零，非零且小于 0.01 人天显示“<0.01 人天”。区间下界向下、上界向上取两位小数。既有 `ewdHours / scopeHours` 等字段继续保持小时语义，显示时除以 8。

#### A2. 分钟数从哪里来：按顺序选择

| 优先级 | 条件 | 使用方法 |
| --- | --- | --- |
| 1 | 当前范围与假设未变，已有采用的估算 | 直接复用，不重新让模型给数 |
| 2 | 用户本次明确给出相关工作的投入估计 | 保存为用户估算；明确它替代哪个分项或整个任务，不能再叠加被替代分项 |
| 3 | 工作满足已发布规则的全部适用条件 | 按规则参数表计算，并保存规则版本；本版只有 A3 的初始规则 |
| 4 | 没有适用规则或关键数量未知 | 该项显示待估算和缺口；可向用户提出具体假设，但未纳入已采用规则的模型自由估计不直接成为正式 EWD |

旧任务的预计值只能提供参考，不能自动覆盖本表单价。当前没有实际人工耗时，不能从状态时间或提交间隔校准参数。以后新增规则需写明适用工作、计量单位、单价、上下界、来源和版本；先用真实样本验证再发布，不能由模型在一次请求中自行改全局参数。

#### A3. 初始参数表：普通文字资料与内部方案

**规则版本：** `office-text-v1`。以下分钟数是本次提出的产品初始参数，用于稳定粗估；不是行业工时标准，也不是已验证的平均耗时。所有采用该表的估算标“初始规则粗估，未使用实际工时校准”。

**资料适用范围：** 1–20 份已有、可直接读取的普通中文文字资料；每份不超过 5,000 字符，总量不超过 20,000 字符。不包含扫描识别、翻译、专业法律或医疗判断、代码审查、复杂表格核算、外部调查。混合材料只计算符合条件的部分，其他部分保留缺口，不能报告完整总投入。

**方案适用范围：** 基于上述材料和已有提纲，用 AI 辅助编写一份内部文字方案；1–10 个内容小节，每节围绕一个已明确问题，预计正文不超过 800 字符。图表、原创设计、研发实现、外部调研等需另有适用规则；不能强行套本表。章节数量需要来自用户或已确认草稿，不能为得到某个人天数而拆章节。

| 编号 | 人工动作与计量单位 | 下界 / 典型 / 上界（分钟） | 使用规则 |
| --- | --- | --- | --- |
| P1 | 建资料清单并核对缺项，每个资料包一次 | 5 / 10 / 15 | 清点当前必需资料，核对是否具备；每包只计一次 |
| P2 | 阅读普通文字，每 1,000 字符 | 3 / 5 / 8 | 每份分别向上取整后相加；读过并有可复用结论时也不能默认免读，须明确本次核对要求 |
| P3 | 记录该资料的要点与出处，每份一次 | 3 / 5 / 8 | 整理可供本次方案引用的要点，不包含方案正文制作 |
| W1 | 整理提示、发起 AI 起草、检查输出结构，每份方案一次 | 10 / 20 / 30 | 不含无人值守生成时间；同一轮中的重发提示已包含，不能按调用次数重复计费 |
| W2 | 对照材料核对并改写一个内容小节，每节一次 | 10 / 15 / 25 | 首稿人工处理；每节满足前述规模上限，特殊小节另估 |
| W3 | 根据业务反馈修改一个受影响小节，每节每轮 | 5 / 10 / 20 | 与首稿核对区分；需明确受影响节数 K 和轮次，不能默认为全部或按固定返工百分比 |
| W4 | 审核一个内容小节，每节每人每轮 | 3 / 5 / 8 | 一轮包含阅读、给出意见和核对本轮修正；多位审核人逐人累加，不把等待算进去 |
| W5 | 核对交付包、版本与提交要求，每份方案一次 | 5 / 10 / 15 | 文件命名、要求覆盖、版本和提交核对；不重复核算 W4 的正文审核 |

**计数方法：** 文件按 ID 和有效版本去重，引用同一文件多次仍为一份。正文去除空白后按 Unicode 字符计数，标点计入；只处理部分正文时必须保存明确的读取范围。P2 的数量为每份 `ceil(字符数÷1000)` 的和，不能先合并所有短文件再取整。空文件不能当作材料齐备。页数和附件个数不能替代正文数量。

**零与未知：** 无某项工作且有范围依据时，该分项为 0；工作存在但资料读不到、数量未定时为未知。审核人数或轮次未定不能默认为 1。规划时可以提出“按两人、一轮审核、修改两个小节估算”的显式假设，用户确认方案时一并采用；后续假设改变生成新版本。

**复用处理：** 若任务开始前已有可直接复用的要点与出处，经确认本次不需要重新提取，可将 P3 数量设为 0 并引用来源；仍需进行的阅读和核对照常计算。如果是本任务执行中刚完成了要点整理，只更新完成情况，不减少原 EWD。人员经验只能改变这类具体工作条件，不乘个人速度系数。

#### A4. 准备资料到底算多久

四份资料，每份 1,000 字符，均要重新阅读和整理要点，由一人处理：

```text
清单核对：1 × 10 = 10 分钟
阅读资料：(1 + 1 + 1 + 1) × 5 = 20 分钟
整理要点：4 × 5 = 20 分钟
准备资料：10 + 20 + 20 = 50 分钟
下界：5 + 4×3 + 4×3 = 29 分钟
上界：15 + 4×8 + 4×8 = 79 分钟
```

| 材料变化，其他条件不变 | 典型分钟如何变化 |
| --- | --- |
| 改成八份，每份 1,000 字符 | 10 + 8×5 + 8×5 = 90 分钟 |
| 仍是四份，每份 3,000 字符 | 10 + 12×5 + 4×5 = 90 分钟 |
| 四份各 1,000 字符，本次明确可复用已有要点，仍需阅读核对 | 10 + 4×5 + 0 = 30 分钟 |
| 四份资料中有一份扫描件，无法可靠读取 | 该资料超出本表适用范围；完整准备投入待估算，不能按一份普通文字代入 |

#### A5. 完整方案算例

承接 A4：四份各 1,000 字符的资料，方案有四个符合条件的小节；明确假设一轮业务修改影响第 1、2 节，两位审核人各审核四节一轮。各项工作没有重复。

| 工作 | 数量 × 单价 × 人数 × 轮次 | 典型分钟 | 下界 / 上界分钟 |
| --- | --- | --- | --- |
| 准备资料 P1–P3 | 按 A4 | 50 | 29 / 79 |
| AI 起草操作 W1 | 1 × 20 × 1 × 1 | 20 | 10 / 30 |
| 首稿核对改写 W2 | 4 × 15 × 1 × 1 | 60 | 40 / 100 |
| 业务反馈修改 W3 | 2 × 10 × 1 × 1 | 20 | 10 / 40 |
| 审核 W4 | 4 × 5 × 2 × 1 | 40 | 24 / 64 |
| 交付检查 W5 | 1 × 10 × 1 × 1 | 10 | 5 / 15 |
| 合计 | 50 + 20 + 60 + 20 + 40 + 10 | **200** | **118 / 328** |

预计投入 `200÷480=0.416666…` 人天，显示“约 0.42 人天”；粗估范围显示“0.24–0.69 人天”。上下界分别求和，只是本组假设下的粗估范围，不表示统计置信概率。等待审核两天不加人工投入；审核改为三人，典型值增加 `4×5=20` 分钟。

用户原例“准备 30、操作 AI 30、修改 60、两人各审核 30 分钟”属于明确的用户估算，按 A2 优先使用，结果为 `30+30+60+60=180` 分钟，显示约 0.38 人天；不再叠加 P1–W5。

#### A6. 汇总、保存和更新

只汇总当前范围的叶子 Task，父任务不另加一份 EWD。共享资料工作只归属一个分项，不在多个叶子中重复计整份。父级还有未归属的必要整合工作时，先标范围缺口。

只要任一叶子缺估、估算过期或范围未读全，总量和投入占比为未知，保留有权查看的“已估部分”。非负整数分钟、有限数值、上下界顺序由代码检查；合计溢出则拒绝，不静默截断。总量为 0 时，比例为空。

每项保存 `ruleId、ruleVersion、unit、quantity、people、rounds、unitMinutes{low,typical,high}、resultId、evidenceRefs、assumptions`，估算整体保存版本、范围版本、来源和采用状态。计算结果由代码生成，不能相信模型自报合计。

资料数量、交付规模、标准、审核人数、轮次、工具分工或复用条件改变时，只重估受影响分项；普通提交、状态变化、等待和已完成动作不自动加减 EWD。候选与已采用版本分开，旧值保留，新值采用后重算当前汇总。相同输入与规则版本复用已有结果。

#### B1. 完成度先区分两种读数

| 读数 | 判断的是什么 | 谁产生 |
| --- | --- | --- |
| AI 估算完成度 | 当前交付证据支持了多少约定结果 | AI 逐结果核对，代码计算比例 |
| 正式完成度 | 当前范围多少工作量已有有效正式验收 | 验收服务提供记录，代码计算比例 |

两者分别返回，不能互相填补未知值。当前页面正式进度仍使用已有本地投影；本章 AI 候选规则尚未接入。状态分析只能引用结果，不再生成第三个百分比。

#### B2. 先确定结果、达标条件和权重

创建或重估时先确定结果清单，每个结果有稳定 ID、可检查的标准、需要的证据以及权重分钟；确认后才能评价进度，不能根据当前已完成多少再调权重。

**权重来源只有一个：A 节已采用的分项分钟。** 每个分项完整归入一个结果。确实服务多个结果的工作先按模板规定拆为明细；同质小节才可以按明确规则等分。不自动平均所有完成标准，不漏算或重复分配分钟。代码检查“各结果权重合计＝叶子 EWD”，不相等就返回权重待核对。

A5 的方案采用如下结果模板；这是可复算的模板设定，不把每个结果自动建成子任务：

| 结果 | 达标条件 | 权重如何得到 | 分钟 |
| --- | --- | --- | --- |
| R1 资料结论可用 | 约定四份资料均有可核对的要点、出处；无关键材料缺口 | P1–P3 | 50 |
| R2 第 1 节达标 | 满足本节全部内容标准，引用正确，适用反馈已处理 | W1 分配 5 + W2 的 15 + W3 的 10 | 30 |
| R3 第 2 节达标 | 同上，按第 2 节自身标准和反馈核对 | 5 + 15 + 10 | 30 |
| R4 第 3 节达标 | 满足本节全部内容标准，引用正确 | 5 + 15 | 20 |
| R5 第 4 节达标 | 同上，按第 4 节自身标准核对 | 5 + 15 | 20 |
| R6 审核与交付条件满足 | 两位约定审核人的有效确认覆盖当前版本，且交付包满足约定提交要求 | W4 的 40 + W5 的 10 | 50 |
| 合计 | W1 的 20 分钟只向四个同质小节各分配 5，其他分项各计一次 | 50 + 30 + 30 + 20 + 20 + 50 | **200** |

第 1、2 节的修改假设被采用时权重已固定；开始执行后仅上传一版文件，不能自动新增修改分钟。若后来改变修改范围，需要走新估算与权重版本。

#### B3. 每个结果怎样判 0、1 或未知

| 条件 | 结果值 |
| --- | --- |
| 当前有效证据覆盖该结果全部必需标准，且全部达标，无未解决矛盾 | 1 |
| 有当前有效证据明确证明至少一项必需标准不满足，且没有与此矛盾的有效证据 | 0 |
| 文件未读取、内容不足、标准无法判断，或只有成员自述和状态 | 未知，保存具体缺口 |
| 当前有效证据相互矛盾，暂不能确定适用结论 | 冲突，保存双方依据 |

判定顺序：先校验版本与适用范围；存在未解决矛盾先标冲突；有明确不满足条件则为 0；全部必需条件被支持才为 1；其余未知。输出必须关联标准 ID、证据版本和具体内容。代码能检查引用和数值，不能仅凭引用存在就证明模型语义判断正确，所以始终标为 AI 候选。

普通结果不允许模型填 0.3、0.7。批量结果仅在事先明确每个单元 ID、同等权重和相同标准时，才允许“达标单元数÷总单元数”；数量去重由代码执行，任一单元未知或冲突则该组比例未知。不按上传次数、文字长度、状态阶段或日期流逝推测完成比例。

“系统没有记录”通常是证据不足。只有标准明确要求“在本系统提交指定文件”，且该范围已完整读取、确实未提交时，才能判这条提交标准未满足；这不等于断言用户线下未做工作。

<a id="completion-example"></a>

#### B4. 百分比怎么算：完整算例

```text
某结果支持分钟 = 结果权重分钟 × 结果值
叶子 AI 候选完成度 = 所有结果支持分钟之和 ÷ 叶子 EWD 分钟
父级 AI 候选完成度 = 全部叶子支持分钟之和 ÷ 全部叶子 EWD 分钟
```

任一必需结果未知或冲突、权重无效、范围不全、估算过期或总 EWD 为 0，总体候选比例为空，保留已核对的结果。不能仅对已知部分重新归一为 100%。即使另有零权重的必需条件，也必须核对；有未知或冲突时不报总体比例，明确未满足且其他加权结果全满时不报 100%，返回必需条件缺口。

承接 B2，假设读到以下有效证据：

| 结果 | 当前核对依据 | 权重 | 结果值 | 支持分钟 |
| --- | --- | --- | --- | --- |
| R1 资料结论 | 四份要点与出处均符合要求 | 50 | 1 | 50 |
| R2 第 1 节 | 所有内容标准满足，反馈已处理 | 30 | 1 | 30 |
| R3 第 2 节 | 当前文件明确缺少必需预算说明 | 30 | 0 | 0 |
| R4 第 3 节 | 所有内容标准满足 | 20 | 1 | 20 |
| R5 第 4 节 | 当前文件中的执行日期违反约定 | 20 | 0 | 0 |
| R6 审核交付 | 一位审核人对当前版本明确要求修正 | 50 | 0 | 0 |
| 合计 | 全部结果都能判断，没有未知或冲突 | 200 | — | **100** |

AI 候选完成度为 `100÷200=50%`。第 2 节修正并通过核对后，变成 `130÷200=65%`。若第 2 节的新版本读不到，结果是“候选完成度待核对”，不是沿用旧版本的 0 或 1。

#### B5. 正式完成度怎么计算

```text
叶子正式值 = 1（有适用于当前范围与版本的有效整项验收）
叶子正式值 = 0（验收集合已完整读取，且没有有效整项验收）
叶子正式值 = 未知（验收未读取、不可用或版本待核对）
正式完成度 = Σ(叶子 EWD × 叶子正式值) ÷ Σ(叶子 EWD)
```

**单个叶子任务正式完成度只有 0% 或 100%。** 需要观察过程中各结果的情况时使用明确标识的 AI 候选读数。正式验收由相应业务操作产生，模型不能生成，普通修改状态也不等于验收。

方案任务为 200 分钟、AI 候选 50%，正式验收完整读取且为空：正式值是 0%。另一个叶子为 100 分钟、候选与正式均 100%：父级候选是 `(100+100)÷300=66.7%`，正式是 `100÷300=33.3%`。两者不能混合为一个读数。

若方案任务完成正式验收，父级正式值变为 100%。缺少任何必需估算或验收读取条件时，完整正式比例未知。范围、标准或估算版本变化后，旧验收须按正式规则复核并绑定适用版本，不能由 AI 自动沿用或撤销。

<a id="burn-up-rules"></a>

#### C. 燃起图怎么产生

燃起图由代码使用正式记录生成，不调用模型预测历史。只展示两条线，单位人天：

```text
某时点范围线 = 该时点当前范围的有效 EWD 分钟 ÷ 480
某时点已验收线 = 同一时点有有效验收的范围 EWD 分钟 ÷ 480
该时点正式完成度 = 已验收分钟 ÷ 范围分钟
```

| 事件 | 范围线 | 已验收线 | 标注 |
| --- | --- | --- | --- |
| 新增一个已估算、尚未验收的叶子 | 增加该叶子 EWD | 原有效部分不变 | 范围增加 |
| 一个叶子正式验收通过 | 不变 | 增加该叶子 EWD | 验收通过 |
| 验收被正式撤销 | 不变 | 减去相关叶子 EWD | 验收撤销 |
| 叶子明确移出范围 | 减去该叶子 EWD | 若原本已验收，也减去对应 EWD | 范围减少 |
| 新估算被采用 | 按新估算计算 | 相关验收需核对新版本；若重新有效绑定则用新权重，未核对则该值未知 | 估算调整，不能写工作效率提高 |
| 仅提交文件、发言、改状态、等待或打开页面 | 不因这些事件直接改变 | 不因这些事件直接改变 | 不新增虚假的进度变化 |

**例子（人天）：** 初始范围 5、已验收 0；验收 2 人天后为 5/2、40%；新增 1 人天后为 6/2、33.3%；再验收 1 人天后为 6/3、50%。历史每个点保留当时的分母，不能全部用今天的 6 人天重算。

**保存规则：** 范围、估算或验收有效性变化时，保存一次完整事件后的快照：任务 ID、事件 ID、事件顺序、发生时间、范围版本、估算版本、验收版本、总分钟、已验收分钟、读取完整性、原因。同一事件重试只记一次，同一时间戳不同事件按顺序保留。没有变化时显示上一有效值的延续，不生成假事件。

没有历史版本记录的时段不反推；只有一个点就显示单点。缺少完整范围、估算或验收时对应值为空，图线断开，不当成 0。当前进度可以已有数值但历史不足，二者分别显示。权限改变后当前用户不能继续读取不可见数据的旧趋势缓存。

#### D. 需要通过的计算例子

| 输入变化 | 应得到的结果 |
| --- | --- |
| A4 四份各 1,000 字符 | 准备资料 29 / 50 / 79 分钟 |
| A5 完整方案 | 118 / 200 / 328 分钟，典型约 0.42 人天，范围 0.24–0.69 人天 |
| A5 审核人数 2 改为 3，其他不变 | 典型总投入 220 分钟，不添加个人效率系数 |
| 用户明确给出原始四项时间 | 180 分钟，约 0.38 人天，不叠加参数表 |
| 四份资料实际是同一有效文件的四次引用 | 去重为一份，不能按四份估 |
| 某资料无法读取或超出规则适用范围 | 完整投入未知，说明缺口 |
| 仅等待两天、TaskStatus 改为已完成 | EWD 不变；不产生正式验收 |
| B4 结果支持分钟为 100 / 200 | AI 候选 50%；第 2 节达标后为 65% |
| 某必需结果未知，或重复分配同一分项权重 | 候选比例为空，不平均或强行缩放 |
| 200 分钟叶子候选 50%、正式 0%；100 分钟叶子均为 100% | 父候选 66.7%；正式 33.3% |
| 范围由 5 增为 6 人天，已验收仍 2 人天 | 当前正式 33.3%，历史 40% 保留 |
| 同一验收事件重复收到，或旧分析晚于新版本返回 | 不重复增长，不覆盖新结果 |

这些是研发接入的验收要求，不代表模型准确率已经验证。页面继续复用预计投入说明、完成度说明和燃起图；规则计算失败显示原因，不需要用户额外填写工时打卡表。

### 7.8 谁调用规则，什么时候更新

#### 创建任务的完整流程

| 流程步骤 | 归属 | 产物 |
| --- | --- | --- |
| 识别意图、明确目标和关键补问 | 创建任务 Skill 内部 | 有范围的需求 |
| 查重、拆分结果、判断父子与依赖 | 创建任务 Skill 内部，代码校验关系 | 任务草稿 |
| 匹配责任、安排必要协作与日期、建议已有标签 | 创建任务 Skill 内部 | 人员与时间建议 |
| 统计工作数量、匹配适用规则、计算预计投入 | 创建任务调用 7.7 A 的共用规则 | 每个叶子 EWD 与假设 |
| 校验草稿、展示差异、用户确认 | 业务服务 | 确认后的提交 |
| 保存任务、估算和变更记录 | 业务服务统一事务 | 正式任务；选他人时负责人仍待接受 |

拆分、人员匹配不各开一个 Skill；规则表也不各开一个 Agent。创建时只调用需要的估算部分；执行中的结果核对和验收不是创建流程的必跑步骤。

#### 保存之后的更新表

| 保存的变化 | 更新什么 | 保留什么 |
| --- | --- | --- |
| 目标、交付数量或标准改变 | 检查受影响范围；相关估算、权重、候选结论失效；检查诊断和推荐 | 未受影响的结果与原始证据 |
| 子任务新增、移除、移动 | 更新新旧父级范围与汇总，相关诊断、进度和趋势；新增叶子按规则估算 | 已有历史点 |
| 本人责任、相关经验或公开窗口改变 | 刷新依赖这些资料的人员建议；实际工作假设改变才重估 | 正式 Owner 不自动更换 |
| 正式 Owner 改变 | 更新新旧负责人的“我的工作”，核对相关工作假设 | 人名变化本身不改变工时 |
| 文件新版本、相关反馈或明确贡献记录 | 只核对关联标准、内容诊断与摘要；内容改变估算假设时才重估 | 仍适用的 EWD |
| TaskStatus 改变 | 更新状态说明、关系诊断、个人推荐 | EWD 与正式验收不随之修改 |
| 截止日期或正式依赖改变 | 检查日期、依赖诊断，更新推荐和摘要 | 仅日期变化不改 EWD；依赖改变实际交付工作时再重估 |
| 正式验收、撤销或有效性变化 | 更新正式进度、父级汇总、燃起图及关联分析 | 原始估算、历史点 |
| 实际跨日 | 按团队时区重新计算到期与个人排序 | 工时、验收、交付核对结果 |
| 权限改变 | 清除当前用户不再有权读取的内容与分析缓存，重新核对覆盖 | 服务端受控历史保留，但不继续展示给无权用户 |

**运行方式：** 正式修改和变更记录一起保存；后台根据上表找受影响任务、祖先、后续依赖任务及相关负责人。代码能算的先算，需要理解文字的再调用对应 Skill。每次结果保存任务版本、证据版本、规则版本和读取范围；发布前重新核对，旧请求丢弃。

同一输入已有有效结果就复用。切页签、展开明细、尚未保存的输入不重算。失败保留有权限的旧结果并标“已过期”，用户可重试；刷新不伪造新的数据截至时间。同一页面的诊断、进度和摘要必须明确各自版本；不能将旧摘要包装成已解释新进度。

**规则维护：** 新规则发布要有编号、适用条件、参数来源、例子和版本。新版本使相关分析需复核，不自动改已采用估算或历史曲线。参数调整、模型理解错误和算术错误分别记录；当前未采集实际投入，不开展个人效率排名或声称估算已完成校准。
